1. Что делать, если JWT-токен пользователя скомпрометирован (украден)? >> Добавить в blacklist (Redis с TTL = оставшееся время жизни); или сократить TTL access token + использовать refresh token
2. Что такое Claims в JWT и на какие категории они делятся? >> Поля payload: стандартные ( `sub` , `exp` , `iat` , `iss` ) и кастомные ( `user_id` , `role` ); описывают контекст пользователя
3. Из чего состоит JWT? >> Три части через точки: `header.payload.signature` ; Header – алгоритм подписи; Payload – claims (user_id, role, exp); Signature – цифровая подпись
4. Как мгновенно инвалидировать сессию? >> Удалить запись из Redis/БД; клиент с тем же `session_id` получит отказ
5. Почему JWT сложно инвалидировать? >> Токен валиден до истечения `exp` ; без blacklist досрочный отзыв невозможен; сервер не хранит список выданных токенов
6. Когда сессии предпочтительнее JWT? >> Монолитные приложения; критически важна мгновенная инвалидация (logout, блокировка); нет требований к горизонтальному масштабированию
7. Где физически хранятся данные сессий? >> В оперативной памяти, БД или Redis; Redis – стандарт для распределённых систем
8. Риск длинного TTL для JWT? >> При компрометации токена злоумышленник использует его до истечения срока
9. Является ли payload JWT зашифрованным? >> Нет; payload только base64-encoded, не зашифрован; не хранить в нём секретные данные (пароли, платёжные данные)
10. Что гарантирует подлинность JWT? >> Цифровая подпись секретным ключом сервера; подделать payload без ключа невозможно
11. Как работает сессионная аутентификация? >> Сервер создаёт сессию и возвращает `session_id` через `Set-Cookie` ; клиент автоматически передаёт его через `Cookie` ; сервер ищет данные в хранилище по этому ID
12. Когда JWT предпочтительнее сессий? >> Микросервисы; мобильные приложения; горизонтальное масштабирование; несколько независимых сервисов
13. Что делает JWT самодостаточным? >> Все необходимые данные пользователя содержатся внутри самого токена; запрос к БД не нужен
14. К чему приводит хранение больших данных в JWT payload? >> Увеличивает размер каждого HTTP-запроса; токен передаётся при каждом запросе
15. Почему HTTP требует механизмов аутентификации? >> HTTP – stateless протокол; сервер не помнит предыдущих запросов; нужен способ идентифицировать пользователя между запросами
16. Как JWT передаётся в запросе? >> `Authorization: Bearer <token>`
17. Как сервер проверяет JWT без обращения к БД? >> Пересчитывает подпись с известным ключом и сравнивает; читает данные из payload
18. Фундаментальное различие сессий и токенов? >> Сессии хранят состояние на сервере (Redis, БД, RAM); токены (JWT) – на стороне клиента; сервер только проверяет подпись
19. Почему JWT предпочтителен для горизонтального масштабирования? >> Любой сервер кластера проверяет токен независимо без обращения к центральному хранилищу; нет sticky sessions
