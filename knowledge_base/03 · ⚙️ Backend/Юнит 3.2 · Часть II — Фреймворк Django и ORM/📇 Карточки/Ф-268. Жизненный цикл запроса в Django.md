1. Перечислите основные этапы прохождения HTTP-запроса в Django от веб-сервера до ответа. >> 1) Nginx (Reverse Proxy) → 2) WSGI/ASGI-сервер (Gunicorn/Uvicorn) → 3) `WSGIHandler` / создание `HttpRequest` → 4) Цепочка `MIDDLEWARE` (сверху вниз) → 5) URL Dispatcher (`urls.py`) → 6) View (и ORM/Templates) → 7) Цепочка `MIDDLEWARE` в обратном порядке (снизу вверх) → 8) Возврат `HttpResponse`
2. В каком порядке выполняются `MIDDLEWARE` при входе запроса и при возврате ответа? >> Как «луковица»: на пути к View запрос проходит список `MIDDLEWARE` сверху вниз (от первого к последнему), а готовый `HttpResponse` проходит через них в обратном порядке — снизу вверх
3. Что произойдёт, если один из `Middleware` вернёт `HttpResponse` до вызова `get_response(request)`? >> Цепочка прервётся (Short-circuit): ни последующие `Middleware`, ни сама `View` вызваны не будут, а ответ сразу пойдёт обратно наверх через уже пройденные слои
4. Почему порядок строк в списке `MIDDLEWARE` в `settings.py` критически важен (на примере `SessionMiddleware` и `AuthenticationMiddleware`)? >> `AuthenticationMiddleware` определяет `request.user`, читая идентификатор из `request.session`, поэтому `SessionMiddleware` обязан стоять выше `AuthenticationMiddleware` в списке
5. Как работает URL-диспетчер Django (`urlpatterns`) при поиске подходящего маршрута? >> Он перебирает список `urlpatterns` строго сверху вниз и останавливается на первом совпавшем шаблоне `path()` / `re_path()`, извлекая параметры пути (например, `<int:pk>`) и вызывая привязанный `view`
6. Что такое Context Processors в Django Templates и когда они вызываются? >> Функции, которые автоматически добавляют общие переменные (`user`, `request`, `messages`, `csrf_token`) в контекст каждого шаблона при рендеринге через `render(request, ...)`
7. Чем метод `redirect()` отличается от `render()` в конце обработки POST-запроса? >> `render()` возвращает `200 OK` с HTML в ответе на POST (при нажатии F5 в браузере форма отправится повторно); `redirect()` возвращает `302 Found` на GET-страницу (паттерн Post/Redirect/Get — PRG)
8. Когда в жизненном цикле запроса Django открывается и закрывается транзакция при настройке `ATOMIC_REQUESTS = True`? >> Перед вызовом самой `View`-функции Django открывает транзакцию БД; если `View` завершилась успешно — делает `COMMIT`, а если выбросила необработанное исключение — делает `ROLLBACK`
9. Какие хуки кроме основного `__call__` может реализовать класс Middleware в Django? >> `process_view(request, view_func, view_args, view_kwargs)` (перед вызовом view), `process_exception(request, exception)` (если view выбросила исключение) и `process_template_response`
10. В каком потоке/контексте выполняются сигналы Django (`post_save`, `request_finished`) по умолчанию? >> Строго синхронно в том же самом потоке и в рамках обработки текущего запроса (поэтому тяжёлая работа в обработчике сигнала задерживает ответ клиенту и должна выноситься в Celery)
