1. Какие задачи решает Rate Limiting (ограничение частоты запросов) в бэкенде? >> Защита от брутфорса паролей и OTP-кодов, защита от DDoS и скрапинга, предотвращение исчерпания ресурсов БД/CPU одним шумным клиентом и контроль расходов на платные внешние API (LLM, SMS)
2. Какой HTTP-статус код и какие заголовки должен возвращать сервер при превышении лимита запросов? >> Статус `429 Too Many Requests` и заголовок `Retry-After` (число секунд до разблокировки), а также информационные заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`
3. Как работает алгоритм Fixed Window Counter и в чём его главная уязвимость на границе окна? >> Счётчик считает запросы в фиксированных интервалах (например, `12:00:00–12:00:59`). Уязвимость: клиент может отправить 100 запросов в `12:00:59` и ещё 100 запросов в `12:01:00` — получив двойную нагрузку (200 запросов за 2 секунды)
4. Как алгоритм Sliding Window Log (и Sliding Window Counter) устраняет проблему границы окна? >> Окно отсчитывается динамически назад от текущего момента времени $(t - W, t]$ (через хранение таймстампов в `Sorted Set` Redis или взвешенную сумму предыдущего и текущего окна), не допуская двойного всплеска на стыке минут
5. Как работает алгоритм Token Bucket (Корзина токенов) и когда он оптимален? >> В корзину с ёмкостью $B$ с постоянной скоростью $R$ капают токены; каждый запрос тратит 1 токен. Позволяет пропускать короткие легитимные всплески трафика (burst до $B$ запросов), сохраняя среднюю скорость $R$
6. Чем алгоритм Leaky Bucket (Дырявое ведро) отличается от Token Bucket? >> В Leaky Bucket запросы попадают в очередь-ведро и вытекают на обработку со строго постоянной скоростью (сглаживает любые всплески в ровный поток), тогда как Token Bucket разрешает мгновенный всплеск в пределах накопленных токенов
7. Почему в продакшене счётчики Rate Limiter хранят в Redis, а не в обычном словаре Python в памяти процесса? >> В продакшене запущено несколько воркеров/контейнеров: локальный словарь в памяти каждого процесса не видит запросы с других воркеров, а Redis даёт единое быстрое атомарное состояние для всего кластера
8. Зачем операции проверки и списания токенов в Redis оборачивают в Lua-скрипт или Pipeline? >> Чтобы избежать состояния гонки (Race Condition) между чтением остатка (`GET`) и его уменьшением (`DECR`): Lua-скрипт выполняется в Redis строго атомарно
9. По какому ключу (идентификатору) лучше ограничивать запросы для анонимных и для авторизованных эндпоинтов? >> Для анонимных (`/login`, `/register`) — по IP-адресу клиента (плюс `username`/`email`); для авторизованных API — по `user_id` или `api_key`, чтобы сотни пользователей за одним офисным или мобильным NAT-IP не блокировали друг друга
10. Какая уязвимость возникает, если Rate Limiter берёт IP клиента напрямую из заголовка `X-Forwarded-For` без настройки доверенных прокси? >> Злоумышленник может в каждом запросе подделывать случайный заголовок `X-Forwarded-For: 1.2.3.4` и полностью обходить лимит по IP; доверять этому заголовку можно только от собственного балансировщика (Nginx/Cloudflare)
