1. Почему вызов `requests.get(url)` без параметра `timeout` опасен в продакшене? >> В `requests` по умолчанию `timeout=None` (бесконечное ожидание): если внешний сервер зависнет, воркер вашего приложения заблокируется навсегда, что приведёт к исчерпанию пула воркеров и падению всего сервиса
2. Что означает передача кортежа `timeout=(3.0, 10.0)` в `requests.get(url, timeout=(3.0, 10.0))`? >> `3.0` секунды — `connect timeout` (максимальное время на установку TCP/TLS-соединения); `10.0` секунд — `read timeout` (время ожидания данных ответа от сервера)
3. Почему нельзя вызывать `requests.get()` внутри `async def` эндпоинта в FastAPI? >> `requests` — синхронная блокирующая библиотека: она заморозит однопоточный Event Loop на всё время сетевого запроса, остановив обработку запросов всех остальных пользователей
4. Зачем использовать `requests.Session()` или единый `httpx.AsyncClient()` вместо одиночных вызовов `get()` на каждый запрос? >> Для переиспользования TCP/TLS-соединений (Connection Pooling / HTTP Keep-Alive): это избавляет от повторного DNS-резолва, 3-way handshake и дорогого TLS-рукопожатия на каждый запрос
5. Выбрасывают ли `requests` и `httpx` исключение автоматически, если сервер вернул статус `500` или `404`? >> Нет! Исключение выбрасывается только при сетевой ошибке или таймауте; чтобы выбросить `HTTPError` / `HTTPStatusError` при кодах `4xx`/`5xx`, нужно явно вызвать `response.raise_for_status()`
6. Какие ключевые преимущества даёт библиотека `httpx` по сравнению с `requests`? >> Поддержка как синхронного (`httpx.Client`), так и асинхронного (`httpx.AsyncClient`) API, поддержка протокола HTTP/2, безопасный таймаут по умолчанию (5 с) и тестирование ASGI-приложений через `ASGITransport`
7. Что такое Exponential Backoff (экспоненциальная задержка) при повторных запросах (Retries)? >> Стратегия, при которой пауза перед каждой следующей попыткой растёт экспоненциально ($t = \text{base} \cdot 2^{n-1}$, например 0.5 с, 1 с, 2 с, 4 с), давая перегруженному серверу время восстановиться
8. Зачем к Exponential Backoff обязательно добавляют Jitter (случайный разброс времени ожидания)? >> Чтобы предотвратить эффект «топота стада» (Thundering Herd): без Jitter сотни клиентов, получивших сбой в одну секунду, ударят по серверу повторными запросами одновременно
9. Какие HTTP-статусы и ошибки имеет смысл повторять (Retry), а какие — нет? >> Повторяют сетевые таймауты и временные сбои сервера: `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`, а также `429 Too Many Requests` (с учётом `Retry-After`). Ошибки клиента `400`, `401`, `403`, `404`, `422` повторять нельзя
10. Почему опасно делать автоматический Retry для обычного `POST /payments` без дополнительной защиты? >> `POST` не идемпотентен: если первый запрос дошёл до сервера и списал деньги, но ответ потерялся по таймауту, повторный `POST` спишет деньги второй раз (нужен заголовок `Idempotency-Key`)
11. Где в FastAPI-приложении правильно создавать и закрывать общий `httpx.AsyncClient`? >> В контекстном менеджере `lifespan` приложения (сохраняя в `app.state.http_client`), чтобы пул соединений жил всё время работы процесса и корректно закрывался при остановке
12. За что отвечают настройки `max_connections` и `max_keepalive_connections` в `httpx.Limits`? >> `max_connections` ограничивает общее число одновременных соединений к хостам, а `max_keepalive_connections` — сколько свободных открытых соединений удерживать в пуле для повторного использования
