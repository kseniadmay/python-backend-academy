1. В чём заключается принцип метода открытой адресации (Open Addressing) при возникновении коллизий в хэш-таблице? >> При коллизии ищется следующий свободный бакет по заданной стратегии зондирования.
2. Каким двум условиям (неизменяемость и метод `__hash__`) должен удовлетворять объект в Python, чтобы считаться хешируемым? >> Объект имеет `__hash__` и его хэш-значение не меняется за время жизни объекта; также требуется корректный `__eq__`.
3. Средняя сложность хэш-таблицы для поиска, вставки, удаления? >> $O(1)$ в среднем; $O(n)$ в худшем случае при множестве коллизий.
4. Почему изменяемые объекты нельзя использовать как ключи? >> Изменение объекта изменит его хэш; элемент окажется в неверном бакете и станет недостижимым.
5. Какая ошибка при `d[[1, 2]]`? >> `TypeError: unhashable type: 'list'`.
6. Что представляет собой «бакет» (Bucket) во внутренней архитектуре хэш-таблицы? >> Ячейка внутреннего массива хэш-таблицы, индекс которой вычисляется по хэш-коду ключа; при разрешении коллизий методом цепочек бакет хранит связный список или сбалансированное дерево элементов с одинаковым хэш-индексом.
7. Load factor для 6 элементов в таблице размером 8? >> 0.75.
8. Какую базовую операцию выполняет хэш-функция над ключом при работе хэш-таблицы? >> Преобразует ключ в целое число (хэш).
9. Какова временная сложность операции динамического расширения и рехэширования всех записей хэш-таблицы? >> $O(n)$.
10. Что такое рехэширование? >> Создание новой таблицы большего размера и перераспределение всех элементов.
11. Почему средняя сложность $O(1)$ несмотря на дорогое рехэширование? >> Рехэширование происходит логарифмически редко; амортизированная сложность $O(1)$.
12. Два типа данных Python на основе хэш-таблиц? >> `dict` и `set`.
13. Что такое load factor? >> Количество элементов / размер таблицы.
14. Три стратегии открытой адресации? >> Линейное зондирование, квадратичное зондирование и двойное хэширование.
15. Можно ли использовать `tuple` как ключ? >> Да, если все элементы кортежа сами хэшируемы; `(1, [2, 3])` — нельзя.
16. Требование к ключу хэш-таблицы? >> Объект должен быть хэшируемым (hashable).
17. В чём заключается метод цепочек (Chaining) при разрешении коллизий в хэш-таблицах? >> Каждый бакет содержит связный список пар (ключ, значение); коллизии добавляются в список.
18. Какова последовательность преобразования ключа в индекс ячейки хэш-таблицы? >> Ключ → хэш-функция → `hash % размер_таблицы` → индекс → ячейка массива (бакет).
19. Как хэш превращается в индекс? >> `hash % размер_таблицы`.
20. При каком load factor Python `dict` расширяется? >> Примерно при $> 2/3$ (~0.67).
21. Почему `list` нельзя использовать как ключ? >> `list` изменяемый и нехэшируемый — `__hash__` не определён.
22. Можно ли использовать `str` как ключ? >> Да — строки неизменяемы и хэшируемы.
23. Что называют коллизией в хеш-таблицах и к чему приводит её возникновение при поиске элементов? >> Ситуацию, когда два разных ключа получают одинаковый индекс (слот); при поиске требуется обход цепочки или зондирование следующих слотов.
24. Как коллизии влияют на производительность? >> Замедляют поиск вплоть до $O(n)$ в худшем случае.
25. Какой метод разрешения коллизий хэш-таблицы используется внутри CPython для dict и set? >> Открытая адресация (Open Addressing) с псевдослучайным зондированием по формуле `j = (5*j + 1 + perturb) & mask`.
26. Что такое dummy (или DKIX_DUMMY) маркер при удалении элемента из хэш-таблицы CPython? >> Специальный маркер «ранее удалённого слота»; он сообщает поиску, что цепочку коллизий нельзя прерывать, но слот свободен для новой записи.
27. Как устроена компактная раскладка словаря `dict` в CPython начиная с версии 3.6? >> Разделена на две таблицы: разреженный массив индексов `dk_indices` (хранит 1, 2, 4 или 8-байтовые индексы в зависимости от размера таблицы) и плотный массив записей `dk_entries` (хранит `hash`, `key`, `value` в порядке вставки).
28. Почему словарь dict в Python 3.7+ гарантирует сохранение порядка вставки (insertion order)? >> Благодаря плотному массиву `dk_entries`, куда новые пары `(key, value)` просто аппендятся в конец по мере добавления.
