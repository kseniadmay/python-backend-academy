## Масштабирование нагрузки на практике

Представьте курьерскую службу доставки при росте числа заказов $n$ от $10$ до $1\,000\,000$. Скорость алгоритмов при этом растёт совершенно по-разному:

- поиск по индексу или ключу (`O(1)`) не зависит от размера базы;
- деление пополам (`O(log n)`) требует ~20 шагов на миллион записей;
- линейный объезд (`O(n)`) растёт прямо пропорционально входу;
- попарная сверка вложенным циклом (`O(n²)`) превращает $1\,000$ заказов в миллион операций.

## Иерархия классов сложности

Сравнение самых частых классов асимптотики показывает, насколько резко расходится число операций уже при $n = 1\,000$:

| Сложность | Название (RU / EN) | Операций при $n = 1\,000$ | Типичный пример в Python |
| :--- | :--- | :--- | :--- |
| **$O(1)$** | Константная (*Constant*) | $1$ | Доступ `arr[i]`, поиск в `dict`/`set`, `list.append()` |
| **$O(\log n)$** | Логарифмическая (*Logarithmic*) | $\approx 10$ | Бинарный поиск (`bisect`), поиск в сбалансированном BST |
| **$O(n)$** | Линейная (*Linear*) | $1\,000$ | Цикл `for x in arr`, `x in list`, `sum(arr)` |
| **$O(n \log n)$** | Линейно-логарифмическая | $\approx 10\,000$ | Сортировка `arr.sort()` (Timsort), Merge Sort |
| **$O(n^2)$** | Квадратичная (*Quadratic*) | $1\,000\,000$ | Двойной вложенный цикл, Bubble Sort |
| **$O(2^n)$** | Экспоненциальная (*Exponential*) | $\approx 10^{301}$ | Рекурсивный Фибоначчи без мемоизации |
| **$O(n!)$** | Факториальная (*Factorial*) | $\approx 10^{2567}$ | Перебор всех перестановок (`itertools.permutations`) |

## Нотация Big-O и три правила упрощения

Измерять скорость кода в секундах ненадёжно — время зависит от железа, поэтому **Big-O** оценивает скорость роста числа операций при $n \to \infty$ по трём правилам:

1. **Худший сценарий (Worst-Case)**: фиксируем верхнюю границу — если поиск бывает и за $1$ шаг, и за $n$, оценка равна $O(n)$.
2. **Отбрасывание констант (Drop Constants)**: $O(2n)$ и $O(500n)$ упрощаются до $O(n)$, важна форма кривой роста.
3. **Старшее слагаемое (Drop Non-Dominant)**: в $O(n^2 + 100n)$ при росте $n$ доминирует $n^2$, итог — $O(n^2)$.

```text
Рост операций от размера входа n:

Операции
   ^
   │  O(2^n)    O(n^2)
   │    │        /     O(n log n)
   │    │       /       /    O(n)
   │    │      /       /    /
   │    │     /       /    /   O(log n)
   │    │    /       /    /     ...
   │────┼───/───────/────/─────── O(1)
   └────┴───────────────────────► n
```

## Сложение и умножение сложностей

Последовательные блоки кода дают **сложение** $O(A + B) = O(\max(A, B))$ — например, два цикла по $n$ шагов подряд дают $O(2n) = O(n)$:

```python
def sum_sequential_ops(n: int) -> int:
    ops = 0
    for _ in range(n):
        ops += 1
    for _ in range(n):
        ops += 1
    return ops

print('O(n) n=10:', sum_sequential_ops(10))
# >>> O(n) n=10: 20
```

Вложенные блоки **перемножают** сложности $O(A \cdot B)$ — цикл на $n$ шагов, внутри которого крутится ещё $n$ шагов (или `x in list`), даёт $O(n^2)$:

```python
def sum_nested_ops(n: int) -> int:
    ops = 0
    for _ in range(n):
        for _ in range(n):
            ops += 1
    return ops

print('O(n^2) при n=10:', sum_nested_ops(10))
# >>> O(n^2) при n=10: 100
```

## Временная сложность и Space-Time Tradeoff

Помимо **временной сложности** (числа шагов CPU), оценивают **пространственную сложность** — объём дополнительной RAM под структуры данных и фреймы стека рекурсии.

Часто время ускоряют за счёт памяти (**Space-Time Tradeoff**): поиск дубликата двойным циклом тратит $O(1)$ памяти и $O(n^2)$ времени, а хэш-множество `set` — $O(n)$ памяти и $O(n)$ времени:

```python
def has_dup_slow(nums: list[int]) -> bool:
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]:
                return True
    return False

def has_dup_fast(nums: list[int]) -> bool:
    seen: set[int] = set()
    for x in nums:
        if x in seen:
            return True
        seen.add(x)
    return False

data = [1, 2, 3, 2]
print('O(n^2):', has_dup_slow(data))
# >>> O(n^2): True

print('O(n):', has_dup_fast(data))
# >>> O(n): True
```

## Шпаргалка по сложности коллекций CPython

Выбор встроенной коллекции определяет асимптотику базовых операций в реальном коде:

| Операция | `list` (массив) | `deque` (двусвязный) | `dict` / `set` (хэш-таблица) |
| :--- | :--- | :--- | :--- |
| Доступ по индексу / ключу | **$O(1)$** | $O(n)$ в центре, **$O(1)$** по краям | **$O(1)$** в среднем (только `dict`) |
| Поиск (`x in col`) | $O(n)$ | $O(n)$ | **$O(1)$** в среднем |
| Добавление (`append` / `add`) | **$O(1)$** аморт. | **$O(1)$** | **$O(1)$** аморт. |
| Вставка / удаление в начале | **$O(n)$** (`insert(0)`) | **$O(1)$** (`appendleft`, `popleft`) | — |
| Удаление по ключу/значению | $O(n)$ (`remove`) | $O(n)$ (`remove`) | **$O(1)$** в среднем (`del d[k]`) |

## Методы `list` и `dict` под капотом CPython

В CPython список `list` — это **динамический массив указателей** на объекты `PyObject*` с запасом памяти (over-allocation). Отсюда вытекает точная стоимость каждого метода:

- **$O(1)$:** `arr[i]`, `arr.append(x)` (амортизированно), `arr.pop()` (с конца), `len(arr)`.
- **$O(n)$:** `arr.insert(i, x)`, `arr.pop(0)`, `arr.remove(x)`, `arr.index(x)`, `arr.count(x)`, `arr.reverse()`, `arr.copy()` — требуют сдвига указателей или полного прохода массива.

Словарь `dict` — это **хэш-таблица** с открытой адресацией: ключ хешируется в индекс бакета, давая $O(1)$ в среднем (при отсутствии ключа выбрасывается `KeyError`). В редком худшем случае при массовых хэш-коллизиях поиск деградирует до $O(n)$.

> **Junior vs Senior**:
> - **Junior**: Проверяет наличие ID через `if uid in user_ids_list:` внутри цикла (скрытая квадратичная сложность $O(n^2)$) или делает очередь через `arr.pop(0)`.
> - **Senior**: Преобразует список в `set` для проверок за $O(1)$, использует `collections.deque` для очередей и всегда оценивает и время, и дополнительную память (Space-Time Tradeoff).
