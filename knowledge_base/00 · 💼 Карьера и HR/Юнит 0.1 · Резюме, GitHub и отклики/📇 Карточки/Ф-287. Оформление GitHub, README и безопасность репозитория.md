1. Сколько закреплённых репозиториев оптимально держать наверху профиля `GitHub` при поиске backend-позиции? >> 2–3 лучших завершённых бэкенд-проекта с понятным описанием, убрав с витрины пустые форки и однотипные заготовки.
2. Какие разделы обязаны присутствовать в продакшен-ориентированном `README.md`? >> Назначение сервиса и схема/архитектура слоёв, технологический стек, шаги локального запуска (`docker compose up`) и запуск тестов (`pytest`).
3. Почему простого удаления файла `.env` в новом коммите недостаточно при утечке секрета на `GitHub`? >> Вся прежняя версия файла остаётся доступной в старых коммитах истории Git; любой желающий или бот может извлечь токен из истории.
4. Какой первый обязательный шаг нужно сделать при случайной публикации секрета или API-ключа в открытый репозиторий? >> Немедленно отозвать и перевыпустить (ротировать) скомпрометированный секрет, так как удаление из истории Git не гарантирует, что его не скопировали.
5. Каким инструментом безопасно вычищают случайно попавший файл секретов из всей истории коммитов Git после его ротации? >> Специализированным инструментом переписывания истории `git filter-repo` (с последующим принудительным обновлением веток).
6. Зачем в репозитории создают файл `.env.example` рядом с исключённым файлом `.env`? >> Чтобы зафиксировать список всех требуемых переменных окружения с безопасными заглушками и сделать запуск сервиса воспроизводимым для любого разработчика.
7. Какие служебные каталоги Python-проекта обязательно вносят в `.gitignore`? >> Виртуальное окружение `.venv/`, реальный файл секретов `.env`, кэш байткода `__pycache__/`, кэш тестов `.pytest_cache/` и локальные артефакты IDE.
8. Как привести серию локальных черновых коммитов `wip` и `fix` в аккуратный вид до отправки Pull Request? >> Объединить и переименовать локальные коммиты через интерактивный ребейз `git rebase -i`, оформив атомарную понятную историю изменений.
9. Для чего подключают фреймворк `pre-commit` в пет-проектах и командной разработке? >> Чтобы автоматически запускать линтеры (`ruff`), проверку форматов и сканеры случайных секретов прямо перед фиксацией каждого коммита.
10. Какое ключевое правило составления описания `Pull Request` демонстрирует зрелость кандидата? >> Кратко зафиксировать цель изменения, перечень затронутых архитектурных компонентов и конкретный способ проверки тестами.
11. Зачем указывать эндпоинт документации `/docs` и версию Python вроде `3.12` в описании проекта? >> Ревьюер за пару секунд видит актуальный стандарт языка, доступный контракт OpenAPI и способ проверки API без чтения десятков файлов кода.
12. Как проверить готовность проекта на `GitHub` перед отправкой резюме техлиду? >> Клонировать репозиторий в чистую директорию и убедиться, что шаги из `README.md` (`cp .env.example .env`, `docker compose up -d`, `pytest`) срабатывают без донастройки.
