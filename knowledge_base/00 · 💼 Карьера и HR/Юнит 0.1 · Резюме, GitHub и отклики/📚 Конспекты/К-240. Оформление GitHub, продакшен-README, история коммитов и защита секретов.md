## Витрина закреплённых репозиториев и структура продакшен-README

Технический лидер обычно тратит не более двух минут на просмотр профиля `GitHub` перед собеседованием. Закрепите наверху профиля 2–3 лучших бэкенд-репозитория с аккуратным описанием и актуальным стеком, убрав с главной витрины пустые форки и шаблонные учебные заготовки.

Сильный файл `README.md` работает как техническая карточка проекта и снимает вопросы ревьюера до запуска кода:

```markdown
# Order Service API

Асинхронный REST-сервис обработки заказов.

## Архитектура и стек
- Python 3.12, FastAPI, Pydantic v2
- PostgreSQL, SQLAlchemy 2.0, Alembic
- Redis, pytest, Docker Compose

## Быстрый старт
- cp .env.example .env
- docker compose up -d
```

Обязательно укажите в `README.md` архитектурную схему или перечень слоёв, ссылку на интерактивную документацию API (`/docs`) и воспроизводимые команды запуска тестов.

## Чистота истории коммитов и культура Pull Request

Сырая история коммитов в стиле `wip`, `fix`, `update` и «поправил баг 2» создаёт впечатление хаотичной работы без ревью. Продуманная история коммитов показывает, как вы декомпозируете задачу и контролируете изменения перед слиянием.

Чтобы репозиторий читался профессионально, поддерживайте дисциплину версионирования с помощью базовых приёмов Git:

- **Атомарные коммиты:** каждый коммит решает одну логическую задачу с ясным глаголом в заголовке без смешивания форматирования и новой логики.
- **Приведение ветки в порядок:** локальную серию черновых коммитов перед публикацией стоит объединять через `git rebase -i`.
- **Читаемые описания Pull Request:** в учебных и командных задачах фиксируйте цель изменения, затронутые узлы и способ проверки работоспособности.

## Гигиена репозитория: .gitignore, .env.example и изоляция окружения

Репозиторий разработки не должен хранить сборочные артефакты, виртуальное окружение `.venv/`, кэш интерпретатора `__pycache__/`, локальные базы SQLite или временные логи IDE. Такие файлы раздувают диффы и ломают переносимость проекта между машинами.

Минимальный набор файлов конфигурации на верхнем уровне бэкенд-проекта задаёт воспроизводимое окружение для каждого участника команды:

```text
├── src/
├── tests/
├── .gitignore
├── .env.example
├── pyproject.toml
├── Dockerfile
├── docker-compose.yml
└── README.md
```

В файле `.gitignore` заранее исключите `.env`, `.venv/`, `__pycache__/`, `.pytest_cache/` и файлы локальной отладки. Вместо реальных конфигов коммитьте безопасный шаблон `.env.example` с фиктивными заглушками вроде `DATABASE_URL=postgresql+asyncpg://user:pass@db:5432/app`.

## Безопасность репозитория: утечки секретов, ротация и pre-commit

Ошибочно закоммиченный пароль от БД, `JWT_SECRET` или API-ключ нельзя скрыть простым последующим удалением файла в новом коммите: секрет навсегда остаётся в предыдущих снимках истории Git. После попадания в публичный репозиторий такой ключ считается скомпрометированным автоматически.

Если секрет всё же попал в историю удалённого репозитория, действует строгий аварийный протокол:

- **Немедленная ротация ключа:** сначала отзовите и перевыпустите токен или пароль у провайдера — перезапись истории не отменяет факт утечки.
- **Очистка истории Git:** после отзыва секрета вычистите файл из истории веток инструментом `git filter-repo`, а не одним новым коммитом удаления.
- **Автоматическая страховка:** подключите локальные хуки `pre-commit` с детектором секретов и проверками стиля вроде `ruff` перед каждым коммитом.

## Экспресс-проверка проекта глазами техлида за 2 минуты

Перед отправкой отклика проведите независимый аудит главного репозитория на свежей ветке или в чистой папке. Проверьте, поднимается ли приложение и проходит ли тестовый прогон одной последовательностью команд без скрытой ручной магии:

```bash
cp .env.example .env
docker compose up -d
pytest -q
```

Убедитесь, что в корне репозитория отсутствуют неиспользуемые скрипты, в `pyproject.toml` зафиксированы точные зависимости и их версии, а файл лицензии и описания эндпоинтов актуальны текущему коду.

> - **Senior**: Закрепляет 2–3 чистых сервиса с лаконичным `README.md`, образцом `.env.example`, строгим `.gitignore`, предсказуемой историей коммитов, локальными проверками `pre-commit` и запуском в одну команду через `docker compose up`.
