## 1. Почему наследование взрывается комбинаторно и как спасает Паттерн Decorator?

> **Ментальная модель — «Многослойная зимняя одежда (принцип капусты)»**:
> Человек на улице зимой — это базовый объект (`CoreService`). Если холодно — вы надеваете поверх него термобельё (`CachingDecorator`). Пошёл дождь — надеваете сверху непромокаемый плащ (`RetryDecorator`). Нужно записывать шаги — пристёгиваете фитнес-браслет (`LoggingDecorator`). Вы можете комбинировать эти слои в любом порядке прямо перед выходом из дома, не меняя ДНК самого человека и не рожая отдельные биологические виды «ЧеловекВПлащеИТермобелье»!

Если пытаться комбинировать 3 независимые фичи (логирование, кэширование, ретраи) через **наследование**, вам придётся создать $2^3 - 1 = 7$ подклассов (`LoggedService`, `CachedService`, `LoggedAndCachedService`...). А при 5 фичах — уже **31 класс**!
Структурный паттерн **Decorator (Декоратор / Обёртка)** решает эту проблему через **композицию**: обёртка реализует **тот же самый интерфейс**, что и оборачиваемый сервис, хранит ссылку на него внутри себя и добавляет поведение *до* или *после* делегирования вызова.

```text
Матрёшка объектных декораторов (все реализуют единый интерфейс DataFetcher):

  Вызов клиента: fetcher.fetch("user:1")
        |
        v
  +---------------------------------------------------------------+
  | LoggingDecorator  (1. Пишет в лог старт и время выполнения)   |
  |   +-------------------------------------------------------+   |
  |   | CachingDecorator (2. Проверяет кэш; если промах -> v) |   |
  |   |   +-----------------------------------------------+   |   |
  |   |   | BaseApiFetcher (3. Реальный поход за данными) |   |   |
  |   |   +-----------------------------------------------+   |   |
  |   +-------------------------------------------------------+   |
  +---------------------------------------------------------------+
```

## 2. Два воплощения в Python: ООП-Декоратор (GoF) vs Функциональный `@decorator`

В Python термин «декоратор» используется в двух смежных значениях — важно чётко различать их на собеседовании:

| Характеристика | Классический ООП-паттерн Decorator (GoF) | Синтаксический `@decorator` функции в Python |
| :--- | :--- | :--- |
| **Что оборачивает?** | Экземпляр класса (сервис, репозиторий, поток ввода-вывода) со множеством методов | Отдельную функцию или метод в момент объявления (`@timer`, `@lru_cache`) |
| **Когда собирается цепочка?** | Динамически **в рантайме** (например, в DI-контейнере в зависимости от конфига) | Статически **при импорте модуля** (в момент определения `def func()`) |
| **Главное правило корректности** | Декоратор обязан реализовывать **полный протокол** оборачиваемого объекта | Внутренняя функция `wrapper` обязана быть помечена **`@functools.wraps(func)`**, чтобы не потерять `__name__`, `__doc__` и аннотации типов |

## 3. Порядок наложения декораторов и важность `@functools.wraps`

Когда над функцией или объектом выстраивается стек декораторов:
```text
@outer_timer
@inner_cache
def compute(x: int) -> int: ...
```
Это в точности эквивалентно матрёшке `compute = outer_timer(inner_cache(compute))`:
- При вызове `compute(5)` **сначала** входит внешний декоратор `outer_timer`, затем внутренний `inner_cache`.
- Если `inner_cache` стоит *внутри* `outer_timer`, то `outer_timer` замеряет время с учётом мгновенных попаданий в кэш. Если поменять их местами (`@inner_cache` снаружи), то при попадании в кэш `outer_timer` даже не будет вызван!

> **Junior vs Senior**:
> - **Junior**: Впиливает логирование, замер времени, проверку прав и `Redis.get/set` прямо внутрь бизнес-метода `OrderService.get_order()`, превращая 5 строк бизнес-логики в 80 строк инфраструктурного шума.
> - **Senior**: Оставляет `OrderService` кристально чистым (только бизнес-логика), а сквозную функциональность (**Cross-Cutting Concerns**: кэш, метрики, аудит) навешивает снаружи через `CachingOrderServiceDecorator` или `@wraps`-декораторы.

## 4. Практикум: собираем цепочку ООП-декораторов (`Logging + Caching`) вокруг сервиса

```python
from typing import Protocol

# Единый контракт (Protocol), который соблюдают и базовый сервис, и все его обёртки
class PriceProvider(Protocol):
    def get_price(self, ticker: str) -> float: ...

class ExchangePriceService:
    """Базовый сервис (имитирует дорогой запрос к бирже)."""
    def __init__(self) -> None:
        self.db_hits = 0

    def get_price(self, ticker: str) -> float:
        self.db_hits += 1
        prices = {"BTC": 65000.0, "ETH": 3500.0}
        return prices[ticker]

class CachingPriceDecorator:
    """Декоратор кэширования: реализует PriceProvider и оборачивает любой другой PriceProvider."""
    def __init__(self, wrapped: PriceProvider) -> None:
        self._wrapped = wrapped
        self._cache: dict[str, float] = {}

    def get_price(self, ticker: str) -> float:
        if ticker not in self._cache:
            self._cache[ticker] = self._wrapped.get_price(ticker)
        return self._cache[ticker]

class LoggingPriceDecorator:
    """Декоратор логирования: прозрачно оборачивает любой PriceProvider."""
    def __init__(self, wrapped: PriceProvider) -> None:
        self._wrapped = wrapped
        self.logs: list[str] = []

    def get_price(self, ticker: str) -> float:
        price = self._wrapped.get_price(ticker)
        self.logs.append(f"Запрошен {ticker} -> ${price}")
        return price

raw_service = ExchangePriceService()
decorated_provider = LoggingPriceDecorator(CachingPriceDecorator(raw_service))

print("1-й вызов BTC:", decorated_provider.get_price("BTC"))
print("2-й вызов BTC (из кэша):", decorated_provider.get_price("BTC"))
print("Реальных обращений к бирже:", raw_service.db_hits)
print("Журнал внешнего декоратора:", decorated_provider.logs)
```
