## 1. В чём проблема прямого использования ORM внутри бизнес-сервисов?

> **Ментальная модель — «Библиотечный каталог против беготни по подвалам книгохранилища»**:
> Прямое использование ORM в сервисе (`session.execute(select(UserModel).where(...))`) похоже на то, как если бы читатель сам спускался в тёмный подвал библиотеки с фонариком, зная номера стеллажей и формат инвентарных карточек. Если завтра библиотека переставит шкафы или переведёт архив в цифру, читатель ничего не найдёт!
> **Паттерн Repository (Репозиторий)** — это окно выдачи книг: для вашей бизнес-логики хранилище выглядит как **обычная коллекция доменных объектов в памяти** с понятными методами `repo.get_by_email(email)` и `repo.save(user)`.

```text
Без Repository (Бизнес-логика привязана к SQLAlchemy):
  [ OrderService ] ---> session.execute(select(OrderORM).join(...).where(...))

С паттерном Repository и Unit of Work (Чистая граница):
  [ OrderService ] ---> <<OrderRepository Protocol>>
                                ^
                                | (Инверсия зависимостей DIP)
                 +--------------+--------------+
                 |                             |
     [ SqliteOrderRepository ]     [ InMemoryOrderRepository ]
       (Для продакшена и БД)         (Для мгновенных тестов за 1 мс)
```

## 2. Сравнение: ORM напрямую в сервисах vs Паттерн Repository

| Критерий | ORM-запросы напрямую в сервисах | Паттерн Repository (прослойка доступа к данным) |
| :--- | :--- | :--- |
| **Скорость старта для мелкого CRUD** | Максимальная (меньше файлов на старте) | Требует написания интерфейса и класса-репозитория |
| **Модульное тестирование (Unit Tests)** | Тяжёлое: нужна реальная тестовая БД или сложные моки цепочек `.select().where().scalars()` | Мгновенное: подставляем `InMemoryRepository` на обычном `dict` |
| **Защита от дублирования сложных запросов** | Условие «активный платящий клиент» копипастится в 15 разных сервисах (нарушение DRY) | Вынесено в один метод `repo.list_active_subscribers()` |
| **Связка с транзакциями (Unit of Work)** | `session.commit()` разбросан где попало, легко получить частичное сохранение | Репозиторий только добавляет изменения, а финальный атомарный `commit/rollback` делает **Unit of Work** |

## 3. Паттерн Unit of Work (Единица работы) — лучший напарник Репозитория

Частая ошибка при внедрении Repository: вызывать `conn.commit()` прямо внутри `UserRepository.save()` и `AccountRepository.save()`.
Но что, если в одном бизнес-сценарии нужно **и создать пользователя, и начислить ему приветственный бонус**? Если `UserRepository.save()` уже сделал `commit()`, а начисление бонуса упало с ошибкой, в базе останется полусозданный пользователь без бонуса!

Поэтому в промышленной архитектуре:
- **Repository** отвечает только за операции с таблицей внутри текущей транзакции (`INSERT`/`SELECT`), **не вызывая `commit()` самостоятельно**;
- **Unit of Work (`with uow:`)** — контекстный менеджер, который управляет жизненным циклом транзакции: делает единый `uow.commit()` в конце сценария или автоматический `uow.rollback()` при любом исключении в `__exit__`!

> **Junior vs Senior**:
> - **Junior**: Либо размазывает SQL/ORM-запросы по всем роутерам и сервисам, либо делает «дырявый» репозиторий, который принимает на вход `sqlalchemy.Select` и делает `commit()` после каждого чиха.
> - **Senior**: Возвращает из репозитория чистые доменные сущности (`@dataclass`), прячет SQL внутри репозитория, а границы транзакций контролирует через контекстный менеджер `UnitOfWork`.

## 4. Практикум: Репозиторий на `sqlite3` и `InMemory` с единым контрактом

Убедимся, что один и тот же `SubscriptionService` работает абсолютно одинаково и с `InMemoryUserRepo`, и с реальным SQL-репозиторием `SqliteUserRepo`:

```python
import sqlite3
from dataclasses import dataclass
from typing import Protocol

@dataclass
class Customer:
    id: int | None
    email: str
    plan: str = "free"

class CustomerRepository(Protocol):
    def add(self, customer: Customer) -> Customer: ...
    def get_by_email(self, email: str) -> Customer | None: ...

class InMemoryCustomerRepo:
    def __init__(self) -> None:
        self._items: dict[str, Customer] = {}

    def add(self, customer: Customer) -> Customer:
        saved = Customer(id=len(self._items) + 1, email=customer.email, plan=customer.plan)
        self._items[saved.email] = saved
        return saved

    def get_by_email(self, email: str) -> Customer | None:
        return self._items.get(email)

class SqliteCustomerRepo:
    def __init__(self, conn: sqlite3.Connection) -> None:
        self._conn = conn
        self._conn.execute("CREATE TABLE IF NOT EXISTS customers (id INTEGER PRIMARY KEY, email TEXT UNIQUE, plan TEXT)")

    def add(self, customer: Customer) -> Customer:
        cur = self._conn.execute("INSERT INTO customers (email, plan) VALUES (?, ?)", (customer.email, customer.plan))
        return Customer(id=cur.lastrowid, email=customer.email, plan=customer.plan)

    def get_by_email(self, email: str) -> Customer | None:
        row = self._conn.execute("SELECT id, email, plan FROM customers WHERE email = ?", (email,)).fetchone()
        return Customer(id=row[0], email=row[1], plan=row[2]) if row else None

class SubscriptionService:
    def __init__(self, repo: CustomerRepository) -> None:
        self._repo = repo

    def register_vip(self, email: str) -> Customer:
        if self._repo.get_by_email(email) is not None:
            raise ValueError(f"Клиент {email} уже зарегистрирован")
        return self._repo.add(Customer(id=None, email=email, plan="vip"))

# 1. Мгновенная проверка на InMemory-репозитории
mem_service = SubscriptionService(InMemoryCustomerRepo())
print("InMemory:", mem_service.register_vip("alice@arch.io"))

# 2. Тот же самый сервис поверх реальной таблицы SQLite
with sqlite3.connect(":memory:") as sql_conn:
    sql_service = SubscriptionService(SqliteCustomerRepo(sql_conn))
    print("SQLite:  ", sql_service.register_vip("bob@arch.io"))
```
