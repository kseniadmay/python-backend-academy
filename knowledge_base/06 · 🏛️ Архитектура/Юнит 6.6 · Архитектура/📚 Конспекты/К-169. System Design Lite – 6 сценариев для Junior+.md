## 1. Алгоритм ответа на System Design Lite для Junior+ (Каркас из 6 шагов)

> **Ментальная модель — «Проектирование дома с архитектором»**:
> Если заказчик говорит: *«Построй мне здание!»*, плохой строитель молча начинает заливать фундамент под 50-этажный небоскрёб с вертолётной площадкой, хотя заказчику нужна была дача на две комнаты. Хороший инженер сначала спрашивает: *«Сколько человек будет жить? Какой участок? Зимой или только летом?»*.
> На собеседовании по **System Design Lite** проверяют не знание модных слов вроде Kafka и Kubernetes, а **ваш инженерный ход мыслей**: умеете ли вы задать уточняющие вопросы, посчитать нагрузку (RPS), предложить простое работающее решение и честно назвать его узкое место (**Bottleneck**).

```text
Типовая масштабируемая архитектура бэкенда (System Design Lite):

  [Клиенты: Web / Mobile]
             |
             v (HTTPS)
  +---------------------+
  | Load Balancer / CDN |  (Nginx / Cloudflare: раздаёт статику, распределяет трафик)
  +---------------------+
        /           \
       v             v
  [API Pod 1]   [API Pod 2]  (Stateless FastAPI воркеры — масштабируются горизонтально)
       \             /
        +-----+-----+
              |
    +---------+---------+-------------------------+
    | (Кэш горячих чтений)                        | (Асинхронные задачи)
    v                   v                         v
 [Redis]        [PostgreSQL Master]       [RabbitMQ / Celery]
 (TTL / Rate)          | (Репликация)             |
                       v                          v
                [Read Replicas]           [Фоновые воркеры: Email/S3]
```

**Универсальный план ответа из 6 шагов (держите его в голове на любом интервью)**:
1. **Уточните функциональные и нефункциональные требования**: Сколько DAU (активных пользователей в сутки)? Читаем чаще или пишем (`Read-Heavy` vs `Write-Heavy`)? Допустима ли задержка в пару секунд (`Eventual Consistency`)?
2. **Прикиньте нагрузку (Back-of-the-Envelope Estimation)**: $100\,000$ запросов в сутки $\approx 1.2\text{ RPS}$ в среднем и $\approx 10\text{ RPS}$ в пике (справится один инстанс FastAPI + PostgreSQL!). А $10\,000\,000$ запросов в сутки — это уже $\approx 120\text{ RPS}$ в среднем и $\approx 1000\text{ RPS}$ в пике (нужен кэш Redis и пул соединений).
3. **Спроектируйте API-контракт**: 2–3 эндпоинта (`POST /links`, `GET /{code}`).
4. **Спроектируйте схему БД и индексы**: таблицы, `PRIMARY KEY`, какие поля индексируем (`B-Tree`).
5. **Найдите узкое место (Bottleneck) и расшийте его**: кэш `Cache-Aside`, курсорная пагинация, очередь сообщений или Read Replica.
6. **Явно проговорите компромисс (Trade-off)**: *«Мы выбрали решение X, потому что оно даёт Y, но платим за это Z»*.

## 2. Сводная матрица 6 классических сценариев System Design Lite

| Сценарий | Профиль нагрузки | Главная ошибка новичка | Инженерное решение (Senior-подход) | Ключевой Trade-off (Компромисс) |
| :--- | :--- | :--- | :--- | :--- |
| **1. Сократитель ссылок (URL Shortener)** | `Read-Heavy` (100 чтений на 1 запись) | Генерировать случайную строку и проверять в БД в цикле на коллизии | Кодировать автоинкрементный `id` (или Snowflake ID) в **Base62** (`[0-9a-zA-Z]`, 6 символов $= 62^6 \approx 56.8$ млрд ссылок) + кэш в **Redis** | Редирект `301` (кэшируется в браузере, 0 нагрузки, но теряем аналитику кликов) vs `302` (каждый клик учитывается в статистике) |
| **2. Rate Limiter (Ограничитель запросов)** | Сверхбыстрые проверка и инкремент на каждый запрос | Хранить счётчик запросов в PostgreSQL (`UPDATE` на каждый клик положит БД) | **Redis `INCR` + `EXPIRE`** (Fixed Window) или **Token Bucket / Sliding Window** в памяти/Redis | Fixed Window сверхдешёвый ($O(1)$), но пропускает до $2\times$ лимита на стыке двух минут |
| **3. Лента новостей / Список заказов** | Чтение страниц списка с сортировкой по дате | Пагинация через `OFFSET 100000 LIMIT 20` (БД читает и выкидывает $100\,000$ строк) + проблема `N+1` | **Курсорная пагинация (Keyset Pagination)** `WHERE created_at < :cursor ORDER BY created_at DESC LIMIT 20` + составной B-Tree индекс + `selectinload` | Курсор работает за $O(\log N)$ на любой глубине, но нельзя прыгнуть сразу на «страницу №47» |
| **4. Загрузка тяжёлых файлов и аватарок** | Долгий сетевой I/O и CPU на ресайз картинок | Принимать `50 МБ` через воркер API и сохранять на локальный диск контейнера | Выдать клиенту **Pre-Signed URL** для прямой загрузки в **S3 (MinIO)**, а нарезку превью делать асинхронно в **Celery** | Прямая загрузка в S3 разгружает API на 99%, но антивирусная проверка и валидация происходят уже асинхронно после загрузки |
| **5. Отправка уведомлений (Email / Push)** | Зависимость от внешних медленных API (SMTP/FCM) | Вызывать `smtp.send()` синхронно внутри `POST /orders` | Паттерн **Transactional Outbox** + очередь **RabbitMQ / Celery** с `Exponential Backoff` ретраями и **Idempotency Key** | Мгновенный ответ клиенту и защита от падения SMTP, но доставка уведомления становится асинхронной (*at-least-once*) |
| **6. Тяжёлый аналитический дашборд** | Дорогие `JOIN + GROUP BY` по миллионам строк | Считать агрегацию в реальном времени при каждом открытии страницы | **Cache-Aside** в Redis с `TTL = 300 с` (плюс защита от *Cache Stampede* локом) или предрасчёт в материализованное представление | Дашборд открывается за `2 мс` вместо `4 с`, но данные могут отставать от реального времени на 5 минут |

## 3. Разбор в деталях: почему Base62 лучше `random` для URL Shortener

Представьте, что вы проектируете `bit.ly`. Если генерировать 6 случайных символов через `random.choices()`, то по парадоксу дней рождения при росте базы вы начнёте постоянно натыкаться на **коллизии** (код уже занят в БД, нужно делать повторный `SELECT` и перегенерацию).
А если взять уникальный целочисленный `ID` записи (например, `125_432_981`) и перевести его из десятичной системы счисления в **62-ричную (`Base62`: цифры `0-9`, буквы `a-z`, `A-Z`)**, то:
- Коллизии **математически невозможны** (взаимно-однозначное соответствие `id <-> short_code`);
- Всего 6 символов кодируют $62^6 = 56\,800\,235\,584$ (почти 57 миллиардов!) уникальных ссылок.

> **Junior vs Senior**:
> - **Junior**: На вопрос «Спроектируй сократитель ссылок» сразу начинает рисовать микросервисы, Kafka и шардирование Cassandra, забыв спросить про RPS и не зная, как сгенерировать короткий код без коллизий.
> - **Senior**: Сначала уточняет нагрузку (например, 100 записей/с и 10 000 чтений/с), предлагает монолит + PostgreSQL + Redis, показывает конвертацию `ID -> Base62` без коллизий и обсуждает разницу между редиректами `301` и `302`.

## 4. Практикум: движок URL Shortener на `Base62` + `Cache-Aside` в Python 3.13

```python
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
BASE = len(ALPHABET)  # 62

def encode_base62(num: int) -> str:
    if num == 0:
        return ALPHABET[0]
    chars: list[str] = []
    while num > 0:
        num, rem = divmod(num, BASE)
        chars.append(ALPHABET[rem])
    return "".join(reversed(chars))

def decode_base62(code: str) -> int:
    num = 0
    for ch in code:
        num = num * BASE + ALPHABET.index(ch)
    return num

class UrlShortenerService:
    def __init__(self) -> None:
        self._db: dict[int, str] = {}
        self._redis_cache: dict[str, str] = {}
        self._next_id = 100_000  # Стартуем со 100 000 для красивых кодов

    def shorten(self, long_url: str) -> str:
        link_id = self._next_id
        self._next_id += 1
        self._db[link_id] = long_url
        return encode_base62(link_id)

    def resolve(self, code: str) -> tuple[str, str]:
        # Паттерн Cache-Aside: сначала проверяем быстрый кэш Redis
        if code in self._redis_cache:
            return self._redis_cache[code], "CACHE_HIT"
        link_id = decode_base62(code)
        long_url = self._db[link_id]
        self._redis_cache[code] = long_url
        return long_url, "DB_LOOKUP -> CACHED"

shortener = UrlShortenerService()
short_code = shortener.shorten("https://academy.python.org/courses/architecture/system-design")
print(f"Короткий код Base62: {short_code} (ID={decode_base62(short_code)})")
print("1-й переход:", shortener.resolve(short_code))
print("2-й переход:", shortener.resolve(short_code))
```
