## 1. Что такое Singleton (Одиночка) и когда он действительно нужен?

> **Ментальная модель — «Директор школы и единый школьный звонок»**:
> В школе много учителей и сотни учеников (обычные объекты), но **расписание звонков** должно быть строго одно на всё здание. Если каждый учитель заведёт свой собственный генератор звонков, уроки будут начинаться и заканчиваться вразнобой. **Singleton (Одиночка)** гарантирует, что у класса во всём процессе существует **ровно один экземпляр**, и предоставляет к нему единую точку доступа.

Где Singleton оправдан в бэкенде:
- **Пул соединений к БД (Connection Pool)** или клиент Redis (создавать новый пул на каждый запрос — верный способ положить БД);
- **Объект конфигурации приложения (`AppSettings`)**, прочитанный при старте из переменных окружения;
- **Реестр метрик или глобальный логгер (`logging.getLogger('app')`)**.

```text
Обычный класс (каждый вызов -> новый объект в куче):
  Client A ---> Config() ---> [Объект #1 по адресу 0x101]
  Client B ---> Config() ---> [Объект #2 по адресу 0x202]  (c1 is c2 == False)

Паттерн Singleton (все вызовы возвращают одну и ту же ссылку):
  Client A ---\
               +---> Singleton() ---> [Единственный объект по адресу 0x101]
  Client B ---/                       (s1 is s2 == True)
```

## 2. Ловушка многопоточности (Race Condition) и Double-Checked Locking

Наивная реализация Singleton через `__new__` проверяет `if cls._instance is None:`. Но что произойдёт, если два потока (`Thread 1` и `Thread 2`) вызовут `Singleton()` одновременно на старте сервера?
Оба потока одновременно увидят `_instance is None`, оба зайдут внутрь `if` и создадут **два разных экземпляра**!

Чтобы защититься от состояния гонки без потери скорости на каждом чтении, используется **блокировка с двойной проверкой (Double-Checked Locking)** на базе `threading.Lock()`:
1. Сначала быстрая проверка `if cls._instance is None` **без блокировки** (если объект уже создан, потоки не ждут замок!).
2. Если объект ещё `None` — захватываем `with cls._lock:` и проверяем `if cls._instance is None` **второй раз** (вдруг соседний поток уже успел создать объект, пока мы ждали замок).

```python
import threading

class ThreadSafePool:
    _instance: "ThreadSafePool | None" = None
    _lock: threading.Lock = threading.Lock()

    def __new__(cls) -> "ThreadSafePool":
        if cls._instance is None:                  # 1-я проверка (быстрая, без Lock)
            with cls._lock:
                if cls._instance is None:          # 2-я проверка (внутри критической секции)
                    instance = super().__new__(cls)
                    instance.connections_created = 1
                    cls._instance = instance
        return cls._instance

p1 = ThreadSafePool()
p2 = ThreadSafePool()
print("Один и тот же объект (p1 is p2):", p1 is p2, "| Создано пулов:", p1.connections_created)
```

## 3. Четыре способа реализации Singleton в Python: от `__new__` до модуля

В Python есть важная особенность: **любой импортируемый `.py`-модуль уже является потокобезопасным Singleton из коробки**, так как интерпретатор выполняет код модуля один раз и кэширует его в словаре `sys.modules`!

| Способ реализации | Плюсы | Минусы и подводные камни |
| :--- | :--- | :--- |
| **1. Экземпляр на уровне модуля (`config.py`)** | Самый питоничный (Pythonic), потокобезопасен за счёт импорт-лока Python | Создаётся сразу в момент `import`, а не лениво при первом вызове |
| **2. `@functools.lru_cache(maxsize=1)` на фабричной функции** | Идиоматично в **FastAPI** (`Depends(get_settings)`), легко сбрасывается через `.cache_clear()` в тестах | Кэширует по аргументам функции |
| **3. Переопределение `__new__` + `threading.Lock`** | Классический ООП-подход, ленивая инициализация | Важно помнить, что **`__init__` вызывается при каждом обращении `MySingleton()`** и может перезатереть поля! |
| **4. Метакласс (`class SingletonMeta(type)`)** | Перехватывает `type.__call__`: метод **`__init__` вызывается строго один раз**! | Чуть сложнее для чтения новичками |

## 4. Почему Singleton часто считают антипаттерном и как решить проблему через Метакласс

Почему опытные архитекторы осторожно относятся к классическому Singleton?
1. **Скрытое глобальное состояние**: если тест №1 изменил поле внутри `Singleton`, тест №2 получит «грязные» данные и упадёт.
2. **Ловушка `__init__` в `__new__`**: когда вы реализуете Singleton через `__new__`, Python всё равно вызывает `__init__` при каждом `Database()`! Решение — использовать **метакласс `SingletonMeta`**, который перехватывает `__call__` и вызывает `__init__` ровно один раз.

> **Junior vs Senior**:
> - **Junior**: Реализует Singleton через `__new__` без `Lock`, а в `__init__` пишет `self.cache = {}` — и удивляется, почему каждое обращение `Cache()` обнуляет словарь кэша!
> - **Senior**: В FastAPI и современном Python использует `@lru_cache(maxsize=1)` на функции `get_settings()` или Dependency Injection, а если нужен строгий ООП-Singleton — реализует его через метакласс с методом `reset_for_tests()`.

```python
import threading
from typing import Any

class SingletonMeta(type):
    """Потокобезопасный метакласс: гарантирует, что и __new__, и __init__ вызовутся ровно 1 раз."""
    _instances: dict[type, Any] = {}
    _lock: threading.Lock = threading.Lock()

    def __call__(cls, *args: Any, **kwargs: Any) -> Any:
        if cls not in cls._instances:
            with cls._lock:
                if cls not in cls._instances:
                    cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]

class AppConfig(metaclass=SingletonMeta):
    def __init__(self, env: str = "production") -> None:
        self.env = env
        self.init_calls = getattr(self, "init_calls", 0) + 1

cfg1 = AppConfig("staging")
cfg2 = AppConfig("development")  # Второй вызов НЕ перезатрёт env и НЕ вызовет __init__ повторно!
print(f"cfg1 is cfg2: {cfg1 is cfg2} | env={cfg2.env} | Вызовов __init__: {cfg2.init_calls}")
```
