1. Что вернёт `user.orders.count()` в цикле после `prefetch_related('orders')` ? >> Значение из кэша в памяти без обращения к БД; данные уже загружены
2. Какие инструменты помогают обнаружить N+1? >> Django Debug Toolbar (счётчик и дубли запросов на страницу), логирование SQL в консоль, профилировщики
3. Как логирование SQL помогает выявить N+1? >> В консоли видны повторяющиеся паттерны запросов с разными значениями параметров
4. Как проявляется N+1 в логах БД? >> Сотни идентичных запросов, различающихся только значением параметра (например, `WHERE user_id = ?` )
5. Как исправить N+1 при доступе к профилю через `OneToOne` ? >> `User.objects.select_related('profile').all()`
6. Является ли N+1 проблемой только Django? >> Нет; это общая проблема любых ORM: SQLAlchemy, Hibernate, ActiveRecord и др.
7. В чём опасность N+1 на больших объёмах данных? >> Экспоненциальный рост числа запросов; сотни тысяч мелких запросов перегружают БД и сеть, резко снижая производительность
8. Как выглядит N+1 на уровне кода Django? >> `users = User.objects.all(); [u.orders.count() for u in users]` – для каждого пользователя генерируется отдельный `SELECT COUNT(*)`
9. Что такое обратный `ForeignKey` в контексте Django ORM? >> Доступ к связанным объектам от модели, на которую ссылаются; например, `user.orders.all()` , где `order` содержит `ForeignKey` на `user`
10. Быстрее ли `prefetch_related` для простых `ForeignKey` по сравнению с `select_related` ? >> Нет; `select_related` эффективнее для прямых FK – один запрос против двух с обработкой в Python
11. Для чего используется `select_related()` ? >> Оптимизирует прямые связи `ForeignKey` и `OneToOne` через SQL `JOIN` ; результат – 1 запрос вместо N+1
12. Для каких типов связей применяется `select_related()` ? >> `ForeignKey` (прямой) и `OneToOne` ; для обратного `ForeignKey` и `ManyToMany` – не работает
13. Для чего используется `prefetch_related()` ? >> Оптимизирует `ManyToMany` и обратные `ForeignKey` ; делает 2 запроса и соединяет данные на стороне Python
14. Можно ли использовать `select_related()` для обратного `ForeignKey` ? >> Нет; для обратных FK используется `prefetch_related()`
15. Что такое проблема N+1? >> Выполнение одного запроса для получения списка и N дополнительных запросов для каждого элемента; итого 1+N запросов к БД
16. Сколько запросов выполнится при итерации по 1000 пользователям с обращением к связанному объекту без оптимизации? >> 1001 запрос: 1 на список + 1000 на каждый связанный объект
17. Как избежать N+1 на чистом SQL? >> `JOIN` с `GROUP BY` и агрегатными функциями ( `COUNT` , `SUM` ) для получения всех данных в одном запросе
18. Чем архитектурно отличаются `select_related` и `prefetch_related` ? >> `select_related` – JOIN на уровне БД (1 запрос); `prefetch_related` – отдельный запрос + склейка в памяти Python (2 запроса)
19. Можно ли оптимизировать `ManyToMany` через `select_related()` ? >> Нет; только через `prefetch_related()`
20. Зачем `LEFT JOIN` предпочтительнее `INNER JOIN` при получении списка пользователей и их заказов? >> `LEFT JOIN` включает пользователей без заказов; `INNER JOIN` исключил бы их из результата
