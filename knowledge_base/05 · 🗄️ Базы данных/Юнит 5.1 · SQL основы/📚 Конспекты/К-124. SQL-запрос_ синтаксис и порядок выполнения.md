## Декларативная природа SQL: что вместо как

> **Декларативный подход**: в SQL вы описываете, **какой набор данных** хотите получить на выходе, а планировщик СУБД сам выбирает оптимальный алгоритм чтения с диска и обхода индексов.

В императивном коде Python мы пишем пошаговый цикл фильтрации, а в SQL задаём декларативную спецификацию выборки одной командой:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute(
        'CREATE TABLE items (name TEXT, price INT)'
    )
    conn.execute(
        "INSERT INTO items VALUES ('Мышь', 80)"
    )
    rows = conn.execute(
        'SELECT name FROM items WHERE price >= 50'
    ).fetchall()
    print('Найдено:', rows)
```

## Лексический порядок против конвейера движка

Главное правило SQL: **порядок написания клауз (Lexical Order)** не совпадает с **физическим порядком их исполнения движком СУБД (Logical Execution Order)**.

```text
1. Синтаксис (как пишем запрос):
   1. SELECT category, COUNT(*) AS cnt
   2. FROM products
   3. WHERE price > 100
   4. GROUP BY category
   5. HAVING COUNT(*) >= 2
   6. ORDER BY cnt DESC
   7. LIMIT 5;

2. Конвейер движка СУБД (как исполняется):
   ┌─ 1. FROM / JOIN  (Загрузка и склейка таблиц)
   ├─ 2. WHERE        (Построчный фильтр сырых строк)
   ├─ 3. GROUP BY     (Схлопывание строк в группы)
   ├─ 4. HAVING       (Фильтрация готовых групп)
   ├─ 5. SELECT       (Вычисление столбцов и AS)
   ├─ 6. DISTINCT     (Удаление дубликатов строк)
   ├─ 7. ORDER BY     (Сортировка результата)
   └─ 8. LIMIT/OFFSET (Отсечение нужной страницы)
```

## Таблица этапов выполнения и видимости алиасов (`AS`)

Поскольку фаза `SELECT` исполняется только **пятой по счёту**, псевдонимы столбцов (`AS`) ещё не существуют в `WHERE`, но уже доступны в `ORDER BY`:

| Фаза | Оператор SQL | Что делает движок БД | Видит алиасы `SELECT`? |
| :--- | :--- | :--- | :--- |
| **1** | `FROM` / `JOIN` | Загружает таблицы и соединяет их по ключу `ON` | ❌ Нет |
| **2** | `WHERE` | Отсекает ненужные сырые строки до группировки | ❌ Нет |
| **3** | `GROUP BY` | Группирует оставшиеся строки по уникальным ключам | ❌ По стандарту нет |
| **4** | `HAVING` | Фильтрует сформированные группы по агрегатам | ❌ Нет |
| **5** | `SELECT` | Вычисляет выражения и создаёт псевдонимы `AS` | ✅ Создаёт здесь |
| **6** | `ORDER BY` | Сортирует итоговую выборку (`ASC` / `DESC`) | ✅ Да, видит |
| **7** | `LIMIT` / `OFFSET` | Ограничивает число возвращаемых записей | — |

## Почему алиасы `SELECT` видны только в `ORDER BY`

Попытка обратиться к псевдониму `SELECT price * 2 AS total` внутри `WHERE total > 100` в стандартном SQL вызовет ошибку, так как `WHERE` работает до вычисления `SELECT`.

В клаузе `ORDER BY` шаг `SELECT` уже позади, поэтому сортировка по алиасу `total DESC` работает штатно:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('CREATE TABLE g (t TEXT, p INT)')
    conn.executemany(
        'INSERT INTO g VALUES (?, ?)',
        [('Кабель', 20), ('Монитор', 300)],
    )
    sql = (
        'SELECT t, p * 2 AS dp FROM g '
        'WHERE p * 2 > 50 ORDER BY dp DESC'
    )
    print(conn.execute(sql).fetchall())
```

## Трёхзначная логика `NULL`: `IS NULL` вместо `= NULL`

**`NULL`** — это не ноль и не пустая строка, а специальный маркер *«значение неизвестно»*.

Проверка через `= NULL` или `!= NULL` всегда возвращает `UNKNOWN` и отбрасывает строку в `WHERE`, поэтому для проверки пустоты используются строго операторы `IS NULL` и `IS NOT NULL`:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('CREATE TABLE u (n TEXT, ph TEXT)')
    conn.executemany(
        'INSERT INTO u VALUES (?, ?)',
        [('Alice', None), ('Bob', '+7900')],
    )
    res = conn.execute(
        'SELECT n FROM u WHERE ph IS NULL'
    ).fetchall()
    print('Без телефона:', res)
```

## Управление позицией `NULL` при сортировке (`NULLS LAST`)

В PostgreSQL значения `NULL` считаются «больше всех чисел» и при сортировке по убыванию (`ORDER BY rating DESC`) всплывают на первые строчки.

Конструкции `NULLS LAST` и `NULLS FIRST` явно фиксируют позицию пустых значений в начале или в конце отчёта:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('CREATE TABLE d (n TEXT, s INT)')
    conn.executemany(
        'INSERT INTO d VALUES (?, ?)',
        [('Ann', None), ('Bob', 95), ('Cid', 80)],
    )
    sql = (
        'SELECT n, s FROM d '
        'ORDER BY s DESC NULLS LAST'
    )
    print(conn.execute(sql).fetchall())
```

## Ловушка глубокого `OFFSET` и курсорная пагинация

Запрос `LIMIT 10 OFFSET 100000` заставляет СУБД прочитать и отсортировать `100 010` строк только ради того, чтобы отбросить первые `100 000` записей.

На больших таблицах вместо `OFFSET` применяют **Keyset Pagination** с фильтром по последнему увиденному ключу `WHERE id > :last_id ORDER BY id ASC LIMIT 10`:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('CREATE TABLE logs (id INT)')
    conn.executemany(
        'INSERT INTO logs VALUES (?)',
        [(1,), (2,), (3,), (4,), (5,)],
    )
    sql = 'SELECT id FROM logs WHERE id > ? LIMIT 2'
    page = conn.execute(sql, (2,)).fetchall()
    print('Следующая страница:', page)
```
