1. В чём ключевое различие между репликацией и шардированием? >> Репликация создаёт полные копии 100% данных на нескольких серверах — масштабирует чтение и повышает отказоустойчивость. Шардирование делит данные на непересекающиеся части по Shard Key — масштабирует запись и объём хранения.
2. На каком сервере выполняются все операции записи в схеме Single-Leader? >> Исключительно на Primary (Master); реплики принимают только запросы SELECT.
3. Что транслирует Primary на реплики в PostgreSQL при репликации? >> Поток WAL (Write-Ahead Log) — журнал всех изменений; реплики воспроизводят его и остаются синхронизированными с Primary.
4. Что такое Replication Lag? >> Задержка между моментом записи на Primary и появлением данных на Read Replica. При асинхронной репликации может достигать сотен мс; пользователь видит устаревшие данные сразу после изменения.
5. Чем асинхронная репликация отличается от синхронной? >> Async: Primary подтверждает COMMIT немедленно, реплики догоняют позже — низкая задержка, риск потери данных. Sync: Primary ждёт подтверждения от реплики (RPO=0), но замедляет каждый COMMIT.
6. Что такое паттерн Read-Your-Own-Writes? >> После POST/PUT запросы на чтение от того же пользователя направляются напрямую на Primary несколько секунд — чтобы не получить устаревший ответ из-за Replication Lag.
7. Что такое Shard Key (ключ шардирования) и почему его выбор критически важен? >> Поле, по которому роутер определяет нужный шард. Неудачный ключ создаёт Hotspot; удачный — равномерно распределяет нагрузку.
8. В чём проблема Hotspot при шардировании? >> Один шард получает непропорционально большую нагрузку. Например, Range Sharding по времени направляет все новые записи на «последний» шард — остальные простаивают.
9. Как работает Range Sharding? >> Данные делятся по диапазонам значений Shard Key (user_id 1–1 000 000 → Shard 1). Плюс: удобны диапазонные запросы. Минус: Hotspot для монотонно растущих ключей.
10. Как работает Hash Sharding? >> shard_id = hash(key) % N — равномерно распределяет данные, устраняя Hotspot. Минус: диапазонные запросы требуют обращения ко всем шардам (Scatter-Gather).
11. Что такое Failover в контексте репликации? >> Автоматическое переключение клиентов на реплику при падении Primary. При синхронной репликации — нулевая потеря данных; при асинхронной — возможна потеря последних операций.
12. Почему Cross-Shard JOIN является архитектурной проблемой? >> Данные из разных шардов хранятся на разных серверах; JOIN требует собрать их всех и объединить в приложении (Application-Side Join) — медленно и сложно.
13. В каком случае выгоднее репликация, а не шардирование? >> Когда данные помещаются на одном сервере, но нагрузка на чтение высокая — репликация масштабирует SELECT без сложности шардирования.
14. Как роутер при Hash Sharding определяет нужный шард? >> shard_id = hash(user_id) % N — вычисляет хэш ключа и направляет запрос на конкретный шард без сканирования остальных.
15. Какие два вида масштабирования решаются репликацией и какой — шардированием? >> Репликация: масштабирование чтения (Read Scaling) и отказоустойчивость (HA). Шардирование: масштабирование записи (Write Scaling) и объёма данных (Storage Scaling).
