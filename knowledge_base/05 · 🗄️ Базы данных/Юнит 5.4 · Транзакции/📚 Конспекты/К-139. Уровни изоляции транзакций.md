## Четыре аномалии конкурентного доступа

> **Совместная работа против фотоснимка**: на уровне **Read Committed** вы сразу видите чужие зафиксированные правки, а на **Repeatable Read** работаете со снимком данных на момент старта транзакции.

Если тысячам параллельных транзакций разрешить свободно читать и менять общие строки, возникают **4 аномалии**:

1. **Dirty Read (Грязное чтение)**: транзакция А читает незафиксированные данные транзакции Б, а затем Б делает `ROLLBACK`.
2. **Non-Repeatable Read (Неповторяющееся чтение)**: два одинаковых `SELECT` по одной строке внутри транзакции А возвращают разные значения, потому что Б успела её обновить и зафиксировать.
3. **Phantom Read (Фантомное чтение)**: повторный `SELECT COUNT(*)` по условию возвращает больше строк, потому что Б успела вставить новую запись.
4. **Lost Update (Потерянное обновление)**: две транзакции прочитали `balance = 100`, отдельно посчитали итог в коде и вторая перезатёрла вклад первой.

## Матрица уровней изоляции SQL и PostgreSQL `MVCC`

В PostgreSQL архитектура **MVCC (Multi-Version Concurrency Control)** хранит версии строк, поэтому читатели не блокируют писателей, а писатели не блокируют читателей.

В результате в PostgreSQL грязное чтение исключено даже на `Read Uncommitted`, а `Repeatable Read` защищает и от фантомов:

| Уровень изоляции | Dirty Read | Non-Repeatable Read | Phantom Read | Serialization Anomaly |
| :--- | :--- | :--- | :--- | :--- |
| **`READ UNCOMMITTED`** | В стандарте да (в **PostgreSQL ❌ нет**) | ⚠️ Возможно | ⚠️ Возможно | ⚠️ Возможно |
| **`READ COMMITTED`** *(дефолт PostgreSQL)* | ❌ Защищено | ⚠️ Возможно (свежий снимок на каждый `SELECT`) | ⚠️ Возможно | ⚠️ Возможно |
| **`REPEATABLE READ`** *(дефолт MySQL InnoDB)* | ❌ Защищено | ❌ Защищено (снимок на всю транзакцию) | В стандарте да (в **PostgreSQL ❌ нет**) | ⚠️ Возможно (Write Skew) |
| **`SERIALIZABLE`** | ❌ Защищено | ❌ Защищено | ❌ Защищено | ❌ Полная защита (SSI) |

## Потерянное обновление (`Lost Update`) на практике

На уровне `READ COMMITTED` наивный паттерн «прочитал остаток в Python ➔ отнял ➔ записал» ломается при одновременных запросах.

Вторая транзакция опирается на устаревшее значение и полностью затирает списание первой:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute(
        'CREATE TABLE stock '
        '(id INT PRIMARY KEY, qty INT)'
    )
    conn.execute(
        'INSERT INTO stock VALUES (1, 10)'
    )

    # Обе сессии прочитали qty = 10
    q = 'SELECT qty FROM stock WHERE id = 1'
    q1 = conn.execute(q).fetchone()[0]
    q2 = conn.execute(q).fetchone()[0]

    conn.execute(
        'UPDATE stock SET qty = ? '
        'WHERE id = 1',
        (q1 - 3,),
    )

    # Перезаписывает остаток от старых 10
    conn.execute(
        'UPDATE stock SET qty = ? '
        'WHERE id = 1',
        (q2 - 4,),
    )
    res = conn.execute(q).fetchone()[0]
    print('Остаток после гонки:', res)
    # >>> Остаток после гонки: 6
```

## Атомарный `UPDATE` и пессимистическая блокировка

Чтобы не терять обновления при конкурентной записи, расчёт выносят внутрь БД или блокируют строку до коммита:

1. **Атомарный инкремент в SQL**: `UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100` — движок сам синхронизирует запись на одной строке.
2. **Пессимистическая блокировка (`SELECT ... FOR UPDATE`)**: сразу захватывает строчную блокировку (*Row Lock*), заставляя конкурирующую транзакцию ждать до нашего `COMMIT`.

## Оптимистическая блокировка по версии строки

**Optimistic Locking** не держит долгих блокировок при чтении, а добавляет колонку `version` и проверяет её в условии `WHERE`.

Если другая сессия уже увеличила версию, запрос вернёт `rowcount == 0`, предотвратив потерю данных:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute(
        'CREATE TABLE items (id INT '
        'PRIMARY KEY, qty INT, ver INT)'
    )
    conn.execute(
        'INSERT INTO items VALUES (1, 10, 1)'
    )

    # Обе транзакции видят ver = 1
    q = 'SELECT qty, ver FROM items'
    q1, v1 = conn.execute(q).fetchone()
    q2, v2 = conn.execute(q).fetchone()

    cur1 = conn.execute(
        'UPDATE items SET qty=?, ver=ver+1 '
        'WHERE id=1 AND ver=?',
        (q1 - 3, v1),
    )
    cur2 = conn.execute(
        'UPDATE items SET qty=?, ver=ver+1 '
        'WHERE id=1 AND ver=?',
        (q2 - 4, v2),
    )
    print(
        'Т1:', cur1.rowcount,
        'Т2:', cur2.rowcount,
    )
    # >>> Т1: 1 Т2: 0

    res = conn.execute(q).fetchone()
    print('Итог (qty, ver):', res)
    # >>> Итог (qty, ver): (7, 2)
```

## Уровень `SERIALIZABLE` и паттерн `Retry`

Самый строгий уровень **`SERIALIZABLE`** в PostgreSQL отслеживает пересекающиеся зависимости (SSI) и прерывает конфликтующую транзакцию ошибкой **`SQLSTATE 40001`**.

При получении `40001` или `rowcount == 0` приложение не падает, а безопасно повторяет транзакцию с начала (`Retry`).

> **Junior vs Senior**:
> - **Junior**: Читает `user.balance` в ORM на `READ COMMITTED`, вычитает сумму в Python и вызывает `commit()`, получая *Lost Update* под нагрузкой.
> - **Senior**: Использует атомарный SQL-апдейт, `SELECT ... FOR UPDATE` или оптимистическую блокировку по `version`, а для `REPEATABLE READ` / `SERIALIZABLE` закладывает автоматический `Retry` при `SQLSTATE 40001`.
