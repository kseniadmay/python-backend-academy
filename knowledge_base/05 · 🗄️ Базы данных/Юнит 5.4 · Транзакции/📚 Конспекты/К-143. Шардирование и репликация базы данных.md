## Репликация против Шардирования

> **Ксерокопии учебника против энциклопедии в томах**: репликация дублирует **100% данных** на несколько узлов для чтения и отказоустойчивости, а шардирование разрезает таблицу на независимые части по серверам.

Схематически оба способа горизонтального масштабирования работают в разных осях нагрузки:

```text
1. РЕПЛИКАЦИЯ (масштабируем чтение):
Запись -> [Primary] ─(WAL)─► [Replica 1]
                    └(WAL)─► [Replica 2]

2. ШАРДИРОВАНИЕ (делим запись и диск):
shard = hash(user_id) % 3
  ├──► [Shard 0]  users 0, 3, 6...
  ├──► [Shard 1]  users 1, 4, 7...
  └──► [Shard 2]  users 2, 5, 8...
```

## Синхронная и асинхронная репликация

В архитектуре **Primary-Replica** все операции записи (`INSERT`, `UPDATE`, `DELETE`) принимает главный узел **Primary**, транслируя поток `WAL` на читающие реплики:

| Тип репликации | Как подтверждается `COMMIT`? | Главный плюс | Главный риск |
| :--- | :--- | :--- | :--- |
| **Асинхронная (Async)** | Primary пишет в свой WAL и сразу отвечает `OK`, реплики догоняют его через 5–100 мс | Не тормозит запись; сбой реплики не останавливает Primary | **Replication Lag**: клиент сразу после обновления профиля видит старые данные |
| **Синхронная (Sync)** | Primary ждёт подтверждения записи в WAL хотя бы от одной реплики перед ответом `OK` | Нулевая потеря данных (`RPO = 0`) при смерти диска Primary | Сетевая задержка до реплики замедляет каждый `COMMIT` |

---

## Ловушка `Replication Lag` и `Read-Your-Own-Writes`

При асинхронной репликации между записью на **Primary** и её применением на реплике всегда есть небольшое отставание (*Replication Lag*).

Чтобы пользователь после изменения данных не увидел старую версию страницы, используют паттерн **Read-Your-Own-Writes**: первые 2–5 секунд после `POST`/`PUT` запросы чтения от этого клиента направляют прямо на **Primary**.

## Выбор ключа шардирования и проблема `Hotspot`

Правильный выбор **ключа шардирования (`Shard Key`)** определяет равномерность нагрузки по всем узлам кластера:

1. **Range Sharding (по диапазону)**: например, разделение по дате или `id` удобно для диапазонных выборок, но все свежие записи бьют в последний сервер (*Hotspot*).
2. **Hash Sharding (по хэшу)**: `crc32(user_id) % N` равномерно распределяет запись по всем шардам, но добавление сервера меняет остаток деления и требует переноса почти всех данных.
3. **Consistent Hashing (консистентное хэширование)**: располагает узлы на кольце хэшей, так что при добавлении нового сервера мигрирует лишь доля $1/N$ ключей.

## Программный роутер шардирования на Python

Роутер на уровне приложения вычисляет детерминированный хэш ключа и мгновенно направляет запрос в нужный шард:

```python
import hashlib

class ShardedCluster:
    def __init__(
        self,
        num_shards: int = 3,
    ) -> None:
        self.num_shards = num_shards
        self.shards: dict[int, dict] = {
            i: {} for i in range(num_shards)
        }

    def get_shard_id(
        self,
        user_id: int,
    ) -> int:
        # Детерминированный хэш ключа
        raw = str(user_id).encode()
        digest = hashlib.md5(raw).hexdigest()
        return (
            int(digest, 16) % self.num_shards
        )

    def save_user(
        self,
        user_id: int,
        name: str,
    ) -> int:
        sid = self.get_shard_id(user_id)
        self.shards[sid][user_id] = name
        return sid

cluster = ShardedCluster(num_shards=3)
for uid in range(1, 10):
    cluster.save_user(uid, f'User_{uid}')

counts = [
    len(s) for s in cluster.shards.values()
]
print('Записей по шардам:', counts)
# >>> Записей по шардам: [4, 2, 3]
```

## Лестница масштабирования БД и ограничения

Горизонтальное шардирование резко усложняет запросы: межшардовые `JOIN` и распределённые транзакции либо недоступны, либо крайне дороги, поэтому к нему прибегают в последнюю очередь.

> **Junior vs Senior**:
> - **Junior**: Предлагает внедрять шардирование на таблице из 5 млн строк, где проблема решается одним B-Tree индексом.
> - **Senior**: Двигается по лестнице: 1) индексы и `EXPLAIN ANALYZE` $\to$ 2) кэширование в Redis и `PgBouncer` $\to$ 3) партиционирование и Read-реплики $\to$ 4) шардирование по `tenant_id` на сотнях терабайт.
