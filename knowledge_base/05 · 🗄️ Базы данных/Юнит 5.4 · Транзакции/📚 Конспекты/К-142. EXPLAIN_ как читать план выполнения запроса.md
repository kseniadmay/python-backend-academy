## Прогнозный `EXPLAIN` против `EXPLAIN ANALYZE`

> **Прогноз навигатора против реальной поездки**: `EXPLAIN` предсказывает план по статистике таблицы без запуска, а `EXPLAIN ANALYZE` реально выполняет запрос и замеряет миллисекунды.

Обычный `EXPLAIN` безопасен для любых запросов, но модифицирующие команды с `ANALYZE` реально изменят или удалят строки.

Чтобы замерить план `DELETE` или `UPDATE` без потери данных, запрос оборачивают в транзакцию с откатом:

```sql
BEGIN;
EXPLAIN ANALYZE
DELETE FROM logs
WHERE created_at < '2025-01-01';
ROLLBACK;
```

## Анатомия строки плана выполнения в PostgreSQL

В выводе `EXPLAIN ANALYZE` слева отображается прогноз оптимизатора, а справа — фактическое время и число обработанных строк:

```text
Index Scan on users
  (cost=0.29..8.31 rows=1 width=64)
   └── старт..итог  └─ прогноз строк
  (actual time=0.018..0.019 rows=1 loops=1)
   └── время в мс            └─ факт  └─ раз
```

Если `cost` показывает условные единицы работы планировщика, то ключевой сигнал ошибки оценки — сильное расхождение прогноза `rows` и факта `actual rows`.

## Четыре базовых алгоритма сканирования таблиц

В зависимости от доли выбираемых строк и индексов движок БД выбирает один из четырёх способов чтения данных:

| Узел плана | Как работает физически | Когда уместен |
| :--- | :--- | :--- |
| **`Seq Scan`** | Читает таблицу подряд от начала до конца ($O(n)$) | Для малых таблиц (< 1000 строк) или выборки > 20% данных |
| **`Index Scan`** | Ищет ключ в B-Tree и прыгает по адресу `TID` в таблицу | Точечные выборки (от единиц до сотен строк) |
| **`Bitmap Heap Scan`** | Собирает карту нужных страниц памяти и читает их подряд | Выборка тысяч строк и объединение нескольких индексов |
| **`Index Only Scan`** | Отвечает прямо из листьев покрывающего индекса без таблицы | Самый быстрый режим при наличии всех колонок в индексе |

## Сравнение `Seq Scan` и `Index Scan` в Python

Добавление B-Tree индекса переводит план с линейного перебора `SCAN` на поиск по дереву `SEARCH USING INDEX`:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute(
        'CREATE TABLE ev (id INT PRIMARY '
        'KEY, uid INT, val TEXT)'
    )
    rows = [
        (i % 500, f'v{i}')
        for i in range(2000)
    ]
    conn.executemany(
        'INSERT INTO ev (uid, val) '
        'VALUES (?, ?)',
        rows,
    )

    q = (
        'EXPLAIN QUERY PLAN SELECT * '
        'FROM ev WHERE uid = 77'
    )
    before = conn.execute(q).fetchone()[3]

    conn.execute(
        'CREATE INDEX idx_ev_uid ON ev(uid)'
    )
    after = conn.execute(q).fetchone()[3]

    print('До индекса   :', before)
    # >>> До индекса   : SCAN ev

    print('После индекса:', after)
    # >>> После индекса: SEARCH ev USING INDEX idx_ev_uid (uid=?)
```

## Физические алгоритмы `JOIN`: Nested Loop, Hash и Merge

При соединении двух таблиц оптимизатор выбирает один из трёх алгоритмов в зависимости от размеров выборок и сортировки:

1. **`Nested Loop`**: для каждой строки внешней таблицы ищет пару во внутренней — идеален, если внешняя выборка мала, а во внутренней есть индекс.
2. **`Hash Join`**: загружает меньшую таблицу в хэш-таблицу в `work_mem` и за один линейный проход сверяет с ней большую таблицу.
3. **`Merge Join`**: если обе стороны уже отсортированы по ключу (например, взяты из B-Tree индексов), соединяет их за один одновременный проход.

## Диагностика деградации: `BUFFERS` и `ANALYZE`

При отладке медленного SQL-запроса недостаточно ориентироваться на теоретический `cost` — важно видеть реальное число прочитанных блоков памяти и диска.

> **Junior vs Senior**:
> - **Junior**: Гадает о причине тормозов запроса или смотрит только на верхний `cost` без реального замера `ANALYZE`.
> - **Senior**: Запускает `EXPLAIN (ANALYZE, BUFFERS)`, читает дерево плана от самых глубоких узлов, обновляет устаревшую статистику через `ANALYZE table`, проверяет `Buffers: shared hit / read` и устраняет `Seq Scan` с большим `Rows Removed by Filter`.
