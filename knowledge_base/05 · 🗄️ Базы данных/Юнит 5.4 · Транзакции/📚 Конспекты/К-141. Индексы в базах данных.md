## Устройство `B-Tree` индекса и поиск за O(log n)

> **Алфавитный указатель в конце книги**: поиск без индекса заставляет читать всю таблицу подряд (**`Seq Scan` за $O(n)$**), а индекс хранит отсортированные ключи с точными адресами строк на диске (**`TID`**).

По умолчанию `CREATE INDEX` строит сбалансированное дерево **B-Tree**, где все листья находятся на одной глубине и связаны двусвязным списком.

Благодаря сортировке ключей B-Tree ускоряет не только `=`, но и диапазоны `>`, `<`, `BETWEEN`, префиксный поиск `LIKE 'abc%'` и `ORDER BY`:

```text
Структура B-Tree по email:
         [ "m..." ] (Корень)
        /          \
  ["a..l"]        ["m..z"]
     /                \
["alice"->p42] <=> ["mike"->p108]
```

## Специализация индексов в PostgreSQL

Выбор структуры индекса напрямую зависит от типа данных и шаблона запросов `WHERE`:

| Тип индекса | Пример синтаксиса | Для каких запросов создан |
| :--- | :--- | :--- |
| **B-Tree** *(дефолт)* | `CREATE INDEX ON users (email)` | `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`, `IS NULL`, `ORDER BY` |
| **Составной** | `ON orders (user_id, created_at)` | Ускоряет `(user_id)` и `(user_id, created_at)` по правилу левого префикса |
| **Покрывающий** | `ON users (email) INCLUDE (name)` | Хранит колонки прямо в листьях и даёт **`Index Only Scan`** без чтения таблицы |
| **Частичный** | `ON orders (user_id) WHERE status='new'` | Индексирует только горячее подмножество строк, экономя RAM и диск |
| **GIN** | `USING GIN (tags)` | Массивы, документы **`JSONB`** (`@>`) и полнотекстовый поиск |
| **Hash / BRIN** | `USING HASH` / `USING BRIN (dt)` | Hash — только `=`; BRIN — компактный индекс диапазонов для огромных логов |

## Составной индекс и правило левого префикса

Составной B-Tree индекс `(user_id, status)` отсортирован сначала по `user_id`, и лишь внутри одинаковых `user_id` — по `status`.

Поэтому запрос по `(user_id, status)` использует индекс, а фильтр только по второму полю `status` вынужден сканировать всю таблицу:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute(
        'CREATE TABLE orders (id INT '
        'PRIMARY KEY, uid INT, status TEXT)'
    )
    conn.execute(
        'CREATE INDEX idx_u_st ON '
        'orders(uid, status)'
    )

    q_fast = (
        'EXPLAIN QUERY PLAN SELECT * FROM '
        "orders WHERE uid=42 AND status='ok'"
    )
    q_slow = (
        'EXPLAIN QUERY PLAN SELECT * FROM '
        "orders WHERE status='ok'"
    )

    r1 = conn.execute(q_fast).fetchone()
    print('Левый:', r1[3])
    # >>> Левый: SEARCH orders USING INDEX idx_u_st (uid=? AND status=?)

    r2 = conn.execute(q_slow).fetchone()
    print('Хвост:', r2[3])
    # >>> Хвост: SCAN orders
```

## Покрывающий индекс и `Index Only Scan`

Если все нужные в `SELECT` колонки уже входят в индекс (или добавлены через `INCLUDE`), СУБД берёт ответ прямо из листьев дерева без прыжков в саму таблицу.

В плане запроса такой режим отражается как **`USING COVERING INDEX`**:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute(
        'CREATE TABLE users (id INT '
        'PRIMARY KEY, email TEXT, name TEXT)'
    )
    conn.execute(
        'CREATE INDEX idx_mail_name ON '
        'users(email, name)'
    )

    # Все колонки есть внутри индекса
    sql = (
        'EXPLAIN QUERY PLAN '
        'SELECT email, name FROM users '
        "WHERE email = 'a@b.ru'"
    )
    plan = conn.execute(sql).fetchone()[3]
    print('План:', plan)
    # >>> План: SEARCH users USING COVERING INDEX idx_mail_name (email=?)
```

## Цена индексов при записи и низкая селективность

Индексы радикально ускоряют чтение, но создавать их на каждую колонку подряд нельзя по двум причинам:

1. **Накладные расходы на запись**: каждый индекс замедляет `INSERT`, `UPDATE` и `DELETE`, так как СУБД обязана синхронно обновлять все деревья и расходовать RAM.
2. **Низкая селективность**: индекс по булевому флагу (`is_active`), где 90% строк одинаковы, бесполезен — движку дешевле прочитать таблицу подряд (`Seq Scan`).

## Когда индекс слепнет и сборка в продакшене

Даже созданный B-Tree индекс перестаёт использоваться в двух типичных ситуациях:

1. **Функция поверх столбца**: условие `WHERE LOWER(email) = 'a@b.ru'` не использует обычный индекс — нужен функциональный индекс `ON users (LOWER(email))`.
2. **Ведущий процент в `LIKE`**: поиск подстроки `WHERE name LIKE '%ov'` не может идти по алфавиту B-Tree и требует триграмм `pg_trgm` с индексом `GIN`.

> **Junior vs Senior**:
> - **Junior**: Пишет `WHERE YEAR(created_at) = 2026` или индексирует каждую колонку по отдельности, удивляясь медленным запросам и тормозам вставки.
> - **Senior**: Заменяет вызов функции диапазоном `created_at >= '2026-01-01' AND created_at < '2027-01-01'`, строит составные и покрывающие индексы, а в продакшене запускает `CREATE INDEX CONCURRENTLY` без блокировки таблицы.
