## Встречный захват ресурсов и клинч (`Deadlock`)

> **Перекрёсток без светофора**: Транзакция `T1` переводит деньги со счёта `1` на `2`, а `T2` одновременно переводит их навстречу — с `2` на `1`.

Каждая транзакция уже заблокировала первый счёт и бесконечно ждёт второй — возникает взаимная блокировка (**Deadlock**):

```text
Хронология Deadlock (T1 против T2):
  t1 │ T1: lock(id=1)   │ T2: lock(id=2)
  t2 │ T1 ждёт id=2     │ T2 ждёт id=1
  ───┴──────────────────┴───────────────
  Цикл ожидания: T1 ──► T2 ──► T1
```

## Граф ожидания (`Wait-For Graph`) и детектор СУБД

PostgreSQL не зависает навсегда при клинче: через заданный таймаут запускается встроенный детектор циклов:

1. Если ожидание блокировки длится дольше `deadlock_timeout` (по умолчанию **`1 секунда`**), СУБД строит **граф ожидания (Wait-For Graph)**.
2. Обнаружив замкнутый цикл `T1 -> T2 -> T1`, ядро выбирает одну транзакцию «жертвой» и обрывает её с ошибкой **`SQLSTATE 40P01`**, выполняя автоматический `ROLLBACK`.
3. Освободившуюся строку мгновенно получает вторая транзакция и успешно завершает свой `COMMIT`.

## Детектор циклов `Wait-For Graph` в Python

Поиск дедлока внутри СУБД сводится к классической задаче обхода направленного графа в поисках цикла:

```python
def has_deadlock_cycle(
    wait_for: dict[str, str],
) -> bool:
    for start in wait_for:
        seen: set[str] = set()
        curr = start

        # Идём по цепочке ожидания ресурсов
        while curr in wait_for:
            if curr in seen:
                return True
            seen.add(curr)
            curr = wait_for[curr]
    return False

naive_graph = {'T1': 'T2', 'T2': 'T1'}
print(
    'Цикл в графе обнаружен:',
    has_deadlock_cycle(naive_graph),
)
# >>> Цикл в графе обнаружен: True
```

## Управление ожиданием: `lock_timeout` и `SKIP LOCKED`

Чтобы запросы не скапливались в очередях блокировок и не исчерпывали пул соединений, в PostgreSQL настраивают лимиты ожидания:

| Настройка / Конструкция | Назначение | Инженерный эффект |
| :--- | :--- | :--- |
| **`deadlock_timeout = '1s'`** | Задержка до запуска детектора | Экономит CPU при коротких штатных блокировках |
| **`lock_timeout = '3s'`** | Макс. ожидание блокировки | Быстрый отказ вместо висящей очереди в пуле БД |
| **`FOR UPDATE NOWAIT`** | Немедленный отказ | Сразу бросает ошибку, если строка занята другой сессией |
| **`FOR UPDATE SKIP LOCKED`** | Пропуск занятых строк | Позволяет воркерам разбирать очереди задач без конфликтов |

## Предотвращение дедлоков: каноническая сортировка ID

Чтобы цикл ожидания стал математически невозможен, все транзакции должны захватывать ресурсы строго в одном порядке — например, по возрастанию `id`.

Тогда вторая транзакция подождёт `id=1`, ещё не захватив `id=2`, и клинч никогда не возникнет:

```python
def acquire_locks_ordered(
    acc_a: int,
    acc_b: int,
) -> list[int]:
    # Единый порядок исключает цикл ожидания
    first_id, second_id = sorted(
        (acc_a, acc_b)
    )
    return [first_id, second_id]

order_t1 = acquire_locks_ordered(1, 2)
order_t2 = acquire_locks_ordered(2, 1)

print('Порядок T1:', order_t1)
# >>> Порядок T1: [1, 2]

print('Порядок T2:', order_t2)
# >>> Порядок T2: [1, 2]
```

## Паттерн `Retry` и инженерная профилактика

При сложных обновлениях нескольких таблиц единый порядок не всегда достижим, поэтому транзакции-жертвы (`SQLSTATE 40P01`) перезапускают с небольшой случайной задержкой (*Retry with Jitter*).

> **Junior vs Senior**:
> - **Junior**: Блокирует строки при пакетном обновлении в произвольном порядке из JSON-запроса, получая `DeadlockDetected` под нагрузкой.
> - **Senior**: Сортирует ID перед `SELECT ... FOR UPDATE` (`ORDER BY id ASC`), ограничивает ожидание через `lock_timeout` и оборачивает транзакции в `Retry` по коду `40P01`.
