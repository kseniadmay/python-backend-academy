## Транзакция: неделимая капсула «всё или ничего»

> **Банковский перевод в бронированной капсуле**: Перевод 1 000 ₽ от Алисы Бобу состоит из двух шагов: списать сумму у Алисы и начислить её Бобу. Если после списания пропадёт питание, деньги не должны раствориться в воздухе.

**Транзакция** объединяет SQL-команды в неделимую операцию через `BEGIN`, `COMMIT` и `ROLLBACK`:

```sql
BEGIN;
  -- 1. Списание со счёта Алисы
  UPDATE accounts
  SET balance = balance - 1000
  WHERE id = 1;

  -- 2. Зачисление на счёт Боба
  UPDATE accounts
  SET balance = balance + 1000
  WHERE id = 2;
COMMIT;
```

Если между шагами случится сбой, команда `ROLLBACK` отменит уже выполненное списание и вернёт базу в исходное состояние.

## Четыре столпа `ACID` и механизмы СУБД

Аббревиатура **ACID** задаёт четыре гарантии надёжности транзакций, каждая из которых опирается на конкретный механизм движка БД:

| Свойство | Смысл простыми словами | Механизм СУБД под капотом |
| :--- | :--- | :--- |
| **`A` — Atomicity** (*Атомарность*) | Либо фиксируются все команды целиком, либо при сбое отменяются все | Журнал отката (*Undo Log*) и статусы транзакций (`xmin`/`xmax` в PostgreSQL) |
| **`C` — Consistency** (*Согласованность*) | БД переходит из одного валидного состояния в другое без нарушения правил | Проверка ограничений (`NOT NULL`, `UNIQUE`, `CHECK`, `FK`) и триггеров |
| **`I` — Isolation** (*Изолированность*) | Параллельные транзакции не видят полуфабрикаты друг друга | **MVCC** (многоверсионность строк) и блокировки (*Row Locks*) |
| **`D` — Durability** (*Долговечность*) | После `COMMIT OK` данные сохранятся даже при внезапном отключении питания | Журнал предзаписи **WAL** с синхронным сбросом на диск (`fsync`) |

## Атомарный перевод средств через `with conn`

В Python контекстный менеджер `with conn:` автоматически выполняет `COMMIT` при успешном выходе из блока.

При любом исключении внутри блока драйвер сам вызывает `ROLLBACK` и оставляет данные неизменными:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute(
        'CREATE TABLE acc '
        '(id INT PRIMARY KEY, bal INT)'
    )
    conn.executemany(
        'INSERT INTO acc VALUES (?, ?)',
        [(1, 1000), (2, 500)],
    )

    # Оба UPDATE в одной транзакции
    with conn:
        conn.execute(
            'UPDATE acc SET bal = bal - 400 '
            'WHERE id = 1'
        )
        conn.execute(
            'UPDATE acc SET bal = bal + 400 '
            'WHERE id = 2'
        )

    rows = conn.execute(
        'SELECT * FROM acc'
    ).fetchall()
    print('После перевода:', rows)
    # >>> После перевода: [(1, 600), (2, 900)]
```

## Откат при нарушении ограничения `CHECK`

Свойство **Consistency** не позволяет транзакции нарушить инварианты таблицы (`CHECK`, `UNIQUE`, `FOREIGN KEY`).

Если вторая команда падает с `IntegrityError`, ядро БД отменяет и первое изменение внутри той же транзакции:

```python
import sqlite3

conn = sqlite3.connect(':memory:')
conn.execute(
    'CREATE TABLE acc (id INT PRIMARY KEY, '
    'bal INT CHECK (bal >= 0))'
)
conn.executemany(
    'INSERT INTO acc VALUES (?, ?)',
    [(1, 500), (2, 100)],
)
conn.commit()

try:
    with conn:
        conn.execute(
            'UPDATE acc SET bal = bal + 999 '
            'WHERE id = 2'
        )
        # Нарушит CHECK (bal >= 0) у id = 1
        conn.execute(
            'UPDATE acc SET bal = bal - 999 '
            'WHERE id = 1'
        )
except sqlite3.IntegrityError:
    print('Откат: нарушен CHECK')
    # >>> Откат: нарушен CHECK

rows = conn.execute(
    'SELECT * FROM acc'
).fetchall()
print('Балансы не изменились:', rows)
# >>> Балансы не изменились:
# >>> [(1, 500), (2, 100)]
```

## Журнал предзаписи `WAL` и долговечность

При `COMMIT` база данных не перезаписывает сразу гигабайтные файлы таблиц в случайных местах диска (*Random I/O*), иначе запись была бы слишком медленной.

Вместо этого работает правило **WAL (Write-Ahead Log)** — сначала быстрая последовательная запись в лог, затем фоновый перенос:

1. Изменения сначала меняют страницы в оперативной памяти (*Shared Buffers*), а на диск **последовательно в конец файла WAL** сбрасывается компактная запись о транзакции (`fsync`).
2. Клиент мгновенно получает подтверждение `COMMIT`, а фоновый процесс *Checkpointer* позже переносит изменённые страницы из памяти в основные файлы таблиц.

## Частичный откат `SAVEPOINT` и дисциплина транзакций

Точка сохранения **`SAVEPOINT`** позволяет откатить внутри большой транзакции только один рискованный шаг, сохранив остальную работу:

```sql
BEGIN;
  UPDATE acc SET bal = bal - 100
  WHERE id = 1;

  -- Точка сохранения до бонуса
  SAVEPOINT sp_bonus;
  INSERT INTO bonuses VALUES (1, 50);
  ROLLBACK TO SAVEPOINT sp_bonus;
COMMIT;
```

> **Junior vs Senior**:
> - **Junior**: Выполняет списание и начисление двумя автокоммит-запросами без транзакции либо держит открытую транзакцию во время долгого HTTP-вызова, блокируя строки БД на секунды.
> - **Senior**: Держит транзакции максимально короткими без сетевого I/O внутри `BEGIN...COMMIT`, использует `with session.begin():` и применяет `SAVEPOINT` (`begin_nested()`) для локального отката.
