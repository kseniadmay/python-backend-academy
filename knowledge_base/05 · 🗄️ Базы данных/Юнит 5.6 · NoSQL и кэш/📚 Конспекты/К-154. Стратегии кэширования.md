## Четыре архитектурных паттерна взаимодействия Приложения, Кэша и БД

> **Блокнот секретаря и главный сейф**: Когда в системе появляются два места хранения — быстрый блокнот на столе (Redis) и бронированный сейф в подвале (PostgreSQL) — возникают две задачи.
>
> Нужно решить, **кто переписывает данные из сейфа в блокнот при чтении** и **в каком порядке обновлять оба хранилища при записи**. Ответы на эти два вопроса образуют 4 классических паттерна кэширования!

```text
1. CACHE-ASIDE (Ленивое чтение — 90% проектов):
   Чтение : Приложение само смотрит в Кэш -> при промахе само читает БД -> кладёт в Кэш.
   Запись : Приложение пишет напрямую в БД -> и УДАЛЯЕТ (DEL) старый ключ из Кэша!

2. WRITE-THROUGH (Синхронная сквозная запись):
   Запись : Приложение пишет одновременно и в БД, и в Кэш (кэш всегда свежий, но запись медленнее).

3. WRITE-BEHIND / WRITE-BACK (Отложенная асинхронная запись):
   Запись : Приложение мгновенно пишет ТОЛЬКО в быстрый Кэш (RAM), а фоновый воркер
            пачками (batch) сбрасывает изменения в БД раз в N секунд.
```

## Сравнительная таблица стратегий кэширования

| Стратегия | Как работает Чтение / Запись | Главный плюс | Главный минус / риск |
| :--- | :--- | :--- | :--- |
| **`Cache-Aside` (Lazy Loading)** | Чтение: `Cache -> DB -> Cache`. Запись: `Update DB + Delete Cache` | В кэше хранятся **только реально запрашиваемые** данные; падение Redis не кладёт запись в БД | Первый запрос к новому ключу всегда медленный (*Cold Start / Cache Miss*) |
| **`Read-Through`** | Приложение всегда спрашивает только провайдер кэша, а кэш сам под капотом ходит в БД | Чистый код бизнес-логики (не знает про детали БД) | Требует поддержки плагина загрузки на стороне кэш-прокси |
| **`Write-Through`** | Запись синхронно обновляет и БД, и кэш | В кэше **никогда нет устаревших данных**, нет промаха при первом чтении | Замедляет каждую запись + забивает RAM данными, которые никто может больше не прочитать (*Cache Pollution*) |
| **`Write-Behind` (`Write-Back`)** | Запись идёт только в RAM (Redis), а в БД сбрасывается асинхронно батчами | ⚡ Колоссальная скорость записи (лайки, просмотры видео, координаты курьеров) | Если сервер Redis упадёт до сброса батча в PostgreSQL — данные за последние секунды **потеряются**! |

## Инвалидация кэша: почему DELETE надежнее SET при Cache-Aside

При обновлении данных в СУБД перезапись ключа в кэше (`r.set(key, val)`) создает состояние гонки (Race Condition) при двух параллельных запросах:

1. Поток А обновляет БД (`price = 100`).
2. Поток Б обновляет БД (`price = 200`).
3. Поток Б быстрее по сети записывает в Redis `price = 200`.
4. Задержавшийся Поток А перезаписывает ключ в Redis значением `price = 100`.

В базе данных зафиксирована актуальная цена `200`, а в кэше сохраняется устаревшее значение `100`.
При стратегии **`UPDATE DB` ➔ `r.delete(key)`** следующий запрос гарантированно прочитает из базы свежее значение `200` и прогреет кэш.

---

## Выбор стратегий кэширования: инженерный подход

> **Junior vs Senior**:
> - **Junior**: При обновлении записи в БД выполняет `r.set(key, new_data)` вместо инвалидации `r.delete(key)` (рискуя рассинхронизировать кэш) или использует асинхронный `Write-Behind` для финансовых транзакций с риском потери данных при сбое.
> - **Senior**: Для 90% сценариев применяет **`Cache-Aside` с удалением ключа (`r.delete`) строго после фиксации транзакции в БД**, а для высоконагруженных счетчиков (просмотры, лайки) использует **`Write-Behind`** с периодическим батч-сбросом.

## Практикум в Python 3.13: реализация `Cache-Aside` и пакетного `Write-Behind` буфера

```python
import json
import sqlite3
import redis

r = redis.Redis()
conn = sqlite3.connect(":memory:")
conn.execute(
    "CREATE TABLE articles (id INTEGER "
    "PRIMARY KEY, title TEXT, views INTEGER)"
)
conn.execute(
    "INSERT INTO articles VALUES (1, "
    "'Архитектура Redis', 100)"
)

# Паттерн Cache-Aside: при обновлении БД
# инвалидируем кэш через DELETE!

def update_article_title_cache_aside(
    article_id: int,
    new_title: str,
) -> None:
    conn.execute(
        "UPDATE articles SET title = ? "
        "WHERE id = ?",
        (new_title, article_id),
    )
    conn.commit()

    # Удаляем ключ, чтобы избежать Race
    # Condition при перезаписи!
    r.delete(f"article:{article_id}")

# Паттерн Write-Behind для высокочастотных
# счётчиков просмотров:

def record_view_write_behind(
    article_id: int,
) -> int:
    r.sadd("dirty_articles", str(article_id))
    return r.incr(
        f"article:{article_id}:views_delta"
    )

def flush_views_to_db() -> int:
    flushed = 0
    for aid_str in (
        list(r.smembers("dirty_articles"))
    ):
        k = f"article:{aid_str}:views_delta"
        delta = int(r.get(k) or 0)
        if delta > 0:
            conn.execute(
                "UPDATE articles SET views "
                "= views + ? WHERE id = ?",
                (delta, int(aid_str)),
            )
            r.delete(
                f"article:{aid_str}:views_"
                f"delta"
            )
            flushed += 1
    conn.commit()
    r.delete("dirty_articles")
    return flushed

for _ in range(5):
    # 5 мгновенных инкрементов в RAM без
    # трогания диска БД!
    record_view_write_behind(1)

# Фоновый сброс накопленной дельты одним
# UPDATE в SQL
flush_views_to_db()
art = conn.execute(
    'SELECT * FROM articles WHERE id = 1'
).fetchone()
print(
    'Статья в БД после Write-Behind flush:',
    art,
)
# >>> Статья в БД после Write-Behind flush: (1, 'Архитектура Redis', 105)
```
