## Три фундаментальных типа связей в реляционной БД

> **Кардинальность отношений**: любая предметная область выражается через три вида связей — **Один-к-Одному (`1:1`)**, **Один-ко-Многим (`1:N`)** и **Многие-ко-Многим (`M:N`)**.

```text
Схема трёх видов реляционных связей:
1. Связь 1:1 (Гражданин ↔ Паспорт):
   [users: id PK] ◄─── [passports: user_id UNIQUE FK]

2. Связь 1:N (Автор ↔ Книги):
   [authors: id PK] ◄─── [books: id PK, author_id FK]

3. Связь M:N (Студенты ↔ Курсы через таблицу связей):
   [students: id PK] ◄── [enrollments: s_id, c_id PK] ──► [courses: id PK]
```

## Физическая реализация связей в SQL DDL

Как ограничения на внешнем ключе определяют тип связи между таблицами:

| Тип связи | Где хранится `FOREIGN KEY` | Ключевое ограничение | Практический пример |
| :--- | :--- | :--- | :--- |
| **`1:1`** | В дочерней таблице (`profiles.user_id`) | На внешний ключ наложен **`UNIQUE`** (или он сам является `PK`) | Вынос тяжёлых полей (`bio`, `kyc_blob`) из узкой таблицы `users` |
| **`1:N`** | На стороне **«Многие»** (`orders.user_id`) | Обычный `FOREIGN KEY` **без `UNIQUE`** | Клиент → Заказы, Отдел → Сотрудники |
| **`M:N`** | В промежуточной **связующей таблице** (`enrollments`) | **Составной `PRIMARY KEY (a_id, b_id)`** из двух внешних ключей | Студенты ↔ Курсы, Заказы ↔ Товары (`order_items`) |

## Связь `1:1` через `UNIQUE FOREIGN KEY`

Чтобы гарантировать на уровне ядра СУБД, что у одного пользователя не появится двух профилей, на колонку `user_id` накладывают ограничение `UNIQUE` (или делают её `PRIMARY KEY`):

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.executescript('''
        CREATE TABLE users (id INT PRIMARY KEY);
        CREATE TABLE profiles (
            user_id INT PRIMARY KEY REFERENCES users(id),
            bio TEXT
        );
        INSERT INTO users VALUES (1);
        INSERT INTO profiles VALUES (1, 'Backend Dev');
    ''')
    print(conn.execute('SELECT * FROM profiles').fetchall())
```

## Связь `1:N`: внешний ключ на стороне «Многие»

В связи «Один-ко-Многим» внешний ключ всегда располагается в таблице дочерних элементов (например, `author_id` в таблице `books` без ограничения уникальности):

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.executescript('''
        CREATE TABLE authors (id INT PRIMARY KEY, name TEXT);
        CREATE TABLE books (id INT PRIMARY KEY, a_id INT, title TEXT);
        INSERT INTO authors VALUES (1, 'Мартин Клеппман');
        INSERT INTO books VALUES (10, 1, 'DDIA'), (11, 1, 'Streams');
    ''')
    sql = 'SELECT a.name, COUNT(b.id) FROM authors a JOIN books b ON a.id = b.a_id GROUP BY a.id'
    print(conn.execute(sql).fetchall())
```

## Связь `M:N`: промежуточная ассоциативная таблица

Реляционные БД не поддерживают прямую связь `M:N` между двумя таблицами — она всегда разбивается на две связи `1:N` через третью связующую таблицу (`Junction Table`):

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.executescript('''
        CREATE TABLE students (id INT PRIMARY KEY, name TEXT);
        CREATE TABLE courses (id INT PRIMARY KEY, title TEXT);
        CREATE TABLE enroll (
            s_id INT, c_id INT, PRIMARY KEY (s_id, c_id)
        );
        INSERT INTO enroll VALUES (1, 101), (1, 102);
    ''')
    print('Курсы студента:', conn.execute('SELECT * FROM enroll').fetchall())
```

## Полезная нагрузка связующей таблицы (`Payload` в `M:N`)

В реальных проектах связующая таблица хранит не только пару ключей `(s_id, c_id)`, но и собственные атрибуты события связи (дату записи, оценку или количество товара):

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('''
        CREATE TABLE order_items (
            ord_id INT, prod_id INT, qty INT, price INT,
            PRIMARY KEY (ord_id, prod_id)
        )
    ''')
    conn.execute('INSERT INTO order_items VALUES (1, 50, 2, 1990)')
    print(conn.execute('SELECT * FROM order_items').fetchone())
```
