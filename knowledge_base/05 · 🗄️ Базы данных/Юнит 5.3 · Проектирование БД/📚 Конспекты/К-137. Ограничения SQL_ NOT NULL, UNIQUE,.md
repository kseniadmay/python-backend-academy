## Эшелонированная оборона данных: приложение плюс СУБД

> **Последний рубеж целостности**: валидация в Pydantic защищает один сервис, но в БД могут писать воркеры, миграции и соседние сервисы. Ограничения SQL (`Constraints`) физически блокируют некорректные данные в ядре СУБД.

```text
Двухконтурная защита целостности данных:
┌───────────────────────────────────────────┐
│ [HTTP-клиент / Внешний вебхук]            │
└─────────────────────┬─────────────────────┘
                      ▼
┌───────────────────────────────────────────┐
│ Контур 1: Pydantic / Сериализатор DRF     │
│ (Быстрый синтаксический отказ HTTP 422)   │
└─────────────────────┬─────────────────────┘
                      ▼
┌───────────────────────────────────────────┐
│ Контур 2: Ядро СУБД (Constraints & B-Tree)│
│ NOT NULL · UNIQUE · DEFAULT · CHECK · FK  │
│ (Атомарная защита при гонках потоков!)    │
└───────────────────────────────────────────┘
```

## Четыре главных стража целостности в таблице

Сводка ограничений уровня столбца и таблицы:

| Ограничение | Гарантия ядра СУБД | Важный нюанс на собеседовании |
| :--- | :--- | :--- |
| **`NOT NULL`** | Запрещает сохранение пустоты (`NULL`) | Ставится по умолчанию на все обязательные поля |
| **`UNIQUE`** | Гарантирует уникальность и **строит B-Tree индекс** | По стандарту SQL `NULL != NULL`, поэтому допускает несколько `NULL` |
| **`DEFAULT expr`** | Подставляет значение при пропуске поля в `INSERT` | Если явно передать `VALUES (NULL)`, `DEFAULT` не сработает! |
| **`CHECK (expr)`** | Проверяет булево условие перед записью строки | Защищает инварианты (`price >= 0`, `end_dt >= start_dt`) |

## `NOT NULL` и `DEFAULT`: защита от пустых полей

Комбинация `NOT NULL DEFAULT 'active'` гарантирует, что столбец всегда заполнен валидным значением, даже если клиент не передал его при вставке:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('''
        CREATE TABLE users (
            id INTEGER PRIMARY KEY,
            status TEXT NOT NULL DEFAULT 'active'
        )
    ''')
    conn.execute('INSERT INTO users DEFAULT VALUES')
    print('Статус:', conn.execute('SELECT * FROM users').fetchone())
```

## Ограничение `UNIQUE` и особенность `NULL != NULL`

В стандарте SQL два `NULL` не считаются равными друг другу, поэтому в столбец с обычным `UNIQUE` можно вставить несколько `NULL` (для запрета в PostgreSQL 15+ используют `UNIQUE NULLS NOT DISTINCT`):

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('CREATE TABLE u (email TEXT UNIQUE)')
    conn.execute('INSERT INTO u VALUES (NULL)')
    conn.execute('INSERT INTO u VALUES (NULL)')
    cnt = conn.execute('SELECT COUNT(*) FROM u').fetchone()[0]
    print('Строк с NULL в UNIQUE:', cnt)
```

## Почему проверка уникальности в Python уязвима к гонке (`TOCTOU`)

Если проверять дубликат в коде через `SELECT` перед `INSERT`, два параллельных запроса одновременно увидят «пусто» и создадут дубль.

Только индекс **`UNIQUE`** в самой БД атомарно блокирует страницу дерева и выбрасывает `IntegrityError` второму потоку:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('CREATE TABLE u (email TEXT UNIQUE)')
    conn.execute("INSERT INTO u VALUES ('dev@py.ru')")
    try:
        conn.execute("INSERT INTO u VALUES ('dev@py.ru')")
    except sqlite3.IntegrityError:
        print('Дубликат email заблокирован ядром БД!')
```

## Защита бизнес-инвариантов через `CHECK (balance >= 0)`

Ограничение **`CHECK`** проверяет произвольное условие при каждом `INSERT` и `UPDATE`, не позволяя балансу кошелька или остатку товара на складе уйти в минус:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('''
        CREATE TABLE wallets (
            id INT PRIMARY KEY,
            bal INT NOT NULL CHECK (bal >= 0)
        )
    ''')
    try:
        conn.execute('INSERT INTO wallets VALUES (1, -50)')
    except sqlite3.IntegrityError:
        print('Отрицательный баланс отклонён CHECK!')
```
