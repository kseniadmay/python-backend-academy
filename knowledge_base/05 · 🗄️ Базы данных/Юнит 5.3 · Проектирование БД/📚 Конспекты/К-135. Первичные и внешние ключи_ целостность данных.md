## Роль `PRIMARY KEY` и выбор типа идентификатора

> **Гарантия ядра СУБД**: первичный ключ (`PRIMARY KEY`) однозначно идентифицирует строку (`UNIQUE` + `NOT NULL` + автоматический B-Tree индекс), а внешний ключ (`FOREIGN KEY`) защищает ссылочную целостность между таблицами.

| Тип `PRIMARY KEY` | Пример | Главное преимущество | Главный недостаток |
| :--- | :--- | :--- | :--- |
| **`BIGINT IDENTITY`** | `1, 2, 3...` | Компактный (8 байт), быстрая вставка в конец B-Tree | Предсказуем в URL (`/orders/102`), сложнее при шардинге |
| **Естественный ключ** | ИНН, ISO-код `'RU'` | Понятен без `JOIN` | При смене бизнес-формата требует миграции всех связей |
| **`UUID v4` (случайный)** | `'f47ac10b-...'` | Генерируется на клиенте/в сервисе до похода в БД | Случайный порядок вызывает фрагментацию страниц B-Tree |
| **`UUID v7` (временной)** | Time-ordered UUID | Глобально уникален и монотонно растёт по времени! | Занимает 16 байт (вдвое больше `BIGINT`) |
| **Составной PK** | `(order_id, item_id)` | Запрещает дубли связей в таблицах `M:N` | Громоздко ссылаться из дочерних таблиц |

## Проверка ссылочной целостности (`FOREIGN KEY`)

При включённом контроле внешних ключей (`PRAGMA foreign_keys = ON` в SQLite, в PostgreSQL включён всегда) база данных блокирует вставку заказа на несуществующего пользователя:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('PRAGMA foreign_keys = ON')
    conn.executescript('''
        CREATE TABLE users (id INT PRIMARY KEY);
        CREATE TABLE orders (id INT, uid INT REFERENCES users(id));
    ''')
    try:
        conn.execute('INSERT INTO orders VALUES (1, 999)')
    except sqlite3.IntegrityError as err:
        print('Защита FK сработала:', err)
```

## Четыре каскадные стратегии `ON DELETE`

Что делает СУБД при попытке удалить родительскую запись `DELETE FROM users WHERE id = 1`, на которую ссылаются дочерние строки:

```text
Поведение внешнего ключа при удалении родителя:
┌────────────────────────────────────────────────┐
│ • ON DELETE RESTRICT (по умолчанию):           │
│   ❌ Запрещает удаление (IntegrityError)       │
├────────────────────────────────────────────────┤
│ • ON DELETE CASCADE:                           │
│   🔥 Автоматически удаляет все дочерние строки │
├────────────────────────────────────────────────┤
│ • ON DELETE SET NULL:                          │
│   👻 Ставит NULL во внешнем ключе детей        │
├────────────────────────────────────────────────┤
│ • ON DELETE SET DEFAULT:                       │
│   🔄 Проставляет дефолтный ID в дочерних полях │
└────────────────────────────────────────────────┘
```

## Защита финансовых документов через `ON DELETE RESTRICT`

Для заказов, платежей и чеков всегда оставляют **`ON DELETE RESTRICT`**, чтобы случайное удаление аккаунта никогда не уничтожило финансовую историю компании:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('PRAGMA foreign_keys = ON')
    conn.executescript('''
        CREATE TABLE u (id INT PRIMARY KEY);
        CREATE TABLE inv (uid INT REFERENCES u(id));
        INSERT INTO u VALUES (1); INSERT INTO inv VALUES (1);
    ''')
    try:
        conn.execute('DELETE FROM u WHERE id = 1')
    except sqlite3.IntegrityError:
        print('RESTRICT сохранил чек!')
```

## Очистка временных данных через `ON DELETE CASCADE`

Каскадное удаление **`ON DELETE CASCADE`** применяют для технических придатков сущности (сессии, кэш-токены, черновики), которые не имеют смысла без владельца:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.execute('PRAGMA foreign_keys = ON')
    conn.executescript('''
        CREATE TABLE u (id INT PRIMARY KEY);
        CREATE TABLE sess (uid INT REFERENCES u(id) ON DELETE CASCADE);
        INSERT INTO u VALUES (1);
        INSERT INTO sess VALUES (1);
        DELETE FROM u WHERE id = 1;
    ''')
    print('Сессий осталось:', conn.execute('SELECT * FROM sess').fetchall())
```

## Индексирование внешнего ключа вручную (`CREATE INDEX`)

СУБД автоматически создаёт индекс для `PRIMARY KEY`, но **не создаёт индекс для `FOREIGN KEY`**!

Без явного `CREATE INDEX idx_orders_uid ON orders(user_id)` любой `JOIN` и проверка при удалении родителя будут вызывать медленный `Seq Scan` всей дочерней таблицы:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.executescript('''
        CREATE TABLE orders (id INT PRIMARY KEY, user_id INT);
        CREATE INDEX idx_orders_uid ON orders(user_id);
    ''')
    idxs = conn.execute('PRAGMA index_list(orders)').fetchall()
    print('Индексы таблицы orders:', len(idxs))
```
