## Горизонтальный `JOIN` против вертикального `UNION`

> **Направление склейки**: `JOIN` приклеивает новые **столбцы справа** по условию связи, а теоретико-множественный `UNION` дописывает новые **строки снизу** из второго `SELECT` в единый список.

```text
1. JOIN (расширяет таблицу вправо — СТОЛБЦЫ):
   [id | name]  ⋈  [user_id | phone]
                ▼
   [id | name | user_id | phone]

2. UNION (удлиняет выборку вниз — СТРОКИ):
   [id | email]  (таблица active_users)
         +
   [id | email]  (таблица archive_users)
         ▼
   [id | email]  (единый вертикальный список)
```

## Три правила совместимости запросов в `UNION`

Чтобы СУБД объединила два или более `SELECT` вертикально, они обязаны соблюдать три строгих инварианта:

- **Одинаковое число столбцов** во всех объединяемых запросах `SELECT`.
- **Совместимые типы данных** на соответствующих позициях (1-й столбец с 1-м, 2-й со 2-м).
- **Имена столбцов** берутся из первого `SELECT`, а итоговый `ORDER BY` пишется один раз в самом конце.

## Битва производительности: `UNION ALL` против `UNION`

Почему в продакшене по умолчанию всегда выбирают `UNION ALL`, если удаление дублей не требуется явно:

| Критерий | `UNION ALL` (Потоковая склейка) | `UNION` (Слияние с дедупликацией) |
| :--- | :--- | :--- |
| **Работа с дубликатами** | **Оставляет все строки** без проверок | **Удаляет дубликаты** (аналог `DISTINCT`) |
| **Алгоритм движка БД** | Потоковый `Append` второго набора к первому | Буферизация + сортировка или хэш-таблица |
| **Память и процессор** | ⚡ $O(1)$ доп. памяти, минимальный CPU | 🐢 $O(n)$ памяти и дорогая дедупликация |

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    sql = '''
    SELECT 'a@py.ru' UNION ALL SELECT 'a@py.ru'
    '''
    all_rows = conn.execute(sql).fetchall()
    uniq_rows = conn.execute(sql.replace('ALL', '')).fetchall()
    print('UNION ALL:', len(all_rows), '| UNION:', len(uniq_rows))
```

## Пересечение выборок через оператор `INTERSECT`

Оператор **`INTERSECT`** возвращает только те строки, которые присутствуют **одновременно в обоих** запросах (теоретико-множественное пересечение $A \cap B$):

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.executescript('''
        CREATE TABLE web (u TEXT);
        CREATE TABLE app (u TEXT);
        INSERT INTO web VALUES ('Ann'), ('Bob');
        INSERT INTO app VALUES ('Bob'), ('Cid');
    ''')
    both = conn.execute(
        'SELECT u FROM web INTERSECT SELECT u FROM app'
    ).fetchall()
    print('Купили и в Web, и в App:', both)
```

## Поиск расхождений через оператор `EXCEPT`

Оператор **`EXCEPT`** (в Oracle — `MINUS`) возвращает строки первого запроса, которых **нет во втором** запросе ($A \setminus B$), что незаменимо при сверке таблиц после миграции:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    conn.executescript('''
        CREATE TABLE web (u TEXT);
        CREATE TABLE app (u TEXT);
        INSERT INTO web VALUES ('Ann'), ('Bob');
        INSERT INTO app VALUES ('Bob'), ('Cid');
    ''')
    diff = conn.execute(
        'SELECT u FROM web EXCEPT SELECT u FROM app'
    ).fetchall()
    print('Только в Web:', diff)
```

## Единая сортировка и `LIMIT` для объединённого запроса

Клаузы `ORDER BY` и `LIMIT` в конце конструкции `UNION ALL` применяются ко всему объединённому набору строк целиком:

```python
import sqlite3

with sqlite3.connect(':memory:') as conn:
    sql = '''
    SELECT 'B' AS code, 20 AS score
    UNION ALL
    SELECT 'A' AS code, 50 AS score
    ORDER BY score DESC LIMIT 1
    '''
    print('Лидер:', conn.execute(sql).fetchall())
```
