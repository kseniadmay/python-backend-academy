## Проблема, которую решают виртуальные окружения

Без виртуального окружения пакеты устанавливаются в глобальный `site-packages` системы: два проекта с конфликтующими версиями (`django==3.2` и `django==5.0`) сломают друг друга.

**Виртуальное окружение** создаёт изолированную папку со своим интерпретатором Python и набором библиотек, независимую от системы и соседних проектов.

---

## venv – встроенный инструмент изоляции

Стандартный модуль `venv` создаёт изолированное окружение в папке проекта; после активации `python` и `pip` указывают только внутрь `.venv`:

```bash
# Создать окружение .venv
python -m venv .venv

# Активировать (Linux/macOS) и (Windows)
source .venv/bin/activate
.venv\Scripts\activate

# Установка и выход
pip install django
deactivate
```

Программный способ проверить, запущен ли скрипт внутри активного окружения (сравниваем префикс с базовым интерпретатором):

```python
import sys

# Внутри venv префиксы различаются
in_venv = sys.prefix != sys.base_prefix
print(f'Активен venv: {in_venv}')
```

## requirements.txt – фиксация зависимостей

Для переноса списка пакетов на другой сервер `pip freeze` сохраняет плоский список версий в файл `requirements.txt`. Минус подхода — смешение прямых и транзитивных зависимостей.

Типичный формат файла `requirements.txt`:

```text
django==5.0.1
requests==2.31.0
psycopg2-binary==2.9.9
```

Команды для снятия снимка установленных пакетов и их установки из файла:

```bash
# Сохранить установленные версии в файл
pip freeze > requirements.txt

# Восстановить окружение на другой машине
pip install -r requirements.txt
```

## Poetry – управление зависимостями и lock-файлы

**Poetry** решает ограничения связки `pip` + `requirements.txt`: он разделяет основные и dev-зависимости в `pyproject.toml`, сам управляет окружением и фиксирует точное дерево всех подзависимостей в `poetry.lock`.

Секции описания зависимостей внутри `pyproject.toml`:

```toml
[tool.poetry.dependencies]
python = '^3.12'
django = '^5.0'
requests = '^2.31'

[tool.poetry.group.dev.dependencies]
pytest = '^8.0'
```

Основные команды CLI для добавления пакетов и запуска проекта в среде Poetry:

```bash
# Добавить пакет и обновить lock-файл
poetry add django

# Установить зависимости из lock-файла
poetry install

# Запустить скрипт внутри окружения Poetry
poetry run python manage.py migrate
```

## Семантическое версионирование и выбор инструмента

Ограничение вида `^2.31` разрешает минорные и патч-обновления внутри мажорной ветки (`2.35.0`, но не `3.0.0`), а жёсткое `==2.31.0` фиксирует точную сборку без права на патчи безопасности.

Выбирайте `venv` + `requirements.txt` для простых скриптов и утилит, а `Poetry` (или современный быстрый `uv`) — для командной продакшен-разработки с воспроизводимыми сборками.

> **Junior vs Senior**:
> - **Junior**: ставит библиотеки в глобальный системный Python и фиксирует всё подряд через `pip freeze`, смешивая тестовые и продакшен-зависимости.
> - **Senior**: изолирует окружение проекта, разделяет прямые требования и lock-файл с хэшами (`Poetry` / `uv`), соблюдает правила SemVer (`^`) и гарантирует детерминированную сборку в CI.
