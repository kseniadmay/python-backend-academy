## Проблема, которую решают виртуальные окружения

Без виртуального окружения все Python-пакеты устанавливаются глобально, в один общий `site-packages` на всю систему. Если проект A требует `django==3.2`, а проект B на той же машине – `django==5.0`, оба не могут одновременно работать с глобальной установкой – один из них сломается. **Виртуальное окружение** – изолированная папка со своим собственным набором пакетов и своим интерпретатором Python, независимая от других окружений и от системного Python.

---

## venv – встроенный инструмент

```bash
python -m venv .venv  # создать окружение в папке .venv

source .venv/bin/activate  # активировать (Linux/macOS)
.venv\Scripts\activate  # активировать (Windows)

pip install django  # установится ТОЛЬКО внутри .venv,

deactivate  # выйти из окружения
```

После активации команда `python`/`pip` внутри терминала указывает на интерпретатор и пакеты именно этого окружения – можно держать сколько угодно проектов с разными, даже конфликтующими версиями зависимостей на одной машине.

## requirements.txt – фиксация зависимостей

```text
django==5.0.1
requests==2.31.0
psycopg2-binary==2.9.9
```

```bash
pip freeze > requirements.txt  # зафиксировать текущие версии установленных пакетов
pip install -r requirements.txt  # установить именно эти версии на другой машине
```

`pip freeze` даёт полный, но плоский список – не различает "я явно установил Django" от "Django притащил это как свою зависимость". Со временем это усложняет понимание, какие пакеты реально нужны проекту, а какие – транзитивные зависимости.

## Poetry – управление зависимостями и упаковка вместе

```toml
[tool.poetry.dependencies]
python = '^3.12'
django = '^5.0'
requests = '^2.31'

[tool.poetry.group.dev.dependencies]
pytest = '^8.0'
```

```bash
poetry add django  # добавить пакет и сразу зафиксировать версию
poetry install  # установить всё из pyproject.toml / poetry.lock
poetry run python manage.py runserver  # запустить команду внутри окружения Poetry
```

**Poetry** решает то, что `pip` + `requirements.txt` не решают из коробки: явно различает основные и dev-зависимости (`group.dev`), генерирует `poetry.lock` с точными, воспроизводимыми версиями всего дерева зависимостей (не только верхнего уровня), и управляет виртуальным окружением автоматически, без ручного `venv`.

## Семантическое версионирование в ограничениях версий

`^2.31` означает "любая версия, совместимая с 2.31 по правилам семантического версионирования" (тот же major, минорная и патч-версии могут расти: подойдёт `2.31.5`, `2.35.0`, но не `3.0.0`). `==2.31.0` – фиксация точной версии без права на обновление вообще. Слишком жёсткая фиксация (`==`) усложняет получение багфиксов, слишком свободная (без верхней границы) рискует внезапно подтянуть breaking change из мажорного обновления зависимости.

---

## Когда использовать

`venv` + `requirements.txt` – минимальный, всегда доступный вариант (входит в стандартную библиотеку), достаточен для небольших проектов и учебных задач. `Poetry` (или альтернативы вроде `pip-tools`, `uv`) – для реальных проектов, особенно командных, где важна воспроизводимость точного дерева зависимостей и разделение основных/dev-зависимостей. Виртуальное окружение – обязательная гигиена для любого Python-проекта, даже однофайлового скрипта, если у него есть внешние зависимости.
