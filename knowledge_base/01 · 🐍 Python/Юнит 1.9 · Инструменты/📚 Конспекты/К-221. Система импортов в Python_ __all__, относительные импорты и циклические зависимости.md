## Что происходит под капотом при вызове import

Когда интерпретатор встречает `import my_module`, он выполняет строгую последовательность шагов:

1. **Проверка кэша `sys.modules`**: это глобальный словарь `{имя_модуля: объект_module}`. Если модуль уже есть в `sys.modules`, Python мгновенно возвращает готовую ссылку и **не выполняет код файла повторно** (поэтому модули в Python по своей природе являются синглтонами).

2. **Поиск по `sys.meta_path` и `sys.path`**: если модуля в кэше нет, поисковики (`finders`) просматривают встроенные C-модули, директорию запущенного скрипта, переменную окружения `PYTHONPATH`, стандартную библиотеку и папку `site-packages` виртуального окружения.

3. **Создание пустого объекта и исполнение**: загрузчик (`loader`) создаёт пустой объект `module`, **сразу кладёт его в `sys.modules`** (ещё до выполнения первой строчки кода!) и лишь затем исполняет байткод файла сверху вниз в пространстве имён этого модуля.

## Точка входа: __name__ == "__main__" и запуск через python -m

У каждого модуля есть строковая переменная **`__name__`**. Когда файл импортируют из другого места (`import app.utils`), его `__name__` равен полному пути пакета (`"app.utils"`). Но если файл запущен напрямую как главный скрипт, интерпретатор присваивает ему имя **`"__main__"`**:

```python
def run_migration() -> None:
    # Миграция применена
    return None

# Код только при прямом запуске:
# (при обычном импорте этот блок пропускается)
if __name__ == '__main__':
    run_migration()
```

## Относительные импорты и запуск модуля через флаг -m

При прямом запуске скрипта `python app/workers/sync.py` интерпретатор присваивает ему `__package__ == None`. Попытка относительного импорта (`from ..models import User`) приводит к сбою:
`ImportError: attempted relative import with no known parent package`.

**Инженерное решение**: всегда запускать вложенные модули как часть пакета с флагом **`-m`** из корня проекта:
`python -m app.workers.sync`. При этом корень проекта добавляется в `sys.path`, а контекст пакета сохраняется.

## Публичный контракт модуля: переменная __all__ и фасад в __init__.py

Список строк **`__all__`** на уровне модуля или `__init__.py` решает две задачи:

1. Декларирует публичный API пакета для других разработчиков и статических анализаторов (`ruff`, `mypy`).
2. Ограничивает экспорт имен при вызове `from module import *`:

```python
# app/models/__init__.py: фасад публичного API
from .user import User
from .order import Order, OrderStatus
# внутренний хелпер
from ._internal_helper import parse_raw

__all__ = ['User', 'Order', 'OrderStatus']
```

## Циклические импорты: почему падает ImportError

Если модуль `a.py` делает `from b import func_b`, а `b.py` делает `from a import func_a`:

1. `a.py` помещается в `sys.modules["a"]` пустым объектом, и управление передается в `b.py`.
2. `b.py` пытается выполнить `from a import func_a`. Python находит модуль `"a"` в кэше `sys.modules`, но в нем еще нет функции `func_a`.
3. Возникает сбой: `cannot import name 'func_a' from partially initialized module 'a'`.

## Устранение циклических зависимостей: TYPE_CHECKING и вынос в третий модуль

**Стратегии устранения циклов**:

1. **Выделение третьего модуля (лучший подход)**: вынести общие интерфейсы, схемы и DTO в отдельный модуль (`schemas.py`), от которого зависят оба сервиса.
2. **`typing.TYPE_CHECKING` для аннотаций**: в рантайме флаг равен `False` и блок не выполняется:

```python
# annotations: откладывает тайпинг (в строки)
from __future__ import annotations
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    # TYPE_CHECKING: нет циклической ошибки
    from app.models.order import Order
class User:
    def can_cancel(
        self, order: Order
    ) -> bool:
        return order.owner_id == self.id
```

3. **Локальный отложенный импорт**: перенос `from a import func_a` внутрь метода для разрыва циклов в сложных легаси-системах.
