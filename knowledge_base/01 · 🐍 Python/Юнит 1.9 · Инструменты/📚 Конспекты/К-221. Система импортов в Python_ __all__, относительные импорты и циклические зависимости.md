## Что происходит под капотом при вызове `import`

Когда интерпретатор встречает `import my_module`, он выполняет три последовательных шага:

1. **Проверка кэша `sys.modules`:** это словарь `{имя: module}`. Если модуль уже загружен, Python возвращает готовую ссылку без повторного выполнения файла (синглтон).
2. **Поиск по `sys.meta_path` и `sys.path`:** при промахе кэша проверяются встроенные C-модули, директория скрипта, `PYTHONPATH`, stdlib и `site-packages`.
3. **Регистрация и исполнение:** загрузчик создаёт пустой объект `module`, заранее кладёт его в `sys.modules` и затем исполняет файл сверху вниз.

## Точка входа: `__name__ == '__main__'`

У каждого модуля есть переменная **`__name__`**: при импорте (`import app.utils`) она равна `'app.utils'`, а при прямом запуске файла становится `'__main__'`.

Это позволяет безопасно отделять объявления функций от кода запуска при импорте:

```python
def run_migration() -> None:
    # Миграция применена
    return None

# Блок пропускается при обычном import
if __name__ == '__main__':
    run_migration()
```

## Относительные импорты и запуск модуля через флаг `-m`

При прямом запуске `python app/workers/sync.py` файл получает `__package__ = None`.

Из-за этого относительный импорт `from ..models import User` падает с `ImportError: attempted relative import with no known parent package`.

Чтобы корень проекта попал в `sys.path` и сохранился контекст пакета, вложенные модули всегда запускают как модуль с флагом **`-m`**:

```bash
python -m app.workers.sync
```

## Публичный контракт модуля: `__all__` и фасад в `__init__.py`

Список строк **`__all__`** в модуле или `__init__.py` задаёт публичный контракт для разработчиков, линтеров (`ruff`, `mypy`) и ограничивает экспорт при `from module import *`.

Пример оформления публичного API пакета в файле `app/models/__init__.py`:

```python
# app/models/__init__.py: фасад публичного API
from .user import User
from .order import Order, OrderStatus

# Внутренний хелпер скрыт из __all__
from ._internal_helper import parse_raw

__all__ = ['User', 'Order', 'OrderStatus']
```

## Циклические импорты: почему падает ImportError

Если `a.py` делает `from b import func_b`, а `b.py` в ответ вызывает `from a import func_a`, возникает взаимная блокировка импорта:

1. Модуль `a.py` помещается в `sys.modules['a']` пустым объектом, и управление уходит в `b.py`.
2. Модуль `b.py` пытается взять `func_a` из полуинициализированного `'a'`, но `a.py` ещё не дочитан до объявления этой функции.
3. Интерпретатор завершает запуск ошибкой `ImportError: cannot import name 'func_a' from partially initialized module 'a'`.

## Устранение циклических зависимостей

Разорвать циклическую зависимость между модулями можно тремя основными способами:

1. **Третий общий модуль:** вынести разделяемые интерфейсы и схемы в `schemas.py`, от которого зависят оба сервиса.
2. **Блок `typing.TYPE_CHECKING`:** флаг равен `False` в рантайме, поэтому импорты для аннотаций типов не выполняются при запуске.
3. **Локальный импорт:** перенос `from a import func_a` внутрь метода (удобно как временный фикс в легаси).

Пример безопасного импорта классов исключительно для аннотаций типов через `TYPE_CHECKING`:

```python
# Откладывает вычисление аннотаций типов
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    # Выполняется только в mypy/IDE
    from app.models.order import Order

class User:
    def can_cancel(
        self, order: Order
    ) -> bool:
        return order.owner_id == self.id
```
