## Преимущества модуля logging перед функцией print() в продакшене

Вызов `print()` пишет неструктурированный текст в `stdout`: у него нет временной метки, имени модуля, уровня критичности. Его нельзя отключить централизованно.

Кроме того, вывод нельзя направить одновременно в консоль, файл с ротацией и систему мониторинга (Sentry, ELK, Loki).

Стандартный модуль **`logging`** решает эти задачи через гибкую архитектуру компонентов и 5 стандартных уровней важности (по возрастанию числового веса):

```python
import logging

# «Слепой» print без метаданных:
print("Сервер запущен")
# => Сервер запущен

# Инженерное логирование с фиксацией времени и уровня:
logging.basicConfig(
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
    datefmt="%H:%M:%S",
    level=logging.INFO,
)
logging.getLogger("web").info("Сервер слушает порт 8000")
# => 12:00:00 [INFO] web: Сервер слушает порт 8000
```

1. **`DEBUG` (10)** — детальная диагностика для разработчиков (параметры запросов, шаги алгоритма).
2. **`INFO` (20)** — штатные события жизненного цикла сервиса (старт воркера, успешная оплата заказа).
3. **`WARNING` (30)** — нештатная, но не фатальная ситуация (повторная попытка запроса, устаревший API, диск заполнен на 85%). Уровень по умолчанию в корневом логгере.
4. **`ERROR` (40)** — ошибка при обработке конкретной операции (не удалось отправить письмо, сбой платежа), но сам сервис продолжает работать.
5. **`CRITICAL` (50)** — фатальный отказ всей подсистемы (недоступна БД на старте, закончилась память).

## Четыре столпа архитектуры logging: Logger, Handler, Formatter, Filter

Вместо того чтобы сваливать всё в один глобальный объект, модуль `logging` разделяет ответственность между 4 сущностями:

- **`Logger` (Логгер)** — точка входа в коде (`logger = logging.getLogger(__name__)`). Принимает сообщения и отсекает те, чей уровень ниже установленного на логгере.
- **`Handler` (Обработчик)** — решает, **куда** физически отправить запись: `StreamHandler` (в консоль `stderr`/`stdout`), `FileHandler` (в файл), `RotatingFileHandler` (в файл с нарезкой по размеру), `TimedRotatingFileHandler` (с ротацией по времени). У каждого хендлера может быть **свой собственный уровень** (например, в консоль писать от `INFO`, а в отдельный файл `errors.log` — только от `ERROR`).
- **`Formatter` (Форматтер)** — определяет **строковый шаблон** или JSON-структуру записи (`%(asctime)s | %(levelname)-8s | %(name)s:%(lineno)d | %(message)s`).
- **`Filter` (Фильтр)** — тонкая фильтрация или обогащение записи (`LogRecord`), например подстановка `request_id` текущего HTTP-запроса или маскирование паролей.

```python
import io
import logging

logger = logging.getLogger("shop.order")
logger.setLevel(logging.INFO)

stream = io.StringIO()
handler = logging.StreamHandler(stream)
fmt = logging.Formatter("[%(levelname)s] %(name)s: %(message)s")
handler.setFormatter(fmt)
logger.addHandler(handler)

logger.info("Заказ #101 успешно оформлен")
print(stream.getvalue().strip())
# => [INFO] shop.order: Заказ #101 успешно оформлен

# Вывод в консоль:
# [INFO] shop.order: Заказ #101 успешно оформлен
```

## Иерархия по точкам и флаг propagate (почему логи дублируются)

Имена логгеров образуют дерево по точкам, повторяя пакеты Python: для файла `app/services/payment.py` переменная `__name__` равна `"app.services.payment"`.

Его родителем становится логгер `"app.services"`, затем `"app"`, а на вершине дерева всегда стоит корневой логгер **`root`**.

По умолчанию у каждого логгера включён атрибут **`logger.propagate = True`**. Это значит, что после того как логгер обработал запись своими хендлерами, он **передаёт её вверх всем родительским логгерам вплоть до `root`**.

**Классическая проблема на собеседовании**: «Почему каждое сообщение в консоли печатается дважды?».

Ответ: разработчик повесил `StreamHandler` на дочерний логгер и одновременно вызвал `logging.basicConfig()` (вешающий хендлер на `root`). При `propagate = True` запись дублируется.

Решение — вешать хендлеры только на корень либо ставить `logger.propagate = False` для полной изоляции.

```python
import logging

child = logging.getLogger("app.service")
print("propagate по умолчанию:", child.propagate)
# => propagate по умолчанию: True

# Для полной изоляции дочернего логгера:
child.propagate = False
print("propagate после настройки:", child.propagate)
# => propagate после настройки: False
```

## Логирование исключений: logger.exception() и exc_info=True

Самая частая ошибка джунов в блоке `except` — писать `logger.error(f"Ошибка: {e}")`. При этом в лог попадает только текст ошибки, а **стек вызовов (traceback) безвозвратно теряется**, и понять, на какой строке упал код, невозможно.

```python
import io
import logging

logger = logging.getLogger("billing")
stream = io.StringIO()
logger.addHandler(logging.StreamHandler(stream))

user_id = 42
try:
    result = 100 / 0
except ZeroDivisionError:
    # logger.exception автоматически логирует уровень ERROR и полный Traceback
    logger.exception("Сбой расчёта для id=%s", user_id)

lines = stream.getvalue().strip().splitlines()
print(lines[0])   # первая строка лога
# => ERROR:billing:Сбой расчёта для id=42
print(lines[-1])  # строка с типом исключения
# => ZeroDivisionError: division by zero
```

Ленивое форматирование через `%s`: `logger.debug("Payload: %s", heavy_obj)` вычисляет строковое представление **лениво** — только если уровень `DEBUG` реально включён.

При f-строке `f"Payload: {heavy_obj}"` строка собирается всегда, даже когда `DEBUG`-логи отключены в продакшене.

## Конфигурация через dictConfig и структурированные JSON-логи

В реальных микросервисах (FastAPI, Django, Celery) логгеры настраивают декларативно на старте приложения через **`dictConfig(LOGGING_CONFIG)`**.

В одном словаре описывают форматтеры, хендлеры и уровни для библиотек (`uvicorn`, `sqlalchemy.engine`, `httpx`):

```python
import io
import logging
from logging.config import dictConfig

stream = io.StringIO()
LOGGING_CONFIG = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "std": {"format": "[%(levelname)s] %(name)s: %(message)s"}
    },
    "handlers": {
        "memory": {
            "class": "logging.StreamHandler",
            "formatter": "std",
            "stream": stream,
        }
    },
    "root": {"level": "INFO", "handlers": ["memory"]},
}
dictConfig(LOGGING_CONFIG)

logging.getLogger("api").info("Сервис запущен на порту 8000")
print(stream.getvalue().strip())
# => [INFO] api: Сервис запущен на порту 8000
```

Для продакшен-кластеров (Kubernetes / Docker) вместо обычного текста используют **JSON-форматтеры** (или библиотеку `structlog`).

Каждая запись становится JSON-объектом с полями `timestamp`, `level`, `logger`, `trace_id` и легко индексируется в Kibana или Grafana Loki.
