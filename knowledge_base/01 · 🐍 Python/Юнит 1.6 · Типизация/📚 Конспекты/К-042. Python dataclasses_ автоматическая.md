## Проблема: бойлерплейт в классах-контейнерах

Когда пишешь класс для хранения данных – профиль пользователя, настройки, результат запроса – приходится вручную описывать одно и то же: `__init__`, `__repr__`, `__eq__`. Этот повторяющийся шаблонный код называют **бойлерплейтом**.

Проблема не только в скуке. Ошибка в `__eq__` – и сравнение объектов работает неправильно. Ошибка в `__init__` – и поле молча не инициализируется. Каждый из этих методов – потенциальное место для человеческой ошибки, особенно при рефакторинге: добавил поле, забыл обновить `__repr__` – и отладка усложняется.

---

## Что такое `@dataclass`

В Python 3.7 появился декоратор **`@dataclass`** из модуля `dataclasses`. Он анализирует аннотации типов в классе и автоматически генерирует стандартные методы.

Генерируются три метода:

**`__init__`** – конструктор, который принимает аргументы и присваивает их полям.

**`__repr__`** – строковое представление: вместо бесполезного `<User object at 0x...>` вы получите `User(name='Alice', age=30)`.

**`__eq__`** – сравнение объектов по содержимому: два объекта с одинаковыми данными будут считаться равными.

---

## Как это выглядит на практике

```python
from dataclasses import dataclass

@dataclass
class User:
    name: str
    age: int
    active: bool = True  # необязательный параметр

u = User('Alice', 30)
print(u)  # User(name='Alice', age=30, active=True)
```

`active: bool = True` делает этот аргумент необязательным в конструкторе – если не передать, подставится значение по умолчанию. Аннотации типов здесь не просто документация: без них `@dataclass` не знает, какие поля генерировать.

То же самое без `@dataclass` выглядело бы так:

```python
class User:
    def __init__(self, name: str, age: int, active: bool = True):
        self.name = name
        self.age = age
        self.active = active

    def __repr__(self):
        return (
            f'User(name={self.name!r}, '
            f'age={self.age!r}, '
            f'active={self.active!r})'
        )

    def __eq__(self, other):
        if not isinstance(other, User):
            return False

        return (
                self.name == other.name
                and self.age == other.age
                and self.active == other.active
        )

u = User('Alice', 30)
print(u)  # User(name='Alice', age=30, active=True)
```

Эквивалентный обычный класс занял бы около 14 строк с ручными `__init__`, `__repr__` и `__eq__`. Дата-класс – 5 строк. При добавлении нового поля в дата-класс все методы обновляются автоматически, в обычном классе нужно не забыть обновить каждый метод вручную.

## Неизменяемость через `frozen=True`

По умолчанию дата-класс мутабельный – поля можно менять после создания. Если нужна защита от изменений, используют `@dataclass(frozen=True)`:

```python
@dataclass(frozen=True)
class Point:
    x: float
    y: float

p = Point(1.0, 2.0)
p.x = 5.0  # FrozenInstanceError
```

`frozen=True` также автоматически делает объект хешируемым, то есть его можно использовать как ключ словаря или элемент множества.

## `dataclass` vs `namedtuple`

Оба инструмента решают одну задачу – именованный контейнер для данных – но с разными trade-off: то, что выигрывает один, теряет другой.

`namedtuple` всегда неизменяем, легковесен и полностью совместим с обычным кортежем: его можно распаковать, передать туда, где ожидается `tuple`. Методы в него не добавить.

`dataclass` по умолчанию мутабелен, поддерживает значения по умолчанию, методы, `__post_init__` для валидации и глубоко интегрирован с системой типов. Это полноценный класс, а не надстройка над кортежем.

Простое правило: если нужен просто лёгкий read-only контейнер без логики – `namedtuple`. Если нужны изменяемость, методы или валидация – `dataclass`.

---

## Когда применять

`dataclass` хорошо подходит для моделей данных: сущностей из базы, DTO (Data Transfer Object), конфигурационных объектов, результатов парсинга. Он не заменяет полноценные классы с нетривиальной логикой, но убирает всю рутину вокруг хранения данных и делает структуру явной с первого взгляда.
