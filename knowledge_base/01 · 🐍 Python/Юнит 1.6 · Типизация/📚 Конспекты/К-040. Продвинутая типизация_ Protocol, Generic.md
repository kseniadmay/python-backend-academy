## Optional и Union – база, без которой дальше никак

`Optional[X]` – это просто сокращение для `Union[X, None]`: значение либо типа X, либо `None`. `Union[A, B]` значит «либо A, либо B».

```python
from typing import Optional, Union

def find_user(user_id: int) -> Optional[dict]:
    ...  # вернёт dict или None, если не найден

def parse_id(value: Union[int, str]) -> int:
    return int(value)

def find_user_modern(user_id: int) -> dict | None:
    ...
```

На собеседовании часто спрашивают: почему нельзя просто написать `def f(x: int = None)` без Optional? Формально это не ошибка на уровне интерпретатора (аннотации не проверяются в рантайме), но `mypy`/`pyright` пометят это как несоответствие типов – сигнатура обещает `int`, а по факту допускает `None`.

## typing.Protocol – структурная типизация ("duck typing" с проверкой)

Обычная типизация в Python – номинальная: класс подходит под тип, только если явно наследуется от него. `Protocol` (PEP 544) переворачивает это – подходит любой объект, у которого есть нужные методы/атрибуты, **без явного наследования**. Это и есть "если ходит как утка и крякает как утка" – но теперь mypy может это проверить статически.

```python
from typing import Protocol

class Comparable(Protocol):
    def __lt__(self, other) -> bool: ...

def sort_items(items: list[Comparable]) -> list:
    return sorted(items)

class Money:
    def __init__(self, amount: int):
        self.amount = amount
    def __lt__(self, other):
        return self.amount < other.amount

sort_items([Money(50), Money(10)])  # подходит под Comparable -
```

Практическая польза для backend-разработки: `Protocol` отлично заменяет абстрактные интерфейсы (`ABC`) там, где не нужна общая иерархия наследования – например, чтобы описать «что угодно с методом `.save()`» для слоя репозиториев, не привязывая реализации к общему базовому классу.

## Generic и TypeVar – типизация "для любого T"

`TypeVar` объявляет типовую переменную – заполнитель, который конкретизируется при использовании. `Generic[T]` делает класс параметризуемым этой переменной.

```python
from typing import TypeVar, Generic

T = TypeVar('T')

class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()

int_stack: Stack[int] = Stack()
int_stack.push(1)
int_stack.push('x')  # mypy отругает: ожидался int, а не str
```

`TypeVar` можно ограничить (`bound=`) – тогда T обязан быть подтипом указанного класса/протокола:

```python
from typing import TypeVar, Protocol

class HasID(Protocol):
    id: int

TID = TypeVar('TID', bound=HasID)

def get_by_id(items: list[TID], target_id: int) -> TID | None:
    return next((i for i in items if i.id == target_id), None)
```

В Python 3.12+ появился новый, более короткий синтаксис (`class Stack[T]: ...`, `def get_by_id[T](...)`), но `TypeVar`/`Generic` остаются актуальны – это то, что реально спрашивают на собеседованиях и что используется в кодовых базах на более старых версиях Python.

## @overload – разные сигнатуры для одной функции

`@overload` из `typing` описывает несколько допустимых сигнатур одной функции для статического анализатора – сама функция при этом реализуется один раз, без `@overload`, последней.

```python
from typing import overload

@overload
def process(value: int) -> int: ...
@overload
def process(value: str) -> str: ...

def process(value):
    if isinstance(value, int):
        return value * 2
    return value.upper()
```

Это не влияет на поведение в рантайме – `@overload`-версии существуют только для type checker'а (mypy видит, что `process(5)` вернёт `int`, а `process("a")` – `str`); реальную логику выполняет последняя, «настоящая» реализация.

## mypy --strict – что это включает

`mypy --strict` – это не одна проверка, а пресет из полутора десятков флагов, среди которых самые заметные: `disallow_untyped_defs` (запрещает функции без аннотаций), `disallow_any_generics` (запрещает голый `list` без параметра типа), `warn_return_any`, `no_implicit_optional` (раньше `def f(x: int = None)` неявно считался `Optional[int]` – strict-режим это запрещает).

На практике `--strict` включают не сразу на весь проект, а точечно – через секцию `[mypy-<module>]` в `mypy.ini`/`pyproject.toml`, чтобы постепенно "дотягивать" типизацию модуль за модулем, не блокируя CI по всему монолиту сразу.

## Абстрактные базовые классы (abc.ABC): рантайм-контракты, register() и __subclasshook__

В отличие от `typing.Protocol`, который работает преимущественно во время статического анализа (`mypy`), модуль `abc` обеспечивает **рантайм-контракты** на уровне самого интерпретатора Python.

### 1. Запрет создания неполных классов через @abstractmethod
Если класс наследуется от `abc.ABC` и содержит методы, помеченные `@abstractmethod`, попытка создать его экземпляр вызовет ошибку `TypeError` ещё до выполнения `__init__`:

```python
from abc import ABC, abstractmethod

class BaseRepository(ABC):
    @abstractmethod
    def get(self, id: int): pass

    @abstractmethod
    def save(self, item: dict) -> None: pass

# Ошибка: TypeError: Can't instantiate abstract class BaseRepository with abstract methods get, save
repo = BaseRepository()
```

### 2. Виртуальное наследование: ABC.register()
Python позволяет классу стать «виртуальным подклассом» без изменения его дерева наследования и без изменения MRO:

```python
class SqlRepo:
    def get(self, id: int): return {"id": id}
    def save(self, item: dict): print("saved")

# Регистрируем SqlRepo как виртуальный подкласс
BaseRepository.register(SqlRepo)

s = SqlRepo()
print(isinstance(s, BaseRepository))  # True!
print(issubclass(SqlRepo, BaseRepository))  # True!
print(SqlRepo.__mro__)  # (SqlRepo, object) — BaseRepository в MRO отсутствует!
```

### 3. Динамическая утиная типизация в рантайме: __subclasshook__
Абстрактный класс может сам проверять, подходит ли ему кандидат, с помощью метода `__subclasshook__(cls, C)`. Именно так устроен модуль `collections.abc`:

```python
from abc import ABC, abstractmethod

class Greeter(ABC):
    @abstractmethod
    def greet(self) -> str: pass

    @classmethod
    def __subclasshook__(cls, C):
        if cls is Greeter:
            if any("greet" in B.__dict__ for B in C.__mro__):
                return True
        return NotImplemented

class Robot:
    def greet(self): return "Beep boop"

r = Robot()
# isinstance автоматически вызывает __subclasshook__ у Greeter:
print(isinstance(r, Greeter))  # True! Без явного наследования и без register!
```
