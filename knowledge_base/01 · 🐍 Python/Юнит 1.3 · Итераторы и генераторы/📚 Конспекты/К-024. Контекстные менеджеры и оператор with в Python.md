## Зачем нужен `with`

При работе с файлами, соединениями с базой данных или сетевыми сокетами важно гарантировать освобождение ресурса после использования – даже если в процессе возникнет исключение. Ручной вызов `f.close()` ненадёжен: если до него произойдёт ошибка, файл останется открытым.

Оператор `with` решает эту проблему структурно: ресурс освобождается автоматически при выходе из блока – в любом случае.

---

## Протокол контекстного менеджера: `__enter__` и `__exit__`

Чтобы объект мог работать с `with`, он должен реализовать два метода. **`__enter__`** вызывается при входе в блок – подготавливает ресурс и возвращает объект, который будет присвоен переменной после `as`. **`__exit__`** вызывается при выходе из блока – освобождает ресурс и получает информацию об исключении, если оно произошло.

Стандартный пример – работа с файлом:

```python
with open('data.txt', 'r') as f:
    content = f.read()
```

При входе в блок вызывается `open().__enter__()`, который возвращает файловый объект в `f`. При выходе – `__exit__()` закрывает файл на системном уровне. Исключение внутри блока не мешает закрытию – `__exit__` вызывается в любом случае.

Важный нюанс: переменная после `as` содержит то, что вернул `__enter__`, а не сам объект контекстного менеджера. Если `__enter__` возвращает `None` – переменная будет `None`.

## Создание собственного менеджера через класс

Класс подходит, когда нужно хранить состояние между входом и выходом:

```python
import time

class Timer:
    def __enter__(self):
        self.start = time.time()
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        print(f'Затрачено: {time.time() - self.start:.4f} сек')

with Timer() as t:
    time.sleep(0.5)
```

Три аргумента `__exit__` – `exc_type`, `exc_val`, `exc_tb` – обязательны по протоколу. Они содержат информацию об исключении, если оно произошло внутри блока. Если вернуть из `__exit__` значение `True`, исключение будет подавлено. Если ничего не возвращать (или вернуть `None`/`False`) – исключение распространится дальше.

## `@contextmanager` – менеджер через генератор

Для простых случаев создавать целый класс избыточно. Декоратор **`@contextmanager`** из модуля `contextlib` позволяет написать контекстный менеджер как функцию с `yield`:

```python
from contextlib import contextmanager
import time

@contextmanager
def simple_timer():
    start = time.time()
    try:
        yield
    finally:
        print(f'Время: {time.time() - start:.4f} сек')

with simple_timer():
    time.sleep(0.5)
```

Код до `yield` – это `__enter__`. Выполнение функции приостанавливается на `yield`, и управление передаётся в тело блока `with`. После завершения блока – или при исключении – выполнение возобновляется после `yield`. Блок `finally` гарантирует выполнение очистки в любом случае.

Если нужно передать значение в `as`-переменную, пишут `yield something`.

---

## Класс vs `@contextmanager`

Класс предпочтителен, когда нужно хранить состояние в `self`, реализовывать сложную логику обработки исключений или переиспользовать менеджер в нескольких местах с наследованием. `@contextmanager` лучше подходит для простых stateless обёрток – когда нужно выполнить действие «до» и «после» без сохранения состояния.

---

## Где применяется в реальном коде

Контекстные менеджеры используют для управления соединениями с базой данных, блокировками потоков (`threading.Lock`), транзакциями, временными файлами, подавлением исключений (`contextlib.suppress`), патчингом в тестах (`unittest.mock.patch`). В Django ORM транзакции оборачиваются в `with transaction.atomic()`.

Ключевое правило: любой ресурс, требующий явной очистки, должен управляться через контекстный менеджер. Это исключает утечки ресурсов и делает поведение кода предсказуемым вне зависимости от того, произошло ли исключение.
