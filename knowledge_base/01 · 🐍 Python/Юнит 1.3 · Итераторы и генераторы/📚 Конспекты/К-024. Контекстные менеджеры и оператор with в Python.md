## Назначение оператора with и гарантированное освобождение ресурсов

При работе с файлами, соединениями БД и сокетами важно освобождать ресурс даже при исключении. Ручной `f.close()` ненадёжен: ошибка до него оставит дескриптор открытым.

Оператор `with` решает эту проблему структурно: ресурс освобождается автоматически при любом выходе из блока.

---

## Протокол контекстного менеджера: `__enter__` и `__exit__`

Чтобы объект работал с `with`, он реализует два метода: `__enter__` (подготовка и возврат ресурса в `as`) и `__exit__` (освобождение ресурса при выходе).

Жизненный цикл контекстного менеджера от входа в блок до обработки исключений:

```text
       with ManagedResource() as res:
                     │
         1. __enter__() вызывается
                     │
        ┌────────────▼───────────┐
        │    Тело блока with     │
        │  выполняется логика    │
        └────────────┬───────────┘
                     │
  Штатный выход      │   Исключение
        ┌────────────┴───────────┐
        ▼                        ▼
 __exit__(None,.)    __exit__(typ,val,tb)
        │                        │
        │                return True?
        │               ┌────────┴───────┐
        │             Да│                │Нет
        ▼               ▼                ▼
Ресурс закрыт    Подавлено     Проброшено
```

Стандартный пример использования этого протокола при чтении файла:

```python
with open('data.txt', 'r') as f:
    content = f.read()
```

Переменная после `as` получает ровно то, что вернул `__enter__` (а не сам объект менеджера, если `__enter__` вернул что-то иное или `None`). При выходе `__exit__` вызывается в любом случае.

## Создание собственного менеджера через класс

Класс подходит, когда нужно хранить внутреннее состояние между входом и выходом или управлять транзакциями:

```python
class DatabaseTransaction:
    def __init__(self, name: str) -> None:
        self.name = name
        self.log: list[str] = []

    def __enter__(self):
        self.log.append('START')
        return self

    def __exit__(self, exc_type, exc_val, tb):
        if exc_type is not None:
            self.log.append(
                f'ROLLBACK: {exc_val}'
            )
            if issubclass(
                exc_type, ValueError
            ):
                return True
        else:
            self.log.append('COMMIT')
        return False

# Штатное завершение блока:
tx1 = DatabaseTransaction('tx1')
with tx1 as tx:
    tx.log.append('UPDATE balances')
print('Успех:', tx1.log)
# >>> Успех: ['START', 'UPDATE balances',
# >>> 'COMMIT']

# Ошибка с откатом и подавлением ValueError:
tx2 = DatabaseTransaction('tx2')
with tx2 as tx:
    tx.log.append('UPDATE balances')
    raise ValueError('Недостаточно средств')
print('Откат:', tx2.log)
# >>> Откат: ['START', 'UPDATE balances',
# >>> 'ROLLBACK: Недостаточно средств']
```

Три аргумента `__exit__` (`exc_type`, `exc_val`, `exc_tb`) обязательны по протоколу. Возврат `True` подавляет исключение, а `False` или `None` пропускает его дальше.

## `@contextmanager` – менеджер через генератор

Для простых случаев вместо класса берут декоратор **`@contextmanager`** из `contextlib`, превращая функцию с `yield` в контекстный менеджер:

```python
from contextlib import contextmanager

@contextmanager
def temporary_flag(
    settings: dict,
    key: str,
    temp_value: object,
):
    old_value = settings.get(key)
    settings[key] = temp_value
    try:
        # Передаём управление в тело with
        yield settings
    finally:
        if old_value is None:
            settings.pop(key, None)
        else:
            settings[key] = old_value

config = {'debug': False, 'timeout': 30}
with temporary_flag(config, 'debug', True):
    print(
        'Внутри with debug =',
        config['debug'],
    )
    # >>> Внутри with debug = True

print('Вне with debug =', config['debug'])
# >>> Вне with debug = False
```

Код до `yield` выполняется как `__enter__` (значение после `yield` попадёт в переменную `as`), затем управление переходит в тело `with`, а блок `finally` после `yield` гарантированно выполняет очистку.

## Класс vs `@contextmanager` и практика в продакшене

Выбор реализации зависит от необходимости хранить состояние и сложной обработки ошибок:

| Реализация | Когда выбирать |
| :--- | :--- |
| **Класс (`__enter__`/`__exit__`)** | Нужно хранить состояние в `self`, наследование или сложный откат |
| **`@contextmanager`** | Компактные обёртки «до/после» вокруг блока кода через `try...finally` |

На практике через `with` управляют соединениями БД, блокировками (`threading.Lock`), транзакциями (`with transaction.atomic()`), временными файлами и моками (`unittest.mock.patch`).

Любой ресурс, требующий явной очистки, обязан управляться через контекстный менеджер. Это исключает утечки при любом сценарии выхода из кода.

> **Junior vs Senior**:
> - **Junior**: открывает файлы, транзакции и блокировки вручную с вызовом `close()`, теряя освобождение ресурса при раннем `return` или исключении.
> - **Senior**: гарантирует детерминированный cleanup через `with`, использует `@contextmanager` с обязательным `try...finally` для простых обёрток и класс с `__enter__`/`__exit__` для менеджеров с состоянием.
