1. Зачем в генераторной функции с декоратором `@contextmanager` инструкцию `yield` обязательно оборачивают в блок `try...finally`? >> При исключении внутри блока with ошибка пробрасывается в точку yield через `generator.throw()`, и без finally код очистки после yield не выполнится.
2. Сколько раз ровно должна сработать инструкция `yield` внутри функции, декорированной `@contextmanager`? >> Строго один раз: до yield выполняется `__enter__`, после yield — `__exit__`; если yield сработает повторно, возникнет `RuntimeError`.
3. Что попадёт в переменную после as при использовании @contextmanager? >> Значение, которое было передано в выражение yield (или None, если написано просто yield без аргумента).
4. Как работает менеджер контекста `contextlib.suppress(*exceptions)`? >> Перехватывает и молча подавляет указанные типы исключений (и их подклассы) внутри блока with, заменяя конструкцию try...except SomeError: pass.
5. Что сделает `contextlib.suppress(KeyError)`, если внутри блока `with` возникнет `ValueError`? >> Не перехватит его — `ValueError` беспрепятственно пробросится наружу.
6. Для чего используется класс `contextlib.ExitStack`? >> Для динамического управления заранее неизвестным количеством контекстных менеджеров (например, открытие списка файлов в цикле) с гарантированным закрытием всех ресурсов.
7. В каком порядке ExitStack закрывает зарегистрированные в нём контекстные менеджеры и колбэки? >> В обратном порядке их добавления (LIFO — последний вошёл, первый вышел).
8. Что произойдёт в ExitStack, если при открытии 3-го из 5 файлов возникнет ошибка? >> Уже открытые 1-й и 2-й файлы будут гарантированно и корректно закрыты при выходе из блока ExitStack.
9. Какой метод `ExitStack` добавляет новый контекстный менеджер в стек? >> `stack.enter_context(cm)` — вызывает `__enter__()` у менеджера, регистрирует его `__exit__()` в стеке и возвращает результат входа
10. Для чего используется контекстный менеджер `contextlib.nullcontext(enter_result)`? >> Как контекстный менеджер-заглушка, когда ресурс или блокировка опциональны, чтобы не дублировать код под ветками if/else.
11. Что делает обёртка `contextlib.closing(thing)` для объектов без контекстного протокола? >> Создаёт контекстный менеджер для объекта без `__enter__`/`__exit__`, гарантируя вызов метода `thing.close()` при выходе из блока with.
12. Чем @asynccontextmanager отличается от @contextmanager? >> Декорирует асинхронный генератор (функцию `async def` с `yield`) для работы с менеджером контекста `async with`.
13. Что произойдёт с исключением из блока `with`, если в `@contextmanager` перехватить его в `except` после `yield` и не сделать `raise`? >> Исключение будет считаться подавленным (аналогично возврату True из `__exit__`), и выполнение программы продолжится после блока with.
14. Как с помощью модуля `contextlib` временно перехватить вывод функции `print()` в строку для теста? >> Использовать менеджер `with contextlib.redirect_stdout(io.StringIO()) as buf:` и прочитать строку через `buf.getvalue()`.
15. Можно ли использовать один и тот же вызов функции с @contextmanager повторно в двух блоках with подряд? >> Нет, вызов функции создаёт одноразовый генератор; для каждого блока with нужно вызывать функцию-менеджер заново (или наследовать ContextDecorator / писать класс).
16. Какой класс из `contextlib` позволяет использовать контекстный менеджер одновременно и с оператором `with`, и как декоратор функции? >> contextlib.ContextDecorator (причём функции, созданные через @contextmanager, уже автоматически поддерживают работу в качестве декоратора).
