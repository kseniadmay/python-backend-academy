1. В какой структуре данных экземпляры классов Python по умолчанию хранят свои атрибуты? >> В личном словаре `__dict__` (а в CPython 3.11+ — в массиве inline values со ссылкой на общую таблицу ключей класса, материализующемся в `dict` при обращении к `obj.__dict__`).
2. Почему хранение атрибутов через стандартный механизм экземпляра всё равно обходится дорого на сотнях тысяч объектов, несмотря на PEP 412 и Python 3.11+? >> При разделении ключей (PEP 412) и inline values экземпляр несёт обвязку управляемого словаря, а при изменении схемы ключей или материализации `__dict__` для объекта выделяется полноценная хэш-таблица с запасом под коллизии.
3. Как `__slots__` хранит значения и представляет атрибуты на уровне класса и экземпляра? >> На уровне класса для каждого имени создаётся дескриптор `member_descriptor`, а в C-структуре каждого экземпляра резервируются фиксированные ячейки без словаря `__dict__`.
4. Почему в `__slots__` принято указывать кортеж `('x', 'y')`, а не список `['x', 'y']`? >> Кортеж неизменяем (защищён от случайной мутации после создания класса) и занимает меньше памяти, чем список.
5. Что вернёт вызов `hasattr(obj, '__dict__')` для экземпляра класса с корректно настроенным `__slots__`? >> `False` (если в `__slots__` не включён `'__dict__'` и среди родителей нет классов без слотов).
6. В чём главная слепая зона функции `sys.getsizeof(obj)` при замере памяти обычного объекта? >> `sys.getsizeof(obj)` возвращает размер только верхнего контейнера объекта и не учитывает память вложенного словаря `obj.__dict__` и других ссылочных объектов.
7. Как с помощью `sys.getsizeof` получить честную поверхностную оценку памяти обычного экземпляра с простыми полями? >> Сложить размер контейнера объекта и размер его словаря атрибутов: `sys.getsizeof(obj) + sys.getsizeof(obj.__dict__)`.
8. За счёт чего чтение и запись атрибутов со `__slots__` обычно быстрее, чем через `__dict__`? >> Обращение идёт по фиксированному смещению в памяти экземпляра, минуя вычисление хэш-функции имени и поиск по бакетам хэш-таблицы.
9. В каких сценариях бэкенд-разработки применение `__slots__` оправдано вместо обычных классов? >> При создании сотен тысяч и миллионов однотипных объектов (события, точки, узлы деревьев), жёстких лимитах RAM или необходимости строго защитить поля от опечаток.
