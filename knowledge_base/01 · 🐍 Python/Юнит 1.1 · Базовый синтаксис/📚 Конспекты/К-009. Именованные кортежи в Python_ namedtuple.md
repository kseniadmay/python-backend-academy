## Проблема индексов и свойства `namedtuple`

Доступ по числовым индексам вроде `user_data[2]` ухудшает читаемость и провоцирует ошибки порядка полей. Фабрика `collections.namedtuple` создаёт подкласс `tuple` с именованными полями.

Главные свойства именованного кортежа в сравнении с обычным `tuple` и классами:

- **Иммутабельность и минимум памяти:** как и обычный `tuple`, объект нельзя изменить после создания, а под капотом нет словаря `__dict__`.
- **Семантический доступ:** вместо `p[0]` вы пишете `p.x`, делая структуру самодокументированной без накладных расходов на класс.
- **Обратная совместимость:** доступ по индексу и распаковка сохраняются, поэтому `namedtuple` подходит везде, где ожидается `tuple`.

## Как это выглядит на практике

Создадим класс `Point` через `namedtuple` и обратимся к его полям обоими способами:

```python
from collections import namedtuple

Point = namedtuple('Point', ['x', 'y'])
p = Point(3, 5)

print(p.x)
# >>> 3

# Обычный индексный доступ тоже работает
print(p[0])
# >>> 3
```

Первый аргумент `'Point'` задаёт внутреннее имя типа (`__name__`), второй `['x', 'y']` — имена полей; на практике имя типа слева и в строке совпадают.

## Полезные методы: `_asdict()`, `_replace()`, `_fields` и `defaults`

Чтобы не конфликтовать с пользовательскими именами полей, служебные методы и атрибуты `namedtuple` начинаются с одного подчёркивания (но являются частью публичного API!):

- **`p._asdict()`** — преобразует кортеж в словарь `dict` (удобно для JSON-сериализации);
- **`p._replace(x=10)`** — возвращает **новый** экземпляр с обновлёнными полями, не мутируя оригинал;
- **`Point._fields`** — кортеж строк с именами всех полей `('x', 'y')`;
- **`defaults=[0]`** — задаёт значения по умолчанию (применяются справа налево).

```python
from collections import namedtuple

User = namedtuple(
    'User',
    ['id', 'name', 'role'],
    defaults=['viewer'],
)
u1 = User(1, 'Аня')
u2 = u1._replace(role='admin')

print(u1.role, u2.role)
# >>> viewer admin

print(u2._asdict())
# >>> {'id': 1, 'name': 'Аня',
# >>> 'role': 'admin'}
```

## Современный синтаксис: `typing.NamedTuple`

В современном коде с аннотациями типов вместо фабрики `collections.namedtuple` используют декларативный класс **`typing.NamedTuple`**:

```python
from typing import NamedTuple


class Coordinate(NamedTuple):
    lat: float
    lon: float
    label: str = 'Moscow'


pos = Coordinate(55.75, 37.61)
print(pos.lat, pos.label)
# >>> 55.75 Moscow
```

Под капотом это всё тот же быстрый неизменяемый кортеж без `__dict__`, но с поддержкой проверки типов в `mypy`/`pyright`, docstring и удобным синтаксисом дефолтных значений.

## Когда использовать `namedtuple` vs `dataclass`

Выбирайте `NamedTuple` для лёгких неизменяемых записей (координаты, строки выборки из БД, ключи словаря `dict`), где важны минимальный расход памяти и совместимость с кортежами.

Если структуре нужна изменяемость полей, валидация или запрет случайного сравнения с обычным кортежем `(55.75, 37.61)`, переходите на `@dataclass(slots=True)`.

> **Junior vs Senior**:
> - **Junior**: Передаёт между слоями приложения сырые кортежи `user[0], user[1]`, где изменение порядка колонок приводит к скрытым багам в рантайме.
> - **Senior**: Описывает типизированные неизменяемые структуры через `typing.NamedTuple` (используя `_replace` и `_asdict`) или `@dataclass(slots=True)`, получая читаемые имена полей и нулевой оверхед по памяти.
