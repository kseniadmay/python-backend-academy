## Что такое инкапсуляция и зачем она нужна

**Инкапсуляция** объединяет данные объекта и методы работы с ними в одной структуре, ограничивая прямой доступ к внутреннему состоянию.

Её цель — защита целостности объекта: внешний код не должен случайно сломать инварианты класса, изменив внутреннее поле напрямую.

---

## Три уровня доступа через префиксы

В Python уровень доступа обозначается количеством подчёркиваний перед именем атрибута:

```python
class BankAccount:
    def __init__(self):
        # Публичный атрибут
        self.owner = 'Alice'

        # Защищённый (соглашение _name)
        self._balance = 1000

        # Приватный (Name Mangling __name)
        self.__pin = 1234
```

Разница между тремя префиксами:

- **Публичный (`owner`):** официальный интерфейс класса без ограничений.
- **Защищённый (`_balance`):** соглашение «внутренняя деталь реализации»; технически доступен, но опираться на него снаружи опасно.
- **Приватный (`__pin`):** к имени применяется механизм искажения на уровне интерпретатора (`name mangling`).

---

## Name mangling: что происходит с `__pin`

Атрибут с двумя ведущими подчёркиваниями Python автоматически переименовывает по шаблону `_ИмяКласса__атрибут`, затрудняя случайный доступ:

```python
class BankAccount:
    def __init__(self):
        self.__pin = 1234

account = BankAccount()
try:
    print(account.__pin)
except AttributeError as exc:
    print(type(exc).__name__)
# >>> AttributeError

# Доступ через искажённое имя
print(account._BankAccount__pin)
# >>> 1234
```

Настоящей приватности (как `private` в Java/C++) в Python нет — главное назначение `name mangling` состоит в **защите от коллизий имён при наследовании**.

> **Риск обхода:** чтение `account._BankAccount__pin` технически работает, но грубо нарушает инкапсуляцию и привязывает ваш код к внутренней детали реализации.

## Как это применяется на практике: `@property` и валидация

Для контролируемого доступа к защищённым полям применяют публичные методы и декоратор `@property`:

```python
class BankAccount:
    def __init__(self):
        self._balance = 1000

    # Защита от некорректного пополнения
    def deposit(self, amount):
        if amount > 0:
            self._balance += amount

    # Чтение баланса без прямой записи
    @property
    def balance(self):
        return self._balance

acc = BankAccount()
acc.deposit(500)
print(acc.balance)
# >>> 1500
```

Клиент класса читает `acc.balance` и не зависит от того, как данные устроены внутри. На собеседовании важно чётко различать конвенцию `_attr` и `name mangling` для `__attr`.

## Сеттер `@property.setter` и почему в Python не пишут `get_x()` / `set_x()`

В Java и C++ принято сразу создавать методы `get_balance()` и `set_balance(v)`. В Python это считается антипаттерном: начинайте с обычного атрибута, а когда понадобится валидация при записи — оберните его в пару **`@property`** и **`@<name>.setter`** без поломки существующего кода:

```python
class Product:
    def __init__(self, price):
        self.price = price

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError('Цена < 0')
        self._price = value


item = Product(100)
item.price = 250
print(item.price)
# >>> 250
```

Выражение `item.price = 250` выглядит как обычное присваивание, но под капотом вызывает метод-сеттер с проверкой `value < 0`.

> **Junior vs Senior**:
> - **Junior**: Пишет `get_name()`/`set_name()` в каждом классе или ставит двойное подчёркивание `__attr` везде подряд, ломая расширение класса в наследниках.
> - **Senior**: Использует одиночное подчёркивание `_attr` для внутренних полей, добавляет `@property` и `@setter` для вычисляемых или валидируемых атрибутов, а `__attr` оставляет только для защиты от коллизий в базовых миксинах.
