## Поток vs процесс: в чём разница

**Процесс** — изолированная единица выполнения со своим адресным пространством памяти, отдельной копией интерпретатора и ресурсами ОС.

**Поток (thread)** выполняется внутри процесса и делит с другими потоками общую память: создание потока дешевле, а обмен данными происходит напрямую без сериализации.

---

## GIL – главное ограничение CPython

В стандартном CPython действует **GIL** (*Global Interpreter Lock*) — мьютекс, разрешающий выполнять Python-байткод только одному потоку в каждый момент времени.

Он защищает счётчики ссылок от гонок данных без блокировок каждого объекта, поэтому для CPU-вычислений потоки в CPython чередуются на одном ядре.

Настоящий параллелизм возможен лишь без GIL (например, в экспериментальной сборке Python 3.13 free-threaded).

---

## Когда threading всё же полезен

На время ожидания ввода-вывода (сеть, диск, БД) интерпретатор отпускает GIL, позволяя другим потокам работать. Поэтому `threading` ускоряет I/O-bound задачи:

```python
import threading

def fetch_data(url: str) -> str:
    # Имитация сетевого запроса (I/O)
    return f'OK: {url}'

t = threading.Thread(
    target=fetch_data,
    args=('https://api.test',),
)
t.start()

# Ожидаем завершения потока
t.join()
```

При тысячах одновременных соединений современному Python выгоднее однопоточный **`asyncio`**, так как он не тратит память ОС на создание тысяч потоков.

## Multiprocessing – настоящий параллелизм

Чтобы нагрузить несколько ядер CPU вычислениями, используют модуль **`multiprocessing`**: каждый процесс получает собственный интерпретатор и свой независимый GIL:

```python
import multiprocessing

def heavy_computation(chunk: list) -> int:
    # Тяжёлые вычисления на ядре CPU
    return sum(x * x for x in chunk)

if __name__ == '__main__':
    # Отдельный процесс ОС со своим GIL
    p = multiprocessing.Process(
        target=heavy_computation,
        args=([1, 2, 3],),
    )
    p.start()
    p.join()
```

Плата за параллелизм — дорогой старт процесса и обмен данными через `Queue`, `Pipe` (с сериализацией `pickle`) или разделяемую память (`shared memory`).

## Сравнение инструментов по типу нагрузки

Выбор инструмента определяется природой узкого места в программе:

| Подход | Модель памяти | Влияние GIL | Оптимальная задача |
| :--- | :--- | :--- | :--- |
| **`asyncio`** | 1 поток (корутины) | Нет конкуренции | Десятки тысяч сетевых I/O-соединений |
| **`threading`** | Общая память процесса | Снимается на I/O | Умеренный I/O, интеграция sync-библиотек |
| **`multiprocessing`** | Изолированная RAM | У каждого процесса свой | Тяжёлые вычисления на CPU (CPU-bound) |

В высоконагруженных системах подходы комбинируют: например, пул процессов-воркеров (`multiprocessing`) с собственным циклом `asyncio` внутри каждого процесса.

## `concurrent.futures` – высокоуровневая обёртка

Модуль `concurrent.futures` предоставляет единый интерфейс пулов `ThreadPoolExecutor` и `ProcessPoolExecutor` поверх потоков и процессов:

```python
from concurrent.futures import (
    ProcessPoolExecutor,
    ThreadPoolExecutor,
)

def fetch_data(url: str) -> str:
    return f'OK: {url}'

def heavy_computation(chunk: list) -> int:
    return sum(x * x for x in chunk)

if __name__ == '__main__':
    urls = [
        'https://a.test',
        'https://b.test',
    ]
    chunks = [[1, 2], [3, 4]]

    with ThreadPoolExecutor(4) as ex:
        res_io = list(
            ex.map(fetch_data, urls)
        )

    with ProcessPoolExecutor(
        max_workers=4,
    ) as ex:
        res_cpu = list(
            ex.map(heavy_computation, chunks)
        )
```

Пул автоматически управляет воркерами, принимая задачи пакетом (`executor.map`) или по одной с возвратом `Future` (`executor.submit`).
