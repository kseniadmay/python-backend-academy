## Что такое «узкое место» и цена неверного выбора

Замедление любой программы упирается в конкретный ресурс на пределе возможностей. Неверная диагностика повышает накладные расходы без реального ускорения.

Применить `multiprocessing` к I/O-задаче — зря потратить память на процессы ради ожидания сети, а `threading` к CPU-нагрузке — получить проигрыш из-за борьбы потоков за GIL.

---

## Связь типа нагрузки с GIL

В CPython **GIL** защищает счётчики ссылок объектов от гонок данных, пропуская в каждый момент времени к байткоду только один поток.

Из-за этого физически распараллелить чистые вычисления в потоках нельзя, но при системном вызове ожидания (сеть, диск) GIL временно отпускается.

---

## CPU-bound: процессор работает на пределе

**CPU-bound задача** тратит почти всё время на вычисления (математика, криптография, обработка видео, парсинг крупных JSON):

```python
def find_primes(n):
    primes = []
    for num in range(2, n):
        rng = range(2, num)

        # Вычисления грузят ядро CPU без сна
        if all(num % i != 0 for i in rng):
            primes.append(num)
    return primes

print(find_primes(15))
# >>> [2, 3, 5, 7, 11, 13]
```

Потоки здесь постоянно конкурируют за единственный GIL и выполняются даже медленнее одного потока. Единственный выход внутри CPython — отдельные процессы (`multiprocessing`) на разных ядрах.

## I/O-bound: процессор ждёт, GIL освобождается

**I/O-bound задача** большую часть времени ожидает ответа внешнего ресурса (сеть, запросы к БД, чтение диска):

```python
def fetch_url(url):
    # На уровне сокета C-код отпускает GIL
    response = requests.get(url)
    return response
```

Пока один поток ждёт ответа сокета, GIL свободен и другой поток выполняет код.

Для тысяч соединений лучше `asyncio` — он обслуживает их в одном потоке без расходов на потоки ОС.

## Как диагностировать тип нагрузки на практике

Сравнивайте реальное «настенное» время (`perf_counter`) со временем работы процессора (`process_time`):

```python
import time

def check_io_profile():
    w0 = time.perf_counter()
    c0 = time.process_time()

    # Имитация I/O (сон не грузит CPU)
    time.sleep(0.05)

    wall = time.perf_counter() - w0
    cpu = time.process_time() - c0
    print('CPU/Wall < 0.3:', cpu / wall < 0.3)
    # >>> CPU/Wall < 0.3: True

check_io_profile()
```

Если `cpu ≈ wall` и ядро загружено на 100% — это **CPU-bound** (профилируйте через `cProfile`); если CPU простаивает (`cpu << wall`), перед вами **I/O-bound**.

## Освобождение GIL в C-расширениях и Python без GIL (PEP 703)

Библиотеки уровня **NumPy** освобождают GIL внутри своего C-кода во время расчётов над матрицами, поэтому многопоточность с ними даёт реальное ускорение даже на CPU-задачах.

С версии Python 3.13 появился **PEP 703** (экспериментальная сборка free-threaded Python без GIL), позволяющая потокам исполнять байткод параллельно.

В стандартном продакшене пока по-прежнему опираются на правила GIL.

Модуль **`concurrent.futures`** даёт единый высокоуровневый API поверх пула потоков (**`ThreadPoolExecutor`** для I/O) и пула процессов (**`ProcessPoolExecutor`** для CPU):

```python
from concurrent.futures import (
    ProcessPoolExecutor,
    ThreadPoolExecutor,
)

def double(x):
    return x * 2

# Для I/O — пул потоков ThreadPoolExecutor
with ThreadPoolExecutor(max_workers=4) as ex:
    res = list(ex.map(double, [1, 2, 3]))
    print(res)
    # >>> [2, 4, 6]

# Для CPU — ProcessPoolExecutor под main
if __name__ == '__main__':
    with ProcessPoolExecutor() as pool:
        out = list(pool.map(double, [4, 5]))
        print(out)
        # >>> [8, 10]
```

> **Junior vs Senior**:
> - **Junior**: пытается ускорить тяжёлый парсинг в `ThreadPoolExecutor` и удивляется, почему из-за GIL время работы выросло.
> - **Senior**: замеряет долю CPU/Wall через `process_time()` и `perf_counter()`, выбирает `asyncio` или `ThreadPoolExecutor` для I/O-ожидания и `ProcessPoolExecutor` для CPU-bound расчётов.
