## Что такое «узкое место» и почему важно его найти

Любое замедление программы вызвано конкретным ограничением — ресурсом, который работает на пределе и не даёт коду выполняться быстрее. Неправильная диагностика ведёт к неверному решению: оптимизируете не то, результата нет, а накладные расходы растут.

Применить `multiprocessing` к I/O-bound задаче — потратить лишнюю память на отдельные процессы без ускорения, ведь узким местом была сеть. Применить `threading` к CPU-bound задаче в CPython — потоки начнут конкурировать за GIL и могут работать медленнее одного потока.

---

## GIL: что это и почему он существует

**GIL** (Global Interpreter Lock) — мьютекс внутри CPython, гарантирующий, что в каждый момент времени байткод выполняет ровно один поток. Python управляет памятью через подсчёт ссылок: без GIL параллельные потоки повредили бы счётчики объектов (race condition).

Вместо отдельных блокировок на каждый объект CPython использует одну общую блокировку `GIL`. Следствие: несколько потоков в одном процессе не могут выполнять вычисления Python физически одновременно даже на многоядерном CPU.

---

## CPU-bound: процессор работает на пределе

**CPU-bound задача** – задача, где основное время тратится на вычисления: математика, сортировка, криптография, машинное обучение, перекодирование видео, парсинг больших JSON/XML.

```python
def find_primes(n):
    primes = []
    for num in range(2, n):
        rng = range(2, num)

        # Вычисления грузят ядро CPU без сна
        if all(num % i != 0 for i in rng):
            primes.append(num)
    return primes
```

CPU загружен на 100%, выполняя непрерывный поток вычислений – программа не ускорится, пока процессор физически не завершит все циклы.

При запуске нескольких таких потоков они постоянно конкурируют за единственный GIL: пока один поток считает – остальные ждут, и код может работать **медленнее**, чем в один поток – контринтуитивно, но логично: добавляется работа по управлению потоками без реального параллелизма.

**Решение для CPU-bound:** `multiprocessing`. Каждый процесс получает собственный интерпретатор со своим GIL и работает на отдельном ядре – настоящий параллелизм, без конкуренции за общий замок.

## I/O-bound: процессор ждёт, GIL освобождается

**I/O-bound задача** – задача, где основное время тратится на ожидание внешних ресурсов: сетевые запросы, чтение файлов, запросы к БД, очереди сообщений.

```python
def fetch_url(url):
    # здесь GIL освобождается на время
    # ожидания сети
    response = requests.get(url)
    return response
```

Во время блокирующего сетевого запроса выполнение уходит в C-код сетевой библиотеки, и GIL там **временно освобождается**: пока первый поток ждёт ответа от сервера, второй захватывает GIL и выполняет полезную работу. Это настоящий параллелизм ожидания – не вычислений, но для I/O-bound нагрузки этого достаточно.

**Решение для I/O-bound:** `threading` или `asyncio`. `asyncio` предпочтительнее при большом числе одновременных соединений – работает в одном потоке и переключается между задачами кооперативно, без накладных расходов на создание потоков (см. тему asyncio).

## Как диагностировать тип нагрузки

Если при медленной работе CPU загружен на 100% – это CPU-bound. Если CPU почти простаивает, а программа всё равно работает медленно – I/O-bound: время тратится на ожидание, а не на вычисления.

```python
def heavy(n):
    return sum(i * i for i in range(n))

def io_task():
    # имитация ожидания
    time.sleep(1)
```

Инструменты диагностики: `cProfile` показывает, какие функции потребляют больше всего CPU-времени; `time`/`perf_counter` – замер конкретных участков; мониторинг утилизации CPU через `top`, `htop` или `psutil` – быстрый способ увидеть общую картину нагрузки.

## Нюанс: NumPy и другие C-расширения

Библиотеки вроде NumPy тоже освобождают GIL во время тяжёлых операций над массивами – это реализовано на уровне C-кода. Поэтому NumPy-вычисления в нескольких потоках могут давать реальное ускорение, хотя технически остаются CPU-bound по природе.

«CPU-bound» не всегда означает «потоки бесполезны» – зависит от того, держит ли конкретная реализация GIL на всё время вычисления или отпускает его в C-коде.

## Будущее: Python без GIL

В Python 3.13 реализован **PEP 703** – экспериментальная сборка без GIL (free-threaded Python), не дефолтная, требует отдельной установки.

В перспективе это позволит потокам выполнять Python-байткод по-настоящему параллельно на нескольких ядрах, и разделение CPU-bound/I-O-bound потеряет часть критичности для выбора между `threading` и `multiprocessing`. Пока это экспериментальная возможность, и в production-коде по-прежнему актуально текущее поведение GIL.

---

## Итог

Выбор между `threading`, `asyncio` и `multiprocessing` – не вопрос предпочтений, а вопрос природы задачи. CPU-bound требует раздельных процессов. I/O-bound выигрывает от конкурентности внутри одного процесса. Правильная диагностика – первый шаг к любой оптимизации производительности.
