1. Как расшифровывается и устроена схема семантического версионирования (SemVer)? >> `MAJOR.MINOR.PATCH` ; мажорная версия меняется при breaking changes; минорная – при новых фичах; патч – при исправлениях
2. Что означает префикс vnd в MIME / медиа-типах (например, application/vnd.github.v3+json)? >> Вендорский (vendor) медиа-тип; нестандартный тип, специфичный для конкретного API
3. Что такое deprecation-период? >> Период, в течение которого старая версия ещё работает, но помечена как устаревшая; клиенты получают время для миграции
4. Что содержит заголовок `Sunset` ? >> Дату и время запланированного отключения версии: `Sat, 31 Dec 2024 23:59:59 GMT` ; стандарт RFC 8594
5. Что такое breaking change (ломающее изменение)? >> Изменение, нарушающее обратную совместимость; требует смены мажорной версии; примеры: удаление поля, изменение типа, переименование
6. Что такое Content Negotiation для версионирования? >> Версия передаётся в заголовке `Accept: application/vnd.myapi.v2+json` ; URL остаётся стабильным
7. Четыре основных подхода к версионированию API? >> Через URL ( `/api/v1/users` ); через заголовок `Accept` (Content Negotiation); через кастомный заголовок ( `API-Version: 2` ); через query parameter ( `?api_version=v2` )
8. Почему версия в URL удобна для отладки? >> Видна сразу в адресной строке; легко изменить вручную; просто тестировать через браузер
9. Зачем поддерживать несколько версий API одновременно? >> Позволяет клиентам мигрировать в своём темпе без потери работоспособности; не все клиенты могут обновиться одновременно
10. Для чего заголовок `Deprecation: true` ? >> Информирует клиента, что используемая версия устарела
11. Самый распространённый подход к версионированию? >> Версия в URL: `api.example.com/v1/users` ; используют Stripe, GitHub, Twitter
12. Основная цель версионирования API? >> Изменение API без нарушения работоспособности существующих клиентов
13. Является ли версионирование через query parameter рекомендуемым? >> Нет; считается наименее предпочтительным для публичных API
14. Основной недостаток версии в URL с точки зрения REST? >> Загрязняет URL технической информацией; `/v1/users` и `/v2/users` воспринимаются как два разных ресурса, хотя представляют одну сущность
15. Что произойдёт при изменении структуры JSON без смены версии? >> Существующие клиенты могут сломаться – они ожидают старый формат
16. Преимущество кастомного заголовка `API-Version: 2` ? >> Проще для понимания и парсинга по сравнению с `Accept: application/vnd.myapi.v2+json` ; URL остаётся чистым
