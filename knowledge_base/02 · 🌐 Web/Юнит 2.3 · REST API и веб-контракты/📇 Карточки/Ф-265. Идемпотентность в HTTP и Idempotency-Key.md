1. Что такое идемпотентность операции в контексте HTTP и REST API? >> Свойство операции, при котором многократное повторение одного и того же запроса приводит к тому же самому состоянию данных на сервере, что и одиночный вызов
2. Какие HTTP-методы являются идемпотентными по спецификации RFC, а какой — нет? >> Идемпотентны: `GET`, `HEAD`, `OPTIONS`, `TRACE`, `PUT`, `DELETE`. Не идемпотентны: `POST` (и в общем случае `PATCH`, если он содержит относительные операции вроде инкремента)
3. В чём разница между «безопасным» (Safe) и «идемпотентным» (Idempotent) HTTP-методом? >> Безопасные методы (`GET`, `HEAD`, `OPTIONS`) вообще не изменяют состояние сервера (только чтение). Все безопасные методы идемпотентны, но `PUT` и `DELETE` — идемпотентны, хотя не безопасны (они изменяют данные)
4. Почему метод `DELETE /users/42` считается идемпотентным, если первый вызов возвращает `200 OK` / `204 No Content`, а повторный — `404 Not Found`? >> Идемпотентность определяется состоянием ресурсов на сервере, а не совпадением статус-кода ответа: и после первого, и после десятого вызова пользователя `42` в базе нет
5. Почему метод `PUT /users/42` идемпотентен, а `POST /users` — нет? >> `PUT` полностью заменяет ресурс по известному URI переданным состоянием (сколько раз ни отправь `{name: 'Alice'}`, в БД будет одна запись с этим именем); `POST` при каждом вызове создаёт новый ресурс
6. При каких условиях метод `PATCH` перестаёт быть идемпотентным? >> Если `PATCH` задаёт абсолютное значение (`{"name": "Bob"}`), он идемпотентен; если он описывает относительное изменение (`{"op": "increment", "balance": 100}`), каждый повтор увеличивает баланс снова
7. Как сделать неидемпотентный запрос `POST /orders` (или `/payments`) безопасным для повторной отправки при обрыве сети? >> С помощью заголовка **`Idempotency-Key`** (уникальный `UUID v4`, который генерирует клиент для конкретной бизнес-операции и передаёт при всех повторных попытках)
8. Опишите алгоритм работы сервера при получении запроса с заголовком `Idempotency-Key`. >> 1) Сервер проверяет ключ в Redis/БД; 2) Если ключ уже обработан — возвращает сохранённый ответ без повторного выполнения логики; 3) Если ключ сейчас в обработке параллельным запросом — возвращает `409 Conflict`; 4) Если ключ новый — атомарно резервирует его, выполняет операцию и сохраняет результат
9. Как защитить реализацию `Idempotency-Key` от состояния гонки (Race Condition), когда два одинаковых запроса приходят в одну миллисекунду? >> Использовать атомарный захват ключа в Redis (`SET key 'IN_PROGRESS' NX EX 60`) или уникальное ограничение (`UNIQUE constraint` / `INSERT ... ON CONFLICT`) в транзакции БД
10. Что должен сделать сервер, если клиент прислал уже использованный `Idempotency-Key`, но с другим телом запроса (другой суммой платежа)? >> Вернуть ошибку `422 Unprocessable Entity` (или `409 Conflict`): для проверки этого сервер сохраняет вместе с ключом хеш тела исходного запроса (SHA-256)
