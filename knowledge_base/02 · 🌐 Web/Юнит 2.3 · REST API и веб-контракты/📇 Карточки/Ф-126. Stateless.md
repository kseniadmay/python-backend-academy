1. Как связка Access и Refresh токенов решает проблему инвалидации и безопасности? >> Access token короткоживущий (5–15 мин) – минимизирует окно компрометации; refresh token долгоживущий и хранится на сервере – может быть отозван немедленно
2. Как принцип Stateless (Отсутствие состояния) в REST API упрощает кэширование ответов? >> Упрощает; одинаковый запрос с одинаковыми данными всегда даёт одинаковый ответ
3. Верно ли, что REST требует хранения состояния на сервере? >> Нет; REST требует хранения состояния на стороне клиента
4. Где хранится контекст пользователя в Stateful-системе? >> В памяти или БД на стороне сервера; сервер сопоставляет `session_id` из куки с сохранённым контекстом
5. Какую роль JWT играет в Stateless-архитектуре? >> Контейнер для передачи контекста (user ID, права доступа) от клиента к серверу при каждом запросе
6. Что такое sticky sessions? >> Механизм привязки клиента к одному серверу; ограничивает гибкость балансировки и усложняет восстановление после сбоев
7. Как Stateless упрощает отладку? >> Каждый запрос самодостаточен; проблему можно воспроизвести без восстановления состояния сессии
8. Почему Stateless масштабируется лучше Stateful? >> Любой сервер кластера может обработать любой запрос без синхронизации сессий; нет привязки к конкретному узлу (sticky sessions)
9. Как реализуется blacklist JWT-токенов? >> Redis: хранит отозванные токены с TTL равным оставшемуся времени жизни токена; при каждом запросе проверяется наличие токена в blacklist
10. Является ли использование `HttpSession` на сервере антипаттерном для REST? >> Да; нарушает принцип Stateless; состояние должно храниться у клиента
11. Почему JWT сложно инвалидировать досрочно? >> Токен валиден до истечения `exp` ; без blacklist досрочный отзыв невозможен – сервер не хранит состояние
12. Главный недостаток Stateless для сетевого трафика? >> Клиент передаёт токен при каждом запросе; чем больше claims в JWT – тем выше накладные расходы
13. Как Stateless влияет на микросервисы? >> Разные микросервисы независимо обрабатывают запросы одного пользователя по его токену; не нужна синхронизация сессий между сервисами
14. Как Stateless влияет на надёжность при отказе сервера? >> Клиент переходит к другому серверу без потери контекста; контекст хранится у клиента в токене
15. Что возвращает Stateless-сервер после успешного логина? >> JWT-токен; клиент хранит его и отправляет в каждом запросе в заголовке `Authorization: Bearer <token>`
16. В чём основной принцип Stateless? >> Сервер не хранит состояние сессии между запросами; каждый запрос самодостаточен и содержит всю информацию для обработки
17. Является ли передача Bearer-токена нарушением Stateless? >> Нет; это реализация Stateless: сервер получает состояние из запроса, а не из своей памяти
