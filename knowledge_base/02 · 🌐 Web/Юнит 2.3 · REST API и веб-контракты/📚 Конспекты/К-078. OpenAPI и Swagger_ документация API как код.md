## Зачем нужен OpenAPI и чем он отличается от Swagger

Когда бэкенд и фронтенд разрабатываются параллельно, ручное описание маршрутов в чатах или документах устаревает за неделю: одно переименованное поле на сервере ломает клиентское приложение.

**OpenAPI Specification (OAS)** — открытый языконезависимый стандарт описания REST API в машиночитаемом формате **YAML** или **JSON**. Спецификация фиксирует все эндпоинты, параметры, тела запросов и ответов, схемы валидации и способы аутентификации.

Разделяйте два понятия, которые часто путают на собеседованиях:

- **OpenAPI** — сама спецификация (единый формат чертежа API). До 2015 года стандарт назывался *Swagger Specification* (версия 2.0), после чего перешёл в Linux Foundation под именем OpenAPI.
- **Swagger** — экосистема инструментов для работы со спецификацией:
  - **Swagger UI** — интерактивная документация в браузере, где можно тестировать запросы без Postman;
  - **Swagger Editor** — визуальный редактор спецификаций с проверкой ошибок в реальном времени;
  - **Swagger Codegen / OpenAPI Generator** — генерация клиентских SDK и серверных заглушек.

| Критерий | OpenAPI 2.0 (Swagger) | OpenAPI 3.0+ (современный) |
| :--- | :--- | :--- |
| **Базовые адреса** | Один `host` + `basePath` | Массив `servers` (prod, stage) |
| **Тело запроса** | Параметр с `in: body` | Отдельный блок `requestBody` |
| **Переиспользование** | Разрозненные `definitions` | Единый блок `components` |

## Каркас спецификации: `openapi`, `info`, `servers` и `paths`

Любой YAML-файл OpenAPI начинается с поля `openapi`, задающего версию стандарта. Далее идут метаданные (`info`), адреса серверов (`servers`) и маршруты (`paths`):

```yaml
openapi: '3.0.3'

info:
  title: Orders API
  version: 1.0.0
  description: Сервис управления заказами

servers:
  - url: https://api.example.com/v1

paths:
  /orders:
    get:
      tags: [Orders]
      operationId: listOrders
      summary: Список заказов
      description: >
        Возвращает заказы с фильтрами
      responses:
        '200':
          description: Успешный ответ
```

- **`info`** — метаданные API (`title`, `version`, `description`).
- **`servers`** — базовые URL, на которых развёрнуто API.
- **`paths`** — эндпоинты и HTTP-методы (`get`, `post`, `patch`, `delete`).
- **`tags`** — группирует эндпоинты в аккуратные разделы в Swagger UI.
- **`summary` и `description`** — краткий заголовок операции и подробное описание (поддерживает Markdown).
- **`operationId`** — уникальный идентификатор операции; генераторы SDK используют его как имя метода клиента.

## Параметры запросов (`in`) и тело `requestBody`

Чтобы схема точно знала, откуда сервер читает входные данные, у каждого параметра в секции `parameters` указывают поле **`in`**:

- **`in: path`** — часть пути URL (`/orders/{id}`), всегда обязателен (`required: true`);
- **`in: query`** — параметр строки запроса после `?` (`/orders?status=paid`), обычно опционален;
- **`in: header`** — HTTP-заголовок (например, `X-Request-ID`);
- **`in: cookie`** — значение из cookie браузера.

Фиксированный набор допустимых значений задают ключевым словом **`enum`**, а JSON-тело запроса в OpenAPI 3.0+ описывают отдельным блоком **`requestBody`**:

```yaml
paths:
 /orders/{id}:
  post:
   parameters:
    - name: id
      in: path
      required: true
      schema:
       type: integer
    - name: status
      in: query
      schema:
       type: string
       enum: [pending, paid, cancelled]
   requestBody:
    required: true
    content:
     application/json:
      schema:
       $ref: '#/components/schemas/Order'
```

## Переиспользуемые модели (`components/schemas`), `$ref` и массивы

Описывать одни и те же поля пользователя или заказа в каждом маршруте неудобно и ведёт к расхождениям. Все общие модели данных выносят в секцию **`components/schemas`**, а внутри `paths` ссылаются на них через директиву **`$ref`**.

Чтобы описать **массив объектов** (например, список заказов), указывают `type: array` и вложенный блок `items` со ссылкой `$ref`:

```yaml
paths:
 /orders:
  get:
   responses:
    '200':
     description: Массив заказов
     content:
      application/json:
       schema:
        type: array
        items:
         $ref: '#/components/schemas/Order'

components:
  schemas:
    Order:
      type: object
      properties:
        id:
          type: integer
        total:
          type: number
```

## Описание аутентификации (Bearer JWT) в OpenAPI

Чтобы разработчики могли тестировать защищённые эндпоинты прямо в Swagger UI через кнопку **Authorize**, схему аутентификации объявляют в **`components/securitySchemes`** и подключают в корневой секции **`security`**:

```yaml
components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

security:
  - BearerAuth: []
```

После этого Swagger UI автоматически подставит заголовок `Authorization: Bearer <token>` во все защищённые запросы.

## Автодокументация в FastAPI: Pydantic, `response_model` и `responses`

В FastAPI не нужно писать YAML вручную: фреймворк генерирует спецификацию динамически из **аннотаций типов Python** и моделей **Pydantic**. Каждая модель `BaseModel` автоматически превращается в **JSON Schema**, поэтому документация всегда синхронизирована с кодом (в Pydantic v2 для преобразования модели в словарь используется `model_dump()`, в v1 был `dict()`).

Из коробки FastAPI открывает три адреса:

- **`/docs`** — интерактивный **Swagger UI**;
- **`/redoc`** — читаемая документация **ReDoc**;
- **`/openapi.json`** — сырая JSON-спецификация.

```python
from fastapi import FastAPI, HTTPException
from fastapi import Path, Query
from pydantic import BaseModel, Field

app = FastAPI(title='Store API')


class OrderOut(BaseModel):
    id: int
    title: str = Field(
        description='Название заказа',
        examples=['Ноутбук'],
        min_length=2,
    )
    note: str | None = None


@app.get(
    '/orders/{order_id}',
    tags=['Orders'],
    summary='Получить заказ по ID',
    status_code=200,
    response_model=OrderOut,
    responses={
        404: {
            'description': 'Заказ не найден'
        },
    },
)
def get_order(
    order_id: int = Path(ge=1),
    limit: int = Query(
        default=20, ge=1, le=100
    ),
):
    """Подробное описание эндпоинта
    в Markdown."""
    if order_id != 1:
        raise HTTPException(status_code=404)

    return {
        'id': 1,
        'title': 'Книга',
        'secret': 9,
    }
```

Обратите внимание на четыре ключевых механизма в примере:

- **`Path(ge=1)` и `Query(...)`** — валидируют и документируют ограничения path- и query-параметров (`ge`, `le`, `min_length`).
- **Docstring функции** — FastAPI автоматически подставляет его в поле `description` операции в Swagger UI.
- **`response_model=OrderOut`** — валидирует исходящий ответ и **отфильтровывает лишние поля** (`secret` не попадёт клиенту). Необязательные поля задаются через `str | None = None` (или `Optional[str] = None`).
- **Ловушка `HTTPException`:** вызов `raise HTTPException(status_code=404)` вернёт JSON `{"detail": "Not Found"}`, но **не попадёт в OpenAPI-схему автоматически** — коды ошибок нужно явно объявлять в параметре `responses`.

## Автодокументация в Django REST Framework: `drf-spectacular`

В проектах на Django REST Framework современным стандартом генерации OpenAPI 3.0 является библиотека **`drf-spectacular`** (`pip install drf-spectacular`).

Она подключается в `settings.py` одной настройкой в `REST_FRAMEWORK`:

```python
REST_FRAMEWORK = {
    'DEFAULT_SCHEMA_CLASS': (
        'drf_spectacular.openapi.AutoSchema'
    ),
}
```

В `urls.py` добавляют два стандартных представления: **`SpectacularAPIView`** (отдаёт сырую схему OpenAPI) и **`SpectacularSwaggerView`** (отображает Swagger UI).

Чтобы уточнить параметры, коды ошибок или схемы конкретного эндпоинта DRF, используют декоратор **`@extend_schema`**:

```python
from drf_spectacular.utils import (
    extend_schema,
)
from rest_framework.views import APIView


class OrderDetailView(APIView):
    @extend_schema(
        summary='Получить заказ',
        responses={200: OrderSerializer},
    )
    def get(self, request, pk):
        ...
```

## Кодогенерация, контракты и подход Junior vs Senior

Машиночитаемая схема `/openapi.json` превращает документацию в рабочий инструмент всей команды:

- **Генерация клиентских SDK (`openapi-generator`):** фронтенд одной командой генерирует типизированного клиента прямо из схемы API:

```bash
openapi-generator-cli generate \
  -i openapi.json \
  -g typescript-axios
```

- **Контрактное тестирование (`schemathesis`):** автоматически проверяет, совпадают ли реальные ответы бэкенда со схемой и не ломают ли они контракт.
- **Мок-серверы (`Prism`):** позволяют фронтенду работать с API по готовой спецификации ещё до завершения реализации логики на сервере.

**Сравнение подходов Junior vs Senior:**

- **Ошибка Junior:** возвращать из эндпоинтов FastAPI сырой `dict` без `response_model`, не документировать `400`/`404` в `responses` и вести описание API вручную в отдельном документе. В итоге Swagger UI показывает пустую схему `{}`, документация расходится с кодом, а в ответах утекают служебные поля.
- **Подход Senior:** задавать строгие входные и выходные Pydantic-схемы (`response_model`), фиксировать ограничения в `Path`/`Query`/`Field`, группировать маршруты через `tags`, явно документировать коды ошибок и подключать генерацию схемы в CI для контрактной проверки.
