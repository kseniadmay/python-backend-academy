## Пагинация Offset-Limit: простота и деградация $O(N)$

Базовый подход к пагинации опирается на SQL-конструкцию `LIMIT n OFFSET m`:

```http
GET /api/v1/products?limit=20&offset=40
```

```sql
SELECT id, title, price
FROM products
ORDER BY id
LIMIT 20 OFFSET 1000000;
```

- **Критический дефект производительности:** чтобы отдать 20 записей со смещением 1 000 000, СУБД вынуждена прочитать с диска и отсортировать **1 000 020 строк**, а затем отбросить первый миллион. Сложность растет линейно $O(N)$.
- **Проблема сдвига данных (Data Shift):** если во время просмотра каталога пользователь переходит со страницы 1 на страницу 2, а в этот момент добавился новый товар, все записи сдвинулись вправо: пользователь увидит один и тот же товар дважды.

## Курсорная пагинация (Keyset Pagination): мгновенный поиск $O(\log N)$

Вместо смещения строк клиент передает **курсор** — значение индексного поля последнего просмотренного элемента (`cursor=1042`):

```sql
SELECT id, title, created_at
FROM products
WHERE id < 1042
ORDER BY id DESC
LIMIT 20;
```

- **Сложность $O(\log N)$:** СУБД по B-Tree индексу мгновенно позиционируется на запись `id = 1042` и считывает следующие 20 строк подряд. Время выполнения на 1-й и 10 000-й странице одинаково.
- **Стабильность выборки:** добавление или удаление строк не вызывает появления дубликатов или пропусков.

## Кодирование курсора и трюк has_more

Чтобы клиенты не завязывались на внутренние ID таблиц, параметры курсора упаковывают в непрозрачную строку Base64:

```python
import base64

def make_cursor(item_id: int) -> str:
    raw = f"item:{item_id}"
    return base64.urlsafe_b64encode(
        raw.encode()
    ).decode()
```

- 💡 **Проверка `has_more` без тяжелого `COUNT(*)`:**
  Не делайте ресурсоемкий `SELECT COUNT(*)`. Запросите из базы **`limit + 1`** записей (например, 21 вместо 20). Если вернулась 21 строка — значит следующая страница есть (`has_more = True`), а клиенту возвращаются первые 20.

## Стандарт ошибок Problem Details (RFC 7807 / RFC 9457)

Хаотичные форматы ошибок (`{'error': 'Not found'}` vs `{'msg': 'Error'}`) усложняют работу клиентских приложений.

Индустриальный стандарт **RFC 7807 / RFC 9457 (Problem Details)** задает единый формат описания ошибок (`Content-Type: application/problem+json`):

```json
{
  "type": "https://api.ex.com/err/409",
  "title": "Item Out of Stock",
  "status": 409,
  "detail": "Product is out of stock.",
  "instance": "/orders/8941"
}
```

- `type`: постоянный URI типа ошибки;
- `title`: краткое человекочитаемое резюме;
- `status`: дублирует HTTP-статус код;
- `detail`: детализация причины ошибки для конкретного запроса;
- `instance`: URI ресурса или уникальный `trace_id` для поиска в логах.

## Глобальный обработчик Problem Details в FastAPI

В FastAPI стандарт RFC 7807 реализуется через кастомный `exception_handler`:

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

class DomainError(Exception):
    def __init__(
        self, title: str,
        detail: str, status: int = 400
    ):
        self.title = title
        self.detail = detail
        self.status = status

@app.exception_handler(DomainError)
async def domain_error_handler(
    request: Request, exc: DomainError
):
    payload = {
        "type": "about:blank",
        "title": exc.title,
        "status": exc.status,
        "detail": exc.detail,
        "instance": str(request.url.path)
    }
    return JSONResponse(
        status_code=exc.status,
        content=payload,
        headers={
            "Content-Type":
            "application/problem+json"
        }
    )
```
