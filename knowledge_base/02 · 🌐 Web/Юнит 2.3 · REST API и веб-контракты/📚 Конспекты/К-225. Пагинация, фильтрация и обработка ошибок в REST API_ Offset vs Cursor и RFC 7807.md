## Пагинация Offset-Limit: простота и деградация O(N)

Базовая постраничная выборка через query-параметры `limit` и `offset` транслируется в классический SQL с отступом `OFFSET`:

```http
GET /api/v1/products?limit=20&offset=40
```

При большом смещении движок БД всё равно вынужден прочитать и отбросить весь префикс строк:

```sql
SELECT id, title, price
FROM products
ORDER BY id DESC
-- Читает 1M строк ради 20 нужных:
LIMIT 20 OFFSET 1000000;
```

- **Линейная деградация $O(N)$:** чтобы отдать 20 строк со смещением 1 000 000, СУБД читает и сортирует **1 000 020 строк**.
- **Сдвиг данных (Data Shift):** если между переходом на страницу 2 добавилась новая запись, пользователь увидит один товар дважды.

## Курсорная пагинация (Keyset Pagination) за O(log N)

Вместо номера смещения клиент передаёт **курсор** — индексное значение последней увиденной строки (`cursor=1042`):

```sql
SELECT id, title, created_at
FROM products
-- Курсор мгновенно отсекает прошлые строки
WHERE id < 1042
ORDER BY id DESC
LIMIT 20;
```

- **Поиск за $O(\log N)$:** по B-Tree индексу СУБД сразу прыгает к `id = 1042` и считывает следующие 20 строк — первая и миллионная страницы открываются одинаково быстро.
- **Стабильная выдача:** новые вставки выше по списку не сдвигают уже прочитанную ленту.

## Кодирование курсора и трюк `has_more`

Чтобы не раскрывать внутренние ID БД и составные ключи сортировки, курсор оборачивают в непрозрачную строку Base64:

```python
import base64

def make_cursor(item_id: int) -> str:
    raw = f'item:{item_id}'
    return base64.urlsafe_b64encode(
        raw.encode()
    ).decode()
```

Чтобы узнать наличие следующей страницы без дорогого `SELECT COUNT(*)`, из БД запрашивают **`limit + 1`** строк (например, 21 вместо 20): если пришла 21 строка, ставят `has_more = True` и отдают первые 20.

## Стандарт ошибок Problem Details (RFC 7807 / RFC 9457)

Вместо разнородных структур ошибок стандарт **RFC 7807 / RFC 9457** задаёт единый JSON-контракт с заголовком `Content-Type: application/problem+json`:

```json
{
  "type": "https://api.ex.com/err/409",
  "title": "Item Out of Stock",
  "status": 409,
  "detail": "Product is out of stock.",
  "instance": "/orders/8941"
}
```

Пять стандартных полей делают ошибки API предсказуемыми для любых клиентов:

| Поле | Назначение в контракте ошибки |
| :--- | :--- |
| **`type`** | Постоянный URI типа ошибки (документация сбоя) |
| **`title`** | Краткое человекочитаемое описание класса ошибки |
| **`status`** | HTTP статус-код ответа (дублирует статус заголовка) |
| **`detail`** | Детальная причина для конкретного запроса |
| **`instance`** | URI ресурса или `trace_id` для поиска в логах |

## Глобальный обработчик Problem Details в FastAPI

В FastAPI единый формат RFC 7807 удобно централизовать через кастомный `exception_handler` для доменных исключений:

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

class DomainError(Exception):
    def __init__(
        self, title: str,
        detail: str, status: int = 400
    ):
        self.title = title
        self.detail = detail
        self.status = status

@app.exception_handler(DomainError)
async def domain_error_handler(
    request: Request, exc: DomainError
):
    payload = {
        'type': 'about:blank',
        'title': exc.title,
        'status': exc.status,
        'detail': exc.detail,
        'instance': str(request.url.path),
    }
    return JSONResponse(
        status_code=exc.status,
        content=payload,
        media_type='application/problem+json',
    )
```

> **Junior vs Senior**:
> - **Junior**: листает миллионы записей через `OFFSET`, убивая производительность БД, и возвращает разнородные JSON-структуры ошибок и сырые стектрейсы с разных эндпоинтов.
> - **Senior**: внедряет курсорную пагинацию за $O(\log N)$ с трюком `limit + 1` для `has_more`, а все ошибки сервиса приводит к единому контракту `Problem Details` (RFC 7807 / RFC 9457) в глобальном обработчике.
