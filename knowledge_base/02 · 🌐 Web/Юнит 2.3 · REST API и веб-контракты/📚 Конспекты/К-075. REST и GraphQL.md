## Ресурсы против единой точки входа

При проектировании HTTP API чаще всего выбирают между классическим ресурсным подходом и языком запросов GraphQL:

- **REST API:** архитектура вокруг ресурсов с множеством отдельных эндпоинтов (`/users`, `/orders`), каждый со своей фиксированной структурой ответа.
- **GraphQL:** язык запросов через **единый эндпоинт** (`POST /graphql`), где клиент сам декларативно описывает точные поля нужного JSON:

```graphql
query GetUserProfile {
  user(id: 42) {
    name
    email
  }
}
```

## Две проблемы REST, решаемые GraphQL

В мобильных и сложных клиентских приложениях фиксированные ответы REST порождают две типичные потери трафика:

**1. Over-fetching (избыточная выборка):** если экрану нужно только имя пользователя, `GET /users/42` всё равно пришлёт 50 лишних полей; в GraphQL клиент запросит строго `name`.

**2. Under-fetching (N+1 по сети):** чтобы собрать заказ, товары и автора, REST шлёт серию запросов (`orders` $\to$ `users` $\to$ `items`), а GraphQL отдает всё дерево за **один запрос**.

Упрощённая модель серверной фильтрации полей против *Over-fetching* в Python:

```python
full_profile = {
    'id': 42,
    'name': 'Алексей',
    'email': 'alex@example.com',
    'bio': 'Длинный текст биографии...',
}

# Отдаём только запрошенные поля
requested = {'name', 'email'}
sparse = {
    k: v for k, v in full_profile.items()
    if k in requested
}

print(sparse)
# >>> {'name': 'Алексей', 'email': 'alex@example.com'}
```

## Версионирование и эволюция схемы

Подходы по-разному справляются с добавлением и устареванием полей без поломки старых клиентов:

- **REST:** ломающие изменения требуют явных версий эндпоинтов (`/api/v1/users` $\to$ `/api/v2/users`) и параллельной поддержки роутов.
- **GraphQL:** единая типизированная SDL-схема; новые поля добавляются без новых URL, а устаревшие помечаются директивой `@deprecated(reason: 'Use newField')`.

## Кэширование и защита от DoS: плюсы REST

Несмотря на гибкость GraphQL, классический REST выигрывает в инфраструктурной простоте:

- **Нативное HTTP-кэширование:** браузеры, CDN и прокси автоматически кэшируют `GET /products/42` по URL и `ETag`, тогда как `POST /graphql` требует сложных клиентских кэшей (Apollo Client).
- **Предсказуемая нагрузка:** в GraphQL злонамеренный клиент может отправить глубоко вложенный циклический запрос (*пользователь $\to$ друзья $\to$ друзья друзей*), поэтому обязателен ограничитель глубины (*Query Depth Limiting*).

## Матрица выбора между REST API и GraphQL

Сводка архитектурных компромиссов и ключевых инструментов Python для обоих подходов:

| Критерий | REST API | GraphQL |
| :--- | :--- | :--- |
| **Характер данных** | Простые CRUD-модели | Сложносвязанные графы сущностей |
| **Клиенты** | Публичные API, интеграции 3rd-party | Мобильные приложения, сложные SPA |
| **Кэширование** | Нативно из коробки (CDN, браузер) | Требует Apollo / Relay Cache |
| **Передача файлов** | Нативно (`multipart/form-data`) | Сложнее (отдельная спецификация) |
| **Стек в Python** | **FastAPI**, **DRF** | **Strawberry**, **Graphene** |
