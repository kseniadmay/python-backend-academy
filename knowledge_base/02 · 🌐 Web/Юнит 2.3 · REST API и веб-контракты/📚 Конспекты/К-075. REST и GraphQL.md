## Что такое REST

**REST (Representational State Transfer)** – архитектурный стиль, в котором всё строится вокруг ресурсов. Каждый ресурс – пользователь, заказ, товар – имеет свой уникальный URL. Для управления данными используются стандартные HTTP-методы: `GET /users` возвращает список пользователей, `GET /users/42` – конкретного пользователя, `POST /users` создаёт нового, `PUT /users/42` обновляет, `DELETE /users/42` удаляет. Вложенные ресурсы получают вложенные пути: `GET /users/42/orders`.

Главный принцип REST – «один URL = один тип ресурса». Это даёт предсказуемость и позволяет использовать стандартные механизмы HTTP: кэширование на уровне браузера, прокси-серверы, CDN. Но в сложных интерфейсах это приводит к «эффекту водопада»: чтобы собрать данные для одного экрана, приходится делать цепочку последовательных запросов, где каждый ждёт ответа предыдущего.

## Что такое GraphQL

**GraphQL** меняет правила: вместо множества эндпоинтов приложение обращается к одному – `/graphql`. Клиент сам описывает форму и объём нужных данных, а сервер возвращает ответ, точно повторяющий структуру запроса.

Если в REST для получения пользователя, его заказов и состава заказа нужно три запроса – `/users/42`, `/users/42/orders`, `/orders/7/items` – то в GraphQL это описывается одним запросом:

```graphql
query {
  user(id: 42) {
    name
    email
    orders {
      id
      total
      items {
        productName
        quantity
        price
      }
    }
  }
}
```

Сервер вернёт ровно те поля, которые были запрошены, в той же иерархии:

```python
{
  "data": {
    "user": {
      "name": "Alice",
      "email": "alice@example.com",
      "orders": [
        {
          "id": "7",
          "total": 1500,
          "items": [
            {"productName": "Кофе", "quantity": 1, "price": 300}
          ]
        }
      ]
    }
  }
}
```

## Over-fetching и Under-fetching

Это две проблемы, с которыми сталкивается REST при работе со сложными данными.

**Over-fetching** – сервер возвращает больше данных, чем нужно. Если на странице нужно показать только имя пользователя, `GET /users/42` всё равно вернёт полный объект со всеми полями: email, телефон, адрес. Лишние данные нагружают сеть и память устройства. В GraphQL запрашиваешь только `name` – сервер возвращает только `name`.

**Under-fetching (проблема N+1)** – одного запроса недостаточно, и клиент вынужден делать шквал дополнительных. Если у пользователя 10 заказов, сначала нужен запрос за списком заказов, потом по одному запросу за деталями каждого – итого 11 запросов. Каждый из них ждёт ответа по сети. В GraphQL всё дерево – пользователь, заказы, товары в каждом заказе – приходит за один запрос.

## Версионирование

Когда структура данных меняется, REST-API приходится версионировать, чтобы не сломать старые клиенты, которые ещё не обновились. В итоге появляются `/api/v1/users` и `/api/v2/users`, которые нужно поддерживать и тестировать параллельно.

GraphQL решает это эволюционно. Новые поля просто добавляются в схему. Устаревшие помечаются директивой `@deprecated`. Старые клиенты продолжают запрашивать свои поля, новые переходят на актуальные – без параллельных версий и без ломающих изменений.

## Когда выбирать REST

REST – правильный выбор для простых CRUD-сервисов без сложных связей между объектами. Публичные API лучше делать на REST: внешние разработчики с ним знакомы, документация понятна. Если критически важно HTTP-кэширование «из коробки» – например, для высоконагруженных контентных сайтов – REST использует его нативно. Передача файлов, изображений и бинарных данных тоже проще на REST.

---

## Когда выбирать GraphQL

GraphQL оправдан, когда объекты сильно связаны между собой – социальные сети, маркетплейсы со сложной вложенностью данных. Для мобильных приложений, где важно минимизировать трафик и количество запросов, GraphQL даёт реальное преимущество. Если у системы несколько типов клиентов – сайт, мобильное приложение, умные часы – и каждому нужен свой набор данных из одной базы, GraphQL позволяет обойтись одним API. Наконец, когда фронтенд меняется быстрее, чем бэкенд успевает переписывать эндпоинты, гибкость GraphQL окупается.

## Инструменты в Python

Для REST два основных варианта: **FastAPI** – быстрый асинхронный фреймворк с автоматической генерацией документации, современный выбор для новых проектов; **Django REST Framework (DRF)** – зрелое решение с глубокой интеграцией в экосистему Django.

Для GraphQL: **Strawberry** использует современную типизацию Python для определения схем – удобен, если проект уже активно использует `typing`; **Graphene** – более зрелая библиотека с хорошей интеграцией в Django.
