## Фундаментальные отличия: ресурсы vs единая точка входа

- **REST API:** архитектура, центрированная вокруг ресурсов. Десятки фиксированных эндпоинтов (`/users`, `/orders`, `/products`), каждый со своей строгой структурой ответа и методами HTTP.
- **GraphQL:** язык запросов к API, разработанный Facebook в 2015 году. Работает через **единственный эндпоинт** (обычно `POST /graphql`). Клиент сам декларативно описывает точную структуру JSON, которую хочет получить.

```graphql
query GetUserProfile {
  user(id: 42) {
    name
    email
  }
}
```

## Две проблемы REST, решаемые GraphQL

- **1. Избыточная выборка (Over-fetching):** REST-эндпоинт возвращает фиксированную модель. Если мобильному экрану нужно показать только имя пользователя, `GET /users/42` всё равно пришлет 50 полей (адреса, логи, телефоны), бесполезно сжигая мобильный трафик. В GraphQL клиент запрашивает только поле `name`.
- **2. Недостаточная выборка (Under-fetching и проблема N+1 по сети):** чтобы отобразить заказ с товарами и автором, в REST клиент вынужден слать каскад запросов:
  `GET /orders/1` ➔ `GET /users/42` ➔ `GET /items?ids=1,2,3`.
  В GraphQL всё связанное дерево сущностей возвращается за **один сетевой запрос**.

## Версионирование и эволюция схемы

- **REST:** изменение схемы требует явного версионирования эндпоинтов (`/api/v1/users` ➔ `/api/v2/users`), что приводит к параллельной поддержке устаревших роутов.
- **GraphQL:** единая строго типизированная схема (Schema Definition Language, SDL). Новые поля добавляются без ломки клиентов. Устаревшие поля помечаются директивой `@deprecated(reason: "Use newField")` — старые приложения работают без сбоев.

## Кэширование и производительность: сильные стороны REST

Несмотря на гибкость GraphQL, у классического REST есть решающие инженерные преимущества:

- **Нативное HTTP-кэширование:** браузеры, CDN (Cloudflare) и прокси легко кэшируют `GET /products/42` по URL и ETag. В GraphQL все запросы идут через `POST /graphql`, поэтому кэширование на уровне HTTP «из коробки» не работает и требует сложных клиентских кэшей (Apollo Client).
- **Сложность выполнения и защита от DoS:** в GraphQL неопытный или вредоносный клиент может отправить циклический глубокий запрос (пользователь ➔ друзья ➔ друзья друзей), который положит сервер БД. Требуется анализ глубины запроса (Query Depth Limiting).

## Матрица выбора стека для бэкендера

| Критерий | REST API | GraphQL |
| :--- | :--- | :--- |
| **Характер данных** | Простые CRUD-модели | Сложносвязанные графы сущностей |
| **Клиенты** | Публичные API, 3rd-party | Мобильные клиенты, SPA |
| **Кэширование** | Идеально (CDN, браузер) | Требует Apollo / Relay Cache |
| **Передача файлов** | Нативно (`multipart`) | Требует костылей (Multipart spec) |
| **Инструменты Python** | **FastAPI**, **DRF** | **Strawberry**, **Graphene** |
