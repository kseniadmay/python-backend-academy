## Ресурсы и имена: существительные во множественном числе

Главное правило чистого REST: **URL идентифицирует ресурс, а HTTP-метод задает действие**.

- ❌ **Ошибочно (глаголы в адресе):** `/getUsers`, `/createOrder`, `/deleteProduct/42`.
- ✅ **Правильно (существительные во множественном числе):**
  * `GET /users` — список пользователей;
  * `POST /users` — создание пользователя;
  * `GET /users/42` — конкретный пользователь;
  * `DELETE /users/42` — удаление пользователя.

Существительные во множественном числе гарантируют единообразие: разработчик заранее знает структуру URI для любой сущности системы.

## Вложенность ресурсов: лимит 2 уровней

Отношения «родитель — потомок» моделируются вложенностью URI. Однако глубокая вложенность превращает URL в антипаттерн:

```text
❌ /org/1/dep/4/team/2/users/42/tasks
   (перегруженная вложенность)

✅ Решение (уплощение путей):
   GET /users/42/tasks
   GET /tasks/9012
```

**Инженерное правило:** глубина вложенности не должна превышать **2 уровней** (`/parents/{id}/children`). Если у ресурса есть собственный глобальный ID, обращайтесь к нему напрямую.

## Path vs Query параметры: правила разделения

- **Path-параметры (`/items/{id}`):** служат для однозначной **идентификации** конкретного ресурса или коллекции в иерархии:
  `GET /api/v1/orders/105`
- **Query-параметры (`?key=val`):** служат для **фильтрации, сортировки, пагинации и проекции**:

```http
GET /api/v1/orders?status=paid&limit=20
```

> Правило: если без параметра ресурс невозможно идентифицировать — это Path; если параметр модифицирует способ выборки/отображения — это Query.

## Стилистика URL: kebab-case и регистр

1. **Нижний регистр:** адресная строка не должна содержать заглавных букв (`/user-profiles`, а не `/userProfiles`).
2. **Разделитель kebab-case:** слова разделяются дефисом (`/order-items`). Подчеркивания (`snake_case`) хуже считываются в подчеркнутых ссылках браузера, а `camelCase` не принят в стандартах RFC URL.
3. **Без расширений файлов:** никогда не пишите `/users.json` или `/export.xml` — формат запрашивается через заголовок `Accept`.

## Нестандартные действия: RPC-стиль внутри REST

Что делать, когда действие не укладывается в стандартный CRUD (например: «опубликовать пост», «активировать аккаунт», «отправить SMS»)?

- **Подход 1: Подресурс-действие (Sub-resource Action):**
  `POST /api/v1/articles/42/publish`
  `POST /api/v1/auth/password-reset`
- **Подход 2: Перевод действия в сущность:**
  Вместо `/send-invoice` создаем ресурс `POST /api/v1/invoices` со статусом `sent`.

Любые действия с сайд-эффектами обязаны выполняться методом **`POST`**, но ни в коем случае не `GET`.
