## Ресурсы – существительные, не глаголы

Главная ошибка при проектировании API – использование глаголов в URL. REST строится вокруг ресурсов (объектов), а не действий. Действие выражается через HTTP-метод, URL описывает объект.

Правильно: `/users`, `/orders`, `/products`.

Неправильно: `/getUsers`, `/createOrder`, `/deleteProduct`.

Использование существительных делает API предсказуемым: если ресурс определён как `/users`, любой разработчик ожидает стандартного поведения – он не угадывает, какой глагол выбрал автор.

---

## Коллекции и идентификаторы: множественное число

Ресурсы всегда именуются во множественном числе. Это закладывает масштабируемость с самого начала:

`/users` – вся коллекция, список пользователей.

`/users/42` – конкретный объект по ID.

`/users/42/orders` – связанная коллекция: все заказы пользователя 42.

Единственное число (`/user`) – тупиковый путь: когда потребуется список, придётся либо ломать совместимость, либо плодить дублирующие эндпоинты.

---

## HTTP-методы: глаголы архитектуры

Действие описывается методом, URL остаётся чистым адресом ресурса. Глагол в URL дублирует смысл метода и считается нарушением REST.

`GET /users` – получить список пользователей.

`POST /users` – создать пользователя.

`GET /users/42` – получить конкретного пользователя.

`PUT /users/42` – полное обновление.

`PATCH /users/42` – частичное обновление.

`DELETE /users/42` – удалить.

Варианты вроде `GET /users/get`, `POST /users/create` или `DELETE /users/delete/42` – избыточны: действие уже выражено методом.

## Вложенность: не глубже двух-трёх уровней

Вложенные пути показывают отношения родитель-потомок. Но глубокая вложенность создаёт проблемы:

```text
❌ /users/42/orders/7/items/3/reviews  - перегруженный путь

✅ /order-items/3/reviews              - item вынесен как самостоятельный ресурс
```

Цена глубокой вложенности – не только длинный URL. Авторизацию нужно проверять по всей цепочке, SQL-запросы требуют множественных JOIN, клиентский код становится хрупким. Оптимальный предел – два-три уровня вложенности.

## Стилистика URL

Единообразие именования критично для автоматизации и читаемости. Только нижний регистр – URL чувствительны к регистру в некоторых системах. Для разделения слов используется **kebab-case** (дефисы): `/product-categories`. `camelCase` плохо читается в адресной строке, `snake_case` допустим в JSON-ответах, но не в URL.

## Query-параметры: фильтрация, сортировка, пагинация

**Query-параметры** позволяют изменять представление данных, не меняя структуру ресурса. Это сохраняет эндпоинт чистым и позволяет комбинировать условия:

```http
GET /orders?created_after=2024-01-01&status=pending
GET /products?sort=-price
GET /users?limit=20&offset=40
```

Знак `-` перед полем сортировки обычно означает убывание. Вместо создания отдельного эндпоинта `/active-admin-users` используется базовый `/users` с фильтрами `?status=active&role=admin`. Это упрощает поддержку и устраняет дублирование логики на бэкенде.

---

## Исключения: нестандартные действия

Иногда бизнес-логика требует действия, которое нельзя свести к простому изменению поля через `PATCH`. Активация пользователя может включать отправку уведомлений и внешние вызовы. Отмена заказа – возврат средств и списание со склада. Такие **процессы** описываются глаголом в конце пути с методом `POST`:

```http
POST /users/42/activate
POST /orders/7/cancel
POST /payments/42/refund
```

Это осознанное отступление от REST, применяемое только тогда, когда стандартные методы не могут точно отразить смысл бизнес-процесса. Всегда через `POST` – это единственный метод без семантики конкретного CRUD-действия.
