## Ресурсы и имена: существительные во множественном числе

Главное правило чистого REST: **URL называет сущность, а HTTP-метод задаёт действие над ней**, поэтому глаголы вроде `/getUsers` или `/deleteProduct/42` считают ошибкой.

Существительные во множественном числе сразу формируют предсказуемый контракт для любой коллекции:

- `GET /users` — список пользователей;
- `POST /users` — создание пользователя;
- `GET /users/42` — конкретный пользователь;
- `DELETE /users/42` — удаление пользователя.

## Вложенность ресурсов: лимит 2 уровней

Связи «родитель — потомок» выражают вложенностью пути, но глубина не должна превышать **2 уровня** (`/parents/{id}/children`).

Если у сущности есть собственный глобальный ID, путь уплощают и обращаются к ресурсу напрямую:

```text
❌ /org/1/dep/4/team/2/users/42/tasks
   (перегруженная вложенность)

✅ Решение (уплощение путей):
   GET /users/42/tasks
   GET /tasks/9012
```

## Path против Query параметров: правила разделения

**Path-параметры (`/orders/{id}`)** служат для однозначной идентификации ресурса в иерархии — например, `GET /api/v1/orders/105`.

**Query-параметры (`?key=val`)** модифицируют выборку (фильтрация, сортировка, пагинация):

```http
GET /api/v1/orders?status=paid&limit=20
```

Разбор пути и параметров строки запроса средствами стандартной библиотеки Python:

```python
from urllib.parse import urlparse, parse_qs

url = '/api/v1/orders?status=paid&limit=20'
parsed = urlparse(url)
params = parse_qs(parsed.query)

print(parsed.path)
# >>> /api/v1/orders

print(params['status'][0], params['limit'][0])
# >>> paid 20
```

> Правило выбора: без этого значения ресурс нельзя найти $\to$ **Path**; значение меняет срез или вид списка $\to$ **Query**.

## Стилистика URL: `kebab-case` и нижний регистр

Чтобы эндпоинты одинаково читались в логах, браузерах и разных ОС, придерживаются трёх правил оформления адресов:

1. **Нижний регистр:** не используйте заглавные буквы (`/user-profiles`, а не `/userProfiles`).
2. **Разделитель `kebab-case`:** слова разделяют дефисом (`/order-items`), потому что подчёркивания `snake_case` теряются под подчёркиванием ссылок, а `camelCase` противоречит стилю REST.
3. **Без расширений файлов:** избегайте `/users.json` или `/export.xml` — формат запрашивают через заголовок `Accept`.

## Нестандартные действия: RPC-стиль внутри REST

Когда операция не укладывается в CRUD (опубликовать статью, сбросить пароль, отправить счёт), применяют один из двух подходов.

**1. Подресурс-действие:** к адресу сущности добавляют глагол действия (`POST /api/v1/articles/42/publish` или `POST /api/v1/auth/password-reset`).

**2. Перевод действия в сущность:** вместо `/send-invoice` создают ресурс `POST /api/v1/invoices` со статусом `sent`.

Любое действие с побочным эффектом строго выполняется через **`POST`**, но никогда не через `GET`.

## Обновление (`PUT` vs `PATCH`), заголовки и подход Junior vs Senior

При проектировании контракта важно чётко различать обновление, пагинацию и служебные заголовки:

- **`PUT /users/42`** — полная замена ресурса (идемпотентна: нужно передать все поля).
- **`PATCH /users/42`** — частичное обновление только переданных полей (`{"email": "new@ex.com"}`).
- **Пагинация и фильтрация:** передаются через query-параметры (`?page=2&per_page=20` или `?limit=20&offset=40`), а не в теле `GET`.
- **Служебные заголовки:** токен авторизации передают в `Authorization: Bearer <token>`, а защиту от дублей при повторах `POST` — через заголовок `Idempotency-Key`.

> **Junior vs Senior**:
> - **Junior**: Строит RPC-адреса вроде `GET /createOrder` или `POST /activateUser`, прячет токен в query-параметрах и вкладывает ресурсы на 4–5 уровней.
> - **Senior**: Использует существительные во множественном числе (`kebab-case`), ограничивает вложенность 2 уровнями, разделяет `PUT`/`PATCH`, передаёт токен в `Authorization: Bearer` и защищает платежи через `Idempotency-Key`.
