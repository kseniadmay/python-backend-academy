## Необходимость версионирования: закон эволюции API

Любой продакшен-API непрерывно развивается, но не все правки требуют новой мажорной версии контракта:

- **Обратно совместимые (Non-breaking):** добавление нового опционального поля ответа, нового query-параметра или нового эндпоинта. Версия остаётся прежней.
- **Ломающие (Breaking Changes):** удаление или переименование поля, смена типа (`int` $\to$ `string`), новые обязательные поля, смена кодов ответа. **Требуют обязательной новой версии API**.

## Стратегии версионирования: три подхода индустрии

Номер версии передают от клиента к серверу одним из трёх стандартных способов:

| Стратегия | Пример запроса | Плюсы и компромиссы |
| :--- | :--- | :--- |
| **В пути URI** *(стандарт)* | `GET /v1/users` | Наглядно, легко кэшируется и проверяется в браузере (FastAPI, GitHub) |
| **В заголовке** | `X-API-Version: 2026-10-01` | Оставляет URI чистым, но неудобно открывать в адресной строке |
| **Через `Accept`** | `Accept: application/vnd.api.v2+json` | Соответствует идеологии REST, но сложнее для интеграций клиентов |

## Уведомление об устаревании: `Deprecation` и `Sunset`

Внезапное отключение старой версии API сломает мобильные приложения, поэтому клиентов предупреждают заранее через стандартные HTTP-заголовки.

RFC 9745 (`Deprecation`) и RFC 8594 (`Sunset`) сообщают факт устаревания и точную дату вывода роута из работы:

```http
HTTP/1.1 200 OK
Deprecation: @1793404800
Sunset: Wed, 11 Nov 2026 00:00:00 GMT
Link: <https://api.example.com/v2>;
  rel="successor-version"
```

- **`Deprecation`:** отмечает, что эндпоинт устарел и клиентам пора планировать переход (ссылка `Link` указывает на замену).
- **`Sunset`:** дата окончательного отключения, после которой сервер начнёт отдавать `410 Gone` или `404`.

## Архитектура версионирования в FastAPI

В FastAPI версии изолируют подключением независимых модулей `APIRouter`, чтобы изменения в `v2` никогда не затронули контракты и Pydantic-схемы `v1`:

```python
from fastapi import APIRouter, FastAPI

app = FastAPI()

v1 = APIRouter(prefix='/api/v1')
v2 = APIRouter(prefix='/api/v2')

@v1.get('/users')
def get_users_v1():
    return [{'name': 'Alice'}]

@v2.get('/users')
def get_users_v2():
    return [{
        'first_name': 'Alice',
        'last_name': 'Smith',
    }]

app.include_router(v1)
app.include_router(v2)
```

## Политика поддержки версий и подход Junior vs Senior

Поддерживать 5 версий API одновременно дорого: каждая версия дублирует тесты, схемы валидации и багфиксы. В индустрии обычно держат **не более 2 активных мажорных версий** (текущую `v2` и предыдущую `v1` в режиме поддержки).

Безопасный вывод старой версии проходит в 4 этапа:
1. Запуск `v2` параллельно с `v1`.
2. Добавление заголовков `Deprecation`, `Sunset` и `Link` в ответы `v1` + мониторинг трафика по логам.
3. Уведомление оставшихся клиентов до даты `Sunset`.
4. Отключение `v1` с честным статусом **`410 Gone`** (ресурс удалён навсегда).

> **Junior vs Senior**:
> - **Junior**: Переименовывает поле `name` в `full_name` прямо в существующем `/api/v1/users`, мгновенно ломая мобильные приложения, или плодит `v2`, `v3`, `v4` на каждое новое опциональное поле.
> - **Senior**: Сохраняет обратную совместимость для аддитивных правок, выпускает новую мажорную версию только для ломающих изменений и выводит старую версию плавно через `Deprecation`, `Sunset` и `410 Gone`.
