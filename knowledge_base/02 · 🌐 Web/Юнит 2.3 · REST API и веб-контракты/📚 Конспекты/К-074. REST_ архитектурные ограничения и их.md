## Сущность `REST`: архитектурный стиль Роя Филдинга

**REST** (*Representational State Transfer*) — это архитектурный стиль проектирования распределённых систем, сформулированный Роем Филдингом в 2000 году.

REST — это не стандарт, не протокол и не библиотека, а набор из **6 фундаментальных ограничений** (*Constraints*), которые определяют масштабируемость и предсказуемость API.

---

## Ограничения 1 и 2: `Client-Server` и `Stateless`

Первые два ограничения задают границы между клиентом и сервером и убирают серверное состояние:

- **1. Client-Server:** интерфейс пользователя (UI/фронтенд) строго отделён от хранения данных и бизнес-логики (бэкенд), поэтому они развиваются и деплоятся независимо.
- **2. Stateless:** сервер не хранит контекст сессии клиента между запросами — каждый HTTP-запрос обязан содержать токен и все параметры для обработки.

> **Выгода Stateless:** любой экземпляр сервера за балансировщиком мгновенно обработает следующий запрос клиента без синхронизации памяти.

Простой пример обработчика, не опирающегося на локальную память прошлых запросов:

```python
def handle_request(payload: dict) -> dict:
    user_id = payload.get('user_id')
    return {
        'status': 'processed',
        'user_id': user_id,
    }

res = handle_request({'user_id': 42})
print(res['status'])
# >>> processed
```

## Ограничения 3 и 4: `Cacheable` и `Layered System`

Следующие два ограничения отвечают за снижение сетевой нагрузки и масштабирование через промежуточные узлы:

- **3. Cacheable:** каждый ответ сервера явно объявляет правила кэширования (`Cache-Control`, `ETag`), чтобы браузер и прокси переиспользовали неизменившиеся данные.
- **4. Layered System:** клиент не знает, общается он с самим приложением или с промежуточным слоем (балансировщик Nginx, WAF, кэш CDN).

---

## Ограничение 5: Единообразие интерфейса (`Uniform Interface`)

Единообразный интерфейс отличает REST от произвольных стилей RPC и включает четыре принципа:

1. **Идентификация ресурсов:** у каждого объекта есть постоянный адрес URI (`/api/v1/orders/105`).
2. **Манипуляция через представления:** клиент получает JSON-представление ресурса и меняет его стандартными методами (`GET`, `POST`, `PUT`, `DELETE`).
3. **Самоописываемые сообщения:** заголовки (`Content-Type`) явно задают формат данных.

Четвёртый принцип **HATEOAS** (*Hypermedia As The Engine Of Application State*) предлагает вкладывать в сам ответ ссылки на доступные дальнейшие действия:

```json
{
  "id": 105,
  "status": "pending",
  "links": {
    "cancel": "/api/v1/orders/105/cancel",
    "pay": "/api/v1/orders/105/pay"
  }
}
```

## `Code on Demand` и модель зрелости Ричардсона

Шестое (необязательное) ограничение **Code on Demand** разрешает серверу передавать клиенту исполняемый JS-скрипт или виджет.

На практике его почти не используют ради безопасности и совместимости с небраузерными клиентами (`curl`, микросервисы).

Глубину следования REST оценивают по **модели зрелости Ричардсона**:

| Уровень | Название | Суть подхода |
| :--- | :--- | :--- |
| **Level 0** | *Swamp of POX* | Одна точка входа (`POST /api`) в стиле RPC |
| **Level 1** | *Resources* | Отдельные URI для сущностей (`/users`, `/orders`) |
| **Level 2** | *HTTP Verbs* | Правильные методы `GET/POST/PUT/DELETE` и статус-коды |
| **Level 3** | *Hypermedia* | Полная поддержка ссылок HATEOAS в ответах |

> Большинство коммерческих API работают на **Level 2**: от HATEOAS часто отказываются, чтобы не усложнять клиентов.
