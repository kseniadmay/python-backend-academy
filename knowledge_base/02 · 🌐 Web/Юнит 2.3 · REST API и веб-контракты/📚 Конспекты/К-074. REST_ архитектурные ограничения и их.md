## Сущность REST: архитектурный стиль Роя Филдинга

**REST (Representational State Transfer)** — это архитектурный стиль проектирования распределенных систем, сформулированный Роем Филдингом в 2000 году.

REST — это **не стандарт, не протокол и не библиотека**, а набор из **6 фундаментальных ограничений (Constraints)**. Система считается истинно RESTful только при одновременном соблюдении всех обязательных ограничений.

---

## Ограничения 1 и 2: Client-Server и Stateless

- **1. Клиент-Сервер (Client-Server):** строгое разделение ответственности. Интерфейс пользователя (UI / фронтенд) отделен от хранения данных и бизнес-логики (бэкенд). Они эволюционируют и деплоятся независимо.
- **2. Отсутствие состояния (Stateless):** контекст сессии клиента **категорически запрещено хранить на сервере** между запросами. Каждый HTTP-запрос обязан содержать всю полноту информации для его выполнения (токен аутентификации, параметры).

> **Инженерная выгода Stateless:** любой сервер из горизонтального кластера за балансировщиком может мгновенно обработать следующий запрос клиента без синхронизации сессий между машинами.

---

## Ограничения 3 и 4: Cacheable и Layered System

- **3. Кэшируемость (Cacheable):** каждый ответ сервера обязан явно декларировать свою политику кэширования через заголовки (`Cache-Control`, `ETag`), чтобы клиенты и промежуточные узлы могли кэшировать данные и снижать сетевую нагрузку.
- **4. Слоистая система (Layered System):** клиент не знает, общается ли он напрямую с сервером приложения или с промежуточным звеном. Архитектура строится из слоев: балансировщики (Nginx/HAProxy), шлюзы безопасности (WAF), кэширующие прокси (Varnish/Cloudflare). Каждый слой выполняет строго одну задачу.

---

## Ограничение 5: Единообразие интерфейса (Uniform Interface)

Ключевое ограничение, отличающее REST от других подходов (RPC, SOAP):

1. **Идентификация ресурсов:** каждый ресурс обладает уникальным постоянным адресом (URI): `/api/v1/orders/105`.
2. **Манипуляция через представления:** клиент получает не строки БД, а представление ресурса (JSON/XML) и модифицирует его стандартными методами (`GET`, `POST`, `PUT`, `DELETE`).
3. **Самоописываемые сообщения:** каждое сообщение содержит метаданные (`Content-Type`), объясняющие, как его парсить.
4. **HATEOAS (Hypermedia As The Engine Of Application State):** ответ сервера содержит ссылки на возможные дальнейшие действия:

```json
{
  "id": 105,
  "status": "pending",
  "links": {
    "cancel": "/api/v1/orders/105/cancel",
    "pay": "/api/v1/orders/105/pay"
  }
}
```

## Ограничение 6: Code on Demand и модель зрелости Ричардсона

- **6. Код по требованию (Code on Demand — опционально):** сервер может передавать клиенту исполняемый код для расширения функционала (например, JavaScript-скрипты).
- **Модель зрелости Ричардсона (Richardson Maturity Model):**
  * **Level 0 (The Swamp of POX):** одна точка входа (`POST /api`), формат RPC.
  * **Level 1 (Resources):** выделены отдельные ресурсы (`/users`, `/orders`).
  * **Level 2 (HTTP Verbs):** корректное использование методов (`GET`, `POST`, `PUT`, `DELETE`) и статус-кодов.
  * **Level 3 (Hypermedia Controls):** полная поддержка HATEOAS.

> На собеседовании: большинство коммерческих сервисов соответствуют **Level 2** (REST-like API). От HATEOAS в индустрии часто отказываются для упрощения клиентов.
