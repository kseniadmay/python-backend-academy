## Что такое REST

**REST** (Representational State Transfer) – не протокол и не стандарт, а архитектурный стиль, описанный Роем Филдингом в 2000 году. Это набор ограничений, которые при соблюдении делают систему масштабируемой, предсказуемой и независимой от конкретных технологий. API, следующий этим ограничениям, называют RESTful.

---

## 1. Client-Server: разделение ответственности

Клиент и сервер должны быть независимы. Клиент не знает, как сервер хранит данные. Сервер не знает, как выглядит интерфейс пользователя. Взаимодействие идёт только через согласованный интерфейс – API.

Практический смысл: можно полностью переписать фронтенд или сменить базу данных на бэкенде – если интерфейс не изменился, система продолжает работать.

---

## 2. Stateless: каждый запрос самодостаточен

Сервер не хранит состояние между запросами. Каждый запрос должен содержать всё необходимое для его обработки: токен аутентификации, параметры, контекст. Сервер не «помнит» предыдущих запросов того же клиента.

Это ключевое условие для **горизонтального масштабирования**: если сервер не хранит сессии в памяти, запрос можно направить на любой из десятков серверов за балансировщиком – каждый обработает его одинаково. Если бы состояние хранилось на конкретном сервере, клиент был бы привязан к нему.

Компромисс: каждый запрос несёт немного больше данных (токены, параметры), что создаёт небольшой сетевой overhead. Это осознанная цена за масштабируемость.

---

## 3. Cacheable: ответы явно помечаются как кешируемые

Сервер должен явно указывать через заголовки (`Cache-Control`, `ETag`, `Expires`), можно ли кешировать ответ и на какой срок. Кешировать может как сам клиент, так и промежуточные слои – CDN, прокси, балансировщики.

Кеширование снижает нагрузку на бэкенд и ускоряет отклик: данные берутся ближе к пользователю, а не запрашиваются каждый раз с сервера.

---

## 4. Uniform Interface: единообразие взаимодействия

Это центральный принцип REST, состоящий из четырёх элементов.

- 1. Первый – **идентификация ресурсов через URI**. Каждый объект системы имеет уникальный адрес: `/users/42`, `/orders/17/items`. Адрес стабилен и предсказуем.
- 2. Второй – **манипуляция через представления**. Клиент получает не «сырые» данные из базы, а представление ресурса в согласованном формате – обычно JSON. Внутреннее устройство базы данных клиента не касается.
- 3. Третий – **самоописывающие сообщения**. HTTP-метод описывает действие (`GET` – читать, `POST` – создать, `PUT` – заменить, `DELETE` – удалить). Заголовки описывают формат (`Content-Type`). Статус-коды описывают результат. Клиент всегда знает, что произошло.
- 4. Четвёртый – **HATEOAS** (Hypermedia as the Engine of Application State). Сервер вместе с данными возвращает ссылки на возможные следующие действия. Клиент не хранит URL в коде, а динамически получает их из ответов. Если сервер изменит структуру адресов – клиент не сломается. На практике HATEOAS реализован редко, но концептуально важен для понимания идеи REST.

---

## 5. Layered System: многоуровневая архитектура

Клиент видит только «соседний слой» и не знает, что за ним стоит. Между клиентом и сервером может находиться балансировщик нагрузки, кеширующий прокси, firewall, API Gateway – всё это прозрачно для клиента. Это позволяет добавлять уровни безопасности и отказоустойчивости, не меняя клиентский код.

---

## 6. Code on Demand: необязательный принцип

Единственное необязательное ограничение REST. Сервер может передать клиенту исполняемый код – например, JavaScript – для расширения функциональности на лету. На практике это редко применяется в API, хотя веб как таковой работает именно так: браузер загружает скрипты с сервера.

---

## REST и реальность

В индустрии «RESTful API» часто означает «HTTP API с JSON и разумными именами эндпоинтов». Полное соблюдение всех ограничений, особенно HATEOAS, встречается редко. На собеседовании важно знать ключевые принципы – stateless, uniform interface, client-server – и понимать их практический смысл: почему они упрощают масштабирование и уменьшают связность между компонентами системы.
