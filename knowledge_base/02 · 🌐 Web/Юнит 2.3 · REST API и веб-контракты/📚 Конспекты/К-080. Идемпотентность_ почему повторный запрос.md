## Математика и протокол: определение идемпотентности

В математике операция идемпотентна, если повторное применение не меняет результат: $f(f(x)) = f(x)$.

В HTTP **идемпотентность означает, что многократная отправка одинакового запроса оставляет состояние сервера таким же, как однократный вызов**.

> **Важно:** идемпотентность касается *состояния БД*, а не статус-кода ответа: первый `DELETE /users/42` вернёт `204`, повторный — `404`, но результат на сервере один: пользователя нет.

## Карта методов HTTP: идемпотентные vs неидемпотентные

Большинство стандартных методов идемпотентны, тогда как создание ресурса и относительная дельта при повторе меняют состояние заново:

```text
Идемпотентные методы:
- GET /orders/42    -> чтение
- HEAD /orders/42   -> метаданные
- PUT /orders/42    -> перезапись
- DELETE /orders/42 -> удаление
- OPTIONS /orders   -> опрос

Неидемпотентные методы:
- POST /orders      -> новый заказ
- PATCH /orders/42  -> инкремент/дельта
```

`POST` принципиально не идемпотентен: повторная отправка платёжной формы без защиты создаст вторую транзакцию.

## Проблема сетевых сбоев и повторов (Network Retries)

В распределённых системах клиент не всегда может отличить падение ответа от сбоя до сервера:

```text
Клиент            Сервер       БД
  │ ── POST /pay ──> │          │
  │                  │ ─Write─> │ (OK)
  │                  │ <─OK──── │
  │   ❌ Сбой сети   │
  │ (Timeout ответа) │
  │                  │
  │ ── Retry: POST ─>│ ─Write─> │ 💥 Дубль!
```

Из-за таймаута клиент делает автоматический повтор (`Retry`), и без защиты от дублей сервер спишет деньги дважды.

## Решение: `Idempotency-Key` в FastAPI

В продакшене (Stripe, маркетплейсы) клиент прикрепляет заголовок `Idempotency-Key` — уникальный UUID операции, по которому сервер кэширует первый итог:

```python
from fastapi import FastAPI, Header

app = FastAPI()

# В продакшене храним в Redis с TTL
store: dict[str, dict] = {}

@app.post('/payments')
def process_payment(
    amount: int,
    idempotency_key: str = Header(...),
):
    if idempotency_key in store:
        return store[idempotency_key]

    res = {'status': 'paid', 'amount': amount}
    store[idempotency_key] = res
    return res
```

## Защита от параллельной гонки (Race Condition)

Если пользователь сделал двойной клик и два запроса прилетели одновременно, проверка в обычной памяти не успеет сработать.

Для защиты применяют **распределённую блокировку** — при старте сервер атомарно ставит в Redis флаг обработки:

`SET lock:idem:<key> "processing" NX EX 30`

- Если ключ уже в статусе `processing`, второй параллельный запрос сразу отклоняется кодом **`409 Conflict`**.
- После коммита транзакции статус меняется на `completed`, а готовый JSON-ответ сохраняется с TTL (например, 24 часа).

## Гарантия на уровне БД (`UNIQUE`) и подход Junior vs Senior

Даже если Redis временно недоступен, последним рубежом защиты от двойного списания всегда выступает сама реляционная СУБД. В таблицу платежей или заказов добавляют колонку `idempotency_key` с уникальным индексом **`UNIQUE`** и контролем хеша тела запроса (`payload_hash`):

```sql
CREATE TABLE payments (
    id SERIAL PRIMARY KEY,
    idempotency_key UUID UNIQUE NOT NULL,
    amount INTEGER NOT NULL
);
```

Если клиент по ошибке отправил **тот же `Idempotency-Key`, но с другой суммой платежа**, сервер обязан вернуть ошибку **`422 Unprocessable Entity`** (или `409 Conflict`), чтобы не вернуть чужой закешированный ответ от другого набора параметров.

> **Junior vs Senior**:
> - **Junior**: Полагается на то, что фронтенд «задизейблит кнопку оплаты после первого клика», не проверяя дубли на бэкенде при сетевых ретраях мобильного клиента.
> - **Senior**: Требует `Idempotency-Key` для всех критичных `POST`/`PATCH` операций, сочетает быструю блокировку `SET ... NX` в Redis с `UNIQUE`-ограничением в PostgreSQL и сверяет хеш параметров запроса.
