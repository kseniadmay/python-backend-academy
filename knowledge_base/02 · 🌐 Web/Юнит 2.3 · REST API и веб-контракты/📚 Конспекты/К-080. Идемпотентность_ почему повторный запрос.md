## Математика и протокол: определение идемпотентности

В математике операция называется идемпотентной, если её повторное применение даёт тот же результат: $f(f(x)) = f(x)$.

В контексте HTTP **идемпотентность означает, что многократное выполнение идентичного запроса приводит к тому же состоянию сервера, что и однократное выполнение**.

> **Важно:** идемпотентность говорит о состоянии данных на сервере, а не о теле или статус-коде HTTP-ответа. Первый `DELETE /users/42` вернет `204 No Content`, а повторный `404 Not Found` — но состояние сервера идентично (пользователь удален).

## Карта методов HTTP: идемпотентные vs неидемпотентные

```text
Идемпотентные методы:
- GET /orders/42    => чтение
- HEAD /orders/42   => метаданные
- PUT /orders/42    => перезапись
- DELETE /orders/42 => удаление
- OPTIONS /orders   => опрос

Неидемпотентные методы:
- POST /orders      => новый заказ
- PATCH /orders/42  => дельта/инкремент
```

- `POST` принципиально не идемпотентен: отправка формы дважды создает две записи в базе данных.

## Проблема сетевых сбоев и повторов (Network Retries)

В распределенных системах сеть по определению ненадежна. Типичный сценарий аварии:

```text
Клиент            Сервер       БД
  │ ── POST /pay ──> │          │
  │                  │ ─Write─> │ (OK)
  │                  │ <─OK──── │
  │   ❌ Сбой сети   │
  │ (Timeout ответа) │
  │                  │
  │ ── Retry: POST ─>│ ─Write─> │ 💥 Дубль!
```

Клиент не получил ответ и делает автоматический повтор (Retry). Без специальной защиты сервер спишет деньги дважды.

## Решение: Idempotency-Key на базе Redis

Стандартное индустриальное решение (Stripe, эквайринги, маркетплейсы) — заголовок `Idempotency-Key` (уникальный UUID v4, генерируемый клиентом на каждую бизнес-операцию):

```python
from fastapi import (
    FastAPI, Header, HTTPException
)

app = FastAPI()

# В продакшене используем Redis
store = {}

@app.post("/payments")
def process_payment(
    amount: int,
    idempotency_key: str = Header(...)
):
    # Проверяем кэш ключей
    if idempotency_key in store:
        return store[
            idempotency_key
        ]

    res = {
        "status": "paid",
        "amount": amount
    }
    store[idempotency_key] = res
    return res
```

## Защита от Race Conditions и параллельных вызовов

Если два идентичных запроса прилетели одновременно (пользователь сделал двойной клик на кнопку), простая проверка ключа в памяти не поможет.

- **Распределенная блокировка (Distributed Lock):** при поступлении запроса сервер атомарно устанавливает блокировку в Redis:
  `SET lock:idem:<key> "processing" NX EX 30`
- Если ключ уже существует со статусом `processing`, второй параллельный запрос немедленно отклоняется с кодом **`409 Conflict`** («Операция уже обрабатывается»).
- После завершения транзакции статус ключа меняется на `completed`, а результат сохраняется в кэше с TTL (например, 24 часа).
