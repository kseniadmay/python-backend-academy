## Проблема HTTP: данные передаются открытым текстом

HTTP передаёт всё – пароли, токены, персональные данные – в незашифрованном виде. Любой узел на пути трафика: администратор публичного Wi-Fi, провайдер, злоумышленник с атакой «человек посередине» (MitM) – может прочитать и скопировать эти данные без каких-либо препятствий.

---

## HTTPS = HTTP + TLS

**HTTPS** – не новый протокол, а HTTP с добавленным криптографическим слоем **TLS** (Transport Layer Security). TLS шифрует данные до передачи, так что перехватчик видит лишь нечитаемый поток байтов.

**SSL** (Secure Sockets Layer) – предшественник TLS. Все версии SSL устарели и небезопасны. Реально используется TLS, но термин «SSL-сертификат» закрепился в индустрии как синоним и встречается повсеместно – даже в современных инструментах.

## TLS Handshake: как устанавливается защищённое соединение

Прежде чем данные начнут передаваться, браузер и сервер проходят процедуру **TLS Handshake** – согласование параметров защиты. Это ресурсоёмкая фаза, которая выполняется один раз при установке соединения.

Браузер отправляет **ClientHello**: список поддерживаемых версий TLS и алгоритмов шифрования. Сервер отвечает **ServerHello**: выбирает алгоритм и отправляет свой **сертификат**, содержащий публичный ключ. Браузер проверяет сертификат через цепочку доверия (Certificate Authority). Затем стороны используют **асимметричное шифрование** (публичный ключ сервера) для безопасного обмена секретом, из которого генерируется **симметричный сессионный ключ**. Все дальнейшие данные шифруются этим ключом.

Асимметричное шифрование используется только для обмена секретом – оно вычислительно дорогое. После handshake всё общение идёт через симметричное шифрование, которое быстрее на порядок. Именно поэтому HTTPS практически не добавляет заметной задержки для пользователя.

## SSL-сертификат: цифровой паспорт сервера

Сертификат выполняет две функции. Во-первых, подтверждает, что сервер действительно принадлежит заявленному домену. Во-вторых, содержит публичный ключ, используемый при handshake.

Браузер доверяет сертификату через **цепочку доверия**: в каждый браузер и операционную систему предустановлен список корневых **Certificate Authorities** (CA) – организаций, которым индустрия доверяет подписывать сертификаты. Когда сервер предъявляет сертификат, браузер проверяет подпись CA. Если подпись валидна и CA в списке доверенных – соединение считается безопасным.

Популярные CA: **Let's Encrypt** (бесплатный, автоматизированный, стандарт для большинства проектов), DigiCert, Comodo.

## Три гарантии HTTPS

- 1. **Шифрование** – данные нечитаемы без сессионного ключа, даже если трафик перехвачен.
- 2. **Аутентификация** – сертификат подтверждает, что вы общаетесь именно с тем сервером, чей домен указан, а не с подменным.
- 3. **Целостность** – данные не могут быть незаметно изменены по пути: любое изменение шифротекста ломает проверку целостности.

---

## Важное ограничение

HTTPS защищает только канал передачи данных. Он гарантирует, что никто не подслушает разговор между вами и сервером, но не гарантирует, что сам сервер легитимен. Злоумышленник может получить сертификат для фишингового домена – и браузер покажет «замочек». Всегда проверяйте доменное имя, даже при наличии HTTPS.

На собеседовании важно понимать разницу между TLS и SSL, уметь объяснить TLS Handshake и зачем используются два типа шифрования. Также часто спрашивают про цепочку доверия и роль CA.
