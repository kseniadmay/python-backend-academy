## Проблема Stateless: как идентифицировать клиента

Протокол HTTP по своей природе не сохраняет состояние (**Stateless**): каждый запрос сервер видит как абсолютно новый.

Чтобы связывать запросы одного пользователя в сессию, сервер и браузер используют пару заголовков:

1. **Сервер** создаёт случайный криптостойкий `session_id` и передаёт его в заголовке `Set-Cookie`.
2. **Браузер** сохраняет куку и сам прикладывает её в заголовке `Cookie` ко всем дальнейшим запросам этого домена.

## Флаги безопасности Cookie: `HttpOnly`, `Secure`, `SameSite`

Ошибки настройки кук открывают путь для кражи сессии через XSS или подделки запросов CSRF:

```http
Set-Cookie: sid=a8f01b3c9;
  HttpOnly; Secure;
  SameSite=Lax; Max-Age=86400; Path=/
```

Защитные директивы в заголовке `Set-Cookie` задают строгие ограничения на хранение и отправку куки:

| Директива | Защита и поведение в браузере |
| :--- | :--- |
| **`HttpOnly`** | Закрывает доступ из `document.cookie` — XSS не сможет прочитать токен |
| **`Secure`** | Отправляет куку только по шифрованному HTTPS |
| **`SameSite=Strict`** | Передаёт куку лишь при переходах внутри того же сайта |
| **`SameSite=Lax`** | Разрешает отправку и при переходе по внешней `GET`-ссылке (дефолт CSRF) |
| **`SameSite=None`** | Разрешает любые сторонние запросы, но строго требует `Secure` |
| **`Max-Age` / `Expires`** | Время жизни куки; без них кука удаляется после закрытия браузера |

## Архитектура серверных сессий: `session_id` и Redis

Кука ограничена **4 КБ** и не должна хранить секретные или тяжёлые поля (баланс, роли) прямо на клиенте.

В паттерне **Stateful-сессий** все данные лежат на сервере в быстром хранилище (Redis или БД), а в куке ездит лишь случайный ключ `session_id` для чтения за $O(1)$:

```text
[Клиент] ──Cookie: sid──> [FastAPI]
                            │ (get sid)
                            ▼
                         [Redis]
```

## Реализация сессий в Django (`SessionMiddleware`)

В Django встроенный механизм сессий хранит словарь `request.session` на сервере и позволяет обновлять ключ после входа:

```python
from django.http import (
    HttpRequest, HttpResponse
)

def login_view(
    request: HttpRequest
) -> HttpResponse:
    request.session['user_id'] = 42
    request.session['cart'] = ['book']

    # Ротация ID от Session Fixation
    request.session.cycle_key()
    return HttpResponse('OK')
```

Вызов `cycle_key()` обязателен после аутентификации, чтобы злоумышленник не подменил жертве заранее известный `session_id`.

## Cookie-сессии против Stateless JWT: матрица выбора

Выбор между хранением состояния на сервере и подписанным токеном у клиента определяет простоту отзыва доступа:

| Критерий | Stateful Session (Cookie + Redis) | Stateless JWT (Bearer Token) |
| :--- | :--- | :--- |
| **Хранилище** | Сервер (Redis / DB) | Клиент (память / localStorage) |
| **Отзыв прав** | Мгновенно (удалить ключ из Redis) | Затруднён до истечения TTL |
| **Размер** | Минимальный (~32 байта UUID) | Большой (~500+ байт) |
| **Применение** | Web SPA, монолиты | Микросервисы, межсервисные вызовы |

> **Junior vs Senior**:
> - **Junior**: выставляет сессионные куки без флагов `HttpOnly`/`Secure`/`SameSite` или выпускает долгоживущий JWT без стратегии экстренного отзыва прав.
> - **Senior**: защищает клиентские cookie строгими флагами, хранит отзываемые сессии в быстром сервере вроде Redis и взвешенно выбирает между stateful-сессиями и stateless JWT по требованиям к масштабу и безопасности.
