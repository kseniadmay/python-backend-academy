## Проблема Stateless: как идентифицировать клиента

Протокол HTTP не сохраняет состояние между отдельными запросами (**Stateless**). Сервер воспринимает каждый запрос как изолированное действие и не знает контекста предыдущих шагов клиента.

Для связывания действий пользователя в непрерывную сессию используется тандем:
1. **Сервер** генерирует уникальный криптостойкий идентификатор сессии (`session_id`) и отправляет его браузеру в заголовке `Set-Cookie`.
2. **Браузер** сохраняет куку и автоматически прикрепляет её в заголовке `Cookie` ко всем последующим запросам к этому домену.

## Флаги безопасности Cookie: HttpOnly, Secure, SameSite

Неправильно настроенная Cookie — главная цель атак XSS и CSRF. Продакшен-стандарты требуют обязательной установки защитных директив:

```http
Set-Cookie: sid=a8f01b3c9;
  HttpOnly; Secure;
  SameSite=Lax; Max-Age=86400; Path=/
```

- **`HttpOnly`:** блокирует доступ к куке из JavaScript (`document.cookie`). Даже если злоумышленник внедрил вредоносный XSS-скрипт, он не сможет прочесть сессионный токен.
- **`Secure`:** предписывает браузеру передавать куку строго по защищенному каналу HTTPS.
- **`SameSite` (защита от CSRF):**
  * `Strict` — кука передается только при прямых переходах внутри исходного сайта;
  * `Lax` — кука передается также при безопасных входящих переходах по ссылкам (`GET`), дефолт для браузеров;
  * `None` — кука передается в любых сторонних встраиваниях (требует флага `Secure`).
- **`Max-Age` / `Expires`:** задает время жизни куки в секундах. Без них кука является сессионной и удаляется при закрытии браузера.

## Архитектура серверных сессий: session_id и быстрый Storage

Кука ограничена размером в **4 КБ** и не должна хранить конфиденциальные данные (права, баланс, пароли), так как данные на клиенте подвержены компрометации.

- **Stateful сессия:**
  * Все данные состояния (корзина, роли, ID пользователя) хранятся в серверном хранилище (Redis, memcached, СУБД).
  * В куке клиента циркулирует только непрозрачный случайный ключ `session_id`.
  * При получении запроса бэкенд мгновенно извлекает состояние из Redis по ключу за $O(1)$.

```text
[Клиент] ──Cookie: sid──> [FastAPI]
                            │ (get sid)
                            ▼
                         [Redis]
```

## Реализация сессий в Python

Django предоставляет зрелый встроенный механизм `SessionMiddleware`:

```python
from django.http import (
    HttpRequest, HttpResponse
)

def login_view(
    request: HttpRequest
) -> HttpResponse:
    # Запись в сессию Django
    request.session['user_id'] = 42
    request.session['cart'] = ['book']
    # Ротация ключа от Session Fixation
    request.session.cycle_key()
    return HttpResponse("OK")
```

При аутентификации всегда вызывайте ротацию идентификатора сессии (`cycle_key()` в Django), чтобы злоумышленник не мог навязать жертве свой заранее заготовленный `session_id`.

## Cookie-сессии vs Stateless JWT: матрица выбора

| Критерий | Stateful Session (Cookie + Redis) | Stateless JWT (Bearer Token) |
| :--- | :--- | :--- |
| **Хранилище** | Сервер (Redis / DB) | Клиент (память / local) |
| **Отзыв прав** | Мгновенно (удалить ключ из Redis) | Затруднен до истечения TTL |
| **Размер** | Минимальный (~32 байта UUID) | Большой (~500+ байт) |
| **Горизонт** | Идеально для Web SPA / монолитов | Идеально для микросервисов |
