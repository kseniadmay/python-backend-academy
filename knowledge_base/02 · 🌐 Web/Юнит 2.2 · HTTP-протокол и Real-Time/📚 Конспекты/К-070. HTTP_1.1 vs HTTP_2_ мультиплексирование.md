## Ограничения HTTP/1.1: Head-of-Line Blocking

Протокол HTTP/1.1 (1997 г.) является текстовым и работает по принципу «один запрос — один ответ» в рамках одного TCP-сокета:

- **Head-of-Line (HoL) Blocking:** если первый запрос в очереди завис (тяжелый SQL-запрос или медленный ответ), все последующие запросы за ним блокируются.
- **Хрупкие костыли веб-разработки:** чтобы обойти HoL-blocking, браузеры открывают до 6 параллельных TCP-соединений к одному домену, а фронтендеры объединяли картинки в CSS-спрайты, собирали монолитные JS-бандлы и шардировали домены (`cdn1.site.com`, `cdn2.site.com`). Это увеличивало нагрузку на ядро ОС и расход памяти.

## Ядро HTTP/2: бинарные фреймы и мультиплексирование

HTTP/2 (2015 г.) сохранил семантику HTTP (методы, статус-коды, заголовки), но полностью переработал транспортный слой:

- **Бинарный протокол:** вместо парсинга строк и пробелов данные упаковываются в бинарные фреймы фиксированной длины (HEADERS, DATA, SETTINGS).
- **Мультиплексирование (Multiplexing):** через **единственное TCP-соединение** клиент и сервер параллельно передают сотни независимых двунаправленных логических потоков (**Streams**). Фреймы разных потоков перемежаются в канале и собираются получателем по `Stream ID`.

```text
TCP-соединение (мультиплекс):
  ├─ [Stream 1: Data Chunks]
  ├─ [Stream 3: Headers Frame]
  └─ [Stream 1: Data Chunks]
```

Один медленный запрос больше не блокирует передачу других ресурсов.

## Сжатие заголовков: алгоритм HPACK

В HTTP/1.1 каждый запрос передает избыточные повторяющиеся заголовки (`User-Agent`, `Cookie`, `Authorization`), расходуя килобайты трафика.

- **HPACK:** алгоритм сжатия, использующий статическую (61 предопределенный частый заголовок) и динамическую таблицы на обоих концах соединения.
- При повторном запросе вместо передачи полного текста передается короткий числовой индекс таблицы. Размер заголовков сжимается более чем на **85%**.

## Приоритизация и депрекейшн Server Push

- **Приоритизация потоков (Stream Weight):** клиент указывает относительный вес и зависимости потоков. Критичные файлы (CSS, главный HTML) загружаются раньше второстепенных картинок.
- **Судьба Server Push:** механизм позволял серверу проактивно отправлять ресурсы (например, `style.css` вместе с `index.html`). На практике он создавал гонки кэша и перерасход трафика мобильных клиентов, поэтому в современных спецификациях и Chrome Server Push был отключен.

## Эволюция к HTTP/3: протокол QUIC поверх UDP

Мультиплексирование HTTP/2 решило HoL-blocking на прикладном уровне, но на уровне TCP проблема осталась: при потере одного IP-пакета всё TCP-соединение останавливается операционной системой до повторной доставки пакета (TCP Retransmission).

- **HTTP/3 (QUIC поверх UDP):** переносит потоки внутрь протокола QUIC. Потеря пакета в Stream 1 не задерживает чтение Stream 2.
- **Мгновенное переподключение (Connection Migration):** при переключении смартфона с Wi-Fi на 4G соединение не рвется, так как QUIC идентифицирует сессию по Connection ID, а не по IP-адресу.
