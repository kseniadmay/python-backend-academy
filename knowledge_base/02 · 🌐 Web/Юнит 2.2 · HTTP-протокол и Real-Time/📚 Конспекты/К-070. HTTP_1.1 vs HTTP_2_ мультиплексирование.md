## HTTP/1.1: проблема Head-of-Line Blocking

В HTTP/1.1 запросы в рамках одного TCP-соединения обрабатываются последовательно: следующий запрос не отправляется, пока не получен ответ на предыдущий. Это называется **Head-of-Line Blocking** – если один запрос «завис», вся очередь стоит.

Браузеры обходили это ограничение, открывая 6-8 параллельных TCP-соединений на один домен. Это работало, но создавало накладные расходы: каждое TCP-соединение требует **трёхстороннего рукопожатия** (three-way handshake) и фазы медленного старта (slow start) – TCP нарочно начинает передачу осторожно, постепенно увеличивая скорость. Восемь соединений – восемь таких фаз одновременно.

## HTTP/2: мультиплексирование в одном соединении

HTTP/2 (2015) устраняет очередь через **мультиплексирование**: данные нарезаются на небольшие фреймы внутри независимых **потоков** (streams) и передаются параллельно через одно TCP-соединение. Фреймы от разных потоков перемежаются в одном канале и собираются на принимающей стороне.

Результат: сотни запросов и ответов обрабатываются параллельно без создания дополнительных TCP-соединений и без накладных расходов на handshake.

## Четыре дополнительных улучшения HTTP/2

- 1. **Бинарный протокол.** HTTP/1.1 – текстовый: парсер ищет символы переноса строки и пробелы, чтобы разграничить заголовки. HTTP/2 упаковывает данные в бинарные фреймы фиксированной структуры. Парсер знает точную позицию каждого поля – обработка быстрее и надёжнее.
- 2. **Сжатие заголовков (HPACK).** В HTTP/1.1 каждый запрос несёт полный набор заголовков: `Cookie`, `User-Agent`, `Authorization` – одинаковых при каждом запросе. HPACK строит таблицу заголовков на обоих концах соединения: если заголовок уже встречался, вместо него передаётся короткий индекс. Повторяющиеся заголовки сжимаются практически до нуля.
- 3. **Приоритизация потоков.** Клиент может указать серверу приоритет каждого потока. CSS, блокирующий рендеринг, получает высокий приоритет и передаётся первым. Картинка в подвале страницы – низкий, передаётся когда канал свободен. Пользователь видит контент раньше, даже если все ресурсы ещё не загружены.
- 4. **Server Push.** Сервер может отправить ресурсы проактивно, не дожидаясь явного запроса. Получив запрос на `index.html`, сервер знает, что браузеру понадобятся `style.css` и `app.js`, и отправляет их сразу. Браузеру не нужно сначала разобрать HTML, потом запросить зависимости – они уже в кеше к тому моменту, как он о них «узнал».

На практике Server Push требует тонкой настройки: если отправить ресурсы, которые уже есть в кеше браузера – трафик потрачен впустую. В HTTP/3 Server Push фактически не используется.

## Ключевое условие: только через HTTPS

Современные браузеры поддерживают HTTP/2 исключительно поверх TLS. HTTP/2 по незашифрованному соединению технически возможен (называется h2c), но браузеры его не реализуют. Таким образом, переход на HTTP/2 автоматически означает наличие HTTPS.

## HTTP/3: следующий шаг

HTTP/2 решил проблему Head-of-Line Blocking на уровне HTTP, но не на уровне TCP: если один TCP-пакет теряется, все потоки внутри соединения блокируются до его повторной передачи. **HTTP/3** заменяет TCP на **QUIC** – протокол поверх UDP с встроенным шифрованием и независимыми потоками на транспортном уровне. Потеря пакета в одном потоке не блокирует остальные. HTTP/3 критически важен для мобильных сетей с нестабильным соединением, где потеря пакетов – норма.
