## Ограничения HTTP/1.1: Head-of-Line Blocking

Текстовый протокол HTTP/1.1 работает в одном TCP-сокете по правилу «один запрос — один ответ», из-за чего возникает узкое горлышко:

- **Head-of-Line (HoL) Blocking:** пока первый тяжёлый запрос ждёт ответа от сервера, все следующие запросы в том же соединении простаивают в очереди.
- **Костыли эпохи HTTP/1.1:** чтобы обойти блокировку, браузеры открывали до 6 параллельных TCP-соединений на домен, а фронтенд склеивал CSS-спрайты, бандлы и шардировал статику на `cdn1`, `cdn2`.

## Ядро HTTP/2: бинарные фреймы и мультиплексирование

HTTP/2 сохранил методы, статусы и заголовки HTTP, но перевёл транспорт на бинарное кадрирование поверх **одного TCP-соединения**:

- Данные разбиваются на бинарные фреймы (`HEADERS`, `DATA`) с 9-байтовым заголовком и идентификатором потока `Stream ID`.
- Сотни независимых потоков (**Streams**) передаются вперемешку по одному TCP-сокету (**мультиплексирование**), поэтому один медленный ответ больше не тормозит остальные ресурсы:

```text
TCP-соединение (мультиплекс):
  ├─ [Stream 1: Data Chunks]
  ├─ [Stream 3: Headers Frame]
  └─ [Stream 1: Data Chunks]
```

На стороне получателя фреймы просто группируются обратно по их `Stream ID`:

```python
frames = [
    (1, 'DATA-A1'),
    (2, 'DATA-B1'),
    (1, 'DATA-A2'),
]

# Демультиплексирование потоков по Stream ID
streams = {1: [], 2: []}
for sid, chunk in frames:
    streams[sid].append(chunk)

print(streams[1])
# >>> ['DATA-A1', 'DATA-A2']

print(streams[2])
# >>> ['DATA-B1']
```

## Сжатие заголовков: алгоритм HPACK

В HTTP/1.1 каждый запрос заново слал объёмные повторяющиеся заголовки (`User-Agent`, `Cookie`, `Authorization`), тратя лишние килобайты.

Алгоритм **HPACK** поддерживает на обеих сторонах статическую и динамическую таблицы: вместо полного текста заголовка при повторе передаётся короткий числовой индекс, сжимая заголовки более чем на 85%.

## Приоритизация потоков и судьба Server Push

В HTTP/2 клиент и сервер могут дополнительно управлять очередью передачи ресурсов:

- **Приоритизация потоков:** клиент задаёт веса зависимостей, чтобы критичные HTML и CSS приходили раньше картинок.
- **Отказ от Server Push:** идея заранее досылать файлы вместе с `index.html` создавала конфликты кэша и лишний мобильный трафик, поэтому современные браузеры (включая Chrome) убрали поддержку Server Push.

## Эволюция к HTTP/3: протокол QUIC поверх UDP

Мультиплексирование HTTP/2 убрало блокировку на уровне HTTP, но на уровне TCP при потере одного IP-пакета ОС всё равно останавливает все потоки до повторной доставки.

Протокол **HTTP/3** решает эту проблему, перенося потоки поверх **QUIC (UDP)**:

- **Независимые потоки:** потеря пакета в `Stream 1` не задерживает чтение `Stream 2`.
- **Connection Migration:** при переходе смартфона с Wi-Fi на LTE соединение не рвётся, так как сессия привязана к `Connection ID`, а не к IP-адресу.
