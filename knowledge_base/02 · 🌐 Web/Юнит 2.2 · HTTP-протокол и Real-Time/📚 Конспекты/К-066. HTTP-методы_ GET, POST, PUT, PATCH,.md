## Безопасность (`Safety`) и идемпотентность методов

Архитектура HTTP-методов строится на двух ключевых свойствах:

- **Безопасность (Safety):** метод не меняет состояние сервера и данные в БД (`GET`, `HEAD`, `OPTIONS`).
- **Идемпотентность (Idempotency):** повторный вызов запроса с теми же данными даёт то же конечное состояние системы: $f(f(x)) = f(x)$.

Сводная матрица основных HTTP-методов по обоим свойствам:

| Метод | Назначение | Safe | Idempotent |
| :--- | :--- | :---: | :---: |
| `GET` | Чтение ресурса | ✅ Да | ✅ Да |
| `HEAD` | Только заголовки | ✅ Да | ✅ Да |
| `POST` | Создание сущности | ❌ Нет | ❌ Нет |
| `PUT` | Полная замена | ❌ Нет | ✅ Да |
| `PATCH` | Частичная дельта | ❌ Нет | ⚠️ Зависит |
| `DELETE` | Удаление ресурса | ❌ Нет | ✅ Да |
| `OPTIONS` | Доступные методы | ✅ Да | ✅ Да |

## Чтение ресурсов: `GET` и `HEAD`

Метод `GET` выбирает данные без побочных эффектов, передавая параметры в строке запроса (*Query String*):

```http
GET /api/v1/users?page=1&limit=20
Host: api.example.com
Accept: application/json
```

Ответы `GET` кэшируются браузерами и CDN через `Cache-Control` / `ETag`, а `HEAD` возвращает те же заголовки без тела — удобно для проверки наличия и размера файла (`Content-Length`).

## Создание и замена: `POST` против `PUT`

**`POST` (не идемпотентен)** создаёт новый подчинённый ресурс или запускает вычисление — повторный запрос создаст вторую запись:

```http
POST /api/v1/orders
Content-Type: application/json

{"user_id": 42, "item_id": 105}
```

**`PUT` (идемпотентен)** полностью заменяет ресурс по указанному URI; если какое-то поле в теле пропустить, оно сотрётся или сбросится в дефолт:

```http
PUT /api/v1/users/42
Content-Type: application/json

{
  "name": "Alice Smith",
  "email": "alice@example.com",
  "role": "admin"
}
```

Наглядное отличие поведения повторного вызова между неидемпотентным и идемпотентным действиями:

```python
state = {'counter': 0, 'status': 'draft'}

# POST: повтор меняет итог снова
state['counter'] += 1
state['counter'] += 1

# PUT: повтор даёт то же состояние
state['status'] = 'published'
state['status'] = 'published'

print(state['counter'], state['status'])
# >>> 2 published
```

## Частичное обновление и удаление: `PATCH` и `DELETE`

**`PATCH`** передаёт только изменившиеся поля ресурса (JSON Merge Patch, RFC 7396):

```http
PATCH /api/v1/users/42
Content-Type: application/json

{"email": "new_alice@example.com"}
```

- При передаче фиксированного поля (`{"status": "active"}`) `PATCH` идемпотентен, но при операции инкремента (`+100`) — нет, поэтому спецификация не гарантирует его идемпотентность.
- **`DELETE` (идемпотентен):** удаляет ресурс; первый запрос вернёт `204`/`200`, повторный — `404`, но состояние сервера одно и то же: ресурса больше нет.

## Служебный метод `OPTIONS` и CORS Preflight

Метод `OPTIONS` запрашивает у сервера список допустимых методов для URI без выполнения бизнес-логики:

```http
OPTIONS /api/v1/orders
Host: api.example.com
```

Сервер отвечает допустимым набором в заголовке `Allow` (именно так браузер запускает предварительный **CORS Preflight** перед сложными запросами с `Authorization`, `PUT`, `PATCH`, `DELETE`):

```http
HTTP/1.1 204 No Content
Allow: GET, POST, HEAD, OPTIONS
```

## Инженерные ловушки на собеседовании

При проектировании HTTP-ручек критично избегать двух частых архитектурных ошибок:

- ❌ **Мутация через `GET` (`GET /users/delete?id=1`):** поисковые краулеры или предзагрузка ссылок браузера удалят данные простым переходом.
- ❌ **Дубли при повторе `POST`:** при обрыве сети клиент шлёт `POST /payments` повторно — для защиты от двойного списания используют заголовок `Idempotency-Key` и кэш в Redis.

> **Junior vs Senior**:
> - **Junior**: удаляет и создаёт данные по `GET`-запросу, игнорирует идемпотентность и путает полную замену ресурса `PUT` с частичным патчем `PATCH`.
> - **Senior**: проектирует HTTP-контракты по правилам `Safety` и идемпотентности (защищает неидемпотентный `POST` ключом идемпотентности) и учитывает служебные запросы `OPTIONS` для CORS.
