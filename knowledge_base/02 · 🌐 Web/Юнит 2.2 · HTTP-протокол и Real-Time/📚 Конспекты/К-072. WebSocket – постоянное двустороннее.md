## Природа WebSocket: Full-Duplex поверх одного TCP

Традиционный HTTP работает по схеме «Запрос — Ответ», где сервер не может сам написать клиенту первым.

Для чатов, биржевых стаканов и live-уведомлений постоянное переоткрытие HTTP неэффективно, поэтому применяют три механизма:

- **Polling:** клиент сам опрашивает `GET /status` по таймеру, плодя лишний трафик заголовков.
- **Server-Sent Events (SSE):** однонаправленный поток событий от сервера к клиенту поверх HTTP.
- **WebSocket (RFC 6455):** двусторонний (*Full-Duplex*) канал обмена фреймами поверх одного TCP с оверхедом всего `2–10` байт.

## Протокольный апгрейд: `HTTP 101 Switching Protocols`

Соединение начинается как обычный HTTP-запрос по стандартным портам 80/443, поэтому без проблем проходит сквозь прокси и файрволы:

```http
GET /chat HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

Сервер подтверждает переключение протокола статусом `101 Switching Protocols`:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept:
  s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

После ответа `101` соединение переходит в бинарный обмен фреймами по схеме `ws://` или защищённой `wss://`.

## Сервер на FastAPI: асинхронный эхо-цикл

FastAPI поддерживает WebSocket нативно через Starlette — `await ws.receive_text()` освобождает цикл событий на время ожидания сообщения:

```python
from fastapi import (
    FastAPI, WebSocket,
    WebSocketDisconnect
)

app = FastAPI()

@app.websocket('/ws/chat')
async def chat_socket(ws: WebSocket):
    # Подтверждаем рукопожатие 101
    await ws.accept()
    try:
        while True:
            msg = await ws.receive_text()
            await ws.send_text(f'Echo: {msg}')
    except WebSocketDisconnect:
        pass
```

## Масштабирование: брокер Redis Pub/Sub

Если бэкенд запущен в нескольких процессах воркеров, Клиент A и Клиент B могут оказаться на разных процессах без общей памяти:

```text
[Клиент A] ─ws─> [Воркер 1] ─┐
                             ├──> [Redis]
[Клиент B] ─ws─> [Воркер 2] ─┘
```

Чтобы доставлять сообщения между воркерами, используют шину сообщений **Redis Pub/Sub**:

1. Воркер публикует входящее событие в общий канал `redis.publish('chat', message)`.
2. Все воркеры подписаны на этот канал и рассылают событие своим подключённым WebSocket-клиентам.

## Стабильность соединения: Heartbeat (`Ping` / `Pong`)

Сетевые маршрутизаторы и мобильные операторы часто молча обрывают «тихие» TCP-соединения по таймауту (*dead socket*).

- Протокол WebSocket предусматривает лёгкие контрольные фреймы **`Ping` (0x9)** и **`Pong` (0xA)**.
- Сервер периодически шлёт `Ping`, а клиент должен сразу ответить `Pong`.
- При отсутствии ответа (например, дольше 30 секунд) сервер закрывает сокет и освобождает память.
