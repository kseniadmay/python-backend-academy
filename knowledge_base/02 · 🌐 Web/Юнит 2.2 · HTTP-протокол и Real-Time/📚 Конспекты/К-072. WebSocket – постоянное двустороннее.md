## Природа WebSocket: Full-Duplex поверх одного TCP

Традиционный HTTP работает по модели «Запрос — Ответ» (полудуплекс). Для интерактивных сервисов (чаты, торговые терминалы, совместные редакторы) оверхед на постоянное открытие соединений неприемлем:

- **Polling:** периодический опрос `GET /status` каждые 2 сек создает паразитный трафик заголовков.
- **Server-Sent Events (SSE):** однонаправленный поток событий от сервера к клиенту поверх HTTP.
- **WebSocket (RFC 6455):** полнодуплексный (Full-Duplex) протокол постоянного обмена сообщениями в реальном времени. После рукопожатия клиент и сервер в любой момент отправляют фреймы данных с оверхедом всего в **2–10 байт** на сообщение.

## Протокольный апгрейд: HTTP 101 Switching Protocols

Соединение всегда начинается как стандартный HTTP-запрос (по портам 80/443), что гарантирует беспрепятственное прохождение через корпоративные прокси и файрволы:

```http
GET /chat HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZQ==
Sec-WebSocket-Version: 13
```

Сервер подтверждает смену протокола ответом `101 Switching Protocols`:
```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept:
  s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

После этого сокет переключается в бинарный режим кадрирования WebSocket (`ws://` или защищенный `wss://`).

## Сервер на FastAPI: приём соединений и асинхронный эхо-цикл

FastAPI предоставляет нативную асинхронную поддержку WebSocket через Starlette:

```python
from fastapi import (
    FastAPI, WebSocket,
    WebSocketDisconnect
)

app = FastAPI()

@app.websocket('/ws/chat')
async def chat_socket(ws: WebSocket):
    # Завершаем рукопожатие 101
    await ws.accept()
    try:
        while True:
            # Неблокирующее чтение
            msg = await ws.receive_text()
            await ws.send_text(f"Echo: {msg}")
    except WebSocketDisconnect:
        # Штатное закрытие клиентом
        pass
```

Метод `receive_text()` освобождает Event Loop, пока клиент не пришлет новые данные.

## Масштабирование: брокер Redis Pub/Sub

В продакшене бэкенд запускается в нескольких процессах воркеров за балансировщиком. Если Клиент A подключен к Воркеру 1, а Клиент B к Воркеру 2, прямая отправка в памяти невозможна.

```text
[Клиент A] ─ws─> [Воркер 1] ─┐
                             ├──> [Redis]
[Клиент B] ─ws─> [Воркер 2] ─┘
```

1. Воркер принимает сообщение и публикует его в канал Redis: `redis.publish('chat', message)`.
2. Все воркеры подписаны на канал и транслируют событие своим локальным WebSocket-клиентам.

## Стабильность соединения: Heartbeat (Ping/Pong)

Сетевое оборудование (NAT-маршрутизаторы, файрволы, мобильные операторы) молча закрывает неактивные TCP-соединения по таймауту (dead socket).

- Протокол WebSocket включает служебные фреймы **`Ping` (0x9)** и **`Pong` (0xA)**.
- Сервер регулярно отправляет `Ping`, клиент обязан мгновенно ответить `Pong`.
- Если за заданный интервал (например, 30 сек) ответ не получен, сокет считается оборванным и сервер безопасно очищает связанные ресурсы памяти.
