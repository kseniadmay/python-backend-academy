## Проблема, которую решает WebSocket

HTTP устроен по модели «запрос – ответ»: клиент всегда инициирует обмен, сервер не может сам отправить данные клиенту без нового запроса от него. Для задач, где сервер должен проактивно присылать обновления – чат в реальном времени, живые котировки, уведомления, онлайн-игры – это создаёт проблему. Раньше её решали костылями вроде **long polling** (клиент держит HTTP-запрос открытым, пока сервер не ответит, и сразу переоткрывает новый) – рабочий, но неэффективный подход с постоянными накладными расходами на установку соединений.

**WebSocket** – отдельный протокол, который устанавливает одно постоянное, двустороннее (full-duplex) соединение между клиентом и сервером: обе стороны могут отправлять сообщения в любой момент, не дожидаясь запроса от другой стороны.

## Handshake: WebSocket начинается как HTTP

Соединение WebSocket всегда начинается с обычного HTTP-запроса со специальными заголовками, сигнализирующими серверу о желании «переключить протокол»:

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

Если сервер поддерживает WebSocket на этом маршруте, он отвечает статусом `101 Switching Protocols`:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

После этого рукопожатия протокол на этом TCP-соединении меняется: HTTP-обмен запрос-ответ заканчивается, и то же самое TCP-соединение начинает использоваться для WebSocket-фреймов в обе стороны, без повторных HTTP-заголовков на каждое сообщение.

## Схема протокола `ws://` и `wss://`

WebSocket-адреса используют собственную схему URL: **`ws://`** – незашифрованное соединение (аналог `http://`), **`wss://`** – соединение поверх TLS (аналог `https://`), обязательный стандарт для production. `wss://echo.example.com/socket` – типичный адрес WebSocket-эндпоинта.

## WebSocket в FastAPI

```python
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()

@app.websocket('/ws/chat')
async def chat_endpoint(websocket: WebSocket):
    await websocket.accept()
    try:
        while True:
            message = await websocket.receive_text()
            await websocket.send_text(f'Эхо: {message}')
    except WebSocketDisconnect:
        print('Клиент отключился')
```

`websocket.accept()` завершает handshake и открывает соединение. Дальше – бесконечный цикл: `receive_text()` асинхронно ждёт следующее сообщение от клиента (не блокируя event loop – другие соединения продолжают обрабатываться), `send_text()` отправляет ответ. `WebSocketDisconnect` – штатное исключение, которое нужно ловить, когда клиент закрывает соединение (закрыл вкладку, потерял сеть).

## Broadcast: рассылка всем подключённым клиентам

Для чатов и уведомлений нужно хранить список активных соединений и рассылать сообщение всем сразу:

```python
connected_clients: list[WebSocket] = []

@app.websocket('/ws/broadcast')
async def broadcast_endpoint(websocket: WebSocket):
    await websocket.accept()
    connected_clients.append(websocket)
    try:
        while True:
            message = await websocket.receive_text()
            for client in connected_clients:
                await client.send_text(message)
    except WebSocketDisconnect:
        connected_clients.remove(websocket)
```

В production такое хранение соединений в памяти одного процесса не масштабируется на несколько серверов – для этого используют Redis Pub/Sub или аналогичный брокер, чтобы сообщение, отправленное через один инстанс приложения, доходило до клиентов, подключённых к другому инстансу.

## WebSocket vs HTTP polling vs Server-Sent Events

**HTTP polling** – клиент периодически спрашивает сервер «есть что-то новое?»: просто, но с задержкой и лишней нагрузкой на пустые ответы. **Server-Sent Events (SSE)** – однонаправленный канал сервер → клиент поверх обычного HTTP, проще WebSocket, но клиент не может отправлять данные обратно по тому же каналу. **WebSocket** – полностью двусторонний канал, оптимален, когда обеим сторонам нужно инициировать сообщения: чаты, совместное редактирование, многопользовательские игры.

---

## Когда использовать

WebSocket оправдан для задач, требующих низкой задержки и двусторонней связи в реальном времени: чаты, торговые терминалы с live-котировками, live-уведомления, коллаборативные редакторы, real-time дашборды. Для сценариев, где серверу достаточно только присылать обновления клиенту (лента новостей, прогресс долгой операции), часто достаточно более простого SSE. Для классических запрос-ответ операций (создать пользователя, получить список заказов) WebSocket избыточен – там достаточно обычного REST.
