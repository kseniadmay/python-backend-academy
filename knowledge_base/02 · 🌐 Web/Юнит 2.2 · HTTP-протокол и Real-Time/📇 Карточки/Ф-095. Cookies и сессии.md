1. От каких типов атак защищает комбинация флагов куки HttpOnly и Secure? >> `HttpOnly` – от XSS; `Secure` – от перехвата по HTTP (MITM)
2. Каково назначение атрибута HttpOnly у HTTP-куки? >> Запрещает доступ к куке через JavaScript; защищает от кражи при XSS-атаках
3. Почему флаг HttpOnly защищает от XSS, но совершенно НЕ защищает от CSRF-атак? >> Скрывает куки от JavaScript, но не мешает браузеру автоматически прикреплять их к запросам с других сайтов
4. Что такое атака Session Fixation (фиксация сессии) и как от неё защититься? >> Злоумышленник навязывает жертве известный ему `session_id` ; после авторизации жертвы получает доступ к её сессии; защита – regenerate session ID после логина
5. Для чего предназначен атрибут SameSite у Cookies и какие 3 значения он может принимать? >> Защита от CSRF; ограничивает передачу кук при межсайтовых запросах
6. Какая проблема при хранении сессий в памяти одного сервера? >> Данные недоступны при запросе к другому серверу кластера (sticky sessions)
7. Для чего `Domain` и `Path` в настройках кук? >> Ограничивают область видимости куки конкретными поддоменами и путями
8. Что делает `login(request, user)` в Django? >> Создаёт сессию в хранилище и добавляет `Set-Cookie: session_id` в ответ
9. Компоненты заголовка `Set-Cookie` с максимальной защитой? >> `Set-Cookie: session_id=value; HttpOnly; Secure; SameSite=Strict`
10. При каком условии браузер отправит куку с атрибутом `Secure` ? >> Только по HTTPS
11. Почему HTTP называют stateless? >> Каждый запрос обрабатывается независимо; сервер не хранит состояние между запросами
12. Что передаётся клиенту при авторизации на основе сессий? >> Уникальный `session_id` ; сами данные пользователя хранятся на сервере
13. Как браузер передаёт куки серверу? >> Автоматически добавляет заголовок `Cookie` ко всем запросам на тот же домен
14. Какая настройка `SameSite` позволяет передавать куки сторонним сайтам? >> `SameSite=None` ; требует атрибута `Secure`
15. Что происходит с кукой без `Max-Age` и `Expires` ? >> Становится сессионной; удаляется после закрытия браузера
16. Что делает `request.session.flush()` ? >> Удаляет все данные текущей сессии
17. Почему JWT сложнее отозвать? >> Валиден до истечения срока; для досрочного отзыва нужен blacklist в Redis/БД
18. В чём разница `SameSite=Strict` и `SameSite=Lax` ? >> `Strict` – кука не отправляется никогда при межсайтовых запросах; `Lax` – отправляется при top-level навигации (GET по ссылке), но не в POST/fetch/iframe
19. Где Django хранит сессии по умолчанию? >> В базе данных (модель `Session` )
20. Что такое `request.session` в Django? >> Dict-like объект для хранения данных текущей сессии пользователя
21. Когда сессии предпочтительнее JWT? >> При необходимости мгновенного отзыва доступа; удаление записи на сервере сразу блокирует пользователя
22. Что такое куки? >> Небольшие фрагменты данных, отправляемые сервером браузеру для хранения и возврата при последующих запросах
23. Где на сервере могут храниться данные сессий? >> В памяти, Redis/Memcached, файлах, реляционной БД
24. Возможен ли доступ к чужой сессии зная `session_id` ? >> Да; поэтому `session_id` должен быть криптографически случайным и передаваться только по HTTPS
25. Почему JWT тяжелее `session_id` ? >> JWT содержит все данные и подпись; строка значительно длиннее простого идентификатора
26. Как сессии обходят stateless-природу HTTP? >> Состояние хранится на сервере; клиент получает только `session_id` в куке
27. Почему JWT не требует хранилища сессий? >> Сервер проверяет подпись токена секретным ключом без обращения к БД
28. В чём разница `Max-Age` и `Expires` ? >> `Expires` – абсолютная дата удаления; `Max-Age` – время жизни в секундах с момента создания
29. Что критично для масштабирования сессий на несколько серверов? >> Общее внешнее хранилище; обычно Redis
30. Как сервер восстанавливает контекст по `session_id` ? >> Находит запись в хранилище по ID и загружает данные пользователя и его права
31. Где хранится состояние при JWT? >> В самом токене на стороне клиента; сервер stateless
