## Что такое CSRF и почему это опасно

**CSRF (Cross-Site Request Forgery)** – это атака, при которой злоумышленник заставляет браузер жертвы отправить HTTP-запрос на сайт, где пользователь уже авторизован. Цель не украсть данные, а совершить действие от имени пользователя: перевести деньги, сменить пароль, удалить аккаунт.

Ключевая проблема – **доверие**: сервер не может отличить запрос, который пользователь отправил сам, от запроса, который тихо отправил за него вредоносный сайт.

---

## Как выглядит атака изнутри

В атаке участвуют три стороны. **Вредоносный сайт** – страница злоумышленника со скрытой формой или скриптом. **Браузер жертвы** – именно он исполняет код и автоматически прикрепляет к запросу куки. **Целевой сервер** – банк, соцсеть или любой сервис, который доверяет сессионным кукам пользователя.

Цепочка событий выглядит так. Пользователь заходит на `bank.com`, авторизуется и получает куки сессии. Не выходя из аккаунта, переходит по спам-ссылке на `evil.com`. Страница злоумышленника содержит скрытую форму:

```html
<form method="POST" action="https://bank.com/transfer">
  <input type="hidden" name="to" value="hacker_account">
  <input type="hidden" name="amount" value="50000">
</form>
<script>document.forms[0].submit();</script>
```

Браузер видит, что запрос идёт на `bank.com`, находит куки для этого домена и **автоматически их прикрепляет** – даже несмотря на то, что запрос инициирован с чужого сайта. Сервер получает запрос с валидной сессией и выполняет перевод.

Это и есть **Ambient Authority (неявная авторизация)**: браузер спроектирован так, чтобы всегда прикреплять куки к запросам на соответствующий домен, не спрашивая пользователя. Для сервера наличие куки – эквивалент того, что пользователь лично нажал кнопку.

## Защита №1: CSRF-токены

**CSRF-токен** – уникальное секретное значение, которое сервер генерирует для каждой сессии и ожидает получить обратно в каждом запросе, изменяющем данные (POST, PUT, DELETE). Злоумышленник не может прочитать содержимое легитимного сайта из своего скрипта, а значит – не знает токен и не может вставить его в поддельную форму.

В Django защита включена по умолчанию. В шаблоне достаточно добавить тег `{% csrf_token %}`:

```html
<form method="post" action="/profile/update/">
    {% csrf_token %}
    <!  -- Django превратит это в скрытое поле: -->
    <!  -- <input type="hidden" name="csrfmiddlewaretoken" value="zXy9..."> -->
    <input type="text" name="username">
    <button type="submit">Обновить</button>
</form>
```

Если токен отсутствует или не совпадает с ожидаемым, Django вернёт `403 Forbidden`.

## Защита №2: атрибут SameSite и проверка заголовков

Современный способ защиты на уровне самих кук – атрибут **SameSite**. Он говорит браузеру, при каких запросах куку вообще отправлять.

`SameSite=Strict` – кука отправляется только если запрос пришёл с того же сайта. Максимальная защита, но есть нюанс: если пользователь перейдёт на ваш сайт по ссылке из письма, кука не отправится и он окажется не авторизован.

`SameSite=Lax` – кука блокируется при скрытых кросс-сайтовых запросах (POST из формы, fetch, iframe), но отправляется при обычном переходе по ссылке (GET). Это разумный баланс между безопасностью и удобством – стандарт по умолчанию в большинстве современных браузеров.

Дополнительно сервер может проверять заголовки `Origin` и `Referer`. Если `Origin` указывает на `evil.com` вместо вашего домена – запрос нужно отклонить.

## Когда CSRF перестаёт быть проблемой: SPA и JWT

В Single Page Applications токен авторизации часто хранится не в куках, а в памяти приложения и передаётся через заголовок `Authorization`. Это архитектурно убирает CSRF.

Почему? Браузер **никогда** не добавляет кастомные заголовки автоматически – для этого нужен JavaScript. А добраться до чужого JavaScript-кода злоумышленнику мешает **Same-Origin Policy**: браузер запрещает скриптам с одного домена делать запросы с кастомными заголовками на другой домен без явного разрешения через CORS. В итоге злоумышленник физически не может заставить браузер добавить нужный `Authorization`-заголовок в поддельный запрос.

## Практические правила

Никогда не используйте GET для действий, изменяющих данные: смена пароля, удаление, оплата – всё это только POST/PUT/DELETE. GET должен только читать.

Используйте `{% csrf_token %}` во всех формах Django – это пять секунд работы, которые закрывают целый класс атак.

Устанавливайте `SameSite=Lax` (или `Strict`) для сессионных кук – это уже стандарт, а не дополнительная мера.

Проверяйте `Origin` и `Referer` на сервере как дополнительный слой защиты.

Для API используйте JWT в заголовках вместо кук – тогда CSRF-защита встроена в саму архитектуру.
