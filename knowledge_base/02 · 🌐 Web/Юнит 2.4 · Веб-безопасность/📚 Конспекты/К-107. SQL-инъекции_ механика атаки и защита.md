## Суть SQL-инъекции: смешение кода и данных

**SQL-инъекция (SQLi)** — это уязвимость, возникающая из-за подстановки пользовательского ввода прямо в строку SQL-запроса через конкатенацию или f-строки.

Рассмотрим опасный код проверки логина и пароля:

```python
# Опасная конкатенация в SQL-запросе
query = (
    f"SELECT * FROM users "
    f"WHERE username = '{username}'"
)
cursor.execute(query)
```

Если злоумышленник передаст в `username` строку `' OR '1'='1' --`, итоговый запрос превратится в условие `WHERE username = '' OR '1'='1' --'`.

Символ `'` преждевременно закрывает строковый литерал, `OR '1'='1'` делает условие истинным для каждой строки, а `--` комментирует оставшийся SQL до конца запроса.

---

## Какие последствия несёт уязвимость

Успешная SQL-инъекция открывает злоумышленнику прямой доступ к данным и логике базы:

- **Обход аутентификации**: вход под администратором без знания пароля через истинное условие.
- **Кража базы данных**: выгрузка паролей, токенов и персональных данных через оператор `UNION SELECT`.
- **Уничтожение и подмена данных**: удаление таблиц (`DROP TABLE`) или изменение баланса через `UPDATE` при поддержке множественных запросов.
- **Эскалация и чтение файлов**: при завышенных правах БД-пользователя возможны запись шелла или чтение системных файлов сервера.

## Главная защита: параметризованные запросы

Основной способ победить SQL-инъекции — **параметризованные запросы** (prepared statements).

СУБД сначала компилирует шаблон запроса с плейсхолдерами (`?` в SQLite или `%s` в PostgreSQL), а затем передаёт значения отдельно.

Благодаря разделению этапа компиляции и передачи данных параметры воспринимаются строго как литералы и не могут изменить структуру SQL:

```python
import sqlite3

conn = sqlite3.connect(':memory:')
cursor = conn.cursor()

cursor.execute(
    'CREATE TABLE users (username TEXT)'
)
cursor.execute(
    "INSERT INTO users VALUES ('alice')"
)

# Плейсхолдер ? передаёт данные безопасно
username = 'alice'
sql = (
    'SELECT * FROM users '
    'WHERE username = ?'
)
cursor.execute(sql, (username,))
print(cursor.fetchone())
# >>> ('alice',)
```

Даже если передать строку `' OR '1'='1`, база честно найдёт пользователя с таким буквальным именем, а не выполнит оператор `OR`.

## Безопасная работа с ORM и ловушка raw-запросов

Популярные ORM вроде Django ORM и SQLAlchemy по умолчанию оборачивают методы `filter()` и `where()` в параметризованные запросы.

Однако защита полностью отключается, если разработчик передаёт в `raw()` или `extra()` строку с ручной подстановкой через f-строки или `%`:

```python
q = 'alice'

# ОПАСНО: f-строка ломает защиту ORM
User.objects.raw(
    f"SELECT * FROM users WHERE name = '{q}'"
)

# БЕЗОПАСНО: параметры в кортеже/списке
User.objects.raw(
    'SELECT * FROM users WHERE name = %s',
    [q],
)

# ЛУЧШЕ ВСЕГО: штатный фильтр ORM
User.objects.filter(name=q)
```

Параметризация не работает для имён таблиц и столбцов (например, в `order_by()`). Такие значения обязательно проверяйте через белый список `ALLOWED_COLUMNS` в Python.

## Дополнительные рубежи защиты

Даже при использовании параметризованных запросов выстраивайте эшелонированную оборону на уровне инфраструктуры:

- **Принцип минимальных привилегий**: аккаунт приложения в БД должен иметь права только на чтение и запись строк, без прав `DROP TABLE` и доступа к системе.
- **Скрытие ошибок БД**: в production клиент видит только общий код `500`, а трассировка пишется в логи, чтобы атакующий не узнал структуру таблиц.
- **WAF (Web Application Firewall)**: фильтрует массовые сканеры и шаблонные атаки на периметре, но не заменяет параметризованные запросы в коде.

> **Junior vs Senior**:
> - **Junior**: подставляет ввод пользователя в SQL через f-strings или считает, что выбор любого ORM автоматически исключает инъекции в raw-запросах и сортировках.
> - **Senior**: всегда передаёт значения как bind-параметры, валидирует динамические имена полей (`ORDER BY`) белым списком, ограничивает права БД-роли принципом минимальных привилегий и скрывает сырые ошибки от клиента.
