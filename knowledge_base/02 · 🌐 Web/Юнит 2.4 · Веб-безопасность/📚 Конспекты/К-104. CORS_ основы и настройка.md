## Что такое Origin и почему это важно

**Origin (источник)** – это комбинация трёх компонентов: протокола, домена и порта. Браузер использует origin, чтобы решить, может ли один сайт получить доступ к данным другого. Два ресурса считаются одним источником только если все три компонента совпадают одновременно.

На практике это выглядит так. Запрос с `https://frontend.com` на `https://frontend.com` – успех, это один и тот же origin. Запрос на `https://api.com` – отказ, разные домены. Запрос на `https://sub.frontend.com` – отказ, поддомен считается отдельным origin. Запрос на `http://frontend.com` – отказ, протоколы различаются. Запрос на `https://frontend.com:3000` – отказ, разные порты.

## Same-Origin Policy: изоляция по умолчанию

**Same-Origin Policy (SOP)** – это встроенное правило браузера: скрипт, загруженный с одного источника, не может читать данные из другого. Это не техническое ограничение ради ограничения, а защита пользователя. Без SOP любой вредоносный сайт, открытый в соседней вкладке, мог бы прочитать содержимое вашей почты или перехватить банковскую сессию.

Проблема в том, что современные приложения почти всегда разделены: фронтенд живёт на одном домене, API – на другом. SOP такое взаимодействие блокирует. Чтобы его разрешить – существует CORS.

## Как работает CORS

**CORS (Cross-Origin Resource Sharing)** – это механизм, с помощью которого сервер явно говорит браузеру: «Я доверяю запросам с этого домена». Работает это через заголовки.

При каждом запросе браузер автоматически добавляет заголовок `Origin` с адресом страницы, которая инициировала запрос. Сервер смотрит на этот заголовок и, если домен в белом списке, отвечает заголовком `Access-Control-Allow-Origin`. Браузер сравнивает значения – и если они совпадают, разрешает JavaScript прочитать ответ.

## Простые и сложные запросы: когда браузер делает предварительную проверку

Браузер разделяет запросы на два типа, чтобы не создавать лишнюю нагрузку там, где это безопасно.

**Простые запросы** – это GET или POST со стандартными заголовками. Они отправляются сразу, а проверка CORS происходит уже на этапе получения ответа.

**Сложные запросы** – это PUT, DELETE или любой запрос с кастомными заголовками вроде `Authorization`. Браузер опасается, что такой запрос может изменить данные на сервере до того, как выяснится, разрешено ли это вообще. Поэтому сначала отправляется **preflight-запрос** методом `OPTIONS` – разведка перед основным запросом.

Сервер отвечает на preflight правилами:

```http
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 86400
```

Если правила подходят – браузер отправляет основной запрос. `Access-Control-Max-Age` позволяет браузеру закэшировать результат preflight на указанное время в секундах. Без этого preflight будет летать перед каждым запросом, добавляя задержку – настраивайте его всегда.

## Настройка в Django

Стандарт для Django – библиотека `django-cors-headers`:

```bash
pip install django-cors-headers
```

```python
INSTALLED_APPS = [
    'corsheaders',
]

MIDDLEWARE = [
    'corsheaders.middleware.CorsMiddleware',  # Строго первым!
    'django.middleware.common.CommonMiddleware',
]
```

Middleware должен стоять самым первым – иначе preflight-запрос (`OPTIONS`) может упасть на проверку аутентификации раньше, чем до него доберётся CORS-логика.

Доверенные источники указывайте явно через белый список:

```python
CORS_ALLOWED_ORIGINS = [
    'https://frontend.example.com',
    'http://localhost:3000',  # Только для локальной разработки
]
```

Если фронтенд должен передавать куки или сессионные заголовки – включите:

`CORS_ALLOW_CREDENTIALS = True`

Важный нюанс: если `CORS_ALLOW_CREDENTIALS = True`, нельзя использовать `*` в `Access-Control-Allow-Origin`. Спецификация это запрещает – браузер заблокирует ответ. Сервер обязан вернуть конкретный домен. И никогда не ставьте `CORS_ALLOW_ALL_ORIGINS = True` в продакшене – это полное отключение защиты для вашего API.

## Главное заблуждение о CORS

Самая частая ошибка – думать, что CORS защищает сервер от взлома. Это не так.

**CORS защищает пользователей от вредоносных сайтов, а не API от прямых запросов.**

Браузер – исполнитель правил: он блокирует чтение данных скриптом, если сервер не разрешил. Но `curl` и Postman – не браузеры, они игнорируют CORS полностью и всегда видят ответ сервера.

Есть ещё один неочевидный момент: даже если браузер заблокировал ответ из-за CORS, сам запрос мог уже выполниться. Например, `DELETE` дошёл до сервера и удалил запись в базе – CORS заблокировал только чтение результата, но не факт соединения.

CORS – это не замена авторизации и не файрвол. Это механизм защиты ваших пользователей, работающих через браузер.
