## Инструменты расследования: `log`, `diff`, `blame` и `bisect`

При разборе инцидентов на продакшене историю Git используют как систему диагностики по четырём основным направлениям:

- **`git log`** — хронология коммитов: какие изменения, когда и с какими сообщениями попадали в ветку.
- **`git diff`** — точное построчное отличие между коммитами, ветками или рабочей папкой и индексом.
- **`git blame`** — автор, дата и хеш коммита напротив каждой строки файла.
- **`git bisect`** — бинарный поиск коммита, в котором впервые сломались тесты, за $\log_2(N)$ шагов.

---

## Шпаргалка команд расследования для продакшена

Обычный `git log` выводит сплошной список текста, поэтому в работе применяют флаги графа и поиск по содержимому кода (`-S`, режим *pickaxe*):

| Задача расследования | Готовая команда | На какой вопрос отвечает? |
| :--- | :--- | :--- |
| **Компактный граф веток** | `git log --oneline --graph --all -n 15` | Как разошлись ветки и где находится `HEAD` / `origin/main`? |
| **Поиск по коду (`-S`)** | `git log -S 'legacy_tax' -p` | В каком коммите добавили или удалили эту строку кода? |
| **Проверка перед коммитом** | `git diff --staged` | Что именно попадёт в следующий коммит после `git add`? |
| **История блока строк** | `git blame -w -L 40,60 app/billing.py` | В какой задаче и почему появилась конкретная проверка? |
| **Автопоиск регрессии** | `git bisect run pytest` | Какой именно коммит из сотен последних сломал тест? |

## Построчный аудит контекста через `git blame` и `git show`

Команда `git blame` нужна не для поиска виноватых, а для быстрого восстановления инженерного контекста перед изменением чужого кода:

1. **Пропуск переформатирования**: флаг `-w` игнорирует изменения пробелов и отступов после автоформаттеров (Ruff/Black), показывая реального автора логики.
2. **Полный контекст изменения**: по найденному хешу вызовите `git show <sha>`, чтобы прочитать описание задачи и весь дифф коммита целиком.

```bash
# История строк 40..60 без учёта пробелов
git blame -w -L 40,60 app/billing.py

# Посмотреть сообщение и весь патч коммита
git show a1b2c3d
```

## Бинарный поиск бага через `git bisect`

Когда тест проходил неделю назад и сломался после сотен коммитов, `git bisect` делит диапазон пополам на каждом шаге и находит виновника среди 1 024 коммитов всего за 10 проверок:

```text
Поиск бага через git bisect (1024 коммита):

[c1: OK] ... [c512: OK] ... [c1024: BAD]
Шаг 1: c512 OK  -> баг правее (512)
Шаг 2: c768 BAD -> баг левее (256)
...
Всего 10 шагов -> виновник c615!
```

```bash
# Запустить поиск и отметить границы
git bisect start
git bisect bad HEAD
git bisect good v1.4.0

# Автоматически найти первый битый коммит
git bisect run pytest tests/test_billing.py

# Вернуть ветку в исходное состояние
git bisect reset
```

## Автоматический `git bisect` за O(log N) на Python

Смоделируем алгоритм `git bisect run pytest` на массиве из 1 000 коммитов, где регрессия начинается с коммита `#742`:

```python
def git_bisect_find(
    commits: list[int],
    bad_threshold: int,
) -> tuple[int, int]:
    low, high, steps = 0, len(commits) - 1, 0
    while low < high:
        steps += 1
        mid = (low + high) // 2
        if commits[mid] >= bad_threshold:
            high = mid
        else:
            low = mid + 1
    return commits[low], steps

culprit, steps = git_bisect_find(
    list(range(1000)),
    742,
)
print(f'Виновник: {culprit} за {steps} шагов')
# >>> Виновник: 742 за 10 шагов
```

> **Junior vs Senior**:
> - **Junior**: ищет регрессию полным ручным перебором недавних коммитов вместо инструментов точечного поиска по диффам и истории.
> - **Senior**: локализует появление строки через `git log -S` и `git blame`, инспектирует контекст патча через `git show` и находит сломавший билд коммит за $O(\log N)$ через `git bisect` (включая `git bisect run`).
