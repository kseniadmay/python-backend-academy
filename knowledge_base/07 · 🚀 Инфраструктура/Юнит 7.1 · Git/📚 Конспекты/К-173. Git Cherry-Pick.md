## Точечный перенос коммитов через `cherry-pick`

Иногда в долгоживущей ветке разработки находится один важный коммит с исправлением бага, который срочно нужен в релизной ветке прямо сейчас — без вливания всей незавершённой ветки целиком.

Команда **`git cherry-pick`** извлекает изменения одного конкретного коммита и применяет их поверх текущей ветки как новый коммит:

```text
Работа с git cherry-pick:

Ветка feat/redesign:
A ── B ── [C: fix tax] ── D
                 │
        git cherry-pick C
                 ▼
Ветка release/v1.2:
M1 ───────────► [C': fix tax]
```

---

## Команды `cherry-pick` и флаг трассировки `-x`

При переносе коммита `C` в другую ветку Git создаёт коммит `C'` с новым родителем и новым SHA-хешем.

Чтобы в истории осталось указание на исходный коммит, используют флаг **`-x`** — он дописывает в сообщение строку `(cherry picked from commit ...)`:

```bash
# Переходим в релизную ветку
git switch release/v1.2

# Переносим фикс с отметкой исходного SHA
git cherry-pick -x f89a12b

# Применить правки без авто-коммита
git cherry-pick -n f89a12b

# После ручного решения конфликтов
git cherry-pick --continue
```

## Таблица режимов `git cherry-pick`

Основные флаги управления точечным переносом и прерыванием операции при конфликте:

| Режим | Команда | Что происходит в репозитории | Когда использовать |
| :--- | :--- | :--- | :--- |
| **С трассировкой** | `git cherry-pick -x <hash>` | Создаёт коммит со ссылкой на исходный SHA | Бэкпорт хотфиксов в `release/*` |
| **Без коммита** | `git cherry-pick -n <hash>` | Кладёт изменения в индекс (`staged`) | Объединение 2–3 фиксов в один коммит |
| **Диапазон** | `git cherry-pick A..B` | Переносит цепочку коммитов после `A` до `B` | Перенос короткой серии правок |
| **Отмена** | `git cherry-pick --abort` | Возвращает ветку к исходному состоянию | При сложных конфликтах переноса |

## Атомарность коммитов и риск дублирования истории

Чтобы `cherry-pick` не разрушил историю проекта, соблюдайте два правила:

1. **Атомарность коммита**: переносить легко только самодостаточный фикс бага; если в коммит попали посторонние модули, вы получите каскад конфликтов.
2. **Опасность массового `cherry-pick`**: регулярный перенос пачек коммитов вместо `git merge` плодит дублирующие изменения с разными SHA-хешами и запутывает дальнейшее слияние веток.

## Перенос патча с новым SHA и меткой `-x` на Python

Посмотрим на Python, как `cherry-pick -x` меняет родителя и хеш коммита при копировании патча на другую ветку:

```python
import hashlib

def cherry_pick(
    target_sha: str,
    patch: str,
    orig_sha: str,
) -> dict[str, str]:
    raw = f'{target_sha}:{patch}:{orig_sha}'
    new_sha = (
        hashlib.sha1(raw.encode())
        .hexdigest()[:8]
    )
    msg = (
        'feat: fix tax\n(cherry picked '
        f'from commit {orig_sha})'
    )
    return {
        'sha': new_sha,
        'parent': target_sha,
        'msg': msg,
    }

res = cherry_pick('m2', '+tax=0.2', 'f89a12b')
print('Новый SHA:', res['sha'])
# >>> Новый SHA: 82b20c47

print(res['msg'])
# >>> feat: fix tax
# >>> (cherry picked from commit f89a12b)
```

> **Junior vs Senior**:
> - **Junior**: переносит большие ветки десятками ручных `cherry-pick`, создавая дубли коммитов с разными SHA и конфликты при следующем слиянии.
> - **Senior**: использует `git cherry-pick -x` точечно для критичных атомарных хотфиксов (с записью ссылки на исходный коммит) и понимает последствия появления дублирующих патчей в графе истории.
