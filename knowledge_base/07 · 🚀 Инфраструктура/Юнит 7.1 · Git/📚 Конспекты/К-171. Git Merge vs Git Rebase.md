## Стратегии слияния: `merge` или `rebase`

При интеграции изменений из одной ветки в другую используются две ключевые стратегии:

- **`git merge`** сохраняет полную историю ветвления с явным узлом-скрепкой (merge-коммитом).
- **`git rebase`** делает историю линейной, последовательно перенося ваши коммиты поверх целевой ветки с новыми хешами.

```text
1. До объединения:
      A ── B  (feat)
     /
M1 ── M2      (main)
2. git merge feat:
      A ── B
     /      \
M1 ── M2 ─── M3 (merge commit)
3. git rebase main:
              A' ── B' (новые хеши!)
             /
M1 ────── M2 (main)
```

## Сравнительная таблица `merge`, `rebase` и `squash`

Выбор стратегии слияния зависит от того, нужна ли в истории точная хронология ветвления или линейный лог:

| Критерий | `git merge` | `git rebase` | `git merge --squash` |
| :--- | :--- | :--- | :--- |
| **Форма истории** | Ветвистая (с узлами слияния) | Идеально линейная | Линейная (1 коммит на фичу) |
| **Хеши коммитов** | Сохраняются неизменными | Пересчитываются (`A'`, `B'`) | Схлопываются в 1 новый коммит |
| **Разрешение конфликтов** | Один раз в merge-коммите | Пошагово на каждом коммите | Один раз при схлопывании |
| **Где применять** | В общих ветках (`main`, `dev`) | В личной ветке перед PR | При слиянии PR с кучей «wip» |

## Безопасная отправка после `rebase`: `--force-with-lease`

Когда вы перебазировали ветку, уже отправленную ранее в Pull Request, обычный `git push` будет отклонён из-за изменившихся хешей коммитов.

Использовать `git push --force` опасно (он затрёт коммиты коллеги), поэтому применяют проверку `--force-with-lease`:

```bash
# Подтянуть свежий main через rebase
git switch feat/orders
git fetch origin
git rebase origin/main

# Безопасно обновить удалённую ветку
git push --force-with-lease \
  origin feat/orders

# Влить ветку с сохранением merge-узла
git switch main
git merge --no-ff feat/orders
```

## Выбор между `merge` и `rebase` в командной разработке

Инженерный стандарт чётко разделяет общие и локальные ветки:

1. **Публичные общие ветки (`main`, `develop`)**: используется только **`git merge`**. Переписывать историю общих веток через `rebase` категорически запрещено.
2. **Локальные ветки фич**: перед отправкой PR ветку синхронизируют со свежим `main` через `git pull --rebase origin main`, чтобы избежать мусорных merge-коммитов.

## Моделирование графа истории: `merge` против `rebase`

Сравним структуру графа коммитов при слиянии и при перебазировании в Python:

```python
main_branch = ['M1', 'M2']
feat_branch = ['A', 'B']

# merge сохраняет исходные коммиты и узел
merge_graph = (
    main_branch
    + feat_branch
    + ['Merge(M2+B)']
)

# rebase пересоздаёт коммиты с новыми ID
rebase_graph = main_branch + [
    f"{c}'(rebased)" for c in feat_branch
]

print('Merge :', ' -> '.join(merge_graph))
# >>> Merge :
# >>> M1 -> M2 -> A -> B -> Merge(M2+B)

print('Rebase:', ' -> '.join(rebase_graph))
# >>> Rebase: M1 -> M2 ->
# >>> A'(rebased) -> B'(rebased)
```

> **Junior vs Senior**:
> - **Junior**: делает `git rebase` для общей командной ветки и перетирает историю коллег жёстким `git push --force`.
> - **Senior**: применяет `rebase` только на локальной фича-ветке до слияния, пушит переписанную историю исключительно через `--force-with-lease` и осознанно выбирает стратегию команды (`merge`, `rebase` или `squash`).
