## Стратегии слияния: сохранение истории (merge) или линейный граф (rebase)
При интеграции изменений используются две ключевые стратегии:
- **`git merge`** сохраняет полную историю слияния с явным узлом-скрепкой (merge-коммитом).
- **`git rebase`** линеаризует историю, последовательно перенося коммиты поверх целевой ветки с новыми хешами.

```text
1. До объединения:
      A ── B  (feat)
     /
M1 ── M2      (main)
2. git merge feat:
      A ── B
     /      M1 ── M2 ─── M3 (merge commit)
3. git rebase main:
              A' ── B' (новые хеши!)
             /
M1 ────── M2 (main)
```

---
### Сравнение стратегий слияния и флаг `--force-with-lease`
Когда вы сделали `rebase` локальной ветки, которую уже пушили в свой Pull Request, обычный `git push` будет отклонён (ведь хеши изменились).

```bash
# 1. Подтянуть main в ветку через rebase:
git switch feat/orders
git fetch origin
git rebase origin/main
git push --force-with-lease origin feat/orders

# 2. Влить ветку в main с узлом слияния:
git switch main
git merge --no-ff feat/orders
```

| Критерий | `git merge` | `git rebase` | `git merge --squash` |
| :--- | :--- | :--- | :--- |
| **Форма истории** | Ветвистая (с узлами слияния) | Идеально линейная | Линейная (1 коммит на всю фичу) |
| **Хеши коммитов** | Сохраняются неизменными | Пересчитываются заново (`A'`, `B'`) | Схлопываются в 1 новый коммит |
| **Разрешение конфликтов** | Один раз в итоговом merge-коммите | Пошагово на каждом коммите ветки | Один раз при схлопывании |
| **Где применять** | В публичных ветках (`main`, `dev`) | В личной feature-ветке перед PR | При слиянии PR с кучей «wip»-коммитов |

---
## Выбор между merge и rebase в командной разработке

Инженерный стандарт разделяет публичные и локальные ветки:

1. **Публичные общие ветки (`main`, `develop`)**: Используется только **`git merge`** (или Merge Commit в Pull Request). Переписывать историю общих веток через `rebase` категорически запрещено.
2. **Локальные ветки фич**: Перед отправкой PR локальная ветка подтягивает свежий `main` через **`git pull --rebase origin main`**, сохраняя линейную историю коммитов без лишних мусорных Merge-коммитов.

### Изменение графа истории: merge vs rebase
Сравнение структуры коммитов при слиянии и линеаризации:

```python
main_branch = ["M1", "M2"]
feat_branch = ["A", "B"]

# git merge feat: создаёт узел слияния с сохранением исходных хешей
merge_graph = main_branch + feat_branch + ["Merge(M2+B)"]

# git rebase main: переписывает коммиты фичи поверх main с новыми хешами
rebase_graph = main_branch + [f"{c}'(rebased)" for c in feat_branch]

print("Merge граф :", " -> ".join(merge_graph))
print("Rebase граф:", " -> ".join(rebase_graph))
```
