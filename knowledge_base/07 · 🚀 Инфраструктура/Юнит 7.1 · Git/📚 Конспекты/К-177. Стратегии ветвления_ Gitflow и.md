## Модели ветвления: Gitflow и Trunk-Based Development

В командной разработке используют две основные модели организации веток:

1. **Gitflow** — строгий релизный цикл с долгоживущей веткой разработки `develop`, отдельными ветками `release/*` и экстренными `hotfix/*` поверх `main`.
2. **Trunk-Based Development (TBD / GitHub Flow)** — быстрая непрерывная интеграция вокруг единственной постоянной ветки `main` (*trunk*), от которой живут короткие ветки на 1–2 дня.

```text
1. Gitflow (релизы по расписанию):
   main    ──●─────────────● (v1.0)
   release    \           /
   develop ──●─●──●──────●
   feature     \───/

2. Trunk-Based (SaaS и микросервисы):
   main ──●────●────●────●────●──►
           \──/ \──/ (PR на 1 день)
```

---

## Сравнительная таблица стратегий и проблема `Merge Hell`

Чем дольше ветка живёт изолированно от `main`, тем сильнее расходятся файлы и выше риск болезненных конфликтов слияния (*Merge Hell*):

| Характеристика | Gitflow | GitHub Flow / Trunk-Based |
| :--- | :--- | :--- |
| **Долгоживущие ветки** | `main`, `develop`, `release/*` | Только одна — `main` (`trunk`) |
| **Время жизни фича-ветки** | От нескольких дней до недель | От нескольких часов до 1–2 дней |
| **Риск «Merge Hell»** | Высокий из-за расхождения веток | Минимальный за счёт ежедневного слияния |
| **Недоделанные фичи в `main`** | Не вливаются до релиза | Скрываются за **Feature Flags** |
| **Где применяют** | Мобильные релизы, On-Premise | Веб-бэкенд, микросервисы, SaaS |

## Рабочий цикл ветки в Trunk-Based Development

Чтобы код интегрировался в `main` ежедневно, задачи дробят на компактные Pull Request (до 200–300 строк) с обязательной проверкой CI:

```bash
# Обновляем основную ветку
git switch main && git pull origin main

# Короткая ветка под одну задачу
git switch -c feat/214-stripe-webhook

# Отправляем на CI и ревью в main
git push -u origin feat/214-stripe-webhook
```

## Незавершённые фичи в `main` через Feature Flags

Если крупная функциональность (например, новый платёжный сценарий) занимает две недели разработки, её не держат в отдельной долгой ветке.

Код вливают в `main` небольшими шагами каждый день, но скрывают точку входа за конфигурационным переключателем **Feature Flag** (`if settings.ENABLE_NEW_CART:`), оставляя фичу выключенной для пользователей до полной готовности.

## Роутинг через Feature Flag на Python

Посмотрим, как конфигурационный флаг позволяет безопасно доставлять новый код в `main` без преждевременного включения для всех пользователей:

```python
feature_flags = {'new_payment_flow': False}

def process_checkout(user_id: int) -> str:
    # Флаг управляет новой веткой логики
    if feature_flags.get('new_payment_flow'):
        return 'Новый шлюз: оплата СБП'
    return 'Базовый шлюз: оплата картой'

print('До:', process_checkout(42))
# >>> До: Базовый шлюз: оплата картой

feature_flags['new_payment_flow'] = True
print('После:', process_checkout(42))
# >>> После: Новый шлюз: оплата СБП
```

## Защита `main` (Branch Protection), `Squash Merge` и подход Junior vs Senior

Чтобы Trunk-Based Development работал без поломок продакшена, основную ветку `main` защищают на уровне GitHub / GitLab (**Branch Protection Rules**):

1. **Запрет прямого `git push` в `main`:** любые изменения попадают только через Pull Request.
2. **Обязательный зелёный CI и Code Review:** кнопка Merge заблокирована, пока не прошли `pytest`, `ruff` и минимум 1 аппрув коллеги.
3. **Стратегия `Squash and Merge`:** при вливании фича-ветки все промежуточные коммиты («wip», «fix typo») схлопываются в **один атомарный коммит** в `main`, сохраняя историю линейной и позволяя откатить фичу одним `git revert`.

> **Junior vs Senior**:
> - **Junior**: Держит фича-ветку открытой 3 недели на 4000 строк кода, получая десятки конфликтов слияния, или пушит хотфиксы напрямую в `main` мимо тестов CI.
> - **Senior**: Декомпозирует задачу на короткие PR по 150–300 строк, прячет незавершённую бизнес-логику за Feature Flags, вливает ветки через `Squash and Merge` и защищает `main` обязательным прохождением CI.
