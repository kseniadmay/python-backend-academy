## Трёхстороннее слияние и маркеры конфликта

Если вы правили строки 10–20 файла `api.py`, а коллега изменила строки 80–90, Git объединит правки автоматически.

**Конфликт слияния (Merge Conflict)** возникает, когда с момента расхождения от общего предка обе ветки изменили одну и ту же строку по-разному. Git останавливается и расставляет в файле маркеры выбора:

```text
Конфликт слияния (формат zdiff3):

<<<<<<< HEAD (Ваша ветка)
TIMEOUT_SECONDS = 30
||||||| common ancestor (как было)
TIMEOUT_SECONDS = 5
=======
TIMEOUT_SECONDS = 15
>>>>>>> feat/fast-retry (Вливаем)
```

---

## Трёхсторонний формат конфликта `zdiff3`

По умолчанию Git показывает в конфликте только два итоговых варианта (`HEAD` и чужой), скрывая, что именно было написано в файле до расхождения веток.

Режим **`zdiff3`** добавляет средний блок `|||||||`, показывающий исходный код общего предка, и упрощает разбор сложных конфликтов:

```bash
# Включить zdiff3 глобально один раз
git config --global \
  merge.conflictstyle zdiff3

# Проверить файлы в статусе конфликта
git status -s

# Зафиксировать решённый файл и продолжить
git add app/config.py
git merge --continue
```

## Инверсия `--ours` и `--theirs` при `rebase` против `merge`

> **Осторожно с инверсией при `rebase`!** Во время `git merge` блок `HEAD` (`--ours`) — это ваша текущая ветка. Но во время **`git rebase`** Git сначала переходит на целевую ветку (`main`) и накатывает ваши коммиты сверху, поэтому в `HEAD` (`--ours`) оказывается `main`, а ваши правки уходят вниз (`--theirs`).

Сводка значений маркеров и команд безопасной отмены для трёх операций:

| Ситуация | Внутри `<<<<<<< HEAD` (`--ours`) | Внутри `>>>>>>>` (`--theirs`) | Как отменить операцию |
| :--- | :--- | :--- | :--- |
| **`git merge feat`** (вы в `main`) | Код ветки `main` | Код ветки `feat` | `git merge --abort` |
| **`git rebase main`** (вы в `feat`) | Код ветки `main` (инверсия!) | Ваш коммит из `feat` | `git rebase --abort` |
| **`git cherry-pick X`** | Ваша текущая ветка | Переносимый коммит `X` | `git cherry-pick --abort` |

## Порядок безопасного разрешения конфликта

После появления конфликтных маркеров решение задачи сводится к двум этапам:

1. **Смысловой разбор сторон**: опираясь на блок общего предка `|||||||`, сверьте намерения обеих веток и аккуратно объедините логику вместо механического нажатия *Accept Current* или *Accept Incoming*.
2. **Очистка и тестирование**: удалите все строки с маркерами `<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`, обязательно прогоните тесты (`pytest`) и только потом делайте `git add` + `--continue`.

## Алгоритм 3-way merge на Python

Реализуем на Python базовую логику трёхстороннего слияния строки с детектированием конфликта:

```python
def resolve_3way(
    base: str,
    ours: str,
    theirs: str,
) -> str:
    # Обе изменили одинаково или наша старая
    if ours == theirs or ours == base:
        return theirs
    if theirs == base:
        return ours

    # Обе изменили по-разному -> конфликт
    return (
        f'<<<<<<< HEAD\n{ours}\n'
        f'=======\n{theirs}\n'
        '>>>>>>> branch'
    )

merged = resolve_3way(
    'TIMEOUT = 30',
    'TIMEOUT = 60',
    'TIMEOUT = 120',
)
print(merged)
# >>> <<<<<<< HEAD
# >>> TIMEOUT = 60
# >>> =======
# >>> TIMEOUT = 120
# >>> >>>>>>> branch
```

> **Junior vs Senior**:
> - **Junior**: стирает маркеры конфликта наугад (теряя код) и путает стороны `--ours` и `--theirs` при выполнении `git rebase`.
> - **Senior**: читает 3-сторонее сравнение относительно общего предка (`zdiff3`), помнит про инверсию `--ours`/`--theirs` во время `rebase` и обязательно прогоняет тесты после ручного разрешения конфликта.
