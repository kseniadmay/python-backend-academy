## Культура Pull Request и конвейер CI/CD

**Pull Request (PR)** в GitHub (или **Merge Request** в GitLab) — это инженерное предложение влить ветку в `main` через автоматические проверки и диалог с командой.

Сначала робот CI прогоняет линтеры и тесты, а затем коллеги на **Code Review** помогают вовремя заметить логические ошибки, гонки или проблемы архитектуры:

```text
Конвейер Pull Request:

[Ветка feat/api]
  │
  ▼ Открытие PR
[Робот CI: ruff + mypy + pytest]
  │ (зелёная галочка ✅)
  ▼
[Code Review: архитектура и логика]
  │ (Approve 👍)
  ▼
[Слияние в main 🚀]
```

## Парадокс размера и критерии эталонного PR

Практика команд показывает: компактный PR на **200 строк** ревьюер внимательно проверяет за 15 минут и находит большую часть потенциальных ошибок.

Когда в PR попадает **1 500 строк**, внимание неизбежно теряется — проверка зависает на дни либо заканчивается формальным `LGTM`, пропуская баги в продакшен:

| Критерий | Слабый PR | Эталонный PR |
| :--- | :--- | :--- |
| **Объём** | 1200+ строк, десятки файлов | **До 200–400 строк**, 1 задача |
| **Заголовок** | `fix` / без контекста | `feat(billing): Stripe webhook` |
| **Границы правки** | Новая фича + массовый рефакторинг | Строго 1 атомарное изменение |
| **Тон ревью** | Переход на личности | Префиксы `[blocker]`, `[nit]` |

## Шаблон понятного описания Pull Request

Хорошее описание снимает лишние вопросы ещё до начала ревью, отвечая на три пункта — **что сделано**, **почему выбрано такое решение** и **как проверено**:

```markdown
## Что сделано (Summary)
Добавлен обработчик вебхуков Stripe:
`POST /webhooks/stripe`.

## Почему так (Context)
- Таблица `processed_events` с ключом
  `UNIQUE(event_id)` защищает от дублей.
- Генерация PDF вынесена в Celery.

## Как проверено (Test Plan)
- [x] Unit-тесты идемпотентности
      (`pytest tests/test_stripe.py`).
```

## Самопроверка и префиксы `Conventional Comments`

Перед отправкой PR на ревью автор сам просматривает вкладку `Files changed` (**Self-Review**), удаляя отладочные принты, мёртвый код и случайные правки соседних модулей.

Чтобы ревьюер и автор однозначно понимали срочность замечания, комментарии маркируют префиксами **Conventional Comments**:

- **`[blocker]`** — критическая уязвимость, баг логики или поломка контракта; без исправления вливать нельзя.
- **`[suggestion]`** — конструктивное предложение по улучшению архитектуры или читаемости.
- **`[nit]`** — мелкая стилистическая шероховатость, не блокирующая одобрение PR.

## Автоматический скоринг готовности PR на Python

Реализуем на Python простой анализатор, проверяющий минимальные ворота качества перед отправкой PR на ревью:

```python
def check_pr_ready(
    lines_changed: int,
    has_tests: bool,
    ci_ok: bool,
) -> dict[str, str]:
    if not ci_ok:
        return {
            'status': 'BLOCKED',
            'reason': 'Упал CI-пайплайн',
        }
    if lines_changed > 400:
        return {
            'status': 'WARN',
            'reason': 'PR больше 400 строк',
        }
    if not has_tests:
        return {
            'status': 'WARN',
            'reason': 'Нет тестов',
        }
    return {
        'status': 'READY',
        'reason': 'Готов к ревью',
    }

print(check_pr_ready(120, True, True))
# >>> {'status': 'READY', 'reason': 'Готов к ревью'}
```
