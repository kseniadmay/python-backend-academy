1. Что находится между `=======` и `>>>>>>> branch` в блоке конфликта? >> Изменения из входящей ветки (той, которую вливают)
2. Каков минимальный порядок шагов при разрешении конфликта слияния? >> `git status` → открыть файлы → убрать маркеры и выбрать нужный код → `git add <file>` → `git commit`
3. Что выводит Git в консоли при обнаружении конфликта в файле `users.py` ? >> `CONFLICT (content): Merge conflict in users.py` и `Automatic merge failed; fix conflicts and then commit the result`
4. Какой третий вариант разрешения конфликта существует помимо выбора одной из версий? >> Вручную объединить оба варианта в итоговый код, сохранив нужные части из обеих веток
5. Что означает выбор «принять входящую версию» при разрешении конфликта? >> Принять изменения вливаемой ветки и отбросить свои
6. Что обозначает маркер `<<<<<<< HEAD` в конфликтном файле? >> Начало блока изменений из текущей ветки (той, в которую вливают)
7. Что отображается в панели Result в merge editor IDE? >> Итоговый код после применения выбранных решений; именно он попадёт в коммит
8. Как с помощью `git status` обнаружить файлы с конфликтами? >> Конфликтующие файлы помечены как `both modified` ; они перечислены в секции `Unmerged paths`
9. Какая команда завершает процесс слияния после разрешения всех конфликтов? >> `git commit` ; Git автоматически подставит стандартное сообщение merge-коммита
10. Обязательно ли использовать IDE для разрешения конфликтов? >> Нет; достаточно любого текстового редактора – маркеры конфликта это обычный текст
11. Является ли `git merge --abort` обязательным шагом при успешном разрешении конфликта? >> Нет; она нужна только для отмены процесса, если разрешение зашло в тупик
12. Какая команда выполняется после ручного разрешения конфликта в `users.py` ? >> `git add users.py` – переводит файл из состояния `unmerged` в `staged`
13. Какая команда начинает слияние ветки `feature/auth` в текущую ветку? >> `git merge feature/auth`
14. Какая команда полностью отменяет незавершённое слияние и возвращает репозиторий к состоянию до `git merge` ? >> `git merge --abort`
15. Может ли конфликт возникнуть при `git rebase` ? >> Да; rebase переносит коммиты по одному, и конфликт может возникнуть на каждом из них; разрешается аналогично, но завершается `git rebase --continue` , а не `git commit`
16. Что служит разделителем между двумя версиями кода в блоке конфликта? >> Семь знаков равенства: `=======`
17. Что означает выбор «оставить HEAD-версию» при разрешении конфликта? >> Сохранить изменения текущей ветки и полностью отбросить входящие
18. Что должен сделать разработчик после сообщения `Automatic merge failed` ? >> Вручную открыть конфликтующие файлы, разрешить конфликты, удалить маркеры, выполнить `git add` и `git commit`
19. Что обязательно нужно сделать с маркерами `<<<<<<<` , `=======` , `>>>>>>>` перед коммитом? >> Полностью удалить их; если оставить – они попадут в код как обычный текст и вызовут ошибки
20. Как называется ситуация, когда Git не может сам решить, какую версию строки оставить? >> Конфликт слияния (merge conflict)
21. Какой визуальный интерфейс предоставляют PyCharm и VS Code для разрешения конфликтов? >> Трёхпанельный merge editor: Current (текущая ветка), Incoming (входящая ветка), Result (итоговый результат)
22. Каким маркером заканчивается блок конфликта? >> `>>>>>>> имя_ветки`
23. Что делает `git commit` без флага `-m` после разрешения конфликтов? >> Открывает редактор с предзаполненным сообщением merge-коммита; можно принять или отредактировать
24. Что произойдёт с незавершённым merge при вызове `git merge --abort` ? >> Репозиторий откатится к состоянию до запуска `git merge` ; все частичные изменения будут отменены
25. В какой ситуации Git не может выполнить автоматическое слияние веток? >> Когда два коммита изменили одну и ту же строку одного файла по-разному; также при конфликтах удаления/изменения файла
