1. Что такое Pull Request (PR)? >> Запрос на перенос изменений из feature-ветки в целевую ветку с обязательной проверкой кода перед слиянием
2. Что должно закрывать описание хорошего PR? >> Ответы на два вопроса: что изменено (краткий обзор правок) и зачем (бизнес-контекст и цель задачи)
3. Что означает принцип «одна задача – один PR»? >> В PR не следует смешивать новую функциональность с рефакторингом или несвязанными фиксами; это упрощает ревью и откат изменений
4. Что означают пометки `nit` или `suggestion` в комментариях к коду? >> Желательные правки (незначительные улучшения), которые не блокируют merge
5. На какие две категории по критичности делятся комментарии в ревью? >> Блокирующие (обязательные) и не блокирующие (желательные)
6. Что рекомендуется сделать с веткой после успешного merge PR? >> Удалить её; большинство платформ (GitHub, GitLab) предлагают это автоматически после merge
7. Чем отличается PR от `git merge` напрямую? >> PR – это процесс с обязательным ревью, обсуждением и CI-проверками на платформе (GitHub/GitLab); `git merge` – локальная операция без этих шагов
8. Что рекомендуется добавлять в описание PR для визуальной демонстрации изменений UI? >> Скриншоты или видео до/после
9. Почему проверку стиля кода не стоит делать в ручном Code Review? >> Стиль должен проверять линтер автоматически; ревьюер тратит ограниченное внимание на логику, архитектуру и безопасность
10. Как перефразировать комментарий «это плохо» в конструктивный? >> «Лучше использовать X, потому что это избегает Y»
11. Каков рекомендуемый максимальный объём изменений для одного PR? >> До 300–400 строк; большие PR сложнее ревьюировать и чаще содержат незамеченные ошибки
12. Какими по форме должны быть комментарии в хорошем Code Review? >> Конструктивными и конкретными: указывать что именно не так и почему, предлагать решение
13. Почему линтер эффективнее человека в проверке стиля? >> Работает автоматически, беспристрастно и мгновенно в CI; не занимает время ревьюера
14. В какую ветку сливается код после успешного PR? >> В целевую ветку, указанную при создании PR (обычно `main` или `develop` )
15. Что такое Code Review? >> Процесс совместной проверки кода другими разработчиками с целью улучшения качества, поиска ошибок и передачи знаний в команде
16. Что происходит с PR при наличии блокирующих комментариев? >> PR не может быть смержен до их исправления
17. К какому разделу ревью относится проверка на N+1 запросы и утечки памяти? >> Производительность
18. Какова основная цель механизма Pull Request? >> Обеспечить проверку кода командой (code review) и прохождение автоматических проверок (CI) до попадания изменений в основную ветку
19. В каком случае комментарий в ревью считается блокирующим? >> Если он указывает на критическую ошибку в логике, безопасности или архитектуре, которая делает код неприемлемым для production
20. Что обязательно должно сопровождать изменения в коде в PR? >> Тесты, подтверждающие корректность изменений и отсутствие регрессий
21. Какие аспекты кода проверяются в Code Review помимо синтаксиса? >> Логика, архитектура, безопасность и производительность
