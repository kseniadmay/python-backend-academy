1. Для чего чаще всего применяется interactive rebase ( `git rebase -i` )? >> Для приведения истории feature-ветки в порядок перед merge: объединение черновых коммитов, исправление сообщений, удаление лишних коммитов
2. Действие `squash` в interactive rebase? >> Объединить коммит с предыдущим, сохранив оба сообщения для редактирования
3. Как выглядит история после успешного `git rebase` ? >> Строго линейная: коммиты feature-ветки идут после последнего коммита целевой ветки без merge-коммитов
4. Почему `git merge` считается безопасным методом интеграции? >> Он не переписывает существующие коммиты: все SHA остаются неизменными, история – честной
5. Как перенести коммиты `feature/auth` поверх `main` ? >> `git checkout feature/auth` → `git rebase main`
6. Что делает `git rebase` с коммитами текущей ветки? >> Переносит их поверх указанной ветки, создавая новые коммиты с теми же изменениями, но новыми SHA
7. Для каких веток предпочтительнее использовать `git merge` ? >> Для публичных (общих) веток, в которые пушат несколько участников; переписывать их историю опасно
8. Как запустить интерактивное редактирование последних трёх коммитов? >> `git rebase -i HEAD~3`
9. Как слить ветку `feature/auth` в `main` через `git merge` ? >> `git checkout main` → `git merge feature/auth` ; или в одну строку: `git merge feature/auth` находясь на `main`
10. Какое преимущество даёт `git rebase` при работе с историей? >> Линейная история упрощает `git log` , `git bisect` и code review; проще отследить причину бага
11. Чем `git merge --no-ff` отличается от обычного `git merge` ? >> Принудительно создаёт merge-коммит даже при fast-forward-ситуации; сохраняет явный след слияния ветки в истории
12. Действие `drop` в interactive rebase? >> Полностью удалить коммит и его изменения из истории
13. Как `git merge` влияет на структуру истории? >> Создаёт новый merge-коммит с двумя родителями, сохраняя оригинальные коммиты обеих веток нетронутыми
14. Почему нельзя делать `rebase` на уже запушенных общих ветках? >> `rebase` меняет SHA коммитов; у других участников локальные ветки расходятся с перезаписанной удалённой, и при следующем `pull` возникают конфликты и дублирующиеся коммиты
15. Почему после `rebase` коммиты получают новые SHA? >> `rebase` создаёт новые коммиты с теми же изменениями, но другим родителем; исходные коммиты технически остаются в reflog, но отвязываются от ветки
16. На каких ветках безопасно применять `git rebase` ? >> На локальных или личных feature-ветках, которые ещё не были запушены или используются только вами
17. В чём основной минус `git merge` при интенсивной разработке? >> История засоряется merge-коммитами и перестаёт быть линейной, что затрудняет чтение `git log`
18. В чём суть «золотого правила rebase»? >> Никогда не делать `rebase` коммитов, которые уже существуют в публичном репозитории и на которые могут ссылаться другие участники
19. Действие `pick` в interactive rebase? >> Оставить коммит как есть, без изменений; используется по умолчанию
20. Действие `reword` в interactive rebase? >> Остановить rebase для редактирования только сообщения коммита, не трогая изменения
21. Действие `fixup` в interactive rebase? >> Как `squash` , но сообщение текущего коммита отбрасывается; удобно для технических правок
22. Какова общая цель `git merge` и `git rebase` ? >> Интеграция изменений из одной ветки в другую; различаются способом построения результирующей истории
