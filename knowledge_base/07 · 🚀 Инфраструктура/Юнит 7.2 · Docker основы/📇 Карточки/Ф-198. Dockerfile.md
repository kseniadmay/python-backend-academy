1. `RUN` vs `CMD` : в какой момент выполняется каждая инструкция? >> `RUN` – на этапе сборки образа (build time), создаёт слой; `CMD` – при запуске контейнера (run time), не создаёт слой
2. Зачем в Dockerfile сначала копируют только `requirements.txt` , а потом весь остальной код? >> Чтобы слой с `pip install` кэшировался: при изменении только кода зависимости не переустанавливаются заново
3. Можно ли переопределить `CMD` при `docker run` ? >> Да, достаточно передать аргументы после имени образа: `docker run myapp python script.py`
4. В чём разница между exec form и shell form для `CMD` и `ENTRYPOINT` ? >> Exec form ( `["uvicorn", "main:app"]` ) запускает процесс напрямую без shell, он получает PID 1 и корректно обрабатывает сигналы; shell form ( `CMD uvicorn main:app` ) запускает через `/bin/sh -c` , PID 1 получает shell, а не приложение
5. Почему `COPY . .` ставят в самом конце Dockerfile? >> Исходный код меняется чаще всего; размещение в конце позволяет максимально использовать кэш предыдущих слоёв
6. Является ли инструкция `WORKDIR` обязательной? >> Нет, но рекомендуется: без неё команды выполняются в корне `/` , что затрудняет организацию файлов
7. Что произойдёт, если директория, указанная в `WORKDIR` , не существует? >> Docker автоматически создаст её
8. Как Docker определяет, нужно ли пересобирать слой `COPY` ? >> Вычисляет контрольную сумму содержимого файлов; если хэш совпадает с предыдущей сборкой – слой берётся из кэша
9. Что означает `--host 0.0.0.0` при запуске сервера в контейнере? >> Сервер принимает соединения на всех сетевых интерфейсах контейнера; без этого сервер слушает только `localhost` и недоступен снаружи контейнера
10. Открывает ли `EXPOSE` порт контейнера для внешней сети? >> Нет; реальное открытие происходит через `-p host:container` при `docker run` ; флаг `-P` публикует все `EXPOSE` -порты на случайные порты хоста
11. Что такое `.dockerignore` и зачем он нужен? >> Файл по аналогии с `.gitignore` , указывающий какие файлы исключить из контекста сборки; уменьшает размер контекста и предотвращает попадание секретов и лишних файлов в образ
12. Почему рекомендуется объединять несколько команд в одну инструкцию `RUN` ? >> Каждая отдельная инструкция `RUN` – отдельный слой; объединение через `&&` уменьшает их количество
13. Что такое слой (Layer) в Docker Image? >> Изменение файловой системы, создаваемое инструкцией `RUN` , `COPY` или `ADD` ; остальные инструкции добавляют только метаданные
14. Что делает инструкция `RUN` во время сборки образа? >> Выполняет команду и создаёт новый слой образа
15. Какая инструкция всегда должна быть первой в Dockerfile? >> `FROM`
16. Что такое `ENTRYPOINT` в Dockerfile? >> Фиксированная основная команда контейнера; не переопределяется аргументами `docker run` , только флагом `--entrypoint`
17. Что произойдёт с последующими инструкциями, если изменить `WORKDIR` в середине Dockerfile? >> Все последующие `RUN` , `COPY` , `CMD` будут выполняться в новой рабочей директории
18. Что такое кэширование слоёв в Docker? >> Механизм, при котором Docker повторно использует слои из предыдущей сборки, если инструкция и её контекст не изменились; изменение любого слоя инвалидирует кэш всех последующих
19. В чём разница между `ENV` и `ARG` в Dockerfile? >> `ARG` доступен только на этапе сборки образа (build time) и не попадает в запущенный контейнер; `ENV` доступен и при сборке, и в работающем контейнере
20. Назначение инструкции `WORKDIR` в Dockerfile? >> Устанавливает рабочую директорию внутри контейнера для всех последующих инструкций; аналог `cd` в Linux; директория создаётся автоматически если не существует
21. Какую функцию выполняет инструкция `COPY` ? >> Копирует файлы или директории с хост-машины в файловую систему образа
22. С какой целью при `pip install` используется флаг `--no-cache-dir` ? >> Чтобы pip не сохранял временный кэш пакетов в образ, уменьшая его итоговый размер
23. Для чего используется инструкция `FROM` ? >> Определяет базовый образ, на основе которого строится новый
24. Какую информацию предоставляет инструкция `EXPOSE` ? >> Документирует в метаданных образа порт, который контейнер планирует использовать
25. Какой form рекомендуется для `CMD` и `ENTRYPOINT` в production? >> Exec form ( `["executable", "arg"]` ): процесс получает PID 1 и корректно реагирует на `SIGTERM` при остановке контейнера
26. За что отвечает переменная `PYTHONUNBUFFERED=1` ? >> Отключает буферизацию stdout/stderr: логи Python появляются немедленно, что критично для docker logs в production
27. Как взаимодействуют `ENTRYPOINT` и `CMD` , если указаны вместе? >> `ENTRYPOINT` задаёт исполняемый файл, `CMD` – аргументы по умолчанию для него; `docker run` заменяет только `CMD`
28. Какая инструкция задаёт переменные окружения, доступные и при сборке, и при запуске? >> `ENV`
29. Какая инструкция предпочтительнее для копирования локальных файлов: `ADD` или `COPY` ? >> `COPY` : поведение предсказуемо, она только копирует; `ADD` – только когда нужна распаковка архивов или загрузка по URL
30. В каком случае слой с `pip install` будет взят из кэша? >> Если `requirements.txt` не изменялся с момента предыдущей сборки
31. Что произойдёт при `docker run myapp --port 9000` , если `CMD` был `["--port", "8000"]` ? >> `CMD` заменится на `--port 9000` ; итого выполнится то, что задано в `ENTRYPOINT` , с аргументом `--port 9000`
32. Что делает `COPY . .` ? >> Копирует все файлы из текущей директории хоста в текущую рабочую директорию контейнера
33. Как принудительно переопределить `ENTRYPOINT` при `docker run` ? >> Флагом `--entrypoint` : `docker run --entrypoint bash myapp`
34. Что выполнит контейнер при `docker run myapp bash` , если задан `ENTRYPOINT ["uvicorn"]` ? >> `uvicorn bash` – `bash` становится аргументом для uvicorn, а не заменяет его
35. Для чего служит инструкция `CMD` ? >> Задаёт команду по умолчанию при запуске контейнера; легко переопределяется аргументами `docker run`
36. За что отвечает переменная `PYTHONDONTWRITEBYTECODE=1` ? >> Запрещает Python записывать файлы байт-кода ( `.pyc` ) на диск
37. Что характеризует образы с тегом `slim` (например, `python:3.11-slim` )? >> Минимальная сборка без лишних системных пакетов и инструментов; значительно меньший итоговый размер образа
