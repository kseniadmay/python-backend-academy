1. Где обычно устанавливается GitLab Runner при использовании self-hosted? >> На собственном сервере; регистрируется в GitLab через токен командой `gitlab-runner register`
2. Какой формат файлов используется для конфигурации GitHub Actions и GitLab CI? >> YAML
3. За что отвечает `flake8` в пайплайне? >> Проверяет стиль кода Python (PEP 8) и находит синтаксические ошибки
4. Что делает `cache: paths` в GitLab CI? >> Сохраняет указанные пути между запусками задач; ускоряет пайплайн за счёт кэширования зависимостей (например, `pip` или `node_modules` )
5. Что означает `when: always` в секции артефактов? >> Артефакты сохраняются независимо от успеха или провала задачи; удобно для сохранения отчётов при упавших тестах
6. Что означает `when: manual` в задаче deploy? >> Задача не запускается автоматически; требует явного нажатия кнопки в интерфейсе GitLab
7. Что определяет параметр `runs-on` в GitHub Actions? >> Тип раннера (окружение): `ubuntu-latest` , `windows-latest` , `macos-latest` или self-hosted
8. Для чего используется `reports: junit` в секции тестирования? >> Сохраняет результаты тестов в формате JUnit XML; GitLab отображает их прямо в интерфейсе MR
9. Какие два типа раннеров существуют в GitHub Actions? >> GitHub-hosted (облачные, управляются GitHub) и self-hosted (собственные серверы пользователя)
10. Где GitHub Actions и GitLab CI выполняют автоматизацию CI/CD? >> Непосредственно внутри Git-платформы; не требуют отдельного CI-сервера как Jenkins
11. Как называется стандартный файл конфигурации GitLab CI? >> `.gitlab-ci.yml` в корне репозитория
12. По какому пути располагаются файлы конфигурации GitHub Actions? >> `.github/workflows/*.yml` ; каждый `.yml` -файл – отдельный workflow
13. Что такое артефакты в контексте CI/CD? >> Файлы, сохраняемые после выполнения задачи и доступные для скачивания или передачи в следующие stages: отчёты тестов, Docker-образы, бинарники
14. Что такое `docker:dind` ? >> Docker in Docker – сервис, позволяющий запускать Docker-команды внутри CI-контейнера; нужен для сборки образов в GitLab CI
15. Что такое раннер (Runner)? >> Агент, который получает задачи из GitLab/GitHub и выполняет их на целевой машине; может быть облачным или self-hosted
16. За что отвечает секция `on` в GitHub Actions? >> Определяет триггеры запуска workflow: `push` , `pull_request` , `schedule` , `workflow_dispatch` и др.
17. Где хранятся секреты (API-ключи, пароли) в GitHub/GitLab? >> В защищённых настройках платформы (Secrets/Variables); в коде репозитория не хранятся, в логах маскируются
18. Чем `rules` в GitLab CI отличается от `only/except` ? >> `rules` – современная замена `only/except` ; поддерживает условия ( `if` , `changes` , `exists` ), более гибкая и не конфликтует с другими параметрами; `only/except` считаются устаревшими
19. Как в GitLab CI ограничить запуск задачи только для ветки `main` ? >> `only: - main` ; современный способ – `rules: - if: '$CI_COMMIT_BRANCH == "main"'`
20. Что делает `docker push` в CI/CD конвейере? >> Загружает собранный Docker-образ в container registry (GitLab Registry, Docker Hub, ECR и др.)
21. За что отвечает `mypy` в пайплайне? >> Выполняет статическую проверку типов в Python-коде на основе аннотаций
22. Для чего используется секция `variables` в GitLab CI? >> Для определения переменных окружения, доступных всем задачам пайплайна
23. Какая секция в GitLab CI определяет порядок этапов конвейера? >> `stages` ; задачи одного stage выполняются параллельно, stages – последовательно
24. В каком виде секреты доступны внутри задачи CI/CD? >> Как переменные окружения; доступны через `$SECRET_NAME` в скриптах
