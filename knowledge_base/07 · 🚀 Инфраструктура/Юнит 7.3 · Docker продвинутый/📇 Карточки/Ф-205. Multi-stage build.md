1. Что является главной целью multi-stage сборки? >> Минимизация итогового образа за счёт исключения инструментов сборки и промежуточных зависимостей из финального образа
2. Какую инструкцию необходимо использовать перед копированием файлов или установкой зависимостей? >> `WORKDIR` – задаёт рабочую директорию для всех последующих инструкций в данной стадии
3. Какая команда используется в примере как `CMD` для запуска приложения? >> `["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]`
4. Команда для сборки только стадии `builder` с тегом `myapp:builder` ? >> `docker build --target builder -t myapp:builder .`
5. Что происходит с промежуточными стадиями в итоговом образе? >> Их слои не включаются в финальный образ; на хосте они могут оставаться в кэше сборки для ускорения повторных сборок
6. С помощью какой опции `pip install` отключается сохранение кэша? >> `--no-cache-dir`
7. С помощью какого флага `docker build` можно собрать только конкретную стадию? >> `--target` : `docker build --target builder -t myapp:builder .`
8. Сколько инструкций `FROM` в multi-stage Dockerfile? >> Минимум две: одна для стадии сборки, одна для финальной стадии; количество не ограничено
9. Каков примерный размер стандартного образа `python:3.11` по сравнению с оптимизированным multi-stage? >> Стандартный ~900 МБ; с `python:3.11-slim` и multi-stage – ~200 МБ (числа приблизительные, зависят от зависимостей)
10. Что попадает в итоговый образ при правильной настройке multi-stage сборки? >> Только артефакты и компоненты, необходимые для запуска приложения
11. Зачем в финальной стадии изменяется переменная `ENV PATH` ? >> Чтобы система находила исполняемые файлы из скопированного `/root/.local/bin`
12. В инструкции `FROM python:3.11 AS builder` , какую роль играет `AS builder` ? >> Назначает имя стадии, чтобы ссылаться на неё в последующих инструкциях `COPY --from=builder`
13. Можно ли использовать `COPY --from` не только из предыдущей стадии, но и из внешнего образа? >> Да: `COPY --from=nginx:latest /etc/nginx/nginx.conf /etc/nginx/nginx.conf`
14. Какая технология Docker позволяет использовать несколько инструкций `FROM` в одном Dockerfile? >> Multi-stage сборка (многоэтапная сборка)
15. Зачем в качестве базового образа финальной стадии берут `python:3.11-slim` , а не `python:3.11` ? >> `slim` не содержит лишних системных пакетов и инструментов сборки; в сочетании с multi-stage даёт минимальный итоговый образ
16. Для чего используется стадия `builder` в сборке Python-приложения? >> Для установки зависимостей и сборки артефактов в изолированной среде; в финальный образ попадает только результат
17. Какая инструкция переносит файлы из стадии `builder` в финальную стадию? >> `COPY --from=builder /путь/в/builder /путь/в/финальном`
18. В примере пакеты Python устанавливаются в `/root/.local` на стадии `builder` – зачем именно туда? >> Чтобы скопировать только директорию с пакетами в финальный образ, не устанавливая pip и setuptools заново
19. Что такое Multi-stage сборка? >> Метод оптимизации Dockerfile, при котором процесс разбивается на этапы; финальный образ содержит только артефакты из нужных стадий, без инструментов сборки
