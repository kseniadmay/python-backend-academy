1. На какие уровни настраивают автоматические алерты? >> `ERROR` и `CRITICAL` ; `WARNING` чаще мониторят в дашбордах, но не алертят немедленно
2. На каком уровне логировать попадание/промах кэша (cache hit/miss)? >> `DEBUG` (техническая деталь внутренней работы, полезная только при отладке)
3. Мнемоника для выбора уровня: «я умираю»? >> `CRITICAL` (фатальная авария, сервис не может продолжать работу)
4. На каком уровне логировать полную недоступность БД, делающую невозможными операции записи? >> `CRITICAL` (система полностью потеряла работоспособность, нужен немедленный алерт дежурному)
5. На каком уровне логировать слишком долгое выполнение запроса? >> `WARNING` (запрос выполнился, но превысил порог SLA — признак деградации)
6. Чем `CRITICAL` отличается от `ERROR` с точки зрения реагирования? >> `ERROR` – часть функциональности нарушена, приложение продолжает работу; `CRITICAL` – приложение полностью теряет работоспособность и требует немедленного вмешательства
7. На каком уровне логировать успешное завершение Celery-задачи? >> `INFO` (штатное бизнес-событие жизненного цикла фоновой задачи)
8. На каком уровне логировать создание нового заказа? >> `INFO` (ключевое бизнес-событие в нормальной работе сервиса)
9. На каком уровне логировать ответ внешнего API с кодом 500? >> `ERROR` (конкретная операция завершилась сбоем из-за отказа внешней зависимости)
10. Мнемоника для выбора уровня: «это произошло в штатном режиме»? >> `INFO` (подтверждение того, что система работает как задумано)
11. Мнемоника для выбора уровня: «это странно, но я справляюсь»? >> `WARNING` (аномалия или пограничная ситуация, которую удалось обойти, например через fallback/retry)
12. На каком уровне логировать заполненный диск, из-за которого логи не записываются? >> `CRITICAL` (исчерпание системного ресурса, грозящее полным падением процесса)
13. На каком уровне логировать SQL-запрос с параметрами? >> `DEBUG` ; детали запросов нужны только при отладке и избыточны в production
14. Какие уровни попадут в лог при `logger.setLevel(logging.WARNING)` ? >> `WARNING` , `ERROR` , `CRITICAL` ; `DEBUG` и `INFO` будут проигнорированы
15. На каком уровне логировать использование устаревшего API endpoint? >> `WARNING` (функциональность пока работает, но требует планового обновления клиента)
16. На каком уровне логировать временную недоступность Redis, если приложение переключилось на БД? >> `WARNING` ; сервис деградировал, но продолжает работать
17. На каком уровне логировать ошибку подключения к БД? >> `ERROR` (текущий запрос или операция не смогли выполниться из-за сбоя соединения)
18. Мнемоника для выбора уровня: «только для разработчика при отладке»? >> `DEBUG` (подробная диагностика переменных и шагов алгоритма, отключаемая в продакшене)
19. На каком уровне логировать запуск сервера на порту? >> `INFO` (штатное событие старта сервиса и готовности принимать трафик)
20. Числовые значения уровней логирования Python? >> `DEBUG=10` , `INFO=20` , `WARNING=30` , `ERROR=40` , `CRITICAL=50` ; используются при программной проверке `logger.isEnabledFor(level)`
21. Как установить минимальный порог логирования программно? >> `logger.setLevel(logging.WARNING)` ; сообщения ниже порога игнорируются без форматирования строки
22. Мнемоника для выбора уровня: «я не смог выполнить то, что должен был»? >> `ERROR` (ошибка при выполнении конкретной бизнес-операции или HTTP-запроса)
23. Какие уровни обычно устанавливают порогом на production? >> `INFO` или `WARNING` ; `DEBUG` в production создаёт избыточный шум и замедляет приложение
