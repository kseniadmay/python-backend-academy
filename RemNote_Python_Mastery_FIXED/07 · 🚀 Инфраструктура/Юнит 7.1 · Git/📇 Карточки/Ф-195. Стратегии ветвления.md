1. Что является триггером для создания `hotfix/*` в Gitflow? >> Обнаружение критического бага в production
2. Что критически необходимо для успешного применения TBD? >> Высокая дисциплина команды, зрелый CI, автотесты с высоким покрытием и система feature flags
3. От какой ветки в Gitflow ответвляются `release/*` -ветки? >> `develop`
4. В какой ветке Gitflow хранится только production-ready код? >> `main` ; каждый коммит в неё соответствует релизу и помечается тегом версии
5. Какая ветка в Gitflow служит основной интеграционной веткой? >> `develop` ; сюда вливаются завершённые feature-ветки и из неё ответвляются `release/*`
6. В какие ветки вливается завершённая `hotfix/*` ? >> В `main` (с тегом) и в `develop` ; если существует активная `release/*` – также в неё
7. Какой механизм в TBD позволяет мержить незавершённый код в `main` без влияния на пользователей? >> Feature flags (флаги фич): неготовая функциональность скрыта за переключателем в коде
8. Какую стратегию выбрать команде SaaS-сервиса с ежедневными обновлениями? >> Trunk-based Development
9. Для каких продуктов лучше всего подходит Gitflow? >> Для продуктов с версионированием и плановыми релизами: коробочное ПО, мобильные приложения, библиотеки
10. От какой ветки в Gitflow ответвляются `feature/*` -ветки? >> `develop`
11. Какая стратегия ветвления характеризуется чёткой иерархией долгоживущих веток? >> Gitflow
12. Для чего используются теги в ветке `main` при Gitflow? >> Для фиксации версий продукта; тег создаётся командой `git tag v1.2.0` после слияния релиза
13. Для чего используется ветка `release/*` в Gitflow? >> Для финальной подготовки версии перед релизом: допускаются только фиксы и обновление номера версии; новые фичи не добавляются
14. В чём главное отличие Gitflow от TBD по скорости доставки изменений? >> Gitflow – медленный плановый цикл релизов; TBD – непрерывная доставка с деплоем после каждого merge в `main`
15. Почему TBD хорошо совместим с CI/CD? >> Частые интеграции в `main` запускают CI-пайплайн и деплой; отсутствие долгоживущих веток устраняет «ад слияний»
16. Каков максимальный рекомендуемый срок жизни feature-ветки в TBD? >> 1–2 дня; долгоживущие ветки – антипаттерн, ведущий к сложным слияниям
17. Назови основное преимущество Gitflow? >> Чёткая структура и изоляция работ: фичи, релизы и хотфиксы развиваются параллельно без взаимного влияния
18. Для каких продуктов идеально подходит TBD? >> SaaS и сервисы с непрерывной доставкой (continuous delivery)
19. В какие ветки вливается завершённая `release/*` ? >> В `main` (с тегом версии) и в `develop` (чтобы фиксы не потерялись)
20. Какую стратегию выбрать команде, выпускающей коробочное ПО с чёткими номерами версий? >> Gitflow
21. Назови основные минусы Gitflow? >> Медленный цикл доставки; большое количество merge-коммитов; сложность поддержки нескольких долгоживущих веток
22. Какая стратегия минимизирует риск merge hell? >> TBD: частые маленькие интеграции в `main` не дают веткам расходиться
23. От какой ветки в Gitflow ответвляются `hotfix/*` -ветки? >> `main` ; исправление критического бага в продакшене должно базироваться на актуальном релизном коде
24. Что такое Trunk-based Development (TBD)? >> Стратегия, при которой все разработчики интегрируют изменения в одну главную ветку ( `trunk` / `main` ) как можно чаще – в идеале ежедневно
