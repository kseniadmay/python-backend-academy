1. Какую роль очередь играет при пиковых нагрузках? >> Выступает буфером между потоком входящих запросов и мощностями обработки; воркеры берут задачи по мере возможности
2. Почему в `delay()` передают `order.id` , а не весь объект заказа? >> Объекты не сериализуются напрямую; ID компактен, безопасен для сериализации и не устареет к моменту выполнения задачи
3. Когда НЕ стоит выносить операцию в фоновую очередь? >> Когда результат нужен пользователю немедленно (создание ID заказа); операции < 100 мс (overhead очереди не оправдан); операции, требующие строгой транзакционности с основным запросом
4. Что рекомендуется возвращать пользователю, если генерация отчёта занимает много времени? >> `task_id` и статус `queued` ; клиент опрашивает `/reports/{task_id}/status` для проверки готовности
5. Чем Loose Coupling отличается от Tight Coupling при добавлении нового уведомления? >> Tight Coupling: нужно менять код `OrderService` ; Loose Coupling: добавляется новый воркер-подписчик без изменения основного сервиса
6. Почему задачи с требованием строгой транзакционности плохо подходят для очередей? >> Запись в БД и задача в очереди – разные системы; гарантировать их одновременный успех/откат сложно
7. Что улучшается для пользователя при переносе тяжёлых операций в очередь? >> Latency (время отклика): вместо 5+ секунд пользователь получает ответ за ~50 мс
8. Что такое Loose Coupling в контексте Celery? >> `OrderService` отправляет событие в очередь, не зная, кто его обработает; добавление нового обработчика не требует изменения `OrderService`
9. Какой объект возвращает `.delay()` ? >> `AsyncResult` ; через него можно получить `task_id` , `status` , `result`
10. В чём главная проблема синхронной обработки тяжёлых задач в HTTP-запросе? >> Блокирует поток и заставляет пользователя ждать; при сбое внешнего сервиса весь запрос падает с ошибкой
11. Как очереди влияют на масштабируемость? >> Тяжёлые задачи распределяются между воркерами независимо от веб-сервера; можно масштабировать воркеры отдельно от API
12. Как очереди изолируют ошибки? >> Ошибка в фоновой задаче (PDF) не влияет на другие задачи и не мешает возврату ответа пользователю
13. Как очереди помогают при временной недоступности внешнего API? >> Задача остаётся в очереди и автоматически повторяется через `max_retries` и `default_retry_delay`
14. Какие задачи являются лучшими кандидатами для фоновых очередей? >> Email, SMS, push-уведомления; генерация PDF/отчётов; обработка изображений/видео; ML inference; интеграции с внешними API; массовые рассылки
15. Почему обновление курсов валют нельзя делать в теле HTTP-запроса? >> Это периодическое действие, не привязанное к пользователю; случайный запрос замедлится, при высокой нагрузке создаётся избыточная нагрузка на сервис
