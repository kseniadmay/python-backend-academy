## Определение

Операция **идемпотентна**, если повторное её выполнение с теми же параметрами приводит к тому же результату, что и однократное – независимо от того, сколько раз она была вызвана: один раз или сто. Это не про то, "быстро ли отработает повтор" – это про то, что **состояние системы после N одинаковых вызовов совпадает с состоянием после 1 вызова**.

---

## Почему это критично именно в распределённых системах

Сеть ненадёжна: клиент может отправить запрос, не получить ответ вовремя (таймаут) и не знать, дошёл ли запрос до сервера – обработан он или нет. Единственный безопасный выход в такой неопределённости – **повторить запрос** (retry). Если операция не идемпотентна, повтор может привести к повторному списанию денег, повторному созданию заказа, дублированному письму – именно поэтому идемпotентность – не теоретическая тонкость, а требование к любому API, где предполагаются ретраи (а они предполагаются почти всегда).

---

## HTTP-методы и идемпотентность по стандарту

```http
GET    /users/5        - идемпотентен: повторное чтение не меняет состояние
PUT    /users/5        - идемпотентен: повторная запись ТЕХ ЖЕ данных даёт тот же результат
DELETE /users/5        - идемпотентен: удаление уже удалённого - то же конечное состояние (объекта нет)
POST   /orders         - НЕ идемпотентен: каждый вызов создаёт НОВЫЙ заказ
PATCH  /users/5        - по стандарту не гарантированно идемпотентен (зависит от семантики патча)
```

`PUT` идемпотентен, потому что полностью заменяет ресурс заданными значениями – второй такой же `PUT` замену не изменит. `POST` по своей природе означает "создать новую сущность" – второй одинаковый `POST` создаст вторую сущность, это ожидаемое, не идемпотентное поведение.

## Idempotency-Key – идемпотентность для операций, которые обязаны быть POST

Создание платежа, заказа – семантически это `POST` (создание), но повторный сетевой сбой не должен создавать второй платёж. Решение – клиент сам генерирует уникальный **ключ идемпотентности** и передаёт его с каждой попыткой одного и того же запроса:

```python
import uuid

idempotency_key = str(uuid.uuid4())  # клиент генерирует один раз для одной 'попытки операции'
```

## Реализация на стороне сервера

```python
def create_payment(request_data, idempotency_key):
    existing = IdempotencyRecord.objects.filter(key=idempotency_key).first()
    if existing:
        return existing.response_data  # уже обработан – просто вернуть тот же результат

    with transaction.atomic():
        payment = Payment.objects.create(**request_data)
        IdempotencyRecord.objects.create(
            key=idempotency_key,
            response_data={'id': payment.id, 'status': 'created'},
        )
    return {'id': payment.id, 'status': 'created'}
```

Ключ и результат первой обработки сохраняются атомарно вместе с самой операцией (в одной транзакции) – иначе возможна гонка: два одновременных запроса с одним ключом оба не найдут существующую запись и оба создадут платёж.

## Где ещё встречается на практике

Обработчики очередей задач (Celery) обязаны быть идемпотентными – брокер сообщений (RabbitMQ, Kafka) в общем случае гарантирует доставку **at-least-once** (см. тему про очереди сообщений), то есть одна и та же задача теоретически может быть доставлена и обработана дважды. UPSERT в базе данных (`INSERT ... ON CONFLICT DO UPDATE`) – идемпотентный способ записи, в отличие от простого `INSERT`, который упадёт или создаст дубль при повторе.

---

## Когда использовать

Идемпотентность нужно закладывать явно в любой эндпоинт, создающий или изменяющий состояние с финансовыми или иначе необратимыми последствиями (платежи, заказы, отправка уведомлений), и в любой обработчик фоновых задач, который брокер может доставить повторно. Для чтения (`GET`) и полной замены (`PUT`) идемпотентность обычно достигается естественно самой семантикой операции и не требует дополнительных усилий.
