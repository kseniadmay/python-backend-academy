## Зачем нужна пагинация в API

Возвращать из эндпоинта `GET /orders` весь миллион записей из таблицы — верный способ положить и базу данных, и Python-воркер (Out of Memory при сериализации в JSON), и браузер клиента. Любой списочный эндпоинт в продакшене обязан отдавать данные порциями (**страницами**).

В бэкенд-разработке используются два основных механизма пагинации: **Offset-пагинация** (`limit` / `offset`) и **Cursor-пагинация** (`keyset` / `seek`). Вопрос об их различиях и деградации `OFFSET` на больших таблицах — один из самых частых на собеседованиях уровня Junior+ и Middle.

## Offset-пагинация (`LIMIT` / `OFFSET`) и её две роковые проблемы

Клиент передаёт размер страницы и смещение: `GET /products?limit=20&offset=40` (или `page=3&page_size=20`). В SQL это транслируется в:

```sql
SELECT id, title, created_at
FROM products
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;
```

На небольших таблицах (до десятков тысяч строк) этот подход удобен: он позволяет легко рисовать номера страниц (`1, 2, 3 ... 50`) и прыгать сразу на любую страницу. Но на больших и активно меняющихся таблицах у `OFFSET` возникают **две фундаментальные проблемы**:

- **1. Линейная деградация производительности $O(\text{OFFSET})$**: чтобы выполнить `LIMIT 20 OFFSET 1000000`, СУБД не может «перепрыгнуть» миллион записей. Она вынуждена **прочитать с диска и отсортировать 1 000 020 строк**, отбросить первые 1 000 000 в корзину и вернуть оставшиеся 20. Чем глубже страница, тем медленнее запрос.
- **2. Дрейф строк (дубликаты и пропуски при вставке/удалении)**: пока пользователь читает первую страницу (`offset=0`, записи 1–20), в таблицу добавляются 2 новых товара. Когда пользователь запрашивает вторую страницу (`offset=20`), старые записи 19 и 20 сдвигаются на позиции 21 и 22 и **приходят повторно** на второй странице. При удалении записей часть элементов, наоборот, бесследно пропадает между страницами.

## Cursor-пагинация (Keyset / Seek Pagination)

Вместо номера строки клиент передаёт **курсор** — значение поля сортировки последнего увиденного элемента (обычно зашифрованное в непрозрачную строку `base64`, например `cursor=MjAyNS0wNS0wMVQxMjowMDowMF8xMDQy`).

Если сортировка идёт по уникальному монотонно растущему полю `id` (или по связке `(created_at, id)` для разрешения коллизий времени), SQL-запрос использует индексное условие `WHERE` вместо `OFFSET`:

```sql
SELECT id, title, created_at
FROM products
WHERE (created_at, id) < ('2025-05-01 12:00:00', 1042)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Почему это работает за **$O(\log N)$ даже на миллиарде строк**:

- СУБД по B-Tree индексу `(created_at, id)` мгновенно встаёт ровно на запись `1042` и читает следующие 20 элементов подряд. Сложность 1-й и 50 000-й страницы одинакова!
- При добавлении новых записей в начало ленты указатель `id < 1042` остаётся привязанным к конкретному элементу, поэтому **нет ни дубликатов, ни пропусков**.
- **Единственный компромисс**: нельзя перепрыгнуть сразу на «страницу № 45» — навигация работает только последовательно («Следующая страница» / бесконечный скролл в лентах соцсетей, чатах, истории транзакций).

```python
import base64
from datetime import datetime
from typing import Optional
from pydantic import BaseModel

def encode_cursor(created_at: datetime, item_id: int) -> str:
    raw = f'{created_at.isoformat()}|{item_id}'
    return base64.urlsafe_b64encode(raw.encode()).decode()

def decode_cursor(cursor: str) -> tuple[datetime, int]:
    raw = base64.urlsafe_b64decode(cursor.encode()).decode()
    ts_str, id_str = raw.split('|', 1)
    return datetime.fromisoformat(ts_str), int(id_str)

class CursorPage(BaseModel):
    items: list[dict]
    next_cursor: Optional[str] = None
    has_more: bool
```

💡 **Хитрый приём определения `has_more` без `COUNT(*)`**: чтобы узнать, есть ли следующая страница, не делайте дорогой `SELECT COUNT(*)`. Запросите из базы `LIMIT (limit + 1)` записей (например, 21 вместо 20). Если вернулась 21 запись — значит `has_more = True`, а клиенту отдаём первые 20.

## Единый стандарт ошибок API: Problem Details (RFC 7807 / RFC 9457)

В плохом API один эндпоинт возвращает `{"error": "Not found"}`, другой — `{"msg": ["Invalid email"]}`, а третий — HTML-страницу `500 Internal Server Error`. Клиентскому приложению приходится писать десятки костылей для парсинга ошибок.

Индустриальный стандарт **RFC 7807 (обновлён в RFC 9457) — Problem Details for HTTP APIs** задаёт единую JSON-структуру для всех ошибок (`Content-Type: application/problem+json`):

- **`type`** – URI-идентификатор типа бизнес-ошибки (например, `https://api.example.com/errors/insufficient-funds`).
- **`title`** – краткое человекочитаемое название типа ошибки.
- **`status`** – HTTP-статус код (`400`, `403`, `404`, `409`, `422`).
- **`detail`** – конкретное описание причины для данного вызова.
- **`instance`** – путь запроса или уникальный `request_id` / `trace_id` для быстрого поиска в логах.

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

class DomainError(Exception):
    def __init__(self, code: str, title: str, detail: str, status: int = 400):
        self.code = code
        self.title = title
        self.detail = detail
        self.status = status

@app.exception_handler(DomainError)
async def domain_error_handler(request: Request, exc: DomainError):
    return JSONResponse(
        status_code=exc.status,
        media_type='application/problem+json',
        content={
            'type': f'https://api.example.com/errors/{exc.code}',
            'title': exc.title,
            'status': exc.status,
            'detail': exc.detail,
            'instance': str(request.url.path),
        },
    )
```

Такой контракт отделяет внутренние исключения Python от публичного протокола API и никогда не раскрывает клиенту стектрейсы (`Traceback`) или структуру таблиц БД.
