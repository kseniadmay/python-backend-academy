## OpenAPI vs Swagger: в чём разница

Это разные вещи, которые часто путают. **OpenAPI** – отраслевой стандарт (спецификация) для описания REST API в формате YAML или JSON. **Swagger** – набор инструментов от компании SmartBear, которые работают с OpenAPI: визуализируют схему, предоставляют интерактивный UI, генерируют код. Называть спецификацию «сваггером» – методологическая неточность: корректно «OpenAPI-схема», «Swagger UI» – для интерфейса.

Проблема, которую решает OpenAPI: когда фронтенд и бэкенд разрабатываются параллельно, фронтенд может ожидать поле `user_id`, а бэкенд вернуть `userId` – интеграция ломается в самый неподходящий момент. OpenAPI формализует контракт: какие эндпоинты существуют, какие данные принимают, что возвращают и какие ошибки возможны.

## Структура OpenAPI-схемы

```yaml
openapi: 3.0.0
info:
  title: Users API
  version: 1.0.0

paths:
  /users:
    get:
      summary: Получить список пользователей
      parameters:
name: limit
          in: query
          schema:
            type: integer
            default: 20
      responses:
        '200':
          description: Список пользователей
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/User'

components:
  schemas:
    User:
      type: object
      properties:
        id:
          type: integer
        name:
          type: string
```

`openapi` – версия стандарта. `info` – метаданные API. `paths` – описание всех эндпоинтов: методы, параметры, тела запросов, форматы ответов. В `parameters` параметр `in: query` точно указывает, где ожидать значение – в пути (`path`), строке запроса (`query`) или заголовке (`header`). `components/schemas` – принцип DRY: модели описываются один раз и переиспользуются через `$ref`, устраняя дублирование.

## FastAPI: разделяй модели запроса и ответа

В FastAPI схема генерируется из Pydantic-моделей и аннотаций типов автоматически – схема доступна по `/openapi.json`, Swagger UI – по `/docs`, ReDoc – по `/redoc`. Важный паттерн – отдельные модели для входящих и исходящих данных, это не перестраховка, а осознанный дизайн:

```python
from fastapi import FastAPI, Path, Query
from pydantic import BaseModel, Field
from typing import Optional

app = FastAPI(title='Orders API', version='1.0.0')

class OrderCreate(BaseModel):
    user_id: int = Field(..., description='ID пользователя')
    items: list = Field(..., min_length=1)
    comment: Optional[str] = None

class OrderResponse(BaseModel):
    id: int
    user_id: int
    status: str
    total: float

@app.post('/orders', response_model=OrderResponse, status_code=201,
          summary='Создать заказ', tags=['orders'])
async def create_order(order: OrderCreate):
    ...

@app.get('/orders/{order_id}', response_model=OrderResponse)
async def get_order(
    order_id: int = Path(..., ge=1),
    include_items: bool = Query(False),
):
    ...
```

`OrderCreate` не содержит `id` – клиент не может знать ID заказа до его создания. `OrderResponse` содержит системные поля (`id`, `status`, `total`), вычисленные сервером. `summary`/`tags` группируют эндпоинты по смыслу в документации – без них в проекте со ста методами невозможно ориентироваться. **Path-параметры** (`order_id`) встроены в URL и идентифицируют ресурс, `ge=1` – валидация прямо на уровне схемы. **Query-параметры** (`include_items`) передаются после `?` – для фильтрации, сортировки, опций. Правило: идентификатор ресурса – в путь, фильтр/опция – в query.

## Коды ответов как часть контракта

`201 Created` – стандарт для успешного создания ресурса (не `200`). `400 Bad Request` – некорректные данные от клиента. `404 Not Found` – ресурс не существует. `422 Unprocessable Entity` – FastAPI возвращает автоматически, когда данные не прошли валидацию Pydantic. Документирование кодов ошибок – контракт для клиентской стороны: мобильный разработчик может заранее прописать обработку каждого кода, не дожидаясь, пока пользователь на него наткнётся.

## Django REST Framework: drf-spectacular

```python
INSTALLED_APPS = ['drf_spectacular']
REST_FRAMEWORK = {
    'DEFAULT_SCHEMA_CLASS': 'drf_spectacular.openapi.AutoSchema',
}
```

`drf-spectacular` анализирует Serializers и Views DRF-проекта и генерирует OpenAPI-схему тем же принципом, что и FastAPI – из уже существующего кода, а не вручную.

## Code First против Design First

**Code First** – документация генерируется автоматически из кода (модели и декораторы → JSON-спецификация → Swagger UI). Документация всегда актуальна, потому что она и есть код – так работают FastAPI и DRF с `drf-spectacular` в подавляющем большинстве реальных проектов. **Design First** – спецификация пишется вручную в YAML до написания кода, используется в крупных командах, где API нужно согласовать между несколькими командами раньше, чем будет написана первая строчка бэкенда.

---

## Почему это важно на практике

**Единый источник истины** – документация не «протухает» после рефакторинга. **Интерактивная песочница** – Swagger UI позволяет отправлять реальные запросы из браузера, фронтенд-разработчик исследует API самостоятельно, не дёргая бэкендера. **Автогенерация клиентских SDK** – из OpenAPI-файла можно сгенерировать клиентские библиотеки на любом языке через `openapi-generator`. **Контракт для команды** – изменение схемы становится явным событием, а не молчаливым изменением кода.
