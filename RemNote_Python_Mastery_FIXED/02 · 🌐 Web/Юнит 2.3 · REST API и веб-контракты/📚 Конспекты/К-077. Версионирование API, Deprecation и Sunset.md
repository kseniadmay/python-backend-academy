## Зачем версионировать API

API – это контракт между поставщиком и потребителем. Изменение структуры ответа, удаление поля или переименование эндпоинта – это разрыв контракта, который ломает клиентский код. Версионирование позволяет нескольким версиям API сосуществовать, пока потребители мигрируют на новую.

---

## Три способа версионирования

**Версия в URL** – самый распространённый подход в индустрии:

```http
https://api.example.com/v1/users
https://api.example.com/v2/users
```

Легко тестировать в браузере, легко логировать, легко объяснять. Stripe, GitHub, Twitter используют именно этот подход. С точки зрения строгого REST `/v1/users` и `/v2/users` – разные ресурсы, и это технически «нечисто». Но на практике отлаживаемость и простота обнаружения важнее архитектурного пуризма.

**Версия в заголовке** – URL остаётся стабильным, версия передаётся в `Accept`:

`Accept: application/vnd.myapi.v2+json`

Академически чище, но отладка сложнее: браузер не поможет, нужны специальные инструменты.

**Версия в query-параметре** – проще всего реализовать:

`GET /users?api_version=v2`

Работает, но воспринимается как менее зрелое решение. Подходит для внутренних API.

## Жизненный цикл версии: три состояния

Зрелая стратегия поддержки обычно выглядит так. Старая версия (`v1`) переходит в статус **Deprecated** – она ещё работает в полном объёме, но развитие прекращено. Текущая версия (`v2`) – стабильная, рекомендованная для всех новых интеграций. Следующая версия (`v3`) находится в разработке и обкатывает будущие breaking changes.

**Deprecation период** – не формальность, а критически важный этап. Он даёт потребителям время на миграцию без экстренных правок в production. Разрыв контракта без предупреждения – это нарушение доверия и потенциальные инциденты у партнёров.

## HTTP-заголовки для автоматизации: `Deprecation` и `Sunset`

Вместо того чтобы только рассылать письма, зрелые API используют стандартные HTTP-заголовки. Клиентские библиотеки умеют их читать и автоматически генерировать предупреждения в логах разработчиков.

**`Deprecation: true`** – мягкое предупреждение: эндпоинт всё ещё работает, но использование не рекомендуется.

**`Sunset: <date>`** – жёсткий дедлайн: точная дата и время отключения в формате HTTP-date с часовым поясом GMT.

```http
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 31 Dec 2024 23:59:59 GMT
Content-Type: application/json
```

После наступления даты из заголовка `Sunset` поставщик API технически и юридически свободен от обязательств по поддержке эндпоинта. Риск поломки переходит на потребителя, который был заблаговременно уведомлён. Это смещает ответственность и снимает «внезапность» breaking change.

## Что считается breaking change

Важно понимать, что ломает обратную совместимость, а что нет.

**Ломает**: удаление поля из ответа, изменение типа поля, переименование поля, удаление эндпоинта, изменение семантики существующего метода.

**Не ломает**: добавление нового необязательного поля в ответ, добавление нового эндпоинта, добавление нового необязательного параметра запроса.

Это важно при планировании эволюции API: аддитивные изменения можно вносить без новой версии, разрушительные требуют создания `v2` и deprecation-периода для `v1`.
