## Зачем нужен посредник между сервером и приложением

Веб-сервер (Nginx, Apache) и Python-фреймворк (Django, Flask, FastAPI) написаны независимо друг от друга – без общего стандарта каждому фреймворку пришлось бы поддерживать интеграцию с каждым сервером отдельно. **WSGI** и **ASGI** – стандартизированные интерфейсы (спецификации), которые описывают, как сервер передаёт запрос приложению и получает от него ответ, независимо от того, какой именно сервер и какой именно фреймворк используются.

---

## WSGI – синхронный стандарт

**WSGI** (Web Server Gateway Interface, PEP 3333) – стандарт для синхронных Python-приложений, действующий с 2003 года. Приложение – это просто вызываемый объект (callable), принимающий окружение запроса и функцию для начала ответа:

```python
def simple_app(environ, start_response):
    status = '200 OK'
    headers = [('Content-Type', 'text/plain')]
    start_response(status, headers)
    return [b'Hello, WSGI!']
```

Django и Flask по умолчанию – WSGI-приложения. WSGI-сервер (например, **Gunicorn**) обрабатывает запросы, создавая несколько worker-процессов – но каждый отдельный worker обрабатывает **один запрос за раз синхронно**: пока идёт обращение к базе данных, этот worker простаивает и не может взять следующий запрос.

---

## ASGI – асинхронный стандарт

**ASGI** (Asynchronous Server Gateway Interface) – более новый стандарт (с 2016 года), спроектированный для поддержки `async`/`await`, WebSocket и долгоживущих соединений, чего WSGI принципиально не умеет.

```python
async def simple_asgi_app(scope, receive, send):
    await send({
        'type': 'http.response.start',
        'status': 200,
        'headers': [(b'content-type', b'text/plain')],
    })
    await send({
        'type': 'http.response.body',
        'body': b'Hello, ASGI!',
    })
```

FastAPI изначально построен на ASGI. ASGI-сервер (например, **Uvicorn**) может обрабатывать множество запросов конкурентно в одном worker-процессе через event loop (см. тему про asyncio) – пока один запрос ждёт ответа от базы данных, worker уже обрабатывает следующий.

## Практическое следствие для деплоя

```bash
gunicorn myproject.wsgi:application  --workers 4

uvicorn myproject.main:app  --workers 4
```

Django поддерживает ASGI начиная с версии 3.0 (для WebSocket, через `Django Channels`), но по умолчанию и исторически остаётся WSGI-приложением для обычных HTTP-запросов. Flask – классический WSGI (есть отдельный проект Quart с похожим API поверх ASGI). Путать их на практике – частая ошибка: попытка запустить Django через `uvicorn myproject.wsgi:application` не сработает, потому что WSGI-приложение не реализует ASGI-протокол (и наоборот).

---

## Когда использовать

WSGI – для классических запрос-ответ приложений без длинных соединений и без остро критичного числа конкурентных запросов на воркер: административные панели, CRUD-приложения, сайты с относительно невысокой нагрузкой на I/O. ASGI – когда приложению нужны WebSocket, Server-Sent Events, много конкурентных операций I/O (внешние API, БД) на один процесс, или когда фреймворк (FastAPI) изначально спроектирован вокруг `async`/`await`. Выбор WSGI vs ASGI – по сути выбор конкретного фреймворка (Django/Flask vs FastAPI), а не отдельное решение, принимаемое независимо.
