## Проблема: HTTP stateless по природе

HTTP не сохраняет состояние между запросами. Каждый запрос для сервера – чистый лист: он не помнит, что вы делали секунду назад, авторизованы ли вы и что лежит в вашей корзине. Cookies и сессии – механизмы, которые решают эту проблему.

---

## Cookies: транспортный механизм идентификатора

**Cookie** – небольшой фрагмент текста, которым сервер помечает браузер. Механизм прост: при первом ответе сервер отправляет заголовок `Set-Cookie`, браузер сохраняет значение и автоматически добавляет его в каждый последующий запрос к этому домену через заголовок `Cookie`.

`Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict; Max-Age=3600`

Атрибуты кук критически важны для безопасности. `**HttpOnly**` запрещает доступ к куке через `document.cookie` в JavaScript – даже если злоумышленник внедрил скрипт через XSS, он не сможет украсть сессионный токен. `**Secure**` разрешает передачу куки только по HTTPS, защищая от перехвата в открытых сетях. `**SameSite**` регулирует отправку куки при переходах с других сайтов и защищает от CSRF-атак: `Strict` – только внутри сайта, `Lax` – разрешает в безопасных сценариях (например, при переходе по ссылке), `None` – без ограничений (требует `Secure`). `**Max-Age**` задаёт время жизни в секундах; без него кука сессионная – удаляется при закрытии браузера.

Никогда не создавайте сессионные куки без `HttpOnly` и `Secure` – это базовый стандарт безопасности.

## Сессии: данные хранятся на сервере

Хранить чувствительные данные прямо в куке нельзя по двум причинам. Во-первых, данные на стороне клиента легко подделать. Во-вторых, кука ограничена 4 КБ.

Сессии решают эту проблему: все данные пользователя хранятся на сервере (в Redis, базе данных или памяти), а в куке передаётся только `session_id` – ключ для доступа к этим данным.

Схема работы: пользователь авторизуется, сервер создаёт запись в хранилище сессий с контекстом (user_id, роли, корзина), генерирует уникальный `session_id` и отправляет его в куке. При каждом следующем запросе сервер читает `session_id` из куки, обращается к хранилищу и восстанавливает контекст пользователя.

## Сессии в Django

Django абстрагирует работу с сессиями – вам не нужно вручную управлять заголовками:

```python
from django.contrib.auth import authenticate, login

def login_view(request):
    user = authenticate(request, username='admin', password='password123')
    if user:
        login(request, user)  # создаёт сессию, добавляет Set-Cookie в ответ
        request.session['cart'] = ['laptop', 'mouse']  # как обычный словарь

def dashboard_view(request):
    cart = request.session.get('cart', [])  # Django уже восстановил сессию
    return render(request, 'dashboard.html', {'cart': cart})
```

`login()` запускает session engine: генерирует ключ, создаёт запись в хранилище и добавляет `Set-Cookie` в ответ. Всё это происходит под капотом.

По умолчанию Django хранит сессии в базе данных. Для production с высокой нагрузкой сессии переносят в **Redis** – он быстрее и не нагружает основную БД.

## Сессии vs JWT: когда что выбирать

Это частый вопрос на собеседованиях, и здесь важно знать trade-off, а не просто называть преимущества.

**Сессии (stateful)** хранят состояние на сервере. Главное преимущество – мгновенный отзыв: нужно заблокировать пользователя – просто удаляешь запись из Redis. Недостаток – масштабирование: при горизонтальном росте все серверы должны иметь доступ к общему хранилищу сессий.

**JWT (stateless)** хранят данные в самом токене на стороне клиента. Серверу не нужно обращаться к базе для проверки – он просто валидирует подпись. Идеально для микросервисов и мобильных API. Главный недостаток – сложность отзыва: токен действует до истечения срока, и досрочно заблокировать его без blacklist на сервере невозможно.

Для монолитных приложений на Django – сессии. Переходить на JWT стоит при построении распределённых систем или если несколько независимых сервисов должны принимать один и тот же токен без обращения к центральному хранилищу.
