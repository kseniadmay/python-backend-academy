## Как работает SQL-инъекция

Уязвимость возникает, когда пользовательский ввод подставляется напрямую в SQL-запрос через конкатенацию строк:

```python
query = f"SELECT * FROM users WHERE username = '{username}'"
```

Если пользователь вводит обычное имя – всё работает. Если вводит `admin' --`, запрос трансформируется:

`SELECT * FROM users WHERE username = 'admin' --'`

Символ `'` закрывает строковое значение раньше времени. Последовательность `--` комментирует всё, что идёт после – включая проверку пароля. База данных выполняет именно это, потому что не различает «логику запроса» и «данные пользователя» – они смешаны в одну строку.

---

## Что может сделать злоумышленник

**Обход аутентификации.** Ввод `admin' --` позволяет войти в систему без знания пароля: условие проверки пароля закомментировано.

**Уничтожение данных.** Ввод `'; DROP TABLE users; --` заставляет базу выполнить две команды: пустой поиск и удаление всей таблицы. База данных не знает, что это не санкционированная команда – она выполняет валидный SQL.

В обоих случаях атака работает с правами приложения. Если у приложения есть права на `DROP` – злоумышленник тоже получает эти права.

## Единственная надёжная защита: параметризованные запросы

**Параметризованные запросы** (prepared statements) разделяют шаблон запроса и данные. SQL-движок компилирует шаблон запроса отдельно, затем получает данные. Данные никогда не могут стать частью логики команды – они всегда интерпретируются как строка, а не как SQL-код.

```python
cursor.execute(
    'SELECT * FROM users WHERE username = %s AND password = %s',
    (username, password)  # данные передаются отдельно от шаблона
)
```

Даже если пользователь введёт `admin' --`, база данных воспримет это как буквальное строковое значение и не найдёт пользователя с таким именем. Никакой инъекции.

## ORM как автоматическая защита

ORM применяет параметризацию ко всем запросам автоматически:

```python
User.objects.get(username=username)

session.query(User).filter(User.username == username).first()
```

Под капотом оба варианта генерируют параметризованные запросы. Это снижает человеческий фактор: разработчику не нужно помнить о безопасности при каждом запросе – она встроена в инструмент.

**Важное исключение:** raw SQL с прямой подстановкой переменных обходит все защиты ORM:

```python
User.objects.raw(f"SELECT * FROM users WHERE username = '{username}'")

User.objects.raw('SELECT * FROM users WHERE username = %s', [username])
```

## Дополнительные уровни защиты

**Принцип минимальных привилегий.** Пользователь базы данных, от имени которого работает приложение, должен иметь только необходимые права: `SELECT`, `INSERT`, `UPDATE`. Права на `DROP`, `TRUNCATE`, `CREATE` приложению не нужны никогда. Даже при успешной инъекции злоумышленник не сможет уничтожить таблицы, если у приложения нет такого права.

**Скрытие ошибок базы данных.** Подробные сообщения об ошибках SQL в ответе сервера – готовая карта для злоумышленника: названия таблиц, структура схемы, типы данных. В production все ошибки БД должны логироваться на сервере, а пользователю возвращаться только общее сообщение об ошибке.

**WAF (Web Application Firewall).** Внешний фильтр, который анализирует входящие запросы на наличие подозрительных паттернов (`DROP TABLE`, `--`, `UNION SELECT`) ещё до того, как они достигают приложения. Это дополнительный слой, а не замена параметризации.
