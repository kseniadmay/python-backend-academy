## 1. Зачем появилась методология Twelve-Factor App?

> **Ментальная модель — «Морской ISO-контейнер для грузоперевозок»**:
> До изобретения стандартного стального контейнера погрузка корабля занимала недели: бочки, мешки и ящики разного размера требовали ручной укладки. Стандартный ISO-контейнер имеет единые замки и габариты — его можно за минуту перегрузить с корабля на поезд или грузовик в любом порту мира.
> **Методология 12-Factor App** (созданная инженерами Heroku) — это такой же «стандарт контейнеризации» для бэкенд-сервисов: если ваш Python-сервис соблюдает эти правила, он одинаково предсказуемо запустится на ноутбуке разработчика, в Docker Compose, в GitHub Actions и в кластере Kubernetes на 100 подах!

```text
Анатомия облачного 12-Factor сервиса в продакшене:

  Переменные окружения (III. Config)             Внешние ресурсы по URL (IV. Backing Services)
  DATABASE_URL, REDIS_URL, SECRET_KEY            PostgreSQL / Redis / S3 / RabbitMQ
                 \                                      /
                  v                                    v
         +----------------------------------------------------+
         |    Stateless Python Worker (VI. Processes)         |
         |  Не хранит сессии в ОЗУ! Быстрый старт и           |
         |  Graceful Shutdown по SIGTERM (IX. Disposability)  |
         +----------------------------------------------------+
                                   |
                                   v (XI. Logs)
                   Поток событий в стандартный вывод (stdout)
                   -> собирается Docker / Loki / ELK
```

## 2. Главные факторы 12-Factor App, которые спрашивают на собеседованиях

| Фактор | Суть правила | Как реализуется в Python-бэкенде |
| :--- | :--- | :--- |
| **I. Codebase** | Одна кодовая база в Git $\to$ множество развёртываний (`dev`, `staging`, `prod`) | Единый репозиторий, а не отдельные ветки с хардкодом под каждый сервер |
| **II. Dependencies** | Явно объявляйте и изолируйте зависимости | `pyproject.toml` + lock-файл (`uv.lock` / `poetry.lock`) + виртуальное окружение / Docker-образ |
| **III. Config** | Храните конфигурацию и секреты **строго в переменных окружения (`os.environ`)** | `pydantic-settings` (`BaseSettings`), `.env` в `.gitignore`. Лакмусовая бумажка: можно ли выложить код в Open Source прямо сейчас без утечки паролей? |
| **IV. Backing Services** | БД, кэш, S3 и SMTP — это **подключаемые ресурсы (Attached Resources)** | Переключение с локального Postgres на облачный AWS RDS делается сменой `DATABASE_URL` без единой правки кода |
| **V. Build, Release, Run** | Строгое разделение этапов сборки, релиза и запуска | `Build` (сборка Docker-образа) + `Config` = неизменяемый `Release`, который запускается в `Run`. Никаких правок кода по SSH на проде! |
| **VI. Processes** | Приложение работает как **stateless-процессы** (`Share-Nothing`) | Никаких глобальных словарей `SESSIONS = {}` в памяти воркера! Любое состояние живёт во внешнем Redis или PostgreSQL |
| **IX. Disposability** | Быстрый запуск и корректная остановка (**Graceful Shutdown**) | По сигналу `SIGTERM` воркер перестаёт брать новые запросы, доделывает текущие за 5–10 с и закрывает пул БД |
| **XI. Logs** | Логи — это поток событий в `stdout` | Приложение пишет структурированный JSON в `sys.stdout`, не занимаясь ротацией файлов на диске |

## 3. Почему хранение состояния в памяти воркера ломает масштабирование?

Представьте, что вы сохранили сессию вошедшего пользователя в глобальный словарь Python `ACTIVE_USERS[token] = user_id` внутри процесса FastAPI.
Пока у вас запущен 1 воркер — всё работает. Но как только нагрузка выросла и вы запустили `uvicorn --workers 4` (или 4 контейнера за балансировщиком Nginx), запрос №1 (логин) попадёт на **Воркер 1**, а запрос №2 (профиль) балансировщик отправит на **Воркер 2**, у которого словарь `ACTIVE_USERS` пуст! Пользователя мгновенно разлогинит (`401 Unauthorized`).
Именно поэтому **Фактор VI (Stateless Processes)** требует выносить любое разделяемое состояние в Redis или БД.

> **Junior vs Senior**:
> - **Junior**: Хардкодит `SECRET_KEY = "my_secret"` в `settings.py`, пишет логи через `open("/var/log/app.log", "a")` (из-за чего контейнер падает по `PermissionError` или переполняет диск) и хранит кэш профилей в глобальном `dict` процесса.
> - **Senior**: Валидирует переменные окружения на старте через типизированный конфиг (Fail-Fast при отсутствии секрета), пишет JSON-логи в `stdout`, держит воркеры полностью stateless и обрабатывает `SIGTERM` для Graceful Shutdown.

## 4. Практикум: 12-Factor конфигуратор с валидацией окружения и JSON-логгером в `stdout`

```python
import json
import os
from dataclasses import dataclass

@dataclass(frozen=True)
class AppSettings:
    """Типизированный конфиг по Фактору III (Config in Environment) с Fail-Fast проверкой."""
    app_env: str
    database_url: str
    redis_url: str
    max_pool_size: int

    @classmethod
    def from_env(cls, env: dict[str, str]) -> "AppSettings":
        missing = [k for k in ("DATABASE_URL", "REDIS_URL") if not env.get(k)]
        if missing:
            raise RuntimeError(f"12-Factor Config Error: не заданы переменные {missing}")
        return cls(
            app_env=env.get("APP_ENV", "production"),
            database_url=env["DATABASE_URL"],
            redis_url=env["REDIS_URL"],
            max_pool_size=int(env.get("MAX_POOL_SIZE", "10")),
        )

def log_event_stdout(level: str, event: str, **context: object) -> None:
    """Фактор XI (Logs as event stream): структурированный JSON-лог в stdout."""
    payload = {"level": level, "event": event, **context}
    print(json.dumps(payload, ensure_ascii=False))

mock_env = {
    "APP_ENV": "staging",
    "DATABASE_URL": "postgresql://app:***@db.internal:5432/orders",
    "REDIS_URL": "redis://cache.internal:6379/0",
    "MAX_POOL_SIZE": "20",
}
settings = AppSettings.from_env(mock_env)
log_event_stdout("INFO", "service_started", env=settings.app_env, pool_size=settings.max_pool_size)
```
