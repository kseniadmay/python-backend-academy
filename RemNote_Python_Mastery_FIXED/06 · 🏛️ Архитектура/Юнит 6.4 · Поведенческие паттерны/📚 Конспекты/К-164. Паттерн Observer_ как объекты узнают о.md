## 1. Паттерн Observer (Наблюдатель / Pub-Sub): разрываем жёсткую связность

> **Ментальная модель — «Подписка на YouTube-канал против обзвона по телефону»**:
> Без паттерна Observer автор видео (`OrderService`) после публикации ролика вынужден лично звонить по телефону конкретным зрителям: Васе (`EmailService`), Пете (`BonusService`) и Маше (`AnalyticsService`). Если добавился новый зритель — автору нужно менять свою телефонную книгу.
> С паттерном **Observer (Издатель — Подписчик)** автор просто нажимает кнопку **«Опубликовать» (`emit("order.paid", event)`)**. Все, кто нажал «Подписаться» (`subscribe`), мгновенно получают уведомление, а сам автор даже не подозревает, кто именно на него подписан!

```text
Архитектура паттерна Observer / Event Bus:

  +------------------+                        +-----------------------+
  |   OrderService   |                        |     <<Subscriber>>    |
  |   (Publisher)    |                        +-----------------------+
  +------------------+                                    ^
           |                                              |
           | 1. emit(OrderPaidEvent)        +-------------+-------------+
           v                                |             |             |
  +------------------+   2. Уведомляет   +-------+   +---------+   +-----------+
  |    EventBus      | ================> | Email |   | Loyalty |   | Analytics |
  |  _subscribers[]  |                   |Handler|   | Handler |   |  Handler  |
  +------------------+                   +-------+   +---------+   +-----------+
```

## 2. Изоляция сбоев: почему падение одного подписчика не должно ломать остальных

Представьте, что при оплате заказа срабатывают три подписчика:
1. `FiscalReceiptSubscriber` (отправка онлайн-чека в налоговую);
2. `LoyaltyPointsSubscriber` (начисление кэшбэка);
3. `AnalyticsSubscriber` (отправка метрики во внешний трекер).

Что произойдёт в наивном цикле `for sub in subscribers: sub(event)`, если внешний сервер аналитики временно недоступен и выбросит `TimeoutError`?
Если `AnalyticsSubscriber` стоял первым в списке, то цикл оборвётся: **клиент не получит чек, кэшбэк не начислится, а оплаченный заказ вернёт HTTP 500**!

| Аспект реализации | Наивный Observer (Уязвимый) | Промышленный EventBus / Domain Events |
| :--- | :--- | :--- |
| **Обработка исключений в `emit()`** | Нет `try/except` — ошибка одного подписчика обрывает всю цепочку | Каждый вызов обёрнут в `try/except`, ошибка логируется, остальные подписчики отрабатывают штатно |
| **Мутация данных события** | Передаётся обычный `dict`, который первый подписчик может случайно испортить (`data.clear()`) | Событие передаётся как неизменяемый `@dataclass(frozen=True)` |
| **Тяжёлые сетевые операции** | Выполняются синхронно в том же HTTP-потоке (тормозят ответ клиенту) | Перекладываются в фоновую очередь (`BackgroundTasks` / `Celery` / `Transactional Outbox`) |

## 3. Где Observer живёт в реальных фреймворках (Django Signals vs FastAPI EventBus)

- В **Django** паттерн Observer встроен из коробки в виде **Сигналов (`django.dispatch.Signal`, `post_save`, `pre_delete`)** и декоратора `@receiver(post_save, sender=Order)`. Однако с сигналами Django нужно быть осторожным: они выполняются **синхронно в том же потоке** и при злоупотреблении превращают логику сохранения в неявный лабиринт.
- В **Чистой архитектуре и DDD** вместо магических сигналов ORM используют **явные доменные события (`Domain Events`)** и **шину событий (`EventBus`)**: сервис явно публикует типизированный объект `UserRegisteredEvent(user_id=42, email="...")`.

> **Junior vs Senior**:
> - **Junior**: Вешает на сигнал Django `post_save` модели `User` синхронный HTTP-запрос к внешнему CRM. В результате каждый `user.save()` в тестах и админке начинает зависать на 3 секунды или падать при сбое сети.
> - **Senior**: Использует явную шину доменных событий (`EventBus`) с неизменяемыми `@dataclass(frozen=True)`-событиями, защищает диспетчер изоляцией ошибок (`try/except` на каждого слушателя), а внешние сетевые вызовы делегирует фоновому воркеру.

## 4. Практикум: отказоустойчивая шина доменных событий (`EventBus`) в Python 3.13

```python
from collections import defaultdict
from dataclasses import dataclass
from typing import Callable, TypeVar

TEvent = TypeVar("TEvent")

@dataclass(frozen=True)
class OrderPaidEvent:
    order_id: int
    user_email: str
    amount: float

class EventBus:
    def __init__(self) -> None:
        self._listeners: dict[type, list[Callable[[object], None]]] = defaultdict(list)
        self.error_log: list[str] = []

    def subscribe(self, event_type: type[TEvent], handler: Callable[[TEvent], None]) -> None:
        self._listeners[event_type].append(handler)

    def publish(self, event: object) -> None:
        for handler in self._listeners.get(type(event), []):
            try:
                handler(event)
            except Exception as exc:
                self.error_log.append(f"{handler.__name__} failed: {exc}")

bus = EventBus()
audit_trail: list[str] = []

def broken_analytics_handler(ev: OrderPaidEvent) -> None:
    raise RuntimeError("Сервер аналитики недоступен")

def send_receipt_handler(ev: OrderPaidEvent) -> None:
    audit_trail.append(f"Чек на {ev.amount} руб. отправлен на {ev.user_email}")

def add_bonus_handler(ev: OrderPaidEvent) -> None:
    audit_trail.append(f"Начислено {int(ev.amount * 0.05)} бонусов за заказ #{ev.order_id}")

bus.subscribe(OrderPaidEvent, broken_analytics_handler)
bus.subscribe(OrderPaidEvent, send_receipt_handler)
bus.subscribe(OrderPaidEvent, add_bonus_handler)

bus.publish(OrderPaidEvent(order_id=77, user_email="bob@example.com", amount=2000.0))
print("Успешно отработавшие подписчики:", audit_trail)
print("Перехваченные сбои (без падения цепочки):", bus.error_log)
```
