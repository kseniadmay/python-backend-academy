## 1. Почему код превращается в «спагетти» и зачем нужен SOLID?

> **Ментальная модель — «Швейцарский нож на профессиональной кухне»**: Представьте повара, который пытается резать стейк, открывать консервы, взбивать соус и чинить проводку одним гигантским складным ножом на 40 лезвий. Если затупится одно лезвие или сломается пружина — весь инструмент отправляется в ремонт, и кухня встаёт. **Принципы SOLID** предлагают вместо одного монструозного «швейцарского ножа» иметь набор специализированных инструментов со стандартными креплениями: шеф-нож только режет (**SRP**), насадки блендера меняются без разборки мотора (**OCP** и **DIP**), любая сковорода подходит к плите (**LSP**), а пульт духовки не заставляет настраивать холодильник (**ISP**).

Акроним **SOLID**, сформулированный Робертом Мартином (Uncle Bob), объединяет 5 принципов объектно-ориентированного дизайна, которые защищают проект от **жёсткой связности (Tight Coupling)** и **хрупкости (Fragility)**:

| Буква | Принцип (EN / RU) | Главный вопрос для самопроверки |
| :--- | :--- | :--- |
| **S** | **Single Responsibility Principle (SRP)** — Принцип единственной ответственности | Есть ли у этого класса больше одного «заказчика» (актора), ради которого его придётся менять? |
| **O** | **Open/Closed Principle (OCP)** — Принцип открытости/закрытости | Можно ли добавить новый способ оплаты или доставки, *не редактируя* существующий проверенный код? |
| **L** | **Liskov Substitution Principle (LSP)** — Принцип подстановки Барбары Лисков | Не сломается ли программа, если вместо базового класса передать любой его подкласс? |
| **I** | **Interface Segregation Principle (ISP)** — Принцип разделения интерфейса | Не заставляем ли мы класс реализовывать «мёртвые» методы (`raise NotImplementedError`), которые ему не нужны? |
| **D** | **Dependency Inversion Principle (DIP)** — Принцип инверсии зависимостей | Зависит ли бизнес-логика от абстрактного контракта (`Protocol`/`ABC`), а не от конкретного драйвера БД или SMTP? |

## 2. SRP и OCP: разделяем ответственность и расширяем без `elif`-простыней

- **S — Single Responsibility Principle**: у класса должна быть **только одна причина для изменения**. Если класс `OrderManager` одновременно считает скидки (для отдела продаж), сохраняет SQL-запросы (для DBA) и верстает HTML-чек (для верстальщиков), то правка вёрстки может случайно сломать расчёт скидки.
- **O — Open/Closed Principle**: программные сущности должны быть **открыты для расширения**, но **закрыты для модификации**. Когда вы добавляете новый способ оплаты через новый класс, реализующий интерфейс `PaymentMethod`, вам не нужно лезть внутрь `CheckoutService` и дописывать пятый `elif`.

```text
Нарушение SRP + OCP (God Object):           Чистый дизайн по SRP + OCP:
+---------------------------------+         +-------------------+      +-------------------+
|         OrderGodObject          |         |  CheckoutService  | ---> | <<PaymentMethod>> |
| - calculate_total()             |         +-------------------+      +-------------------+
| - save_to_postgres()            |                   |                   ^       ^       ^
| - if type == 'card': ...        |                   v                   |       |       |
|   elif type == 'sbp': ...       |         +-------------------+      CardPay  SbpPay  CryptoPay
+---------------------------------+         |  OrderRepository  |
                                            +-------------------+
```

```python
from typing import Protocol

# Контракт оплаты (открыт для новых реализаций — OCP)
class PaymentMethod(Protocol):
    def pay(self, amount: int) -> str: ...

class CardPayment:
    def pay(self, amount: int) -> str:
        return f"Оплачено картой: {amount} руб."

class SbpPayment:
    def pay(self, amount: int) -> str:
        return f"Оплачено через СБП (QR): {amount} руб."

# CheckoutService отвечает ТОЛЬКО за проведение заказа (SRP) и не меняется при добавлении SbpPayment (OCP)
class CheckoutService:
    def process_order(self, order_id: int, amount: int, method: PaymentMethod) -> str:
        receipt = method.pay(amount)
        return f"Заказ #{order_id} завершён -> {receipt}"

service = CheckoutService()
print(service.process_order(101, 2500, CardPayment()))
print(service.process_order(102, 1800, SbpPayment()))
```

## 3. LSP и ISP: честное наследование и узкие интерфейсы

- **L — Liskov Substitution Principle**: подкласс обязан соблюдать **контракт базового класса** (предусловия не могут быть строже, постусловия — слабее). Классическое нарушение: унаследовать `ReadOnlyFile` от `WritableFile` и выбросить `NotImplementedError` в методе `write()`. Код, ожидающий `WritableFile`, упадёт в рантайме!
- **I — Interface Segregation Principle**: клиенты не должны зависеть от методов, которые они не используют. Вместо одного «жирного» интерфейса `Worker(work, eat, sleep)` лучше создать узкие ролевые протоколы `Workable` и `Feedable`, чтобы класс `RobotWorker` не был вынужден реализовывать пустой метод `eat()`.

```python
from typing import Protocol

# Узкие специализированные протоколы (ISP) вместо одного гигантского класса
class Reader(Protocol):
    def read_data(self) -> str: ...

class Writer(Protocol):
    def write_data(self, text: str) -> None: ...

class MemoryBuffer:
    """Поддерживает и чтение (Reader), и запись (Writer)."""
    def __init__(self, initial: str = "") -> None:
        self._content = initial

    def read_data(self) -> str:
        return self._content

    def write_data(self, text: str) -> None:
        self._content += text

class ReadOnlyConfig:
    """Честно реализует только Reader (соблюдены ISP и LSP — никаких NotImplementedError!)."""
    def __init__(self, config_str: str) -> None:
        self._config_str = config_str

    def read_data(self) -> str:
        return self._config_str

def print_source(source: Reader) -> None:
    print("Прочитано из источника:", source.read_data())

buf = MemoryBuffer("hello")
buf.write_data(" world")
print_source(buf)
print_source(ReadOnlyConfig("ENV=production"))
```

## 4. DIP: инверсия зависимостей и внедрение через конструктор (Dependency Injection)

**D — Dependency Inversion Principle** гласит:
1. Модули верхнего уровня (бизнес-логика) не должны зависеть от модулей нижнего уровня (драйвер БД, HTTP-клиент). Оба должны зависеть от **абстракций**.
2. Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.

Технический приём передачи готовой зависимости снаружи (через `__init__`) называется **Dependency Injection (DI)**. Благодаря DIP + DI мы можем протестировать бизнес-сервис за `1 мс`, передав ему `FakeNotificationSender` вместо реального SMTP-сервера!

> **Junior vs Senior**:
> - **Junior**: Внутри метода `UserService.register()` напрямую создаёт `smtp = smtplib.SMTP('smtp.gmail.com')` и `conn = psycopg2.connect(...)`. В результате ни один юнит-тест невозможно запустить без интернета и поднятой БД.
> - **Senior**: Описывает узкий `Protocol` (`NotificationSender`), принимает его в `UserService.__init__(self, sender: NotificationSender)` и в продакшене передаёт `SmtpSender`, а в `pytest` — легковесный `InMemorySender`.

```python
from typing import Protocol

class NotificationSender(Protocol):
    def send(self, recipient: str, message: str) -> None: ...

class InMemorySender:
    """Тестовый двойник (Fake), реализующий абстракцию NotificationSender."""
    def __init__(self) -> None:
        self.sent_messages: list[tuple[str, str]] = []

    def send(self, recipient: str, message: str) -> None:
        self.sent_messages.append((recipient, message))

class RegistrationService:
    """Бизнес-модуль верхнего уровня зависит только от абстракции NotificationSender (DIP)."""
    def __init__(self, notifier: NotificationSender) -> None:
        self._notifier = notifier

    def register_user(self, email: str) -> dict[str, str]:
        user = {"email": email, "status": "active"}
        self._notifier.send(email, "Добро пожаловать в Python Academy!")
        return user

fake_notifier = InMemorySender()
reg_service = RegistrationService(notifier=fake_notifier)
reg_service.register_user("alice@example.com")
print("Отправленные уведомления (без SMTP):", fake_notifier.sent_messages)
```
