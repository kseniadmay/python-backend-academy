## 1. Зачем нужен тактический DDD: богатая модель против анемичной (Anemic Model)

> **Ментальная модель — «Паспорт гражданина против купюры в 1000 рублей»**:
> - **Человек (`Entity` / Сущность)** имеет уникальный идентификатор (серия и номер паспорта / СНИЛС). Даже если человек сменит фамилию, причёску и адрес проживания, это всё равно **тот же самый человек** (равенство определяется по `id`).
> - **Купюра 1000 рублей (`Value Object` / Объект-значение)** в вашем кошельке не имеет личной биографии для магазина: вам абсолютно всё равно, какую именно тысячерублёвую купюру отдать на кассе — любые две купюры номиналом `Money(1000, "RUB")` полностью взаимозаменяемы (равенство определяется **по значению всех полей**, а сам объект неизменяем!).

Без **Domain-Driven Design (DDD)** проекты часто скатываются в антипаттерн **Анемичная доменная модель (Anemic Domain Model)**: классы превращаются в «тупые мешки с геттерами и сеттерами» без проверок, где любой внешний код может написать `order.status = "paid"; order.total = -500`. В **богатой доменной модели (Rich Domain Model)** данные и бизнес-инварианты защищены внутри самих объектов!

```text
Три базовых строительных блока тактического DDD:

  +-------------------------------------------------------------------+
  |                   AGGREGATE (Граница транзакции)                  |
  |                                                                   |
  |   +-----------------------------------------------------------+   |
  |   | 👑 Order (Aggregate Root / Корневая Entity, id=101)       |   |
  |   |   Инвариант: "Нельзя добавить позицию в оплаченный заказ" |   |
  |   +-----------------------------------------------------------+   |
  |              |                                    |               |
  |              v (Внутренние Entity)                v (Value Object)|
  |   +-----------------------+            +----------------------+   |
  |   | OrderLine (product=5) | ---------> | Money(1500, "RUB")   |   |
  |   +-----------------------+            | (frozen=True, без id)|   |
  |                                        +----------------------+   |
  +-------------------------------------------------------------------+
  ⬆️ Внешний мир общается ТОЛЬКО через методы корня Order.add_item()!
```

## 2. Сравнительная таблица: Entity vs Value Object vs Aggregate

| Строительный блок DDD | Как сравнивается (`==`)? | Изменяемость (Mutability) | Примеры из реального бэкенда |
| :--- | :--- | :--- | :--- |
| **Entity (Сущность)** | Только **по уникальному `id`** (`self.id == other.id`) | **Изменяема**: проходит жизненный цикл статусов во времени | `User`, `Order`, `BankAccount`, `SupportTicket` |
| **Value Object (Объект-значение)** | **По совпадению всех атрибутов** (`amount == amount and currency == currency`) | **Строго неизменяем (`@dataclass(frozen=True)`)**: любая операция возвращает *новый* экземпляр | `Money(100, "RUB")`, `EmailAddress`, `GeoCoordinates(lat, lon)`, `DateRange` |
| **Aggregate (Агрегат)** | По `id` своего корня (**Aggregate Root**) | Изменяется только целиком через методы **Aggregate Root** в одной транзакции | Кластер `Order` (корень) + список `OrderLine` + `ShippingAddress` |

## 3. Золотые правила проектирования Aggregate Root

**Aggregate Root (Корень агрегата)** — это главный страж бизнес-инвариантов:
1. **Единый вход**: внешний код не имеет права напрямую делать `order.items.append(line)` в обход корня. Все изменения идут только через методы корня (`order.add_item(...)`, `order.pay()`), которые проверяют бизнес-правила!
2. **Защита внутренней коллекции**: чтобы внешний код случайно не мутировал внутренний список `_items`, наружу отдаётся только неизменяемая копия (`tuple(self._items)`).
3. **Один репозиторий на один Aggregate Root**: мы создаём `OrderRepository`, но **не создаём** отдельный `OrderItemRepository` — позиции заказа сохраняются и загружаются вместе со своим заказом.

> **Junior vs Senior**:
> - **Junior**: Хранит деньги в `float` (`0.1 + 0.2 == 0.30000000000000004`), email — в непроверенной строке `str`, а статус заказа меняет напрямую `order.status = "shipped"` без проверки, был ли заказ вообще оплачен.
> - **Senior**: Выделяет `Money` (с проверкой совпадения валют в `__add__`) и `Email` в неизменяемые **Value Objects** (`@dataclass(frozen=True)`), а переходы статусов и инварианты заказа закрывает внутри методов **Aggregate Root** `Order`.

## 4. Практикум: Value Object `Money`, `Entity` и `Aggregate Root` `Order` в Python 3.13

```python
from dataclasses import dataclass, field

# 1. VALUE OBJECT: неизменяемый (frozen=True), валидирует себя при создании, сравнивается по значению
@dataclass(frozen=True)
class Money:
    amount: int  # Храним в минорных единицах (копейках/рублевых целых) без ошибок float!
    currency: str = "RUB"

    def __post_init__(self) -> None:
        if self.amount < 0:
            raise ValueError("Сумма Money не может быть отрицательной")
        if len(self.currency) != 3 or not self.currency.isupper():
            raise ValueError(f"Некорректный код валюты ISO: {self.currency}")

    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise ValueError(f"Нельзя складывать разные валюты: {self.currency} и {other.currency}")
        return Money(self.amount + other.amount, self.currency)

    def multiply(self, qty: int) -> "Money":
        return Money(self.amount * qty, self.currency)

@dataclass(frozen=True)
class OrderLine:
    sku: str
    qty: int
    unit_price: Money

    @property
    def subtotal(self) -> Money:
        return self.unit_price.multiply(self.qty)

# 2. AGGREGATE ROOT (и Entity): равенство по id, строгая защита бизнес-инвариантов
class Order:
    def __init__(self, order_id: int, currency: str = "RUB") -> None:
        self.id = order_id
        self.currency = currency
        self.status = "draft"
        self._lines: list[OrderLine] = []

    def __eq__(self, other: object) -> bool:
        return isinstance(other, Order) and self.id == other.id

    def add_item(self, sku: str, qty: int, unit_price: Money) -> None:
        if self.status != "draft":
            raise ValueError("Инвариант нарушен: нельзя менять уже оформленный заказ!")
        if qty <= 0:
            raise ValueError("Количество товара должно быть > 0")
        self._lines.append(OrderLine(sku=sku, qty=qty, unit_price=unit_price))

    @property
    def total(self) -> Money:
        result = Money(0, self.currency)
        for line in self._lines:
            result = result + line.subtotal
        return result

    def confirm(self) -> None:
        if not self._lines:
            raise ValueError("Инвариант нарушен: нельзя подтвердить пустой заказ!")
        self.status = "confirmed"

order = Order(order_id=501)
order.add_item("BOOK-DDD", qty=2, unit_price=Money(1200, "RUB"))
order.add_item("COFFEE", qty=1, unit_price=Money(450, "RUB"))
order.confirm()
print(f"Заказ #{order.id} [{order.status}] | Итого: {order.total.amount} {order.total.currency}")
print("Проверка равенства Value Object:", Money(1200, "RUB") == Money(1200, "RUB"))
```
