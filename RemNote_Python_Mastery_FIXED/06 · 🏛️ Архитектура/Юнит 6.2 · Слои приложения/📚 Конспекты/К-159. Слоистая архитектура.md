## 1. Слоистая и Чистая архитектура (Layered & Clean Architecture): правило зависимостей

> **Ментальная модель — «Ядро ореха в защитной скорлупе»**:
> Самое ценное в вашем приложении — это **правила бизнеса (Domain / Entities)**: как рассчитывается процент по вкладу, когда заказ считается просроченным, кому положена скидка. Законы бизнеса меняются редко, а вот внешние технологии (веб-фреймворк, драйвер БД, платёжный шлюз) меняются постоянно. В **Чистой слоистой архитектуре (Clean / Hexagonal Architecture)** доменное ядро лежит в самом центре и **ни от кого не зависит**, а все внешние слои (API, БД, брокеры) направляют свои стрелки зависимостей строго **внутрь, к ядру**!

```text
Правило направления зависимостей (Dependency Rule):

  +-------------------------------------------------------------------+
  | Внешний мир: FastAPI Controllers / CLI / PostgreSQL / Redis / SMTP|
  |         |                                               |         |
  |         v (Зависимости направлены СТРОГО ВНУТРЬ к ядру) v         |
  |   +-----------------------------------------------------------+   |
  |   | Слой сценариев (Application / Use Cases / Services)       |   |
  |   |   Координирует поток данных и интерфейсы репозиториев     |   |
  |   |                         |                                 |   |
  |   |                         v                                 |   |
  |   |         +-------------------------------+                 |   |
  |   |         | ДОМЕННОЕ ЯДРО (Domain Layer)  |                 |   |
  |   |         | Чистый Python: Entities,      |                 |   |
  |   |         | Value Objects, бизнес-правила |                 |   |
  |   |         +-------------------------------+                 |   |
  |   +-----------------------------------------------------------+   |
  +-------------------------------------------------------------------+
```

Главный закон: **внутренний слой никогда не должен ничего знать о внешнем слое**. Доменная модель `LoanApplication` не импортирует ни `sqlalchemy`, ни `fastapi`, ни `redis`.

## 2. Четыре слоя и три типа моделей (Schema vs Domain Entity vs ORM Model)

Новички часто пытаются использовать один и тот же класс и для валидации JSON в FastAPI, и для бизнес-расчётов, и как таблицу SQLAlchemy. В зрелой слоистой архитектуре эти роли разделены:

| Артефакт | В каком слое живёт | Инструмент в Python | За что отвечает |
| :--- | :--- | :--- | :--- |
| **API Schema (DTO)** | `Presentation` (`schemas.py`) | `pydantic.BaseModel` | Валидация синтаксиса входного/выходного JSON, скрытие секретных полей (`password_hash`) |
| **Domain Entity** | `Domain` (`domain/models.py`) | `@dataclass` / чистый класс Python | Хранение состояния и выполнение бизнес-инвариантов (`order.approve()`, `account.charge()`) |
| **ORM Model** | `Infrastructure / DAL` (`db/models.py`) | `sqlalchemy.orm.Mapped` / `django.db.models` | Отображение строк реляционной таблицы, индексов и внешних ключей (`ForeignKey`) |

## 3. Синтаксическая vs Семантическая (бизнес-) валидация

Почему нельзя перенести всю валидацию в Pydantic-схему? Потому что валидация делится на два совершенно разных уровня:
1. **Синтаксическая валидация (в Presentation Layer / Pydantic)**: проверяет форму входных данных без похода в базу — «строка `email` содержит `@`», «поле `amount` является целым числом `> 0`».
2. **Семантическая валидация (в Business / Domain Layer)**: проверяет выполнимость операции с точки зрения текущего состояния бизнеса — «не занят ли этот `email` другим пользователем?», «активен ли промокод?», «не заблокирован ли счёт получателя?».

> **Junior vs Senior**:
> - **Junior**: Пытается внутри `@field_validator` в Pydantic-схеме открывать сессию БД и делать `SELECT` для проверки уникальности email, из-за чего простая сериализация схемы начинает падать без подключения к БД.
> - **Senior**: В Pydantic проверяет только формат данных, а бизнес-правила («свободен ли email», «хватает ли товара на складе») проверяет в `Service` / `Domain Layer`.

## 4. Практикум: чистая доменная сущность и сценарий использования (Use Case)

Реализуем выдачу книги в библиотеке со строгим разделением доменного ядра, порта репозитория и прикладного сервиса:

```python
from dataclasses import dataclass, field
from typing import Protocol

# 1. ДОМЕННЫЙ СЛОЙ (Domain Layer): чистый Python, 0 внешних зависимостей
@dataclass
class Book:
    id: int
    title: str
    available_copies: int
    borrowed_by: set[int] = field(default_factory=set)

    def borrow(self, reader_id: int) -> None:
        if reader_id in self.borrowed_by:
            raise ValueError("Читатель уже взял экземпляр этой книги")
        if self.available_copies <= 0:
            raise ValueError("Свободных экземпляров нет в наличии")
        self.available_copies -= 1
        self.borrowed_by.add(reader_id)

# 2. ПОРТ РЕПОЗИТОРИЯ (контракт на границе прикладного слоя)
class BookRepositoryPort(Protocol):
    def get_by_id(self, book_id: int) -> Book: ...
    def save(self, book: Book) -> None: ...

# 3. ПРИКЛАДНОЙ СЛОЙ (Application Service / Use Case)
class LibraryUseCase:
    def __init__(self, repo: BookRepositoryPort) -> None:
        self._repo = repo

    def checkout_book(self, book_id: int, reader_id: int) -> str:
        book = self._repo.get_by_id(book_id)
        book.borrow(reader_id)
        self._repo.save(book)
        return f"Книга «{book.title}» выдана читателю #{reader_id}. Осталось: {book.available_copies}"

# 4. ИНФРАСТРУКТУРНЫЙ АДАПТЕР (In-Memory реализация порта)
class InMemoryBookRepo:
    def __init__(self) -> None:
        self._books = {1: Book(id=1, title="Чистая архитектура", available_copies=2)}
    def get_by_id(self, book_id: int) -> Book:
        return self._books[book_id]
    def save(self, book: Book) -> None:
        self._books[book.id] = book

use_case = LibraryUseCase(InMemoryBookRepo())
print(use_case.checkout_book(book_id=1, reader_id=42))
print(use_case.checkout_book(book_id=1, reader_id=99))
```
