## 1. Что такое Separation of Concerns (Разделение ответственности)?

> **Ментальная модель — «Ресторан: зал, кухня и склад»**:
> В хорошем ресторане роли строго разделены:
> - **Официант (Controller / Presentation Layer)** встречает гостя, принимает заказ по меню, проверяет, что гость не заказал несуществующее блюдо, и приносит готовый счёт. Официант **не стоит у плиты**!
> - **Шеф-повар (Service / Business Layer)** знает рецепты и правила приготовления. Ему всё равно, пришёл заказ от официанта в зале или через приложение доставки.
> - **Кладовщик (Repository / Data Access Layer)** знает, на какой полке холодильника лежат продукты, и выдаёт их по запросу шеф-повара.
> Если смешать всё в одного человека, который одновременно бегает по залу, жарит котлеты и разгружает грузовик, ресторан рухнет при первых десяти гостях.

**Separation of Concerns (SoC)** — фундаментальный архитектурный принцип разделения программы на изолированные секции (слои), каждая из которых решает строго одну задачу и общается с соседними через чёткие контракты (DTO / доменные объекты).

```text
Поток обработки запроса при соблюдении Separation of Concerns:

 [HTTP-запрос клиента: POST /orders]
                 |
                 v
 +-------------------------------------------------------+
 | 1. PRESENTATION LAYER (Controller / Router + Schema)  |
 |    Парсит JSON, проверяет формат полей, мапит ошибки  |
 |    бизнеса в HTTP-статусы (400, 404, 409, 201)        |
 +-------------------------------------------------------+
                 | Передаёт валидный DTO / аргументы
                 v
 +-------------------------------------------------------+
 | 2. BUSINESS / APPLICATION LAYER (Service)             |
 |    Проверяет бизнес-правила (хватает ли баланса?),    |
 |    координирует репозитории и отправку уведомлений    |
 +-------------------------------------------------------+
                 | Вызывает методы контракта репозитория
                 v
 +-------------------------------------------------------+
 | 3. DATA ACCESS LAYER (Repository / DAO)               |
 |    Выполняет SQL / ORM-запросы и возвращает сущности  |
 +-------------------------------------------------------+
```

## 2. Таблица зон ответственности трёх классических слоёв

Главное правило разделения слоёв: **HTTP-детали (`Request`, `Response`, `HTTPException`, статус-коды `404/409`) никогда не должны проникать в `Service` и `Repository`**, а **SQL-запросы никогда не должны писаться в `Controller`**!

| Слой | Что ДОЛЖЕН делать | Чего КАТЕГОРИЧЕСКИ НЕ ДОЛЖЕН делать |
| :--- | :--- | :--- |
| **Controller (Presentation)** | Принимать запрос, валидировать синтаксис входного JSON (Pydantic), вызывать `Service`, переводить доменные исключения в HTTP-коды | Писать `SELECT`/`INSERT` в БД, считать скидки, отправлять письма по SMTP |
| **Service (Business Logic)** | Применять бизнес-правила, проверять права и лимиты, управлять сценарием (Use Case), выбрасывать доменные исключения (`InsufficientFundsError`) | Импортировать `fastapi.Request` или `HTTPException`, возвращать HTTP-статусы или писать сырой SQL |
| **Repository (Data Access)** | Инкапсулировать чтение/запись в БД (`get_by_id`, `save`, `list_active`), скрывать детали таблиц и индексов | Принимать бизнес-решения («кому дать VIP-скидку») или формировать JSON-ответы для фронтенда |

## 3. Почему «толстые контроллеры» (Fat Controllers) убивают проект?

Когда разработчик пишет всю логику прямо внутри функции маршрута (`@app.post("/transfer")`):
1. **Нулевое переиспользование**: если завтра тот же перевод денег нужно запускать из Telegram-бота, CLI-скрипта или фоновой задачи Celery — код из HTTP-контроллера нельзя вызвать без фейкового HTTP-запроса!
2. **Хрупкие и медленные тесты**: чтобы проверить простое правило «нельзя перевести сумму больше баланса», приходится поднимать HTTP-клиент, базу данных и мокать полмира.
3. **Каскадные поломки**: изменение структуры таблицы в БД ломает код сериализации JSON-ответа.

> **Junior vs Senior**:
> - **Junior**: Пишет в роутере FastAPI/Django View `if balance < amount: raise HTTPException(400)` вперемешку с `cursor.execute("UPDATE accounts...")`. При появлении CLI-команды просто копирует эти 60 строк в другой файл.
> - **Senior**: Держит контроллеры «тонкими» (5–10 строк): контроллер вызывает `TransferService.transfer()`, который работает одинаково и из REST API, и из Celery-таски, и из юнит-теста.

## 4. Полный рабочий пример: три изолированных слоя в Python 3.13

Посмотрите, как один и тот же `WalletService` без единой правки вызывается и из веб-контроллера, и из консольного сценария:

```python
from dataclasses import dataclass

# --- Доменные сущности и доменные исключения (не знают ни про HTTP, ни про SQL) ---
class DomainError(Exception):
    pass

class InsufficientFundsError(DomainError):
    pass

@dataclass
class Wallet:
    user_id: int
    balance: int

# --- 1. Слой доступа к данным (Data Access Layer / Repository) ---
class WalletRepository:
    def __init__(self) -> None:
        self._storage: dict[int, Wallet] = {1: Wallet(user_id=1, balance=1000)}

    def get(self, user_id: int) -> Wallet:
        return self._storage[user_id]

    def save(self, wallet: Wallet) -> None:
        self._storage[wallet.user_id] = wallet

# --- 2. Сервисный слой бизнес-логики (Business Layer / Service) ---
class WalletService:
    def __init__(self, repo: WalletRepository) -> None:
        self._repo = repo

    def withdraw(self, user_id: int, amount: int) -> Wallet:
        if amount <= 0:
            raise DomainError("Сумма списания должна быть положительной")
        wallet = self._repo.get(user_id)
        if wallet.balance < amount:
            raise InsufficientFundsError(f"Недостаточно средств: баланс {wallet.balance} < {amount}")
        wallet.balance -= amount
        self._repo.save(wallet)
        return wallet

# --- 3. Слой представления (Presentation Layer / Controller) ---
class WalletController:
    def __init__(self, service: WalletService) -> None:
        self._service = service

    def post_withdraw(self, payload: dict[str, int]) -> tuple[int, dict[str, object]]:
        try:
            wallet = self._service.withdraw(payload["user_id"], payload["amount"])
            return 200, {"status": "ok", "new_balance": wallet.balance}
        except InsufficientFundsError as exc:
            return 409, {"error": str(exc)}
        except DomainError as exc:
            return 400, {"error": str(exc)}

controller = WalletController(WalletService(WalletRepository()))
print("Успешное списание:", controller.post_withdraw({"user_id": 1, "amount": 400}))
print("Попытка овердрафта:", controller.post_withdraw({"user_id": 1, "amount": 900}))
```
