## Зачем нужен модуль contextlib

Писать полноценный класс с методами `__enter__` и `__exit__` ради простой обёртки вокруг ресурса — многословно и утомительно. Стандартный модуль **`contextlib`** предоставляет готовые декораторы и утилиты для создания и комбинирования контекстных менеджеров с минимумом шаблонного кода.

---

## @contextmanager и критическая ловушка с try/finally

Декоратор `@contextmanager` превращает функцию-генератор с ровно одним `yield` в полноценный контекстный менеджер. Всё до `yield` выполняется в `__enter__`, переданное в `yield` значение попадает в переменную после `as`, а код после `yield` выполняется в `__exit__`.

**Главный вопрос на собеседовании**: что произойдёт, если внутри блока `with` возникнет исключение, а в генераторе нет `try...finally`?

```python
from contextlib import contextmanager

# ОШИБКА: если внутри with упадёт исключение, код после yield НЕ выполнится!
@contextmanager
def broken_session(db):
    session = db.connect()
    yield session
    session.close()  # не вызовется при ошибке в блоке with!

# ПРАВИЛЬНО: оборачиваем yield в try...finally (и при необходимости except)
@contextmanager
def transactional_session(db):
    session = db.connect()
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise  # пробрасываем ошибку дальше, чтобы не проглотить её молча
    finally:
        session.close()  # выполнится гарантированно всегда
```

При возникновении исключения внутри тела `with` интерпретатор пробрасывает его в точку `yield` с помощью метода генератора `.throw()`. Если `yield` не обёрнут в `try...finally`, генератор аварийно завершится прямо на строке `yield`, и закрытие ресурса будет пропущено.

## contextlib.suppress — декларативное подавление ожидаемых ошибок

Вместо громоздкой конструкции `try ... except FileNotFoundError: pass` в Python принято использовать **`suppress(*exceptions)`**:

```python
import os
from contextlib import suppress

# Чисто и явно выражает намерение проигнорировать конкретные исключения
with suppress(FileNotFoundError, PermissionError):
    os.remove("temp_cache.tmp")
```

`suppress` перехватывает только указанные классы исключений (и их наследников), подавляя их возвратом `True` из `__exit__`. Любые другие ошибки (например, `TypeError` или `KeyboardInterrupt`) проходят насквозь без изменений.

## closing, nullcontext и redirect_stdout

В `contextlib` есть ещё несколько незаменимых инструментов для продакшен-кода и тестов:

**`closing(thing)`** — оборачивает объект, у которого есть метод `.close()`, но нет собственных `__enter__`/`__exit__`, гарантируя вызов `thing.close()` на выходе из блока.

**`nullcontext(enter_result=None)`** — «пустой» контекстный менеджер-заглушка, который ничего не делает при входе и выходе, просто возвращая `enter_result`. Идеален, когда контекстный менеджер опционален (например, блокировка передаётся по условию):

```python
from contextlib import nullcontext

def process_data(data, lock=None):
    cm = lock if lock is not None else nullcontext()
    with cm:
        # единая ветка кода без дублирования тела функции под if lock / else
        return [x * 2 for x in data]
```

**`redirect_stdout(new_target)`** / **`redirect_stderr`** — временно перенаправляет стандартный вывод (`sys.stdout`) в другой файлоподобный объект (например, `io.StringIO()`), что часто используется для перехвата вывода чужих функций в тестах.

## ExitStack — динамический стек контекстных менеджеров

Что делать, если заранее неизвестно, сколько файлов или соединений нужно открыть одновременно (например, список путей приходит в аргументе функции)? Вкладывать `with` в цикле нельзя, но выручает **`ExitStack`**:

```python
from contextlib import ExitStack

def merge_files(file_paths: list[str], output_path: str) -> None:
    with ExitStack() as stack:
        # Открываем произвольное число файлов; если 5-й файл упадёт при открытии,
        # первые 4 гарантированно закроются в обратном порядке (LIFO)!
        files = [stack.enter_context(open(p, encoding="utf-8")) for p in file_paths]
        out = stack.enter_context(open(output_path, "w", encoding="utf-8"))
        for f in files:
            out.write(f.read())
```

`ExitStack` хранит стек открытых менеджеров и колбэков (`stack.callback(cleanup_func)`). При выходе из `with ExitStack()` все зарегистрированные ресурсы закрываются строго в обратном порядке (**LIFO** — от последнего к первому), даже если ошибка произошла на середине инициализации.

## @asynccontextmanager и AsyncExitStack

Для асинхронного кода (`async with`), где вход и выход требуют `await` (подключение к БД, сессия `aiohttp`/`httpx`, распределённый лок в Redis), используется **`@asynccontextmanager`** вокруг асинхронного генератора (`async def` + `yield`), а для динамического набора асинхронных ресурсов — **`AsyncExitStack`**:

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def redis_lock(redis_client, key: str):
    acquired = await redis_client.set(key, "1", nx=True, ex=10)
    if not acquired:
        raise RuntimeError(f"Lock {key} is already held")
    try:
        yield
    finally:
        await redis_client.delete(key)

# Использование:
# async with redis_lock(redis, "order:42"):
#     await process_order(42)
```

Как и в синхронном `@contextmanager`, блок `try...finally` вокруг `yield` здесь строго обязателен, чтобы гарантировать освобождение асинхронного ресурса при любом исключении или отмене корутины (`asyncio.CancelledError`).
