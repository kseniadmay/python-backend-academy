## Почему в продакшене используют logging, а не print()

Вызов `print()` пишет неструктурированный текст в `stdout`: у него нет временной метки, имени модуля, уровня критичности, его нельзя централизованно отключить для отладочных сообщений или направить одновременно в консоль, файл с ротацией и систему мониторинга (Sentry, ELK, Loki). Кроме того, синхронный `print()` при блокировке буфера вывода может замедлять приложение.

Стандартный модуль **`logging`** решает эти задачи через гибкую архитектуру компонентов и 5 стандартных уровней важности (по возрастанию числового веса):

1. **`DEBUG` (10)** — детальная диагностика для разработчиков (параметры запросов, шаги алгоритма).

2. **`INFO` (20)** — штатные события жизненного цикла сервиса (старт воркера, успешная оплата заказа).

3. **`WARNING` (30)** — нештатная, но не фатальная ситуация (повторная попытка запроса, устаревший API, диск заполнен на 85%). Уровень по умолчанию в корневом логгере.

4. **`ERROR` (40)** — ошибка при обработке конкретной операции (не удалось отправить письмо, сбой платежа), но сам сервис продолжает работать.

5. **`CRITICAL` (50)** — фатальный отказ всей подсистемы (недоступна БД на старте, закончилась память).

## Четыре столпа архитектуры logging: Logger, Handler, Formatter, Filter

Вместо того чтобы сваливать всё в один глобальный объект, модуль `logging` разделяет ответственность между 4 сущностями:

**`Logger` (Логгер)** — точка входа в коде (`logger = logging.getLogger(__name__)`). Принимает сообщения и отсекает те, чей уровень ниже установленного на логгере.

**`Handler` (Обработчик)** — решает, **куда** физически отправить запись: `StreamHandler` (в консоль `stderr`/`stdout`), `FileHandler` (в файл), `RotatingFileHandler` (в файл с нарезкой по размеру), `TimedRotatingFileHandler` (с ротацией по времени). У каждого хендлера может быть **свой собственный уровень** (например, в консоль писать от `INFO`, а в отдельный файл `errors.log` — только от `ERROR`).

**`Formatter` (Форматтер)** — определяет **строковый шаблон** или JSON-структуру записи (`%(asctime)s | %(levelname)-8s | %(name)s:%(lineno)d | %(message)s`).

**`Filter` (Фильтр)** — тонкая фильтрация или обогащение записи (`LogRecord`), например подстановка `request_id` текущего HTTP-запроса или маскирование паролей.

```python
import logging
from logging.handlers import RotatingFileHandler

# Всегда создаём модульный логгер через __name__, а не используем root напрямую!
logger = logging.getLogger(__name__)
logger.setLevel(logging.DEBUG)

fmt = logging.Formatter("%(asctime)s [%(levelname)s] %(name)s: %(message)s")

console_handler = logging.StreamHandler()
console_handler.setLevel(logging.INFO)
console_handler.setFormatter(fmt)

file_handler = RotatingFileHandler("app.log", maxBytes=5_000_000, backupCount=3, encoding="utf-8")
file_handler.setLevel(logging.ERROR)
file_handler.setFormatter(fmt)

logger.addHandler(console_handler)
logger.addHandler(file_handler)
```

## Иерархия по точкам и флаг propagate (почему логи дублируются)

Имена логгеров образуют дерево по точкам, повторяющее структуру пакетов Python: для файла `app/services/payment.py` переменная `__name__` равна `"app.services.payment"`. Его родителем автоматически становится логгер `"app.services"`, затем `"app"`, а на вершине дерева всегда стоит корневой логгер **`root`** (`logging.getLogger()`).

По умолчанию у каждого логгера включён атрибут **`logger.propagate = True`**. Это значит, что после того как логгер обработал запись своими хендлерами, он **передаёт её вверх всем родительским логгерам вплоть до `root`**.

**Классическая проблема на собеседовании**: «Почему каждое сообщение в консоли печатается дважды?». Ответ: разработчик повесил `StreamHandler` на дочерний логгер `app.payment` и одновременно вызвал `logging.basicConfig()` (который вешает ещё один `StreamHandler` на `root`). При `propagate = True` запись печатает сначала дочерний хендлер, а затем хендлер корневого логгера. Решение — либо вешать хендлеры только на корень, либо ставить `logger.propagate = False` там, где нужна полная изоляция.

## Логирование исключений: logger.exception() и exc_info=True

Самая частая ошибка джунов в блоке `except` — писать `logger.error(f"Ошибка: {e}")`. При этом в лог попадает только текст ошибки, а **стек вызовов (traceback) безвозвратно теряется**, и понять, на какой строке упал код, невозможно!

```python
try:
    1 / 0
except ZeroDivisionError:
    # ПРАВИЛЬНО: logger.exception() логирует на уровне ERROR и АВТОМАТИЧЕСКИ
    # прикрепляет полный traceback текущего исключения!
    logger.exception("Не удалось рассчитать конверсию для пользователя %s", user_id)

    # Альтернатива для любого уровня (например, WARNING):
    logger.warning("Временный сбой внешнего API", exc_info=True)
```

Обратите внимание и на форматирование через `%s`: `logger.debug("Payload: %s", heavy_obj)` вычисляет строковое представление `str(heavy_obj)` **лениво** — только если уровень `DEBUG` реально включён. При использовании f-строки `f"Payload: {heavy_obj}"` строка собирается всегда до вызова метода, даже когда `DEBUG`-логи отключены в продакшене.

## Конфигурация через dictConfig и структурированные JSON-логи

В реальных микросервисах (FastAPI, Django, Celery) логгеры настраивают декларативно на старте приложения через **`logging.config.dictConfig(LOGGING_CONFIG)`**, описывая форматтеры, хендлеры и уровни для сторонних библиотек (`uvicorn`, `sqlalchemy.engine`, `httpx`) в одном словаре. А для продакшен-кластеров (Kubernetes / Docker) вместо многострочного текста используют **JSON-форматтеры** (или библиотеку `structlog`), чтобы каждая запись лога была валидным однострочным JSON-объектом с полями `timestamp`, `level`, `logger`, `trace_id` и легко индексировалась в Kibana или Grafana Loki.
