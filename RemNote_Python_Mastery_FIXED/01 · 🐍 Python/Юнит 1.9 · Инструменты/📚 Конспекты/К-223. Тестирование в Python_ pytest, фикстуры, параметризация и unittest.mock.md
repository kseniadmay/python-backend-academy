## Почему pytest — индустриальный стандарт, и паттерн AAA

В отличие от встроенного `unittest`, требующего наследования от `TestCase` и десятков специальных методов (`self.assertEqual`, `self.assertRaises`), **`pytest`** позволяет писать тесты как обычные функции с нативным оператором **`assert`**. При падении теста `pytest` переписывает AST-дерево байткода (assertion introspection) и детально показывает значения всех подвыражений.

Любой грамотный тест строится по принципу **AAA (Arrange — Act — Assert)**:

1. **Arrange (Подготовка)** — создаём входные данные, фикстуры и моки.

2. **Act (Действие)** — вызываем ровно одну тестируемую функцию или метод.

3. **Assert (Проверка)** — проверяем возвращённый результат и побочные эффекты.

## Проверка исключений: pytest.raises

Чтобы проверить, что функция корректно выбрасывает ожидаемое исключение при невалидных данных (и с нужным текстом ошибки), используют контекстный менеджер **`pytest.raises(ExpectedException, match="...")`**:

```python
import pytest

def withdraw(balance: float, amount: float) -> float:
    if amount <= 0:
        raise ValueError("Сумма списания должна быть положительной")
    if amount > balance:
        raise ValueError("Недостаточно средств на счёте")
    return balance - amount

def test_withdraw_insufficient_funds():
    # Проверяем и сам класс исключения, и регулярное выражение по тексту ошибки!
    with pytest.raises(ValueError, match="Недостаточно средств"):
        withdraw(100.0, 250.0)
```

Важно: в блоке `with pytest.raises(...)` должна находиться **только одна строка с вызовом целевой функции** (шаг Act). Если поместить туда и подготовку данных, тест может ложно пройти из-за случайной ошибки на этапе подготовки.

## Фикстуры (@pytest.fixture), teardown через yield и области видимости (scope)

**Фикстуры** — это механизм внедрения зависимостей (Dependency Injection) в `pytest`. Достаточно указать имя функции-фикстуры в параметрах теста, и `pytest` сам вызовет её и передаст результат.

Если в фикстуре вместо `return` использовать **`yield`**, всё до `yield` работает как **setup** (подготовка ресурса), а код после `yield` — как гарантированный **teardown** (очистка: откат транзакции БД, удаление временных файлов), который выполнится даже при падении теста:

```python
import pytest

@pytest.fixture(scope="function")
def db_session(engine):
    session = engine.connect()
    transaction = session.begin()
    yield session  # передаём сессию в тест
    # Teardown: откатываем изменения после каждого теста, чтобы БД оставалась чистой!
    transaction.rollback()
    session.close()
```

**5 уровней `scope` (области жизни фикстуры)** от самого узкого к самому широкому:

**`function`** (по умолчанию) — создаётся заново для каждого теста; **`class`** — один раз на тестовый класс; **`module`** — один раз на `.py`-файл; **`package`** — на пакет; **`session`** — ровно один раз на весь прогон `pytest`.

Общие фикстуры выносят в файл **`conftest.py`** — `pytest` обнаруживает его автоматически, и импортировать `conftest.py` вручную в тестах не нужно (и запрещено). Встроенные фикстуры, которые нужно знать: **`tmp_path`** (возвращает уникальный временный `pathlib.Path`), **`monkeypatch`** (безопасная подмена переменных окружения `monkeypatch.setenv` и атрибутов), **`caplog`** (проверка записей `logging`).

## Параметризация: @pytest.mark.parametrize

Вместо копипасты пяти одинаковых тестов или написания цикла `for` внутри одного теста (который упадёт на первой же ошибке, не проверив остальные кейсы) используют **`@pytest.mark.parametrize`**:

```python
import pytest

@pytest.mark.parametrize(
    "price, discount, expected",
    [
        pytest.param(100.0, 10, 90.0, id="standard_10_percent"),
        pytest.param(100.0, 0, 100.0, id="zero_discount"),
        pytest.param(100.0, 100, 0.0, id="full_free_discount"),
    ],
)
def test_calculate_discount(price, discount, expected):
    assert price * (1 - discount / 100) == expected
```

Каждый набор параметров запускается как **отдельный независимый тест** со своим отчётом о прохождении или падении.

## Изоляция внешних сервисов: unittest.mock (Mock, MagicMock, AsyncMock, patch)

Юнит-тесты не должны ходить в реальный платёжный шлюз, отправлять реальные SMS или зависеть от внешнего HTTP API. Для их замены используют модуль **`unittest.mock`**:

**`Mock` и `MagicMock`** — объекты-имитаторы (`MagicMock` дополнительно реализует магические дандер-методы вроде `__len__`, `__iter__`, `__enter__`/`__exit__`).

Два ключевых атрибута любого мока:

1. **`return_value`** — фиксированное значение, которое мок вернёт при вызове.

2. **`side_effect`** — позволяет: а) выбросить исключение при вызове (`mock.side_effect = TimeoutError("API down")`); б) возвращать разные значения при последовательных вызовах (`mock.side_effect = [500, 200]`, например для теста retry-логики); в) подставить функцию-обработчик.

Для проверки вызовов используют методы **`assert_called_once()`**, **`assert_called_once_with(*args, **kwargs)`**, **`assert_not_called()`** и свойство **`call_count`**. А для мокирования `async def` корутин (`await client.get(...)`) обязательно применяется **`AsyncMock`**.

## Главное правило patch(): мокай там, где объект ИСПОЛЬЗУЕТСЯ, а не где он определён!

Это самый популярный вопрос по тестированию на собеседовании. Представьте, что в файле `app/service.py` написано:

`from app.payment_client import charge_card`

Если в тесте написать `@patch("app.payment_client.charge_card")`, мок **НЕ сработает**! Почему? Потому что `app.service` при импорте уже создал у себя локальную ссылку `charge_card` на оригинальную функцию.

```python
from unittest.mock import patch

# ПРАВИЛЬНО: патчим имя в пространстве имён того модуля, КОТОРЫЙ ТЕСТИРУЕМ (где делается вызов)!
@patch("app.service.charge_card")
def test_checkout_calls_gateway(mock_charge):
    mock_charge.return_value = {"status": "ok", "tx_id": "tx_99"}

    result = process_checkout(user_id=1, amount=500)

    assert result["tx_id"] == "tx_99"
    mock_charge.assert_called_once_with(user_id=1, amount=500)
```

Наконец, чтобы мок не позволял вызывать несуществующие методы или передавать неверные аргументы, всегда используйте параметр **`autospec=True`** (или `create_autospec`): он привязывает мок к сигнатуре реального класса/функции и сразу бросит `TypeError` или `AttributeError`, если интерфейс реального объекта изменился, а тест устарел.
