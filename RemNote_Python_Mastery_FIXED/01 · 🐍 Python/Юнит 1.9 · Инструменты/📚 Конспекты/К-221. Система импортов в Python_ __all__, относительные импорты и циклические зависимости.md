## Что происходит под капотом при вызове import

Когда интерпретатор встречает `import my_module`, он выполняет строгую последовательность шагов:

1. **Проверка кэша `sys.modules`**: это глобальный словарь `{имя_модуля: объект_module}`. Если модуль уже есть в `sys.modules`, Python мгновенно возвращает готовую ссылку и **не выполняет код файла повторно** (поэтому модули в Python по своей природе являются синглтонами).

2. **Поиск по `sys.meta_path` и `sys.path`**: если модуля в кэше нет, поисковики (`finders`) просматривают встроенные C-модули, директорию запущенного скрипта, переменную окружения `PYTHONPATH`, стандартную библиотеку и папку `site-packages` виртуального окружения.

3. **Создание пустого объекта и исполнение**: загрузчик (`loader`) создаёт пустой объект `module`, **сразу кладёт его в `sys.modules`** (ещё до выполнения первой строчки кода!) и лишь затем исполняет байткод файла сверху вниз в пространстве имён этого модуля.

## Точка входа: __name__ == "__main__" и запуск через python -m

У каждого модуля есть строковая переменная **`__name__`**. Когда файл импортируют из другого места (`import app.utils`), его `__name__` равен полному пути пакета (`"app.utils"`). Но если файл запущен напрямую как главный скрипт, интерпретатор присваивает ему имя **`"__main__"`**:

```python
def run_migration() -> None:
    print("Миграция применена")

# Этот блок сработает ТОЛЬКО при прямом запуске файла,
# но не выполнится, если модуль просто импортировали в тестах или другом модуле!
if __name__ == "__main__":
    run_migration()
```

**Почему возникает `ImportError: attempted relative import with no known parent package`?**

Если внутри файла `app/workers/sync.py` есть относительный импорт `from ..models import User`, и вы запускаете его напрямую через `python app/workers/sync.py`, Python считает `sync.py` верхнеуровневым скриптом (`__name__ == "__main__"`, `__package__ == None`) и не знает ничего о родительском пакете `app`.

**Решение**: всегда запускать вложенные модули пакета с флагом **`-m`** из корня проекта:

`python -m app.workers.sync` — тогда корень проекта добавляется в `sys.path`, пакет `app` корректно распознаётся, и все относительные импорты работают без ошибок.

## Публичный контракт модуля: переменная __all__ и фасад в __init__.py

Список строк **`__all__`** на уровне модуля или `__init__.py` решает сразу две задачи:

1. Явно определяет список имён, которые экспортируются при `from module import *` (без `__all__` импортируются все имена, не начинающиеся с нижнего подчёркивания `_`, включая случайно импортированные в этот файл чужие библиотеки!).

2. Документирует **публичный API пакета** для других разработчиков, IDE и линтеров (`ruff`, `mypy`, `flake8`), чтобы реэкспортированные в `__init__.py` классы не помечались как «неиспользуемый импорт»:

```python
# app/models/__init__.py — собираем удобный публичный фасад пакета
from .user import User
from .order import Order, OrderStatus
from ._internal_helper import parse_raw  # внутренний хелпер

__all__ = ["User", "Order", "OrderStatus"]
```

## Циклические импорты (Circular Imports): почему падает ImportError и как лечить

**Как возникает ошибка?** Пусть модуль `a.py` в первой строке делает `from b import func_b`, а модуль `b.py` в первой строке делает `from a import func_a`.

1. Загружается `a.py`: пустой объект модуля `a` помещается в `sys.modules["a"]`, и сразу на 1-й строке управление уходит в импорт `b.py` (до объявления `def func_a` интерпретатор ещё не дошёл!).

2. Загружается `b.py`: он пытается выполнить `from a import func_a`. Python видит, что `"a"` уже лежит в `sys.modules`, берёт этот **наполовину инициализированный** объект `a`, ищет в нём атрибут `func_a` — и падает с ошибкой:

`ImportError: cannot import name 'func_a' from partially initialized module 'a' (most likely due to a circular import)`.

**4 способа решения циклических зависимостей (от лучшего к тактическому)**:

1. **Архитектурный (лучший — Выделение третьего модуля)**: вынести общие типы, константы, интерфейсы или модели в отдельный нижнеуровневый модуль (`common.py` / `schemas.py`), от которого будут зависеть и `a.py`, и `b.py` (принцип инверсии зависимостей — слои должны зависеть только сверху вниз).

2. **`typing.TYPE_CHECKING` (если цикл нужен только для аннотаций типов)**: константа `TYPE_CHECKING` равна `True` только во время статического анализа (`mypy`/`pyright`/IDE), а в реальном рантайме Python всегда равна **`False`**:

```python
from __future__ import annotations  # откладывает вычисление аннотаций (превращает их в строки)
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    # В рантайме этот импорт НЕ выполняется -> циклической ошибки нет!
    from app.models.order import Order

class User:
    def can_cancel(self, order: Order) -> bool:
        return order.owner_id == self.id
```

3. **Импорт самого модуля вместо `from ... import`**: написать `import a` и обращаться как `a.func_a()` внутри тела функции — к моменту реального вызова функции оба модуля уже успеют загрузиться до конца.

4. **Локальный (отложенный) импорт внутри функции**: перенести `from a import func_a` внутрь тела конкретной функции или метода. Используется как точечная мера в легаси-коде или в Django/Celery при разрыве связей между моделями и тасками.
