## Python – это спецификация, CPython – реализация

**Python** как язык – это спецификация синтаксиса и семантики. **CPython** – эталонная, самая распространённая реализация этой спецификации, написанная на языке C (отсюда название) – именно её вы запускаете командой `python`. Существуют и другие реализации: **PyPy** (с JIT-компиляцией, часто быстрее CPython на вычислительных задачах), **Jython** (на JVM), **IronPython** (на .NET) – но подавляющее большинство продакшен-кода на Python выполняется именно на CPython.

## Путь от .py файла до выполнения

```text
Исходный код (.py)
      ↓  парсинг
Абстрактное синтаксическое дерево (AST)
      ↓  компиляция
Байткод (.pyc, кэшируется в __pycache__)
      ↓  выполнение
Python Virtual Machine (PVM) - интерпретатор байткода
```

Python **не компилируется напрямую в машинный код**, как C или Go, и не является чисто интерпретируемым построчно, как иногда упрощённо говорят. Исходный код сначала компилируется в промежуточный **байткод** – набор низкоуровневых инструкций для виртуальной машины Python (PVM), и уже этот байткод исполняется построчно интерпретатором. Именно поэтому в проектах появляются папки `__pycache__` с файлами `.pyc` – закэшированный байткод, чтобы не перекомпилировать модуль из исходников при каждом запуске, если исходный файл не менялся.

## Посмотреть байткод самостоятельно

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
```

Модуль `dis` (disassembler) показывает, во что именно скомпилировалась функция – полезно для понимания, почему одна конструкция быстрее другой на низком уровне.

## Почему Python называют "медленным" – и что это значит на практике

Интерпретация байткода на лету (в отличие от заранее скомпилированного машинного кода) – основная причина, почему чистый Python-код медленнее эквивалентного кода на C/Go/Rust для CPU-интенсивных задач. На практике это редко является реальной проблемой backend-разработки: большая часть времени backend-приложения уходит не на вычисления в Python, а на ожидание I/O (сеть, база данных) – а там, где действительно нужна сырая скорость вычислений, критичные участки обычно реализуют через C-расширения (как это сделано внутри `numpy`, `pandas`) или переписывают на более быстром языке, оставляя Python как "клей" (glue language) для оркестрации.

## Компиляция vs интерпретация – не строгая дихотомия

Классическое деление языков на "компилируемые" и "интерпретируемые" – упрощение. CPython и компилирует (в байткод), и интерпретирует (этот байткод построчно исполняется виртуальной машиной) – сочетание обоих подходов, характерное для многих современных языков (та же модель, в общих чертах, у Java с байткодом JVM).

## Когда это важно

Понимание внутреннего устройства помогает объяснить на собеседовании, почему `.pyc`-файлы появляются в `__pycache__`, почему GIL существует именно в CPython (это деталь конкретной реализации, а не требование спецификации языка Python – PyPy, например, экспериментирует с моделями без GIL), и в целом различать язык Python и его конкретную, самую популярную реализацию – CPython.
