## Проблема: CPU простаивает во время I/O

С точки зрения процессора, выполняющего миллиарды операций в секунду, ожидание ответа от сетевого сервера длится вечность – и всё это время CPU не делает ничего полезного. Синхронный код усугубляет проблему: следующая строка не выполнится, пока не завершится предыдущая.

```python
import requests

def fetch_all(urls):
    results = []
    for url in urls:
        r = requests.get(url)  # поток заблокирован до получения ответа
        results.append(r.json())
    return results
```

Три запроса по одной секунде каждый – итого три секунды: время суммируется, чем больше запросов, тем медленнее, хотя между запросами CPU просто ждёт без всякой пользы.

## async def: функция, которая возвращает объект, а не результат

Обычная функция при вызове немедленно начинает выполнение. Функция с **`async def`** ведёт себя иначе: вызов **не выполняет** её тело сразу – вместо этого создаётся объект-корутина, «замороженная» задача с инструкциями, но не запущенная.

```python
async def greet():
    return 'hello'

result = greet()   # возвращает объект корутины, а не 'hello'
print(result)         # <coroutine object greet at 0x...>
```

Чтобы корутина реально выполнилась, её нужно передать в event loop – через `await` или `asyncio.run()`.

## await: точка добровольной передачи управления

**`await`** – не просто «подожди». Это инструкция корутине: «здесь я завишу от внешней операции, и нет смысла удерживать управление». При встрече с `await` происходит три вещи: текущая корутина приостанавливается (все локальные переменные сохраняются), управление возвращается в event loop, и event loop запускает другие готовые задачи, пока ожидается результат.

```python
import asyncio

async def fetch():
    await asyncio.sleep(0.01)  # приостановиться, отдать управление
    return 'done'
```

`await` можно использовать только внутри `async def` – попытка использовать его в обычной функции даёт `SyntaxError`.

## Event loop – диспетчер корутин

**Event loop** – центральный механизм `asyncio`, работающий в одном потоке и управляющий всеми корутинами и задачами (Task): решает, какую запустить, какую приостановить, какую возобновить. Алгоритм прост: event loop выбирает готовую к выполнению корутину и запускает её; когда та достигает `await`, приостанавливается и помещается в список ожидающих; event loop немедленно переключается на следующую готовую. Когда ожидаемая операция завершается – корутина возвращается в очередь и возобновляется ровно с той точки, где была приостановлена.

---

## Task – единица планирования event loop'а

`asyncio.gather` (и другие способы запуска конкурентно) оборачивает каждую корутину в объект **`Task`** – именно задачи, а не сами корутины, реально планируются и переключаются event loop'ом. Задачу можно создать явно через `asyncio.create_task()`, чтобы она начала выполняться "в фоне", не дожидаясь немедленно:

```python
async def main():
    task = asyncio.create_task(worker("Background", 3))
    print("Task запущена, делаем что-то ещё")
    await asyncio.sleep(1)
    print("Прошла секунда, а фоновая задача всё ещё работает")
    await task   # дожидаемся её завершения явно
```

## Критическая ошибка: блокирующий вызов в async-коде

Если внутри async-функции вызвать обычную блокирующую операцию – `time.sleep()`, синхронный HTTP-запрос, тяжёлые вычисления без `await` – весь event loop заморозится до её завершения, и никакие другие корутины не выполнятся, даже если формально код обёрнут в `async def`.

```python
import asyncio, time

async def bad():
    time.sleep(0.01)          # весь event loop стоит

async def good():
    await asyncio.sleep(0.01) # event loop свободен, другие задачи работают
```

Это самая распространённая ошибка при переходе к `asyncio` – ставить `async def` не значит "стало асинхронным", асинхронным должно быть и всё, что внутри. Правило: в async-коде используйте только async-совместимые библиотеки (`aiohttp`/`httpx.AsyncClient` вместо `requests`).

## asyncio.gather – параллельный запуск нескольких корутин

```python
async def task(name, delay):
    await asyncio.sleep(delay)
    return name

async def main():
    results = await asyncio.gather(
        task('A', 2),
        task('B', 1),
        task('C', 3),
    )
    print(results)   # ['A', 'B', 'C']

asyncio.run(main())
```

Задача B завершается первой (через 1с), затем A (через 2с), затем C (через 3с) – но результаты `gather` возвращаются в ТОМ ЖЕ порядке, в котором корутины были переданы, независимо от порядка их фактического завершения. Общее время выполнения – время самой долгой задачи, а не сумма всех.

## asyncio.run – точка входа

**`asyncio.run(main())`** – стандартный способ запустить асинхронный код из синхронного контекста: создаёт новый event loop, запускает переданную корутину, ждёт её завершения и закрывает loop. Вызывать его следует один раз – это точка входа в асинхронную часть программы. До Python 3.7 для этого приходилось вручную создавать event loop через `asyncio.get_event_loop().run_until_complete(main())` – сейчас `asyncio.run()` полностью заменяет эту связку.

## Конкурентность – это не параллелизм

Частая путаница. **Параллелизм** – физическое одновременное выполнение на нескольких ядрах: несколько потоков или процессов работают буквально в одну микросекунду. **Конкурентность** – грамотное управление множеством задач в одном потоке: задачи не выполняются одновременно, но быстро чередуются. `asyncio` – это конкурентность без параллелизма: один event loop, один поток, тысячи одновременных соединений – работает именно потому, что во время I/O-ожидания CPU свободен, а переключение между задачами дешевле создания отдельных потоков.

## Когда asyncio, а когда threading или multiprocessing

`asyncio` оптимален для **I/O-bound задач с большим числом одновременных операций**: HTTP-запросы, работа с базой данных через async-драйверы, WebSocket-соединения – один асинхронный поток способен обслуживать тысячи соединений, это его главное преимущество перед `threading`. `threading` имеет смысл, когда нужно интегрировать синхронный блокирующий код в асинхронную среду или работать с библиотеками без async-поддержки. `multiprocessing` остаётся единственным вариантом для **CPU-bound задач** – `asyncio` не обходит GIL и не ускоряет вычисления, он только устраняет простои при ожидании (см. тему CPU-bound vs I/O-bound).

---

## Практические сценарии

`asyncio` критически важен в высоконагруженных системах: чат-боты с тысячами одновременных пользователей, веб-скрейперы, собирающие данные с сотен источников, API-агрегаторы, делающие параллельные запросы к внешним сервисам. В таких системах синхронный код создаёт линейно растущие задержки, а асинхронный держит их почти постоянными вне зависимости от числа параллельных задач.
