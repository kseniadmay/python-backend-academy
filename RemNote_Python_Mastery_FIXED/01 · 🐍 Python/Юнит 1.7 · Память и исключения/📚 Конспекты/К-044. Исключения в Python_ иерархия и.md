## Иерархия исключений

Все встроенные исключения наследуются от **`BaseException`**, но перехватывать стоит почти всегда от **`Exception`** – ветки `BaseException`, которые не входят в `Exception` (`SystemExit`, `KeyboardInterrupt`, `GeneratorExit`), сигнализируют о намеренном завершении программы и не должны молча глотаться.

```text
BaseException
 ├── SystemExit
 ├── KeyboardInterrupt
 ├── GeneratorExit
 └── Exception
      ├── ArithmeticError
      │    └── ZeroDivisionError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── ValueError
      ├── TypeError
      ├── AttributeError
      ├── OSError (FileNotFoundError, PermissionError, ...)
      └── ...
```

Практическое следствие: `except Exception:` – уже осмысленная, безопасная граница перехвата (в отличие от голого `except:`, который ловит вообще всё, включая `KeyboardInterrupt`). А ловить конкретный класс (`except KeyError:`) точнее, чем ловить его родителя (`except LookupError:`) – иерархия позволяет выбрать нужную "ширину" перехвата.

## try/except/else/finally – все четыре блока

```python
def read_config(path):
    try:
        f = open(path)
        data = f.read()
    except FileNotFoundError:
        print(f'Файл {path} не найден')
        return None
    except PermissionError:
        print(f'Нет прав на чтение {path}')
        return None
    else:
        print('Файл успешно прочитан')
        return data
    finally:
        f.close()
        print('Файл закрыт')
```

**`try`** – код, который может бросить исключение. **`except`** – что делать при конкретном исключении (можно несколько блоков подряд для разных типов). **`else`** – выполняется, только если `try` завершился без исключений – используют, чтобы отделить "код, который может упасть" от "кода, который должен выполниться только при успехе", не пряча его внутрь `try`. **`finally`** – выполняется в любом случае, даже если в `try`/`except`/`else` есть `return` или необработанное исключение – используется для гарантированной очистки ресурсов (закрытие файла, соединения, освобождение блокировки).

---

## Зачем нужен отдельный else, если код можно просто оставить в try

Код в `else` выполняется только при успехе `try`, но при этом исключения, возникшие **в самом `else`**, не будут пойманы теми же `except`-блоками, что стоят над ним – это разделяет ответственность: `try` ловит именно ту операцию, которая может упасть, а `else` – то, что зависит от её успеха, но само по себе не должно маскироваться под ту же ошибку.

## raise и цепочки исключений

```python
class InsufficientFundsError(Exception):
    """Пользовательское исключение - наследуется от Exception."""
    pass

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFundsError(f'Недостаточно средств: есть {balance}, нужно {amount}')
    return balance - amount

try:
    withdraw(100, 150)
except InsufficientFundsError as e:
    print(f'Ошибка: {e}')

try:
    withdraw(100, 150)
except InsufficientFundsError as e:
    raise RuntimeError('Операция отменена') from e
```

Собственные исключения принято наследовать от `Exception` (не от `BaseException`) и называть с суффиксом `Error`. `raise ... from e` явно связывает новое исключение с исходным в трейсбеке – вместо того, чтобы исходная причина потерялась при повторном `raise`.

## Когда использовать

Ловить максимально конкретный класс исключения, какой возможен – это даёт точную реакцию на конкретную проблему и не маскирует непредвиденные баги под общий `except Exception`. `finally` – для любой очистки ресурсов (хотя на практике для файлов/соединений чаще используют `with`, который делает то же самое декларативно). Собственные исключения – когда нужно различать бизнес-ошибки домена (`InsufficientFundsError`) от технических (`ValueError`), это упрощает обработку на уровне, где ошибка перехватывается осмысленно.
