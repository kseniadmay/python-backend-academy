1. Почему нежелательно хранить в Redis объекты больше 1 МБ? >> Снижает производительность: нагрузка на сеть и память при сериализации/десериализации
2. Что произойдёт при `vc.get` после `invalidate_namespace` ? >> Cache miss: поиск идёт по новой версии ключа, данных там нет – пересчёт
3. Что делает `cache.delete('users:list')` при изменении профиля одного пользователя? >> Инвалидирует общий список, так как данные в нём стали неактуальными
4. Что происходит с БД при `hit rate = 10%` ? >> 90% запросов проходят сквозь кэш – огромная нагрузка на БД
5. В чём риск использования Redis как единственного хранилища данных? >> Данные хранятся в RAM и могут быть потеряны при перезапуске без настройки персистентности (RDB/AOF)
6. Почему при смене версии не нужно удалять старые ключи вручную? >> Старые ключи недостижимы по новому адресу и удалятся автоматически по истечении TTL
7. Что такое Cache Tags (теги кэша)? >> Механизм логической группировки ключей по меткам; одним вызовом можно инвалидировать все ключи с нужным тегом
8. К какой проблеме приводит некорректная обработка `None` из кэша? >> Невозможно различить «ключа нет в кэше» от «объекта нет в БД» – каждый запрос несуществующего объекта идёт в БД
9. Как `post_save` определяет, какой ключ удалить? >> Через `instance.id` для формирования уникального ключа: `f'user:{instance.id}'`
10. В чём главная опасность команды `KEYS` в Redis на production? >> Она блокирует выполнение всех остальных команд до завершения полного перебора – Redis однопоточный
11. Почему инвалидация по тегам удобнее, чем по паттерну? >> Позволяет логически связывать разнородные ключи, не полагаясь на строковое соответствие имён
12. За что отвечает `@receiver(post_save, sender=User)` в контексте кэширования? >> Запускает функцию очистки кэша сразу после сохранения экземпляра `User`
13. Для чего в `good_get_user` используется переменная `cache_key` ? >> Для единообразного формирования ключа при записи и чтении – исключает расхождение ключей
14. Что возвращает `r.keys(pattern)` ? >> Список всех ключей, соответствующих шаблону; именно из-за блокировки `KEYS` недопустим на production
15. Что передаётся в аргумент `match` функции `r.scan` ? >> Паттерн имён ключей: например, `'products:category:5:*'`
16. Как изменяется VersionedCache при `invalidate_namespace` ? >> Внутренняя версия пространства имён увеличивается (например, `v1` → `v2` )
17. Зачем в `invalidate_pattern_safe` нужен `while True` ? >> Чтобы продолжать итерации по страницам ключей, пока курсор не вернётся в `0`
18. В какой момент выполнения `update_user` следует производить инвалидацию кэша? >> После успешного `db.commit()` – только если данные гарантированно сохранены
19. Какие причины могут привести к низкому `hit rate` (менее 50%)? >> Слишком короткий TTL или неправильно сформированные ключи
20. Что такое hit rate? >> Процент запросов к кэшу, обработанных без обращения к БД
21. Какой TTL рекомендуется для негативного кэша (отсутствующих данных)? >> Короткий: например, 60 секунд
22. Что означает аргумент `count` в `r.scan` ? >> Примерное количество ключей, которые Redis проверит за одну итерацию (не гарантированное)
23. Почему `SCAN` безопаснее `KEYS` ? >> Возвращает ключи частями, не блокируя сервер; другие команды продолжают выполняться
24. Какое значение курсора `SCAN` сигнализирует о завершении итерации? >> `0`
25. Какая команда Redis безопасно итерирует по ключам без блокировки сервера? >> `SCAN` – возвращает ключи частями через курсор
26. Почему мониторинг hit rate важен? >> Позволяет вовремя заметить деградацию производительности и неэффективность стратегии кэширования
27. Что должно быть единственным источником правды при работе с кэшем? >> База данных
28. Почему строка-маркер `'NOT_FOUND'` лучше, чем возврат `None` из кэша? >> Позволяет кэшировать сам факт отсутствия записи – негативный кэш
29. О чём свидетельствует `hit rate > 80%` ? >> Кэш настроен эффективно
30. Что такое версионирование ключей (VersionedCache)? >> Инвалидация через смену номера версии в пространстве имён: старые ключи становятся недостижимыми без явного удаления
31. Что представляет собой инвалидация кэша? >> Удаление или обновление устаревших данных в кэше для предотвращения выдачи неактуальной информации
32. Что произойдёт с `product:42` при вызове `invalidate_tag('category:5')` , если ключ имеет этот тег? >> Ключ будет удалён из кэша
33. Какая типичная ошибка при работе с кэшем? >> Полагаться на кэш как на постоянное хранилище, забывая о временности данных в памяти
34. Что такое sentinel в контексте кэширования? >> Специальное маркерное значение (например, `'NOT_FOUND'` ), явно указывающее, что объекта нет в БД – предотвращает повторные запросы
35. Какие два Django-сигнала наиболее эффективны для автоматизации инвалидации? >> `post_save` и `post_delete`
36. Какой метод инвалидации считается самым надёжным? >> Явная инвалидация непосредственно в момент записи или обновления данных в БД
37. Какую проблему программирования называют одной из самых сложных? >> Инвалидация кэша: гарантировать, что кэш не отдаёт устаревшие данные
38. Как выглядит структура ключа при `namespace='products'` и версии `v1` ? >> `products:v1:key_name`
39. Каков максимальный размер строки в Redis? >> 512 МБ
40. Пример паттерна для инвалидации всех продуктов категории 5? >> `'products:category:5:*'`
41. Из каких четырёх компонентов состоит «идеальная формула кэша»? >> Правильный TTL, явная инвалидация, Jitter и мониторинг hit rate
42. Что делать, если объект в кэше слишком велик? >> Разбить на несколько мелких ключей
43. Почему при `post_delete` важно очищать и список, и конкретный ключ объекта? >> Иначе удалённый объект продолжит отображаться в общем списке или быть доступным по прямому ключу
