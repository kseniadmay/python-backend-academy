1. Какую задачу решает использование декоратора для кэширования? >> Устранение boilerplate: логика кэширования выносится в одно место и применяется через `@decorator`
2. Почему Write-Through может быть избыточным для систем с редким чтением? >> Кэш постоянно обновляется при записях, но данные из него почти не запрашиваются
3. Какое ключевое различие между Cache-Aside и Write-Through при записи? >> В Cache-Aside запись идёт только в БД; в Write-Through – одновременно в БД и кэш
4. Как Write-Through влияет на latency при обновлении данных? >> Увеличивает: нужно дождаться успешной записи и в БД, и в кэш
5. Какой метод кэша используется для записи в декораторе? >> `cache.set(key, result, timeout=timeout)`
6. Что такое Cache Stampede? >> Ситуация, когда тысячи одновременных запросов получают cache miss и одновременно идут в БД, создавая пиковую нагрузку
7. Какая стратегия минимизирует вероятность cache miss при чтении? >> Write-Through (или Write-Behind): кэш наполняется при каждой записи
8. Сравните риск потери данных в Write-Through и Write-Behind? >> Write-Through: риска нет (запись синхронна); Write-Behind: риск высокий из-за асинхронности
9. Что передаётся в `key_template.format(*args, **kwargs)` в декораторе кэширования? >> Аргументы декорируемой функции для формирования уникального ключа кэша
10. Какая проблема с памятью характерна для Write-Through? >> Кэш может заполняться данными, которые никогда не будут прочитаны
11. Какая стратегия кэширования наиболее экономно расходует память Redis? >> Cache-Aside
12. Что проверяет условие `if result is None` в декораторе `cached` ? >> Был ли cache miss – отсутствие данных по ключу в кэше
13. Какое преимущество Write-Through по актуальности данных? >> Кэш всегда консистентен с БД; вероятность cache miss при чтении минимальна
14. В Write-Behind база данных обновляется синхронно или асинхронно? >> Асинхронно – это ускоряет отклик для клиента, но создаёт риск потери данных
15. Что такое boilerplate в программировании? >> Повторяющиеся участки кода, которые приходится копировать с минимальными изменениями
16. Главный недостаток Write-Through при записи? >> Каждая запись медленнее: два последовательных обращения – к БД и к кэшу
17. Какая стратегия кэширования используется реже всего из-за сложности и рисков? >> Write-Behind (Write-Back)
18. Что делает `@cache_page(60 * 60)` в Django? >> Кэширует HTTP-ответ вью на 3600 секунд (1 час)
19. Какова временная сложность чтения при cache hit для любой стратегии? >> O(1)
20. Как предотвратить Cache Stampede? >> Через блокировку ( `lock_key` ): первый поток берёт блокировку, загружает данные и кладёт в кэш; остальные ждут и затем берут из кэша
21. Почему Write-Behind характеризуется слабой консистентностью? >> Данные в БД временно отстают от кэша; при сбое расхождение может стать постоянным
22. Для каких операций на практике рекомендуется комбинация Cache-Aside и явной инвалидации? >> Cache-Aside для чтений; инвалидация кэша – при записи, чтобы избежать устаревших данных
23. Почему Cache-Aside устойчива к отказу Redis? >> При недоступности кэша приложение продолжает работу, запрашивая данные напрямую из БД (с деградацией производительности)
24. Почему в Write-Through отсутствуют задержки при чтении актуальных данных? >> Данные уже находятся в кэше после записи
25. В чём преимущество Cache-Aside по составу кэша? >> Кэш хранит только реально запрашиваемые данные – экономно расходует память Redis
26. Как изменяется сложность системы при переходе от Cache-Aside к Write-Behind? >> Значительно возрастает
27. Как оценивается сложность реализации Write-Behind? >> Высокая
28. Какую проблему решает инвалидация кэша при записи в Cache-Aside? >> Проблему устаревших данных: после изменения в БД старая запись удаляется из кэша
29. Как называется проблема медленного первого запроса в Cache-Aside? >> Cold start (холодный старт)
30. Как называется стратегия, при которой данные при записи обновляются одновременно в БД и кэше? >> Write-Through
31. Какая стратегия требует реализации очередей или фоновых задач для синхронизации с БД? >> Write-Behind
32. Какой параметр отвечает за TTL ключа в реализации декоратора? >> `timeout`
33. Что означает `eventual consistency` в контексте Cache-Aside? >> Данные в кэше и БД станут одинаковыми через некоторое время – после истечения TTL или явной инвалидации
34. Зачем использовать `JsonResponse({'users': list(users.values())})` в Django? >> Для преобразования QuerySet в сериализуемый формат перед отправкой JSON-ответа
35. Как называется стратегия кэширования, при которой приложение сначала ищет данные в кэше, а при отсутствии идёт в БД? >> Cache-Aside (Lazy Loading, ленивое кэширование)
36. Какая стратегия кэширования считается самой распространённой на практике? >> Cache-Aside
37. В чём основной риск Write-Behind? >> Потеря данных при сбое Redis до их асинхронного сохранения в БД
38. В какой стратегии cache miss при чтении происходит наиболее часто? >> Cache-Aside – кэш заполняется только при реальных запросах
39. Что должен делать код после получения блокировки в `get_user_safe` ? >> Снова проверить кэш (другой поток мог уже заполнить его) и только при повторном miss идти в БД
40. Какое основное преимущество Write-Behind? >> Максимальная скорость записи для пользователя: ответ возвращается сразу после записи в кэш
41. Что делает приложение в Cache-Aside при cache miss? >> Запрашивает данные из БД, затем сохраняет их в кэш и возвращает ответ
42. Как работает стратегия Write-Behind (Write-Back)? >> Данные записываются сначала в кэш, а в БД сохраняются асинхронно через некоторое время
43. Как оценивается сложность реализации Cache-Aside? >> Низкая
44. Как Cache-Aside влияет на производительность при холодном кэше? >> Каждый первый запрос требует обращения к БД; производительность временно снижается
45. Что произойдёт в Cache-Aside, если Redis временно недоступен? >> Приложение продолжит работу, но скорость ответов снизится из-за прямой нагрузки на БД
46. Если данные не найдены в кэше при чтении в Write-Through – как это классифицируется? >> Редкое событие: кэш наполняется при каждой записи, поэтому промахи при чтении нетипичны
47. Какая стратегия кэширования обеспечивает наибольшую консистентность? >> Write-Through
